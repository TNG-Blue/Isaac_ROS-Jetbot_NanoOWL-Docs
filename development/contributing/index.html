    Contributing Guide¶

    Thank you for your interest in contributing to Isaac ROS Jetbot NanoOWL! This guide will help you get started.

    🤝 How to Contribute¶

    We welcome contributions of all types:

    • 🐛 Bug Reports: Help us identify and fix issues
    • ✨ Feature Requests: Suggest new capabilities
    • 📝 Documentation: Improve guides and tutorials
    • 💻 Code: Implement features or fixes
    • 🧪 Testing: Write tests or test pull requests
    • 🌐 Translation: Translate documentation
    • 💡 Ideas: Share concepts and designs

    📋 Contributor License Agreement (CLA)¶

    Before contributing code, you must agree to our CLA:

    By submitting a pull request, you certify that:

    1. Your contribution is your original work or you have permission to submit it
    2. You grant TNG-Blue a perpetual, worldwide license to use your contribution
    3. You accept the Apache License 2.0 for your contribution

    To agree, comment on your first PR: 

    I have read and agree to the CLA

    See full CLA: CLA.md

    🚀 Getting Started¶

    1. Fork and Clone¶

    # Fork repository on GitHub
# Then clone your fork
git clone https://github.com/YOUR_USERNAME/Isaac_ROS-Jetbot_NanoOWL.git
cd Isaac_ROS-Jetbot_NanoOWL

# Add upstream remote
git remote add upstream https://github.com/TNG-Blue/Isaac_ROS-Jetbot_NanoOWL.git

    2. Set Up Development Environment¶

    # Install ROS2 Humble (if not already)
sudo apt install ros-humble-desktop -y

# Install development dependencies
pip3 install -r requirements-dev.txt

# Install pre-commit hooks
pre-commit install

    3. Create a Branch¶

    # Update main branch
git checkout main
git pull upstream main

# Create feature branch
git checkout -b feature/my-new-feature

# Or for bug fixes
git checkout -b fix/issue-123

    💻 Development Workflow¶

    Making Changes¶

    1. Write Code:
    2. Follow Code Style Guide
    3. Add copyright headers to new files

    4. Keep commits focused and atomic

    5. Add Tests: 

      # Python tests
pytest tests/python/test_my_feature.py

# C++ tests
colcon test --packages-select my_package

    6. Update Documentation:

    7. Add docstrings to functions
    8. Update relevant .md files

    9. Add examples if applicable

    10. Run Checks: 

      # Format code
black src/
clang-format -i src/*.cpp

# Lint
flake8 src/
cppcheck src/

# Build
colcon build --packages-select my_package

# Test
colcon test --packages-select my_package

    Commit Guidelines¶

    Follow Conventional Commits:

    # Format
<type>(<scope>): <subject>

# Examples
feat(detection): add YOLOv8 support
fix(nav): resolve path planning deadlock
docs(readme): update installation instructions
test(slam): add unit tests for loop closure
perf(cuda): optimize kernel launch overhead
refactor(control): simplify PID controller

    Types: - feat: New feature - fix: Bug fix - docs: Documentation only - test: Adding/fixing tests - perf: Performance improvement - refactor: Code restructuring - style: Code style (formatting) - chore: Build/tooling changes - ci: CI/CD changes

    Pull Request Process¶

    1. Push to Your Fork: 

      git push origin feature/my-new-feature

    2. Create Pull Request:

    3. Go to GitHub
    4. Click "New Pull Request"
    5. Select your branch

    6. Fill out template

    7. PR Template: 

      ## Description
Brief description of changes

## Type of Change
- [ ] Bug fix
- [ ] New feature
- [ ] Breaking change
- [ ] Documentation update

## Testing
Describe how you tested

## Checklist
- [ ] Code follows style guidelines
- [ ] Comments added for complex code
- [ ] Documentation updated
- [ ] Tests added/updated
- [ ] All tests pass
- [ ] CLA signed

    8. Address Review Comments: 

      # Make requested changes
git add .
git commit -m "fix: address review comments"
git push origin feature/my-new-feature

    9. Merge:

    10. Maintainer will merge when approved
    11. PR is squash-merged with Co-authored-by tag

    📝 Code Review Guidelines¶

    As a Reviewer¶

    • ✅ Be constructive and respectful
    • ✅ Explain why changes are needed
    • ✅ Suggest specific improvements
    • ✅ Approve when satisfied
    • ❌ Don't nitpick minor style issues (automated tools handle this)

    As a Contributor¶

    • ✅ Respond to all comments
    • ✅ Ask for clarification if needed
    • ✅ Make requested changes promptly
    • ✅ Thank reviewers for their time
    • ❌ Don't take feedback personally

    🐛 Reporting Bugs¶

    Before Reporting¶

    1. Search existing issues
    2. Try latest version
    3. Gather system information

    Bug Report Template¶

- Jetson Model: Orin Nano 8GB
- JetPack Version: 6.2
- ROS2 Version: Humble
- Installation Method: Native

**Describe the Bug**:
Clear description of what's wrong

**To Reproduce**:
1. Step 1
2. Step 2
3. Step 3

**Expected Behavior**:
What should happen

**Actual Behavior**:
What actually happens

**Logs**:
    [paste relevant logs] 
    **Screenshots**:
[if applicable]

**Additional Context**:
[any other relevant information]

    ✨ Requesting Features¶

    Feature Request Template¶

    **Problem Statement**:
What problem does this solve?

**Proposed Solution**:
How would you implement it?

**Alternatives Considered**:
What else did you think about?

**Use Case**:
Real-world scenario where this helps

**Implementation Complexity**:
- [ ] Simple (< 1 day)
- [ ] Medium (1-3 days)
- [ ] Complex (> 3 days)

**Would you contribute implementation?**:
- [ ] Yes
- [ ] No
- [ ] With guidance

    📚 Documentation Contributions¶

    Documentation Style¶

    • Use Markdown with MkDocs Material extensions
    • Add code examples for clarity
    • Include diagrams for complex topics
    • Keep language clear and concise
    • Test all code examples

    Adding New Documentation¶

    # Create new file
nano Docs/new-section/new-page.md

# Add to navigation in mkdocs.yml
nano mkdocs.yml

# Preview locally
mkdocs serve

# View at http://localhost:8000

    🧪 Testing Requirements¶

    Test Coverage¶

    Aim for: - 80%+ coverage for new code - 100% coverage for critical paths - All public APIs tested

    Writing Tests¶

    # tests/python/test_detection.py
import pytest
from jetbot_detection import ObjectDetector

def test_detector_initialization():
    detector = ObjectDetector()
    assert detector is not None

def test_detection_accuracy():
    detector = ObjectDetector()
    result = detector.detect(test_image)
    assert result['confidence'] > 0.9

@pytest.mark.parametrize("model", ["yolov8n", "yolov8s"])
def test_multiple_models(model):
    detector = ObjectDetector(model=model)
    assert detector.model_name == model

    // tests/cpp/test_slam.cpp
#include <gtest/gtest.h>
#include "jetbot_slam/slam_node.hpp"

TEST(SlamTest, Initialization) {
    auto slam = std::make_shared<SlamNode>();
    EXPECT_NE(slam, nullptr);
}

TEST(SlamTest, MapCreation) {
    auto slam = std::make_shared<SlamNode>();
    slam->process_scan(test_scan);
    auto map = slam->get_map();
    EXPECT_GT(map.size(), 0);
}

TEST(SlamTest, LoopClosure) {
    auto slam = std::make_shared<SlamNode>();
    // Test loop closure detection
    EXPECT_TRUE(slam->detect_loop_closure());
}

    Running Tests¶

    # All tests
colcon test

# Specific package
colcon test --packages-select jetbot_detection

# With coverage
colcon test --pytest-args --cov=jetbot_detection

# View results
colcon test-result --verbose
