    Deployment OTA

    Server OTA — Deployment¶

    Four ways to run the service, plus the CI pipeline that validates every change.

    💻 Local Binary¶

    cd Server_OTA

./scripts/build.sh     # → bin/ota-server-3.0.0-linux and -rpi
./scripts/run.sh       # → http://localhost:8080

    build.sh cross-compiles two targets from src/main.go with -ldflags "-X main.Version=3.0.0 -s -w": linux/amd64 (-linux) and linux/arm GOARM=7 for Raspberry Pi (-rpi); on MSYS/Cygwin it adds a -windows.exe build.

    run.sh honours PORT (default 8080), creates data/firmware, data/logs and the web/ asset directories, and logs to data/logs/server.log. If Go is installed but no binary exists, it falls back to go run ./src/main.go.

    The process resolves its own base directory: started from src/, it walks up until it finds web/templates, so relative paths (config/config.json, data/firmware) keep working. A missing config/config.json is written from the built-in defaults on first start.

    Stage firmware manually for now

    POST /upload is still a placeholder (see API Reference), so copy images into data/firmware/ directly. Only .bin, .hex, .elf, .img and .fw are listed and downloadable.

    🐳 Docker¶

    The image is built from the repository root, because the Dockerfile copies from Server_OTA/:

    docker build \
  -f Docker/images/server_ota/Dockerfile \
  -t tngblue/server_ota:3.0.0 \
  .

docker run -d --name ota-server \
  -p 8080:8080 \
  -v "$(pwd)/firmware:/app/data/firmware" \
  -v "$(pwd)/ota-logs:/app/data/logs" \
  tngblue/server_ota:3.0.0
    Stage Base Contents
    builder golang:1.20-alpine Builds main.go with CGO_ENABLED=0, -ldflags="-s -w -X main.Version=3.0.0"
    runtime alpine:latest Static binary, config/, web/, empty data/firmware and data/logs

    The runtime stage declares a health check that polls /api/health every 30 s (10 s timeout, 5 s start period, 3 retries), so docker ps reports the container unhealthy when the API stops answering.

    Mount the firmware directory

    data/firmware lives in the container layer. Without a volume, every image uploaded or copied in is lost when the container is replaced.

    ☁️ App Engine¶

    Two manifests ship with the service:

    cd Server_OTA
gcloud app deploy app.yaml
    Setting Value
    Runtime go120, service ota-server, version v3-0-0
    Instance class F2
    Scaling 1–10 instances, CPU target 60 %, throughput target 70 %
    Firmware dir /tmp/firmware (ephemeral)
    Probes liveness and readiness on /api/health
    Static /static/.* served from web/static, secure: always 
    cd Server_OTA
gcloud app deploy app-flexible.yaml
    Setting Value
    Runtime custom / env: flex, service ota-server-flex
    Resources 1 vCPU, 1 GB RAM, 5 GB disk + 10 GB firmware-storage volume at /firmware
    Scaling 1–20 instances, CPU 65 %, memory 70 %, 120 s cooldown
    Concurrency MAX_CONCURRENT_REQS: "10"
    Session affinity enabled

    Standard uses ephemeral storage

    app.yaml points FIRMWARE_DIR at /tmp/firmware, which does not survive an instance restart and is not shared between instances. For a fleet that must pull the same image from any instance, use the Flexible manifest's mounted volume or move firmware to Cloud Storage.

    Environment variables are declared twice in app.yaml

    The manifest contains two env_variables: blocks (the second holds the timeout values); YAML keeps the last one, so PORT, ENVIRONMENT, LOG_LEVEL, FIRMWARE_DIR and MAX_UPLOAD_SIZE from the first block are dropped at deploy time. Merge them into a single block before relying on those values.

    🏗️ Cloud Build¶

    cloudbuild.yaml builds, pushes and deploys:

    gcloud builds submit --config Server_OTA/cloudbuild.yaml
    1. docker build tagged latest, $SHORT_SHA and 3.0.0
    2. docker push of the $SHORT_SHA tag
    3. gae-deploy with --appyaml=app.yaml and the pushed image
    4. Health check against https://$PROJECT_ID.appspot.com/api/health

    Machine type N1_HIGHCPU_8, timeout 3600 s, Cloud Logging only. The Flexible deployment step is present but commented out.

    ✅ CI Pipeline¶

    .github/workflows/ota-server-ci.yml runs on every push and pull request touching Server_OTA/**:

    Job Checks
    code-quality gofmt -l . must be empty, then go vet ./...
    build-and-test go mod download, go build -ldflags="-s -w", go test -race -coverprofile, uploads binary + config/config.json and the coverage report
    integration-test Downloads the artifact, prepares the runtime directory layout, verifies the binary
    summary Aggregates the three results into the job summary

    Changes under Server_OTA/web/** additionally trigger the documentation workflow, which rebuilds the Web Interface preview and republishes it with the docs site.

    🩺 Post-Deploy Checklist¶

    BASE=https://your-deployment.example.com

curl -fsS "$BASE/api/health"        | jq '.success'          # expect true
curl -fsS "$BASE/api/stats"         | jq '.data'             # counters present
curl -fsS "$BASE/api/firmware/list" | jq '.data | length'    # staged files visible
    • /api/health returns 200 with success: true
    • data/firmware is a persistent volume, not container-local storage
    • data/logs is writable (the logger opens it at startup)
    • Firmware names follow the _v<version> and device-keyword rules in Firmware metadata
    • Concurrency limit raised via SetMaxConcurrent if more than 5 devices may pull simultaneously
    • Reverse proxy or raised WriteTimeout if images take longer than 30 s to transfer
