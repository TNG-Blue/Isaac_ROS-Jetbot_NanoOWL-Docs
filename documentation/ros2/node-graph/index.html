    ROS 2 node graph — JetOwl_FlightControl · JetOwl_Vision · Isaac_ROS-Jetbot_NanoOWL¶

    Source

    This page is rendered from Docs/flowcharts/ros2_nodes_flowchart.md, the authoritative description kept next to the code in Docs/flowcharts/.

    A single diagram of every ROS 2 node in the three repositories, connected through topics, services and transport links (UDP, TCP, HTTP).

    • Two micro-ROS nodes on MCUs: jetowl_fc (STM32N657) and jetowl_vision (STM32N657). The control chain inside the firmware is drawn as well, so that every closed loop is visible.
    • 74 nodes in Isaac_ROS-Jetbot_NanoOWL: 64 in Source/, 3 in MATLAB/ and 7 in Examples/.
    • 9 external node blocks started by the repository's launch files, e.g. micro_ros_agent, ros_gz_bridge, the Isaac ROS DNN encoder/TensorRT.

    2. Closed loops in the diagram¶

    Under the project's control convention (.claude/rules/control-systems.md), every path from a sensor to an actuator must pass through filtering, estimation and control, and be closed by measured feedback. The diagram contains the following loops:

    # Loop Path in the diagram Status
    1 Rotor speed, 1 kHz per rotor (FC) FC_ROT → DShot → ESC → RPM telemetry → FC_ROT Closed in firmware
    2 Angular rate 1 kHz and attitude 250 Hz (FC) IMU → imu_frontend → imu_fusion → attitude loop → rate loop → mixer → ESC → body motion → IMU Closed in firmware
    3 Position / trajectory, 50 Hz (Jetson ↔ FC) /imu/data → uav_state_estimator (ESKF) → /odometry/filtered → uav_trajectory_controller (MPC) → /control/attitude_setpoint + /control/thrust → jetowl_fc → loop 2 → IMU → /imu/data Closed, over micro-ROS/UDP
    4 Flight commands flight_controller_node → flight/setpoint + flight/active → MPC → … → ESKF → /odometry/filtered → flight_controller_node Closed. odom_topic defaults to /odometry/filtered
    5 Camera AE/AWB (Vision) ISP → cam_isp_ctrl → exposure/gain → IMX335 sensor Closed in firmware
    6 Thermal imaging thermal_camera → filter + CA-CFAR → Kalman/GNN Estimation chain only, no actuator. ros2_dashboard_node (Vision → Thermal tab) only displays it
    6a Camera arm gaze 2 × IMX477 → panorama_node → detector → object_detections → arm_look_at_node → /camera_arm/look_at → camera_arm_node (IK, SIMC PI on the detection offset) → PCA9685 servos → camera moves → detection moves; MPU-6050 → horizon hold Closed on the image and on the plate IMU
    6b Stereo depth 2× IMX219 (worker) → stereo_node: rectification → SGM → spatial filter → per-pixel Kalman → Z, σ_Z Estimation chain only. The Stereo tab of ros2_dashboard_node displays it, calls services and writes parameters; every action is confirmed by the node's response and a read-back
    7 Target following isaac_ros_target_follower_node → /cmd_vel (heading frame) → flight_controller_node (MANUAL mode, manual.source: cmd_vel, v_w = R_z(ψ̂) v_h) → loop 4 Closed on the UAV when the follower reads odom_topic:=/odometry/filtered. On the Jetbot, the base driver (subscribes /cmd_vel, publishes /odom) is outside the three repositories
    8 RF defence spectrum_analyzer_cuda → rf_threat_alert → failsafe_controller → flight/nav_command (JAMMING → RTH, SPOOFING → LAND) → flight_controller_node Closed through the FCN. Commands are latched, escalate-only, cleared with ~/reset
    8b RF / GNSS link security (JetOwl) jetowl_fc → /jetowl/security/{rf_link,gnss} → link_security (detection only) → /jetowl/security/threat → flight_controller_node (GNSS attack → LAND, command link jammed and lost → RTH) → /jetowl/security/response → uav_state_estimator (stops fusing a distrusted receiver) → /jetowl/security/advice → jetowl_fc (/gps/fix NO_FIX for that receiver) → next epochs measured again Closed. The FC only lowers GNSS trust; every flight decision stays on the Jetson (JetOwl_FlightControl docs/ARCHITECTURE.md §9, docs/SECURITY.md)
    8c Remote_UAV RTH button and missions remote → LoRa → jetowl_fc → /jetowl/status rc_rth_request → jetowl_bridge → flight/nav_command RTH (switch AUTO only); /jetowl/mission/geo → geo_mission_node → mission/upload_waypoints → mission_planner_node → flight_controller_node → loop 4, progress back on /jetowl/mission/progress → remote Closed through loop 4; the pilot's switch decides whether the Jetson flies (JetOwl_FlightControl docs/ARCHITECTURE.md §9)
    8d Photo downlink (data, not control) jetowl_fc → /jetowl/camera/request → snapshot_node → /jetowl/camera/jpeg → jetowl_fc → 2.4 GHz image slot → remote; /jetowl/camera/fc_status (bitmap of chunks held) → snapshot_node resends the missing ones Closed by acknowledgement (selective repeat, CRC-32)
    8e GNSS-free navigation and return to home ground_vo_node → /vo/twist → uav_state_estimator → /estimator/nav_health → flight_controller_node → flight/setpoint → uav_trajectory_controller → /control/attitude_setpoint → jetowl_fc → … → /imu/data → uav_state_estimator → /odometry/filtered → nav_map_node → /nav/return_path → flight_controller_node Closed. With GNSS distrusted, the camera + LPB40B velocity keeps the ENU estimate (and home) valid; a GNSS attack or lost fix with healthy navigation → RTH along the flown path, σ_h above its bound → LAND (ros2_gnss_denied_nav README)
    9 Relative altitude BMP280 → jetowl_fc → /baro/pressure (σ² = 1.44 Pa²) → ESKF → loop 3 Closed. Previously there was no barometer source

    4. Unconnected topics and fixed mismatches¶

    In the diagram, topics with a dashed red border have no publisher in the three repositories. All of them are inputs from hardware or external drivers, which is expected:

    • /points: 3-D LiDAR.
    • joy: joy_node.
    • rf_monitor/raw_iq: SDR.
    • camera_arm/joint_command · target_pose · target_point · jog · step: operator commands of the camera arm (tools, dashboards).
    • mission/upload: mission files from an operator tool.
    • /odom: wheel odometry from the Jetbot base driver. Only the target follower (on the Jetbot) and lidar_slam_node (with use_odom) read this topic.

    Drawing the diagram exposed the following mismatches, all of which have been fixed:

    # Mismatch Fix
    1 The launch file remapped gnss/velocity → /gps/velocity, while the bridge publishes /gps/vel_cov control_system.launch.py and the SIL now use /gps/vel_cov
    2 No node published /baro/pressure The FC firmware reads the BMP280 (already on the SEN0253 module) and jetowl_fc publishes FluidPressure. Settings from datasheet BST-BMP280-DS001: ×4/IIR 2, 25 Hz, σ² = 1.44 Pa², timestamp minus 18 ms (airframe_config.h section 6.4). The ESKF's baro_sigma is now sourced from the BMP280
    3 flight_controller_node read /odom by default, and /odom has no publisher odom_topic defaults to /odometry/filtered
    4 telemetry_logger_node read flight/state, a topic without a publisher It reads odometry/filtered (remapped through odom_topic)
    5 The MPC expected /perception/obstacles, a topic without a publisher Remap obstacles → /tracked/markers. The node now accepts CUBE markers with the tight bounding sphere ½‖s‖, and the CYLINDER bounding sphere is corrected to ½√(d² + h²) (the old formula did not enclose the shape). Markers are transformed to odom through tf2, or through the ESKF pose when the frame is base_link, and expire with their lifetime (test test_obstacle_geometry)
    6 /cmd_vel carried two different meanings and had no subscriber The FCN publishes its world-frame command on flight/cmd_vel and subscribes to /cmd_vel (heading frame) in MANUAL mode. Added the nav commands MANUAL/MANUAL_RELEASE; the mode was previously unreachable. Two further bugs fixed: the joystick was not rotated by ψ̂, and signal loss was only detected when the next message arrived
    7 /jetowl/motor_rpm had no subscriber The bridge's fc link monitors rate, per-rotor rpm, valid ratio and malformed messages (jetowl_bridge/fc: rotors)
    8 /imu/data has two sources (FC and sensor_link) Kept by design: the two sources are never enabled together, and the bridge warns when both are
    9 MATLAB read /ld19_scan and /lpb40b_scan, ran SLAM on a single-point range sensor, and used a ROS 1 connection It reads /scan (lidarSLAM, rays filtered to 0.3–12 m) and /range (limit checks only), and uses ros2node with ROS_DOMAIN_ID
    10 The RF package had wrong executable names and remaps, entry points to missing modules, two empty launch files, no setup.cfg and no find_packages (no node could run), and a failsafe_controller that was only a TODO All fixed. failsafe_controller uses failsafe_policy.py (tested) and publishes flight/nav_command
    11 pipeline_params.yaml and full_pipeline.launch.py set different topics Kept: the launch parameters win, and the diagram follows the launch file
    12 thermal_detector put the centre of the Detection2D bbox at the hot blob's centroid, so the box was offset from the object (vision_msgs defines bbox as the object's bounding box) bbox is the blob's true bounding box (centre u_min + (w − 1)/2); the centroid and its 2×2 covariance are in results[0].pose. read_detection and ros2_qt read the position from the same covariance-carrying field; producers without a covariance (NanoOWL) still use the bbox centre
    13 The diagram showed /stereo/left/camera_info as a topic without a publisher stereo_node publishes left/image_rect + left/camera_info through an image_transport camera publisher: stereo_node → topic is now connected. The Stereo tab uses this topic as its heartbeat and takes the P matrix from it

    Completed in the node-inventory pass of 2026-11-05 (nodes that existed in the packages but not in the diagram): geo_mission_node, snapshot_node, arm_look_at_node, camera_arm_node, and the FC topics /gps/fix (FC as publisher), /jetowl/dr/*, /jetowl/ctrl_feedback, /jetowl/link/{ping,pong}, /jetowl/mission/{geo,progress}, /jetowl/camera/*. mission/upload_waypoints was drawn as a topic without a publisher; geo_mission_node publishes it. Not drawn (tools, not run in the system): snapshot_encode, mcu_link_dump, stereo_calibrate, slam_sim_publisher, hexa_design_report.

    Found in the command-authority review (JetOwl_FlightControl docs/ARCHITECTURE.md §9.3), fixed:

    • The rc_rth_request key of /jetowl/status had no consumer: jetowl_bridge now publishes flight/nav_command RTH on a press, only with rc_authority = 2 (switch AUTO).
    • flight_controller_node answered a jammed and lost command link with RTH without reading rc_authority; it now issues nothing under pilot authority and reports the FC's own descent.
    • The arm relay of jetowl_bridge could disarm a pilot-flown UAV; it is silent under pilot authority.

    Found in the camera review of 2026-11-06 (master: 2 × IMX477, no stereo; worker: 2 × IMX219 stereo pair), fixed:

    • stereo_node was deployed on the master and opened CSI 0/1 there — the two IMX477, not a stereo pair — and CSI 0 collided with snapshot_node's own Argus capture. stereo now runs on the worker; the two IMX477 belong to the camera layer panorama_node alone.
    • /camera/color/image_raw, the input of every detector, and its camera_info had no publisher: panorama_node (ros2_panorama) is the camera layer of the master's IMX477 Dual — the only node configuring the IMX477 — and publishes one camera for all consumers. The snapshot node's own Argus capture and the decoders' fixed camera size were removed: they read the camera layer (image size from camera_info).
    • ros2_lidar_ai_solution read cameras that do not exist (/camera_front/image_raw, /camera/image_rect, /image_raw, /camera_info, frame camera_color_optical_frame) and lifted image detections with the stereo camera's intrinsics: BEVFusion, the lifter, semantic fusion/overlay and arm pointing now read the camera layer, the frame and the aim tolerance come from its camera_info.
    • arm_look_at_node, camera_arm_node and the Isaac ROS semantic fusion/overlay read /camera_info and /image_raw, which nothing published; they default to /camera/color/camera_info and /camera/color/image_raw.

    5. Network boundaries¶

    Host Address Role in the diagram
    Jetson Orin Nano Super 192.168.10.1/24 Every Source/ node, micro_ros_agent on UDP 8888
    JetOwl FC (STM32N657) 192.168.10.2/24 jetowl_fc
    JetOwl_Vision (STM32N657) 192.168.10.3/24 jetowl_vision
    Server_OTA 192.168.10.200:8080 HTTP from the ota task of both MCUs, straight through the switch to the MetalLB address of the OTA Service (Helm chart ros2-jetson)
    Virtual MCU (Gazebo) UDP 9870 (data), 9871 (time synchronisation) McuEmulatorSystem plugin → sensor_link link
    OpenMV Cam (RT1062 / N6 with the Gigabit PoE Shield on the robot switch, other boards over USB) TCP or USB CDC vision link
    GCS MAVLink v2 over UDP or serial network_bridge_node

    6. Updating and re-rendering the image¶

    When adding or changing a node, update together:

    1. The mermaid block of section 1. Declare each topic once, in the subgraph of its main publisher.
    2. The table of section 3, and section 4 if a topic has no publisher or no subscriber.
    3. The SVG image, re-rendered with the bundled script. The script runs Mermaid 12 (dagre) in headless Chromium, converts labels to plain SVG, adds a white background and rounds the coordinates:
    npm i --no-save mermaid@12 playwright-core            # at the repository root
CHROMIUM=/path/to/chromium node Docs/flowcharts/render_flowchart.mjs \
    Docs/flowcharts/ros2_nodes_flowchart.md Docs/flowcharts/images/ros2_nodes_flowchart.svg
    1. The data and layout of the Live Node Graph page (Docs/assets/node-graph/), rebuilt from this file — Tests/test_node_graph_live.py fails until it is:
    npm i --no-save elkjs@0.9.3                  # once, at the repository root
python3 Scripts/diagrams/node_graph_live.py

    Keep "layout": "dagre" in the %%{init}%% line. Without it, Mermaid 12 (including mmdc) lays this graph out about twice as wide (~17 000 px instead of ~8 400 px) with many detours.

    The diagram must stay below Mermaid's default limits (500 edges, 50 000 characters) so that GitHub can still render the mermaid block.
