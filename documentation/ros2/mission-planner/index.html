    ROS2_Mission_Planner — mission layer above the flight controller¶

    Source

    This page is rendered from Source/ROS2_Mission_Planner/README.md, the authoritative description kept next to the code in Source/ROS2_Mission_Planner/.

    ros2_mission_planner 0.3.0 loads a mission and checks that it can be flown before arming. It then sequences the mission through ros2_flight_controller and supervises it until touchdown. The flight controller (FC) keeps the safety authority and runs the flight: trajectory, position loop and failsafes. The planner never commands velocities or set-points. It sends waypoint legs and navigation commands, then watches what the FC and the vehicle actually do.

     mission YAML / WaypointList ─▶ loader ─▶ survey / orbit generators ─▶ waypoints + keep-out zones
                                                                          │
     pre-flight analysis on the FC's own min-jerk trajectory (limits read from the FC):
     clearance to geofence + keep-out zones, detours, energy with the wind bound ─▶ accept / refuse
                                                                          │
 odometry/filtered ──┐                                                    ▼
 flight/status ──────┤                         ┌─▶ flight/waypoints (one leg, detour points included)
 battery/state ──────┼─▶ MissionExecutive ─────┤
 control/disturbance ┘    (10 Hz) state machine └─▶ flight/nav_command (ARM, TAKEOFF, START, HOVER,
       ▲                  + monitors + wind /                          RTH, LAND, DISARM)
       │                  power estimators
       └──── FC ─▶ ros2_control_system (MPC + ESKF) ─▶ vehicle ─▶ sensors ──┘

    The loop is closed at mission level. A leg ends only when the FC reports HOVER and the measured position is inside the waypoint's acceptance radius. The FC's failsafes (RTH, LANDING, EMERGENCY_STOP, manual joystick) are followed rather than fought. The planner commands a return or a landing on its own in three cases:

    • the odometry goes stale (landing);
    • the vehicle leaves the geofence or enters a keep-out zone (return home);
    • the battery reaches the energy needed to return with the reserve (return home).

    Mission state machine (mission_state_machine.cpp)¶

    EMERGENCY_STOP (→ EMERGENCY) and RESET (→ IDLE) are accepted from every state; LAND from every airborne state.

    stateDiagram-v2
    [*] --> IDLE
    IDLE --> PREFLIGHT: START_MISSION
    PREFLIGHT --> TAKEOFF: PREFLIGHT_OK
    PREFLIGHT --> IDLE: ABORT
    TAKEOFF --> NAVIGATING: TAKEOFF_COMPLETE
    TAKEOFF --> LANDING: ABORT / LAND
    NAVIGATING --> HOLDING: WAYPOINT_REACHED
    HOLDING --> NAVIGATING: HOLD_COMPLETE
    NAVIGATING --> RTL: ALL_WAYPOINTS / ABORT
    HOLDING --> RTL: ALL_WAYPOINTS / ABORT
    NAVIGATING --> LANDING: LAND
    HOLDING --> LANDING: LAND
    RTL --> LANDING: RTL_REACHED / LAND
    RTL --> COMPLETE: LANDED
    LANDING --> COMPLETE: LANDED
    EMERGENCY --> HOLDING: RESUME
    COMPLETE --> IDLE: RESET

    Design (control-systems.md §5)¶

    MISSION DESIGN
  Inputs      : odometry/filtered (ESKF, 100 Hz), flight/status (FC, 10 Hz), battery/state (BMS:
                SoC, V, I), control/disturbance (MPC d̂, 50 Hz), FC parameters (services + events)
  Filters     : SoC first-order low-pass α = T/(τ + T), τ = 5 s; measured/model power ratio
                low-pass τ = 20 s; odometry is already filtered by the ESKF
  Estimators  : wind: drag-law inversion of m d̂_xy + random-walk Kalman filter, 95 % disc
                ρ_w = 2.45 σ; power ratio r = max(1, r̂); energy-to-return along the planned
                return route with the wind disc
  Supervisor  : finite state machine IDLE → PREFLIGHT → TAKEOFF → NAVIGATING ⇄ HOLDING → RTL →
                LANDING → COMPLETE; EMERGENCY from any state; in-flight mission change
  Actuation   : legs of waypoints + START, acknowledged by the FC mode, re-sent after ack_timeout
                (3 retries), leg deadline 2·T_planned + 30 s; return = FC RTH or detour waypoints
  Loop        : closed on the FC's measured mode and odometry; watchdog 0.5 s → LAND
  Guarantees  : (1) clearance: c(p) (fence ∧ keep-out) is 1-Lipschitz ⇒ samples every Δt with
                    c ≥ v_pk·Δt/2 + margin keep the whole continuous path clear
                (2) detours: edges tangent to the inflated circle + FC path-deviation bound e_max
                    ⇒ c ≥ margin + v̄Δt/2 along the flown path by construction
                (3) energy: P̄(v, a, ŵ, ρ_w) ≥ P(v, a, w) for every wind in the disc; accept iff
                    SoC − 100·k·r·E/E_usable ≥ reserve; RTL when SoC_f ≤ reserve + 100·k·r·E_ret/E_usable
  Verification: 53 gtest cases (fake-FC executive tests included); SIL of the whole stack with a
                3.4 m/s wind, +10 % mass and aerodynamic drag: 4 scenarios, all checks pass
  Reference   : Richter, Bry & Roy 2013 (min-jerk); Leishman, Principles of Helicopter
                Aerodynamics §2.14, §5.4 (momentum theory, power); Simon, Optimal State
                Estimation §5.1 (Kalman filter); Galceran & Carreras 2013 (coverage)

    Clearance along the trajectory, not only at the waypoints¶

    The signed clearance c(p) is the minimum of these terms:

    • Horizontal fence: for the cylinder around home, R − ‖p_xy − home_xy‖. For a polygon, ± the distance to its nearest edge.
    • Altitude: z − z_min and z_max − z.
    • Keep-out zones: for each vertical cylinder {‖p_xy − c‖ ≤ r, z ≤ top} (a mast, a tree line, a building), its exact signed distance:
      • d_r = ‖p_xy − c‖ − r and d_z = z − top;
      • √(d_r² + d_z²) above the rim, max(d_r, d_z) elsewhere.

    Each term is 1-Lipschitz, because the signed distance to a convex set is. Their minimum is therefore 1-Lipschitz too: |c(p) − c(q)| ≤ ‖p − q‖.

    The analysis evaluates the same minimum-jerk trajectory the FC will fly (ros2_flight_controller::MinJerkTrajectory, with the FC's own limits) every Δt = 0.1 s. Between two samples, any point lies within v_pk·Δt/2 of one of them. So c ≥ v_pk·Δt/2 + margin at every sample proves c > 0 on the whole path. A leg can have all its waypoints inside and still be rejected when the path between them crosses a notch of the fence (test RejectsPathThroughKeepOutNotch).

    Detours around keep-out zones¶

    A segment AB that enters a zone is rerouted around it:

    1. Inflate the zone. Its radius becomes ρ = r + margin + v̄Δt/2 + b. The buffer b is at least the FC's trajectory.max_path_deviation_m.
    2. Build the detour. AB is replaced by A → V_0 … V_{n−1} → B. The V_k are the vertices of the polygon circumscribed about the circle ρ between the tangent points of A and B:
      • vertex radius ρ / cos(δ/2);
      • δ ≤ 45°;
      • the shorter side is tried first.
    3. Why it clears. Every edge lies on a tangent line of the circle, so the polyline stays at least ρ from the centre. The FC keeps the flown trajectory within e_max ≤ b of the polyline. Because c is 1-Lipschitz, the clearance test therefore passes by construction.
    4. Verify anyway. The test still runs, because the outer fence or other zones can interfere. If it fails, the other side and larger buffers are tried.

    The return path works the same way. When the FC's straight RTH is clear, the planner sends RTH. Otherwise it flies the verified detour route as waypoints and sends LAND above home.

    A zone taller than the RTH altitude raises a warning at start. The reason is that a failsafe RTH decided by the FC itself flies straight and does not know the zones.

    The FC-side fix that makes the detour guarantee hold is described in its changelog. The minimum-jerk spline could leave the waypoint polyline by tens of metres; the FC now bounds that deviation by adding stops at the offending knots.

    Energy with wind¶

    Electrical power in steady flight comes from momentum theory (Leishman §2.14, §5.4). The inputs are the ground velocity v, the acceleration a and the wind w, with air velocity V_a = v − w:

    F_aero = −(½ρ C_D A ‖V_a‖ V_a + c_H V_a,xy)        C_D A = 0.05 m², c_H = Σ k_H ω_hover = 0.571 N·s/m
f      = m a + m g e_z − F_aero,  T = ‖f‖            required rotor force
P      = P_hover (T / m g)^{3/2} + max(0, f·V_a) / η_p     P_hover = 383 W, η_p = 0.5
    • First term. It is exact for the static propeller model: T ∝ ω² and P ∝ ω³, so P ∝ T^{3/2}. In forward flight it is an upper bound, because the induced velocity drops below its hover value.
    • Second term. It is the climb and parasitic power.
    • Bound over the wind disc. P̄(v, a, ŵ, ρ_w) bounds P for every wind with ‖w − ŵ‖ ≤ ρ_w. It follows from the triangle inequality and the monotonicity of the drag law; the proof is in mission_analysis.h, and it is checked on 20 000 random cases in Power.HoverAndBoundDominatesModel.
    • Where the wind disc comes from. Before take-off it is ŵ = 0 with ρ_w = the design wind (5 m/s, any direction). In flight it is the estimate below.

    Mission energy is E = ∫ P̄ dt over take-off, every planned leg, holds, the return and the landing. A mission is accepted when SoC − 100·k·r·E / E_usable ≥ reserve, with k = 1.2 and E_usable = 88.8 Wh.

    Wind estimate. The MPC disturbance observer of ros2_control_system publishes the unmodelled acceleration d̂ on control/disturbance.

    • In steady flight the horizontal aerodynamic force is F = m d̂_xy, and it satisfies F = −D(‖V_a‖) V_a/‖V_a‖.
    • The drag law D(V) = ½ρC_DA V² + c_H V is strictly increasing, so it inverts uniquely: ‖V_a‖ = (−c_H + √(c_H² + 2ρC_DA‖F‖)) / (ρC_DA).
    • The wind measurement is then w_meas = v_xy + F ‖V_a‖/‖F‖.
    • A random-walk Kalman filter gives ŵ and σ. The disc ρ_w = 2.45 σ holds the truth with 95 % probability for an isotropic 2-D Gaussian (1 − e^{−3}).

    Measured-power correction. When the BMS reports voltage and current, the planner computes r̂ = LPF(V·|I| / P(v, 0, ŵ)) and uses r = max(1, r̂). The model is only ever scaled up, so it stays an upper bound. This covers a heavier payload, an aged battery or cold air.

    Flight-controller profile read at run time¶

    The planner reads these parameters from the FC's parameter services at start-up and again on every change the FC announces on /parameter_events:

    • speed limits, velocity-loop time constants, acceleration and minimum segment time;
    • take-off altitude, landing descent speed, RTH altitude and RTH speed;
    • the path-deviation bound.

    The profile is then computed by the FC's own PositionController::trajectory_limits(). With flight_controller.require_sync: true, mission/start is refused until the parameters have been read.

    In-flight mission change¶

    A mission uploaded while NAVIGATING or HOLDING goes through these steps:

    1. It is analysed from the current position. The analysis uses the current SoC, the wind disc and the power ratio, and assumes no take-off.
    2. If it is feasible, the planner sends HOVER and waits for the FC to hover.
    3. It then continues with the new plan. Home is unchanged.

    An infeasible mission is rejected, and the running mission continues.

    Patterns¶

    Pattern Rule Example
    Survey (boustrophedon) footprint W = 2h·tan(FOV/2), spacing s = W(1 − overlap), n = ⌈H/s⌉ + 1 lines; every point of the area is within W/2 of a line 50 × 40 m at 12 m, FOV 70°, overlap 0.3 → s = 11.8 m, 5 lines
    Orbit chord sagitta e = R(1 − cos(π/N)) ⇒ N = ⌈π / acos(1 − e/R)⌉ points per turn (smallest N with error ≤ e) R = 15 m, e = 0.2 m → N = 20

    Mission file¶

    mission:
  name: "demo square"
  frame: home            # home (relative to the arming position, default) | odom
  end_action: rtl        # rtl | land | hover
  defaults: {acceptance_radius: 1.5, hold_time: 0.0}
  waypoints:
    - {x: 10, y: 0, z: 5, heading_deg: 0, hold_time: 2.0}
    - {x: 10, y: 10, z: 5, action: navigate}   # navigate | takeoff | land | rtl | hover
  survey: {...}          # optional, appended after the waypoints (see config/missions/)
  orbit: {...}
  keep_out:              # optional known obstacles, same frame as the waypoints
    - {name: mast, x: 12, y: 0, radius: 3, top: 20}   # top omitted = unlimited height

    The altitude z and the zone top are relative to the take-off point (AGL at home) when frame: home. Per-waypoint speed fields are ignored with a warning, because the FC's trajectory limits set the speed.

    Kind Name Type Notes

    sub mission/upload_waypoints ros2_mission_planner/msg/WaypointList frame_id odom = absolute, otherwise home-relative
    pub flight/waypoints geometry_msgs/PoseArray one leg, frame odom, detour points included
    pub flight/nav_command std_msgs/String ARM, TAKEOFF, START, HOVER, RTH, LAND, DISARM
    pub mission/status ros2_mission_planner/msg/MissionStatus state, progress, SoC / required SoC, wind + radius, power ratio
    pub mission/geofence ros2_mission_planner/msg/GeofenceStatus clearance, binding constraint, keep-out name
    pub mission/preview nav_msgs/Path planned route (with detours after start), transient local
    pub mission/diagnostics diagnostic_msgs/DiagnosticArray
    srv mission/start, mission/abort, mission/reset, mission/reload std_srvs/Trigger

    The mission can start only while the FC is DISARMED. start first runs the analysis with home at the current position and the design wind. After arming, it re-runs the analysis with the home recorded at arming.

    Parameters: config/mission_planner_params.yaml. Every value is tagged with its source: vehicle, FC (read at run time), or assumption.

    Messages¶

    The interfaces are generated in this package (sources in msgs/msg/, types ros2_mission_planner/msg/*):

    Message Topic Content
    MissionStatus mission/status state, progress, SoC and SoC needed to return, wind estimate with its 95 % radius, measured-power ratio, return route type
    GeofenceStatus mission/geofence signed clearance, binding constraint (range, polygon, altitude, keep-out zone)
    WaypointList mission/upload_waypoints waypoints with acceptance radii, hold times, actions, end action; header.frame_id: odom = absolute, otherwise relative to home

    The STATE_* and VIOLATION_* constants equal MissionState and GeofenceViolation. A package that only needs the messages still depends on the whole planner (and through it on ros2_flight_controller).

    ros2 interface show ros2_mission_planner/msg/MissionStatus
ros2 topic echo /mission/status

    Launch¶

    # Planner only (FC and control stack already running)
ros2 launch ros2_mission_planner mission_planner.launch.py \
  mission_file:=$(ros2 pkg prefix ros2_mission_planner)/share/ros2_mission_planner/config/waypoint_mission.yaml
ros2 service call /mission/start std_srvs/srv/Trigger

# Whole stack: control system + flight controller + mission planner
ros2 launch ros2_mission_planner autonomous_mission.launch.py auto_start:=true

# Re-task in flight
ros2 topic pub --once /mission/upload std_msgs/msg/String "{data: '$(cat retask.yaml)'}"

    Known limitations¶

    • The wind estimate assumes steady flight and the drag model of the vehicle description (C_D A, c_H are assumptions until measured). During aggressive manoeuvres d̂ also carries the inner-loop lag. The measurement σ is inflated to 1 m/s for that, and the energy estimate uses the 95 % disc, not the point estimate.
    • η_p = 0.5 for the climb and parasitic power is an assumption. The measured-power ratio corrects the model upwards only, so an optimistic η_p is caught in flight but a pessimistic one is not relaxed.
    • Keep-out zones are known static cylinders from the mission file. Moving or unknown obstacles are handled below the planner by the MPPI mode of ros2_control_system. An FC-decided failsafe RTH flies straight; a warning is raised when a zone reaches above the RTH altitude.
    • An in-flight change stops the vehicle (HOVER) before switching; it does not blend into the new route.
    • HIL and bench evidence are still to be produced. They need the vehicle, a battery with a current sensor and a thrust stand; nothing more can be proven in software.
