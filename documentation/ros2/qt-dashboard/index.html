    ros2_qt — Qt operator dashboard¶

    Source

    This page is rendered from Source/ROS2_Qt/README.md, the authoritative description kept next to the code in Source/ROS2_Qt/.

    Operator dashboard for the JetOwl flight stack. One ROS 2 node, ros2_dashboard_node, reads the stack's topics with the same names and QoS as their publishers, supervises them (rate, jitter, staleness, publisher presence), and sends flight commands on flight/nav_command only. Every command is confirmed against the measured flight/status, never assumed. For the stereo camera it also calls ros2_stereo's services and writes its parameters, each confirmed by the node's response and a read-back.

    Look¶

    • Dark theme by default (less glare in the field), light theme with the header's sun / moon button or Ctrl+T. One QSS template (src/resource/styles/theme.qss) with two palettes (MainWindow::loadThemes): slate surfaces, one blue accent, 8 / 10 / 12 px radii.
    • Status colours keep their meaning in both themes (green OK, amber attention, red fault, blue info, grey unknown) and switch shade with the theme: every one has ≥ 4.5:1 contrast on its surface (WCAG AA); body text is 15:1 (dark) and 18:1 (light).
    • State badges (command result, E-STOP, RF failsafe) are tinted, not filled, so they never look like buttons; E-STOP is the only filled red control.
    • Icons are Lucide SVGs (ISC, src/resource/icons/), tinted to the theme at run time through Qt's SVG image plugin (libqt5svg5); without the plugin the text labels remain. Image, map and 3-D views share one dark canvas tone in both themes.
    • Fonts: Inter, else Segoe UI / Ubuntu / Noto Sans / DejaVu Sans (whichever is installed).

    Role in the control system¶

    The project rule (control-systems.md) requires every sensor-to-actuator path to be filtered, estimated, controlled and closed by feedback. The dashboard is not on any such path:

    • It subscribes only. The loops close elsewhere: rotor/attitude in jetowl_fc, position in uav_state_estimator (ESKF) → uav_trajectory_controller (MPC) → jetowl_fc, flight logic in flight_controller_node (flowchart §2).
    • It never publishes /cmd_vel, flight/cmd_vel, control/*, flight/setpoint or calls /jetowl/arm. Arming reaches the FC only through the stateflow (ARM → PRE_ARM_CHECK → flight/status → ros2_jetowl_bridge → /jetowl/arm) with its pre-arm checks.
    • Its one flight output, flight/nav_command, is a discrete event for the stateflow, and the operator loop is closed on the measured state (below).
    • Its other outputs act on ros2_stereo, a perception node that drives no actuator: set_processing, ~/capture_calibration_pair, ~/reset_temporal_filter and parameter writes. Each is closed the same way: the node's response (its own validation) is shown, a written parameter is read back, and the processing state is read from the node's diagnostics, not assumed from the button.

    Interface contract¶

    Source of truth: include/ros2_qt/core/topic_contract.hpp (unit-tested). Names are spelled exactly as the publisher spells them — relative names stay relative — so a namespace or --ros-args -r remap moves the dashboard together with the stack.

    QoS: a best-effort subscription matches reliable and best-effort publishers, so periodic streams use SensorDataQoS. Reliable is used where the publisher is reliable and a lost sample matters (status strings, flags). Transient local is requested only from latched publishers, so their last sample arrives on connect.

    Publication¶

    Topic Type QoS Content
    flight/nav_command std_msgs/String reliable, depth 10 ARM DISARM TAKEOFF LAND HOVER RTH START ORBIT PATH_START EMERGENCY_STOP EMERGENCY_CLEAR

    Nothing is published when the topic has no subscriber (the operator is told that flight_controller_node is not running in this domain). MANUAL / MANUAL_RELEASE are left out: they hand the vehicle to a joystick or /cmd_vel source the dashboard does not provide.

    Service clients¶

    std_srvs/Trigger: mission/start · mission/abort · mission/reset · mission/reload (mission_planner_node) · lidar_slam_node/save_map · stereo/stereo_node/capture_calibration_pair · stereo/stereo_node/reset_temporal_filter. std_srvs/SetBool: stereo/set_processing. Parameter services (list / get / describe / set_parameters) of stereo/stereo_node, stereo/depth_stereo_node, stereo/stereo_3d_node. An unavailable service is reported, not waited for.

    stereo_node converts and sends a layer only while it has subscribers, so the contract holds only its small left CameraInfo (health, and P for the probe); the stereo panel subscribes the two layers on screen plus depth and σ_Z, and unsubscribes them when they are no longer shown.

    Mathematics¶

    All formulas live in the ROS/Qt-free headers of include/ros2_qt/core/ and are unit-tested in tests/test_core.cpp.

    Topic rate, jitter and staleness — topic_rate_estimator.hpp¶

    For the receive times t₁ < … < tₙ in a sliding window of health.rate_window_s = W seconds:

    mean period   T̄ = (1/(n−1)) Σᵢ (tᵢ − tᵢ₋₁) = (tₙ − t₁)/(n − 1)        (telescoping sum)
rate          f̂ = 1/T̄
jitter        σ_T = √( Σᵢ (Δtᵢ − T̄)² / (n − 2) )                      (unbiased, n ≥ 3)

    This is the estimator of ros2 topic hz (ros2cli ros2topic/verb/hz.py), so the table and the CLI agree. The standard error of T̄ is σ_T/√(n−1). health.max_samples = 1000 ≥ W·f_max = 5 s · 200 Hz keeps the whole window for /imu/data.

    A topic with nominal period T (from its publisher's configuration) is STALE when its age exceeds k·T, health.stale_periods k = 3. With independent message loss probability p and jitter below T, that needs k consecutive losses, so a false alarm has probability pᵏ per period (1.25·10⁻⁴ for p = 5 %). k = 3 is also the ros2_jetowl_bridge link timeout (vision_mcu.link_timeout_s = 3 status periods). Event-driven topics have no period and are never called stale; the measured T̄ is never used as the threshold, because a stream that slows down would move its own limit.

    Command acknowledgement — flight_status.hpp, ros_bridge.cpp¶

    A command is confirmed when a flight/status message received after the send reports a mode in its expected set (e.g. TAKEOFF → {TAKEOFF, HOVER}; ARM → armed flag or {PRE_ARM_CHECK, ARMED_IDLE}), not confirmed after command.ack_timeout_s = 1 s. The bound: the slowest honest path is T_ui (50 ms) + T_status (20 ms at 50 Hz) + DDS latency (O(10 ms)) ≈ 80 ms, so 1 s leaves a > 10× margin, including the stateflow's own pre-arm transition. If the vehicle is already in the expected state, the dashboard says so instead of reporting a confirmation of a transition that did not happen.

    Attitude — conversions.hpp¶

    Unit quaternion → intrinsic Z-Y-X (roll φ, pitch θ, yaw ψ), after normalisation:

    φ = atan2(2(wx + yz), 1 − 2(x² + y²))
θ = asin(clamp(2(wy − zx), −1, 1))
ψ = atan2(2(wz + xy), 1 − 2(y² + z²))

    J. Diebel, Representing Attitude: Euler Angles, Unit Quaternions, and Rotation Vectors, Stanford University, 2006. Frames follow REP-103 / REP-105 (ENU world, FLU body).

    Uncertainty display¶

    ESKF position 1σ = √diag(P) from pose.covariance (6×6 row-major). GNSS horizontal 1σ = √((σ²_E + σ²_N)/2), SLAM pose 1σ = √((σ²_x + σ²_y)/2) (RMS of the two axes). Barometer ± √variance (1.2 Pa for the BMP280 σ² = 1.44 Pa², Bosch BST-BMP280-DS001).

    Occupancy grid — conversions.hpp¶

    Cell (i, j) centre in the map frame: p = o + R(ψ_o)·((i + ½)r, (j + ½)r); inverse i = ⌊x_g/r⌋, j = ⌊y_g/r⌋ with (x_g, y_g) = R(ψ_o)ᵀ(p − o); image row = H − 1 − j. Grey levels follow nav2_map_server: unknown → 205, otherwise g = 255·(1 − p/100). Since g(19) = 207 and g(20) = 204, the value 205 identifies unknown cells exactly (used by the colour schemes).

    Flight data tiles — conversions.hpp¶

    REP-105 odometry carries the twist in the child frame (odom_twist_in_child_frame: true in uav_control.yaml), so the body velocity is rotated into the world frame first: v_w = q ⊗ v_b ⊗ q*, computed as v_w = v_b + 2w(u × v_b) + 2u × (u × v_b) with u = (x, y, z) (J. B. Kuipers, Quaternions and Rotation Sequences, 1999, §5.14). Ground speed = √(v_w,x² + v_w,y²), vertical speed = v_w,z. Compass heading h = (90° − ψ_ENU) mod 360° (ENU yaw is counter-clockwise from east, REP-103). Position 1σ = √((σ_x² + σ_y²)/2).

    Subsystem status and command availability — system_health.hpp, flight_status.hpp¶

    Each of the 7 contract groups is reduced to one state from its periodic topics (an event topic's silence is normal): no publisher at all → NOT RUNNING (a FAULT for flight controller, estimation and flight manager); a present topic STALE → FAULT; never delivered or partly missing → DEGRADED; else OK. Diagnostics are STALE after k·T = 3 × 1 s.

    A command button is enabled only in the modes where flight_controller_node's stateflow has a transition for its event (stateflow.cpp table plus the airborne failsafes added by add_if_missing); E-STOP is never disabled. Battery colour bands are the flight manager's own battery_warning_pct 30 % / battery_critical_pct 15 % (flight_params.yaml).

    SLAM 3D — slam3d_mapper.hpp, voxel_map.hpp¶

    The sensors. The LD19 is a 360° scanner that measures one plane (450 rays, 10 Hz, 0.3–12 m used); the LPB40B measures one point along +x (0.05–40 m, 2.2° beam). Neither is a 3-D sensor. The third dimension comes from the vehicle: each revolution is placed with the full pose, so slices taken at different altitudes and attitudes stack into a 3-D map (on a ground robot it is the single slice at the sensor height).

    Pose of a scan. x, y, ψ from slam/pose, matched by time stamp (the SLAM stamps its pose with the scan time); z, φ, θ from the ESKF odometry/filtered, the nearest sample within 30 ms, decided once a sample at or after the scan time has arrived. The 2-D SLAM's map → odom is planar, so z and the gravity-referenced roll/pitch are the same in both frames. Without ESKF data the scan is placed planar (z = φ = θ = 0, the 2-D SLAM's own assumption) and the view says so. p_map = R_z(ψ) R_y(θ) R_x(φ) (R_m p_s + t_m) + t, mounts (R_m, t_m) from /tf_static.

    Motion during a revolution. Ray i is taken at tᵢ = stamp + i·time_increment; a constant-velocity de-skew from the last two SLAM poses moves it to (x + vₓΔtᵢ, y + v_yΔtᵢ, ψ + ωΔtᵢ). Without it the error is v·T_rev (0.1 m at 1 m/s).

    Occupancy. Binary Bayes filter in log-odds (Thrun et al., Probabilistic Robotics, §9.2) with the same inverse sensor model as the 2-D grid (occupancy_grid.cpp): l_hit = logit(P_D/(P_D + P_FA)) = 2.48, l_pass = logit((1−P_D)/((1−P_D)+(1−P_FA))) = −0.865, clamped to ±4 (as OctoMap, Hornung et al. 2013), shown when p > 0.5. Rays are traversed with the 3-D DDA of Amanatides & Woo (1987). The LPB40B follows the SLAM's wide-beam rule: its end voxel is marked only while r·FOV ≤ 2 voxels (r ≤ 2.6 m), else only free space to r − 3σ. Voxels are created by their first hit, so memory follows the surface (37 k voxels for a 9 × 6.5 × 3 m room, against 1.4 M for its volume); free evidence still clears existing voxels.

    Thermal view — thermal_view.hpp¶

    The view only displays; the thermal chain ends at its tracker and closes no loop here.

    • Position. A covariance belongs to one estimate, so position and covariance are read from the same field: results[0].pose when its 2×2 block P = [a b; b c] is positive definite (a > 0, c > 0, ac − b² > 0), otherwise the bbox centre (producers without uncertainty, such as NanoOWL; no ellipse is drawn then). This is read_detection() of the publishing package.
    • 95 % ellipse (Bar-Shalom, Li, Kirubarajan 2001, §1.4.17, §3.7.1). For e ~ N(0, P), d² = eᵀP⁻¹e is χ²₂ with the closed-form CDF 1 − e^(−γ/2), so the region holding probability p is d² ≤ γ_p = −2 ln(1 − p) (5.991 for 95 %). Eigenvalues λ₁,₂ = (a + c)/2 ± √(((a − c)/2)² + b²), major-axis angle θ = ½·atan2(2b, a − c), semi-axes √(γ_p λᵢ). The table's 1σ is √λ₁, the error in the worst direction. A Monte-Carlo test (2·10⁵ samples) checks the 95 % coverage.
    • Time alignment. Overlays are drawn on the frame with the same header.stamp (the detector copies the image header, the tracker the detection header). On the latest frame instead, a target moving at the 32.7 px/s the detector's low-pass still passes would be off by v·Δt = 1.3 px per 40 ms frame (10 screen px at 8× zoom). An overlay that arrives before its frame waits for it (16-frame history); if that frame was lost (image is best effort) or the stamps come from another clock, the nearest frame is used and the offset Δt is printed. With no detections or tracks for thermal.overlay_timeout_s = k·T = 3 × 40 ms, the raw frame is shown alone.
    • Colour scale. [T_lo, T_hi] = the 1 % and 99.5 % quantiles of the finite pixels (as the detector's debug image), linear interpolation between order statistics (Hyndman & Fan 1996, type 7), widened to ≥ 1 K so a uniform scene does not stretch sensor noise over the palette. Index i = round(255·clamp((T − T_lo)/(T_hi − T_lo))). Inferno is matplotlib's 256-entry table (van der Walt & Smith 2015, CC0) at 8 bit, lightness increasing with temperature; white hot is grey. Non-finite pixels are cyan. Hold scale freezes [T_lo, T_hi].
    • Pixels. Nearest-neighbour magnification with an integer zoom: each sensor pixel is one square, no interpolated temperature is shown. Pixel centres are on integers, so pixel (u, v) covers [u − ½, u + ½) and a box (centre c, size w) holds the pixels ⌈c − w/2⌉ … ⌊c + w/2⌋; T max is the hottest raw pixel among them.
    • Decoding = thermal_detector's: 32FC1/64FC1 are °C; 16UC1/mono16/mono8 map T = counts_scale·counts + counts_offset.

    Stereo view — stereo_view.hpp¶

    Display only: ros2_stereo is the sensor → filter → estimator part of the depth consumers' loops.

    • Pixel grid. Disparity, depth, σ_Z, confidence and the left rectified image share the left rectified pixel grid at the working resolution, so one cursor probes all of them; the right image is another camera and does not probe.
    • Depth. The node's depth is used; without it Z = f·T/d from the DisparityImage (stereo_msgs definition, zero-disparity rectification, Hartley & Zisserman §9.3). depth/image_mm is millimetres with 0 = no return (REP-118).
    • 3-D point. The ray of pixel (u, v) is m = ((u − c_x)/f_x, (v − c_y)/f_y, 1) with f, c from the rectified projection P of left/camera_info; p = Z·m, i.e. X = (u − c_x)Z/f_x, Y = (v − c_y)Z/f_y, the node's own back-projection. For a fixed pixel p is linear in Z, so the range r = ‖m‖Z has σ_r = ‖m‖σ_Z exactly to the first order in which σ_Z = Z²σ_d/(fB) is itself propagated by the node.
    • Same frame. depth, σ_Z, disparity and confidence of one pair carry one stamp; the probe reads each layer at the stamp of its Z (4-frame history ≥ ⌈30 Hz · 50 ms⌉ + 1) and leaves a value out rather than take it from another frame.
    • Region. valid fraction, nearest Z = min over valid pixels with σ_Z at that pixel (what an obstacle check needs), median Z (type-7 quantile).
    • Colours (inferno): depth over the node's depth window [min_depth, max_depth], read from its parameters, near = bright; disparity over [min_disparity, max_disparity] of the message, large d = bright (the same near = bright); σ_Z over [0, 99.5 % quantile]; confidence over [0, 1]. Non-finite (invalid) pixels are cyan. Scalar layers are drawn nearest-neighbour.
    • Rates of the shown layers come from their header stamps, so they are the node's output rate, not the GUI poll rate.

    Images and clouds¶

    Depth encodings (16UC1/mono16, 32FC1) are stretched linearly over the finite, non-zero values of each frame (0 = no return, REP-118). Point clouds are decimated with a fixed stride s = ⌈n / N_max⌉ (viewer.max_cloud_points), NaN returns dropped; all numeric PointField types and either byte order are decoded.

    Architecture¶

    src/core/main.cpp            argv → RosBridge; SIGINT/SIGTERM → self-pipe → QApplication::quit
src/ros/ros_bridge.cpp       rclcpp::Context per connection (InitOptions::set_domain_id),
                             SingleThreadedExecutor in a std::thread, Qt signals, command ack
src/ros/dashboard_node.cpp   subscriptions / publisher / clients, copies into plain types
src/ros/introspected_message.cpp  decode a message by type name via its run-time type support
include/ros2_qt/core/        contract, rate estimator, status protocol, conversions (no ROS/Qt)
include/ros2_qt/widgets/     status strip, flight data, commands, alerts, topic health, diagnostics,
                             camera, thermal, stereo, remote parameters; + map and point-cloud
                             viewers (built in code, no .ui forms)
src/resource/styles/theme.qss  one theme template; MainWindow fills the dark / light palette
    • Domain switching works. ROS_DOMAIN_ID is read once by rclcpp::init; the previous build set the variable afterwards, which had no effect. Each connect now creates a new context with the domain from the GUI and passes it the process's --ros-args, so launch remaps and parameter files still apply.
    • The GUI never blocks on ROS. Callbacks copy into a snapshot under one mutex; image decoding, grid conversion and cloud decimation happen in the executor thread. The GUI polls the snapshot at ui.refresh_rate_hz (20 Hz) and the health table at 2 Hz.
    • Clean shutdown. Disconnect / close / SIGINT cancel the executor, join its thread, then release node and context.

    Firebase (optional)¶

    FirebaseClient (libcurl + jsoncpp, REST API) is enabled at run time when FIREBASE_URL and FIREBASE_API_KEY are set (configure_firebase.sh, .env.example). It is independent of ROS.

    Known limitations¶

    • Saving / opening dashboard layouts (*.dash) and the preferences dialog are not implemented; their menu entries are hidden and the default tab is rebuilt on start-up.
    • One image topic and one point-cloud topic are subscribed at a time (shared by all viewers).
    • Poses and paths are drawn only when their frame equals the map frame (no TF lookup).
    • battery/state has no publisher in the three repositories yet; the overview says so.
    • The stereo panel makes stereo_node publish the layers it shows (that is how the node saves work); set the image pane to None when the Jetbot's CPU or the link is tight (depth and σ_Z stay subscribed for the probe).
    • The thermal view shows the raw frame (image_temperature), not the low-passed frame the detector thresholds; T max is therefore the hottest raw pixel in the box, not the detector's filtered peak (which Detection2D has no field for).

    Troubleshooting¶

    Symptom Check
    Everything NO PUBLISHER ROS_DOMAIN_ID in the GUI matches the stack; ros2 node list from a shell in that domain
    Command NOT SENT flight_controller_node not running: nothing subscribes flight/nav_command
    Command NOT CONFIRMED the stateflow rejected it from the current mode (see flight_controller_node log), or flight/status is stale
    mission/status fields n/a ros2_mission_planner not installed in the sourced environment (no rebuild of ros2_qt needed), or its MissionStatus fields changed (warning at start-up)
    Black 3-D view OpenGL 2.1 needed; on WSL2/headless use LIBGL_ALWAYS_SOFTWARE=1
    Thermal: "Waiting for thermal/image_temperature" pipeline not started, or started in another namespace: thermal_namespace:= must equal the pipeline's namespace:=
    Stereo panes "Waiting for stereo/…" stereo_node not running, or in another namespace (stereo_namespace:=); confidence exists only with the VPI matcher, right/image_rect only with output.right_rectified: true, depth/image_mm only from depth_stereo_node
    Stereo parameters "not available" the node's parameter services are not discovered yet (press Refresh), or the node name differs (stereo.node_name, or type it in the selector)
    Thermal: "overlay Δt = … ms" the overlay's own frame was not received (best-effort image under load), or the producer stamps with another clock; the offset is the stamp difference to the frame drawn
