    ros2_panorama — camera layer of the IMX477 Dual¶

    Source

    This page is rendered from Source/ROS2_Panorama/README.md, the authoritative description kept next to the code in Source/ROS2_Panorama/.


    The master Jetson carries two IMX477 side by side (CSI 0 and CSI 1, optical axes some tens of degrees apart, rigidly mounted; no stereo — the IMX219 stereo pair is on the worker). ros2_panorama is the camera layer of that pair: the one place where the IMX477 are configured (sensors, modes, frame rate, intrinsics, stitching), publishing one camera that every image-processing and detection node uses as it is. No consumer has an IMX477 setting.

    Camera contract (namespace /camera/color)
    image_raw sensor_msgs/Image rgb8: the two IMX477 stitched into one frame (output.mode: panorama, 1920 × 720) or one IMX477 (single, 1280 × 720)
    camera_info with every frame: width/height (the detectors read the image size from it), and K/D/R/P when the intrinsics are known — all zero otherwise, which sensor_msgs/CameraInfo defines as uncalibrated
    frame arm_camera_optical_frame (panorama: the virtual camera bisecting the two optical axes)
    Consumer Reads Camera settings of its own
    isaac_ros_objectdetection (YOLOv5, SSD, NanoOWL decoders, visualizer, DNN encoder) image_raw, size from camera_info none (source_image_* / img_* = 0)
    arm_look_at_node, camera_arm_node camera_info (idle while K = 0) none
    isaac_ros_snapshot_downlink image_raw none (no Argus code any more)
    ros2_lidar_ai_solution: BEVFusion, detection lifter, semantic fusion / overlay, arm pointing image_raw, camera_info (intrinsics, size, frame, aim tolerance) none

    With stabilizer.enabled the same two topics carry the stabilised frame (the camera shake removed by image processing, §9); camera_info then carries the zoomed intrinsics of the virtual camera and stabilizer/correction the rotation applied. It is off by default.

    Switching the camera (panorama ↔ one IMX477, another size, new intrinsics) is a change of config/panorama.yaml only. It uses no OpenCV: GStreamer appsink for capture, Eigen for the 3 × 3 / 9 × 9 linear algebra, and the image processing below written out and tested here.

    The goal is the failure shown by a naive stitch — a visible seam region: a brightness/colour step where one camera's image starts, the slanted border of the warped image, and black corners. Each has a cause and a remedy:

    Artefact Cause Remedy (stage)
    Brightness / colour step each sensor runs its own AE and AWB per-channel gain compensation + Kalman filter (§3)
    Low-frequency band (vignetting, residual gain) the step is removed in the mean, not everywhere multi-band blending: low frequencies fade over the whole strip (§5)
    Ghosts / doubled edges parallax b/Z of near objects, moving objects, pair skew seam through the pixels where both images agree (§4)
    Slanted border, black corners the warped footprints are not rectangles crop to the largest rectangle of the output aspect inside the union (§2)

    Source layout and the rules between the modules: Architecture.

    This package drives no actuator: it is the sensor and filter stage of the loops that use the camera (arm gaze loop 6a, detections). Its failsafe is on the data: no panorama is published until the rig is calibrated (the raw topics are), a lost camera stops the output (no half panorama), /diagnostics goes to ERROR after 1 s without a frame.

    Quick start¶

    colcon build --packages-select ros2_panorama && source install/setup.bash

# 1. (recommended) intrinsics of each IMX477 at 1280×720, with the lens it will fly with:
#    publish_raw gives each sensor as captured, so no other camera node is needed
ros2 launch ros2_panorama panorama.launch.py publish_raw:=true
ros2 run camera_calibration cameracalibrator --size 8x6 --square 0.025 \
    image:=/camera/color/cam0/image_raw camera:=/camera/color/cam0     # → imx477_0.yaml
ros2 run camera_calibration cameracalibrator --size 8x6 --square 0.025 \
    image:=/camera/color/cam1/image_raw camera:=/camera/color/cam1     # → imx477_1.yaml
#    (without them: homography model, camera_info with K = 0)

# 2. run: the first start calibrates the rig from the images (point it at a textured scene
#    with something in the overlap, ≥ 5 m away), stores it, and verifies it on later starts
ros2 launch ros2_panorama panorama.launch.py \
    camera0_info:=$HOME/imx477_0.yaml camera1_info:=$HOME/imx477_1.yaml
ros2 run rqt_image_view rqt_image_view /camera/color/image_raw
ros2 topic echo /diagnostics --field status[0].values     # gains, NIS, overlap |ΔY|, seam, ms

# 3. after moving a camera
ros2 service call /camera/color/panorama_node/recalibrate std_srvs/srv/Trigger

# One IMX477 only (bench, or a camera failed): same topics, no stitching
ros2 launch ros2_panorama panorama.launch.py mode:=single camera:=0 camera0_info:=$HOME/imx477_0.yaml

# Offline, no camera: two PPM images of the rig
ros2 run ros2_panorama panorama_stitch left.ppm right.ppm out.ppm --f 1050 --save rig.yaml

    4. remove the camera shake (needs both camera_info files: the rotation model of §9)¶

    ros2 launch ros2_panorama panorama.launch.py stabilize:=true \ camera0_info:=\(HOME/imx477_0.yaml camera1_info:=\)HOME/imx477_1.yaml ros2 topic echo /diagnostics --field status[0].values # stab_* : status, NIS, innovation rms, ms

    shake_std_deg: hold the camera still on its mount and read stab_innovation_rms_deg¶

    Without ROS: cmake -S . -B build -DBUILD_TESTING=ON && cmake --build build -j && ctest --test-dir build.

    Interfaces (panorama_node, namespace /camera/color in the launch file)¶

    Topic / service Type
    image_raw sensor_msgs/Image rgb8: panorama output.width × output.height (1920 × 720), or one camera as captured (single) stamp = mid-exposure of the pair, frame arm_camera_optical_frame
    camera_info sensor_msgs/CameraInfo, every frame panorama: virtual pinhole (planar projection with intrinsics), K = 0 otherwise; single: that camera's K and D, or zeros
    cam0/image_raw, cam1/image_raw + camera_info with publish_raw: true each sensor as captured (calibration, debugging)
    ~/recalibrate std_srvs/Trigger pool calibration.frames new pairs and refit
    stabilizer/correction geometry_msgs/QuaternionStamped with stabilizer.enabled: the rotation applied to the frame, physical camera ray = R · output ray (frame arm_camera_optical_frame)
    /diagnostics rate, pair skew, calibration inliers / RMS, gains, gain NIS, overlap |ΔY| raw → compensated, seam, blended columns, time per frame; with the stabiliser: stab_status, correction and rate, stab_nis, stab_innovation_rms_deg, registration std / R² / inliers / σ, saturated and coasting frames, stab_ms

    Parameters: config/panorama.yaml (every value tagged with its origin).

    Stabilised output. The image is rotated about the optical centre and zoomed by z ≥ 1 (derived, §9.5), so camera_info carries fx·z, fy·z and the zoomed principal point of the virtual camera, D = 0. A consumer that only needs the image and camera_info (detection, arm gaze, snapshot) needs nothing else. A consumer that projects with the camera extrinsics (lidar fusion in ros2_lidar_ai_solution) sees a camera rotated by up to the crop box (1° by default): either apply stabilizer/correction or leave the stabiliser off for it.

    Architecture¶

    The package is layered. What the camera layer decides — the rig calibration state machine, stitching, stabilising, the /diagnostics rules — is in a library that does not know ROS; the node is a thin adapter around it (parameters, cameras, one capture thread, messages).

    The layering is a test. test_layering (test/architecture/check_layering.py, run by ctest) fails when a module includes one it must not (table above), when a ROS header is included outside node/ or a GStreamer header outside capture/, or when an Eigen header is reachable from a .cu file (Eigen under nvcc is fragile; both kernel files keep it out). Everything below node builds and is tested without a ROS installation.

    Threads. One capture thread: blocking GStreamer reads, the pipeline, the publishing. The executor runs the diagnostics and ~/recalibrate. They share the pipeline (an atomic request and a status copy under a mutex) and PanoramaDiagnostics (its own mutex) — nothing else, and no lock is held across a call into the other side. An exception in the capture thread is a FATAL log and an ERROR in /diagnostics, not std::terminate of the process (or of the container).

    Composition. ros2_panorama::PanoramaNode is registered as a component (rclcpp_components), panorama_node is its executable (own main(): a bad parameter or a camera that cannot be opened is a FATAL log and exit code 1). To run it inside a container: ros2 component load <container> ros2_panorama ros2_panorama::PanoramaNode. The launch file still starts the executable.

    Adding something. A stage of the pipeline: write it in its own module with no ROS, call it from PanoramaPipeline, test it in test/pipeline/. A parameter: a field of PanoramaParams (or of the stage's params), declared in panorama_params.cpp, tagged in config/panorama.yaml. A /diagnostics value: PanoramaDiagnostics, with its test: the keys are an interface.

    Design record¶

    1. Capture and rig model¶

    Two GStreamer pipelines nvarguscamerasrc sensor-id=N → nvvidconv → appsink max-buffers=1 drop=true: the Argus ISP debayers and runs AE/AWB per sensor, the VIC scales the 1920 × 1080 binned mode to 1280 × 720 RGBA (same field of view, filtered — no CPU conversion), the sink keeps the newest frame. The sensors are free-running, so a pair is up to one frame period apart (33 ms at 30 Hz); the skew is measured from the buffer timestamps and reported. A moving object is misregistered by u̇ · skew in the overlap — the seam (§4) avoids cutting through it.

    Camera model: ROS plumb_bob (Brown–Conrady), core/camera_model.hpp. Rig model: the cameras rotate about (nearly) one centre, so the unit rays of a scene point satisfy

    r1 = R r0                      (exact up to the parallax angle b/Z, b = lens separation)

    For b = 3 cm and f = 1050 px, a point at Z = 10 m is 3.2 px off the model, at Z = 50 m 0.6 px. The model is the standard one for panoramas (Szeliski, Image Alignment and Stitching, 2006, §2.2); what it cannot represent (near objects) is handled by the seam.

    2. Calibration and geometry (once)¶

    Step Method Source
    Corners Harris in the harmonic-mean form f = det H / tr H, σd = 1, σi = 1.5, 3 × 3 maxima, bucketed 16 × 9, sub-pixel quadratic peak Brown, Szeliski, Winder, CVPR 2005
    Descriptor 8 × 8 samples, spacing 5 px, σ = 2.5 blur, bias/gain normalised (exposure-invariant) ibid. (MOPS without rotation)
    Matching SSD nearest neighbour, ratio < 0.8, mutual Lowe, IJCV 2004 §7.1
    Rotation (with intrinsics) RANSAC, 2-point minimal sets, threshold 2 px / f, then least squares on the inliers: M = Σ r1 r0ᵀ = U S Vᵀ, R = U diag(1, 1, det UVᵀ) Vᵀ Fischler & Bolles 1981; Kabsch 1976
    Homography (without) normalised DLT, RANSAC 4-point, N = log(1−p)/log(1−w⁴) Hartley & Zisserman, Alg. 4.2, 4.5
    Acceptance ≥ 40 inliers and RMS ≤ 1.5 px (0.5 px corner noise + 1 px parallax budget) —

    The rig is rigid, so R is a constant: it is fitted once on 10 pooled pairs and stored (calibration_file), then on each start the stored R is checked against the live images (check(): inliers and RMS of the stored model) and refitted only if the rig moved. Fitting it per frame would make the panorama jitter with the feature noise.

    Virtual camera: halfway rotation R_h = exp(½ log R), so r0 = R_hᵀ d, r1 = R_h d — the panorama axis bisects the two cameras and both are distorted alike. Projections of d: planar (dx/dz, dy/dz) (a pinhole image: camera_info is published and every consumer keeps its pinhole model), or cylindrical (atan2(dx, dz), dy/√(dx²+dz²)) for a total field of view beyond ~120°. The output rectangle is the largest rectangle of the output aspect ratio inside the union of both footprints (binary search on its height, summed-area table of the coverage), centred on the footprint: no black corners and no slanted border. A look-up table holds, per output pixel and camera, the source position (bilinear sampling).

    3. Gain compensation and its estimator (every frame)¶

    Brown & Lowe, Automatic Panoramic Image Stitching using Invariant Features, IJCV 2007, §6, for two images: with the overlap means a (camera 0) and b (camera 1) of one channel,

    e = N (g0 a − g1 b)²/σN² + ½ N [(1 − g0)² + (1 − g1)²]/σg²
∂e/∂g = 0:  [2αa² + β, −2αab; −2αab, 2αb² + β] [g0; g1] = [β; β],   α = 1/σN², β = 1/σg²

    With the paper's σN = 10, σg = 0.1 the prior leaves part of the difference (3.5 % of a at a/b = 1.25), which is a step in the panorama. With two images the data term can be zeroed exactly and the prior only fixes the common scale; the limit σN/σg → 0 is

    g0 = 2b/(a + b),   g1 = 2a/(a + b)        (g0 a = g1 b,  (g0 + g1)/2 = 1)

    the default (gain.sigma_n: 0), per channel R, G, B — which also equalises the white balance.

    The per-frame solution is noisy (moving objects, noise); the true ratio changes only as fast as the two AE loops. Each gain is a random walk g[k+1] = g[k] + w, w ~ N(0, q), measured as z = g + v, v ~ N(0, r), and filtered by the scalar Kalman filter

    P⁻ = P + q,  K = P⁻/(P⁻ + r),  g ← g + K (z − g),  P = (1 − K) P⁻

    with √q = 0.01/frame (AE drift ≤ 1 %/frame) and √r = 0.02. Steady-state gain K∞ = P⁻∞/(P⁻∞ + r), P⁻∞ = (q + √(q² + 4qr))/2 = 0.39: a step in exposure is followed with a time constant of ≈ 2 frames (67 ms). The normalised innovation squared ν²/S is published (gain_nis); its mean ≈ 1 when q and r match the data (χ²₁), the check for tuning r on the rig.

    4. Seam (every frame)¶

    The overlap is divided into 4 × 4 px cells; the cost of a cell is the mean |Y0 − Y1| of the gain-compensated luma. The seam is the top-to-bottom path of minimum total cost, moving at most one cell sideways per cell row, found by dynamic programming (Efros & Freeman, Image Quilting, SIGGRAPH 2001; Avidan & Shamir, Seam Carving, SIGGRAPH 2007):

    M(y, x) = C(y, x) + λ |x − s_prev(y)| + min(M(y−1, x−1), M(y−1, x), M(y−1, x+1))

    It runs where the two images agree, around near objects (parallax) and moving objects. The λ term (1 grey level per cell of displacement) keeps it from jumping between frames, so the cut does not flicker. Rows seen by one camera only (top/bottom of a tilted footprint) are filled with that camera in both strips, so any seam gives that camera there.

    5. Multi-band blending¶

    Burt & Adelson, A Multiresolution Spline With Application to Image Mosaics, ACM ToG 2(4), 1983: Laplacian pyramids of both strips, Gaussian pyramid of the binary seam mask M, L_k = G_k(M) L_k(A) + (1 − G_k(M)) L_k(B), collapsed. Each band is blended over a transition proportional to its wavelength: the low band (residual gain, vignetting) fades over ≈ 64 px on each side, edges stay sharp — no step and no doubled edges. Since the pyramids are linear it is computed as B + collapse(G_k(M) · L_k(A − B)): one pyramid instead of two, same result. Generating kernel [1 4 6 4 1]/16 (a = 0.375).

    Only a band is blended, exactly. A level-k coefficient depends on input pixels within 2^(k+1) − 2 px and the collapse at a pixel uses coefficients within 2^(k+1) − 2 px, so where the mask is constant within 2^(L+2) px (64 px for L = 4) the blended pyramid is that of one image and the collapse returns that image exactly (collapse inverts the construction, G_k = L_k + EXPAND(G_(k+1)), whatever the border handling). Only the columns within 64 px of the seam are sampled from both cameras and blended each frame; every other pixel is sampled from the one camera on its side of the seam — with no step at the band edges (test Pyramid.FarFromTheSeamTheBlendIsExact). The look-up table stores the top-left source pixel and 8-bit bilinear weights (interpolation error ≤ 0.5 grey level), so one table read gives the three channels.

    6. Precision: fast and exact¶

    The per-pixel stages run in one of two arithmetics (precision):

    fast (CPU) exact (CUDA, or CPU on request)
    bilinear weights 8 bit (error ≤ 0.5 grey level) float
    overlap means for the gains every 4th pixel in x and y (1/16) every overlap pixel
    seam cell cost 2 × 2 samples of a 4 × 4 cell all 16 pixels

    Measured on the synthetic rig (Stitch.ExactArithmeticIsAtLeastAsAccurate): PSNR equal (36.94 / 36.92 dB — the error is dominated by resampling and noise, not by the weights), luma step at the seam 0.60 → 0.475 grey levels (−21 %: the cost of a cell is its true mean, so the seam follows the agreeing pixels more closely), gain-ratio error 0.0290 → 0.0287. The exact arithmetic is never worse, and costs 2.4× the CPU time — which is what the GPU removes.

    7. GPU path (stitch_cuda.cu)¶

    The per-pixel maths is written once in pixel_ops.hpp (__host__ __device__): bilinear sampling, luma, rounding, and REDUCE / EXPAND of the pyramid. The CPU exact path and the CUDA kernels call the same functions, so the CPU tests check the arithmetic the GPU runs, and Stitch.CudaMatchesCpuExact compares the two images on a Jetson (≤ 1 grey level: the float reduction order and FMA contraction differ).

    Stage Kernel Work
    upload cudaMemcpyAsync two RGBA frames (Orin: DRAM to DRAM, same memory)
    gains k_overlap_sums every overlap pixel; block tree reduction in shared memory, one atomicAdd(double) per block
    seam cost k_seam_cost one thread per 4 × 4 cell → host
    seam CPU dynamic programme on ~180 × 150 cells (sequential in rows)
    direct pixels k_direct one thread per output pixel outside the band
    band k_band → k_sub → k_reduce_h/v (D, mask) → k_top → k_expand_h/v + k_band_level → k_band_write B + collapse(G_k(M) · L_k(A − B))
    download cudaMemcpyAsync rgb8 frame

    All buffers are allocated once at configure (the band lies inside the overlap strip). The CPU keeps the 6-scalar gain filter, the seam programme, and the ROS message.

    8. Timing¶

    CPU (CI, x86, 1920 × 720 output, overlap up to 561 px, 4 threads): fast ≈ 12 ms per frame wall, 29 ms CPU (≈ 0.9 core at 30 Hz); exact ≈ 29 ms wall. Calibration: ≈ 1 s per pair (features of two 1280 × 720 images), only at start. GPU: the kernels are compiled for sm_87 in CI (nvcc 12.0) but not run (no GPU there); measure on the Orin with /diagnostics (ms_total, backend), which warns when a frame takes longer than 1/f_s. Helm requests 0.75 core for the node with the GPU path (gains, seam programme, message).

    9. Image stabiliser (stabilizer.enabled)¶

    A camera on an airframe or an arm shakes. Its orientation is R_c = Q exp(ς): Q is the intentional orientation (the pan and tilt the consumers must see), ς the shake. The stabiliser shows the image the camera would have taken at Q̂ ≈ Q, by image processing alone (no IMU), by rotating the frame digitally inside a crop box. It runs on the stitched panorama (output.mode panorama, planar projection, both camera_info files); otherwise it is refused and bypassed, with the reason in the log.

    9.1 The model is a rotation, not a translation¶

    Shake is a rotation about the optical centre (the translation of the airframe is cm against objects metres away: the same argument as the rig model of §1), so a frame is related to the next by u′ ~ K R K⁻¹ u (Hartley & Zisserman, Multiple View Geometry, §8.4.2). A panorama is wide: the flow of a rotation Δ at the normalised point (x, y) is, to first order (Longuet-Higgins & Prazdny, Proc. R. Soc. Lond. B 208, 1980),

    ∂u/∂Δ = fx [ −x y,   1 + x²,  −y ]            ∂v/∂Δ = fy [ −(1 + y²),  x y,  x ]

    For a 1° yaw on the 1920 × 720 panorama (f = 1050 px, x_edge = 0.914) the image moves f ψ = 18.3 px at the centre and f ψ (1 + x²) = 33.6 px at the edges: a translation model (the usual "2D stabiliser") leaves 7.6 px of wobble at the edges even when fitted to the mean. The rotation model has 3 parameters, uses the intrinsics the stitcher already has, and is exact for pure rotation.

    9.3 Measurement: registration to the previous output¶

    Template T = the previous output O_{k−1} (intrinsics Kₛ), image I = the new frame (K). With W(u; R) = π(K R Kₛ⁻¹ ũ) and the residual e = I(W(u; R)) − T(u), the inverse compositional algorithm precomputes the steepest-descent images SD = ∇Tᵀ ∂W/∂Δ once per template (the Jacobian of §9.1) and solves, per pass,

    (Σ w SDᵀ SD) Δ = Σ w SDᵀ e,         R ← R exp(−Δ)

    Why exp(−Δ): if I(R r) = T(exp(Δ) r) for every ray r, the true warp satisfies I(R_true r′) = T(r′) with r′ = exp(Δ) r, hence R_true exp(Δ) = R.

    • Gradient. ∇T is the central difference. It is not an approximation: the derivative of the Keys interpolant at a sample is (I(n+1) − I(n−1))/2, because the kernel has h′(±1) = ∓½ and h′(0) = h′(±2) = 0. The gradient is that of the very interpolant used by the warp.
    • Pyramid. REDUCE keeps sample 2i, so the pixel index of level l is the level-0 coordinate divided by 2ˡ and the intrinsics of level l are those of level 0 divided by 2ˡ. With 4 levels a 15 px shift is 2 px at the coarsest (the tests recover a 1.7° rotation, 15.6 px at f = 525, to 0.004 px).
    • Robustness. w = min(1, kσ/|e|), k = 1.345 (95 % efficiency at the Gaussian). The scale is the concomitant estimate of Huber's Proposal 2, σ² = Σ min(e², k²σ²) / (β (N − 3)), β = E[min(Z², k²)] = 0.710, started by a least-squares pass and floored at 1/√12 (the quantisation noise of an 8-bit value). A block that moves (a second motion) keeps a bounded pull: Huber's ψ is bounded, not redescending, and so the IRLS is convex and converges from any start.
    • Covariance. Σε = σ² (β/ψ′²) (Σ SDᵀSD)⁻¹, the asymptotic covariance of the M-estimate (ψ′ = 2Φ(k) − 1; ψ′²/β = 0.950 is its efficiency). It enters the estimator as R.
    • Goodness of fit. Σε depends on the template only: a flat new frame against a textured template gives a well-conditioned normal matrix. The pair is therefore also refused when the explained variance R² = ρ² of I∘W against T is below min_explained_variance, when the 1σ of the fit exceeds max_registration_std_px, or when fewer than min_inlier_fraction of the pixels follow the dominant motion.

    9.4 Estimator: where the shake goes¶

    Per axis, the intentional rate is constant between samples with white acceleration σa constant over a period (Δω = aT, Δθ = aT²/2), so Qd = σa² g gᵀ, g = [T²/2, T]ᵀ. The error state x = [δθ; δω] of the multiplicative EKF (Q_true = Q̂ exp([δθ]×)) propagates with F = [exp(−[ω̂T]×) T·I; 0 I]. The registration gives the camera orientation relative to the predicted intentional one,

    Q_{k−1} = R_c R_reg                            (O_{k−1} warped by R_reg matches I_k)
exp(ν)  = Q̂⁻ᵀ R_c = exp(−ω̂T) R_regᵀ           ν = δθ⁻ + ς + ε,   H = [I 0],   R = σς² I + Σε

    The shake ς is the measurement noise of the intentional path, and the Kalman gain follows from the two physical numbers σa (how fast the arm and airframe may change their rate) and σς (how much of the measured motion is shake). The state is observable ([H; HF] has rank 6). The steady state solves the DARE; the table gives it for T = 1/30 s and σς = 0.2°:

    σa [°/s²] Kθ Kω [1/s] f_c [Hz] |H| at 3 / 5 / 10 Hz phase at 0.5 Hz output lag at a = 5 °/s²
    2 0.138 0.309 1.00 0.23 / 0.14 / 0.08 −33.0° 0.465°
    5 (default) 0.210 0.741 1.56 0.37 / 0.22 / 0.13 −12.9° 0.178°
    10 0.283 1.411 2.17 0.51 / 0.31 / 0.18 −5.1° 0.085°
    20 0.375 2.635 2.99 0.71 / 0.43 / 0.24 −1.9° 0.040°

    |H| is the fraction of the shake that remains in the output; a larger σς lowers f_c (σa = 5: 2.17 Hz at σς = 0.1°, 1.12 Hz at 0.4°). The filter has a double zero at z = 1 (checked in the tests): zero error to a constant rate, and (1 − Kθ) a T/Kω to a constant acceleration a (checked against a simulation: 0.1778° = 0.1778°). This is a low-pass in the loop of every consumer that servoes on the image (arm gaze, loop 6a): budget its phase at the crossover from the table (−12.9° at 0.5 Hz by default; accel_std_deg_s2 trades smoothing for lag). σς is measured, not guessed: with the camera held still, stab_innovation_rms_deg of /diagnostics is σς, and stab_nis (mean 1 when σa, σς match the data) is the check.

    9.5 Controller and actuator¶

    The correction that makes the virtual camera R_c R_corr equal to the estimate Q̂⁺ is the exact inverse of the plant, and the unknown absolute orientations cancel:

    R_corr = R_cᵀ Q̂⁺ = R_reg exp(ω̂T) exp(δθ⁺)        (ω̂ before the update)
R_c R_corr = Q_{k−1} R_regᵀ R_reg exp(ω̂T) exp(δθ⁺) = Q_{k−1} exp(ω̂T) exp(δθ⁺) = Q̂⁺

    For a still intentional pose and shake ς, R_corr = exp(−(I − Kθ) ς) to first order: what remains is the fraction |H| of §9.4. The law uses increments only, so nothing integrates: the correction cannot drift, and the output follows the camera at low frequency (type-2 tracking) instead of an integral of measurements. Because the next registration is made against what the actuator really produced, a saturated or imperfect frame appears in the next innovation: that is the feedback.

    Crop box. |φx|, |φy| ≤ max_angle, |φz| ≤ max_roll for φ = log R_corr. The zoom z ≥ 1 that keeps every output pixel inside the input for every rotation of the box is derived: Kₛ = S K (zoom about the image centre), the four output corners must satisfy margin ≤ u′, v′ ≤ size − 1 − margin (margin 2 px for the bicubic taps) over a 5³ grid of the box, and z is found by bisection. The test checks it against an independent first-order derivation (c₀(1 − 1/z) ≥ f[ψ(1 + x²) + θxy] + margin, solved by fixed point: 1.0829 against 1.0814).

    Crop box (pitch, yaw, roll) 1920×720, f = 1050 1280×720, f = 700
    0.5° z = 1.067 (94 % of the field kept) 1.052 (95 %)
    1.0° (default) 1.133 (88 %) 1.100 (91 %)
    1.5° 1.202 (83 %) 1.149 (87 %)
    2.0° 1.275 (78 %) 1.201 (83 %)

    Saturation. When R_corr leaves the box it is clipped and the estimator is projected on the orientation that was reached, as a perfect measurement (Simon, IET Control Theory Appl. 4(8), 2010): x ← x − P Hᵀ (H P Hᵀ)⁻¹ (H x − b), P ← P − P Hᵀ (H P Hᵀ)⁻¹ H P. This is the anti-windup: the state never keeps an orientation the actuator could not reach. A 4° step (outside the 1° box) holds the correction at the box (saturated or rejected from frame 30 to 46) and the correction is back to 0.00° afterwards.

    Innovation the model does not explain NIS above χ²₃ 99.9 % (16.27) the update is skipped (the output holds the predicted pose); after 0.3 s of it the estimator is re-seeded from the measurement

    9.7 GPU path and what is verified of it¶

    The per-pixel maths is written once in stab_ops.hpp (__host__ __device__): bicubic sampling, the steepest-descent image, one registration pixel. The CPU back end and the kernels call the same functions.

    Stage Kernel Work
    upload, luma cudaMemcpyAsync, k_gray frame → level 0 of the image pyramid
    pyramids k_reduce_h/v image pyramid, then template pyramid
    registration k_register one thread per template pixel → 24 sums (normal matrix, gradient, scale, correlation) → block tree reduction in shared memory (24 KB) → one atomicAdd(double) per block and sum; the 3 × 3 solve is on the CPU
    template k_sd steepest-descent images of every level
    warp k_warp bicubic RGB through the homography → rgb8, and its luma (the next template)

    Verified here, without a GPU: the kernels compile for sm_87 with the CUDA 12.4 headers (clang, -Wall -Wextra clean; 6 kernels, 24 576 B of shared memory); and test_stab_cuda_emu runs the same source (stab_cuda.cu) as host C++ against test/stabilization/cuda_emu.hpp (one fiber per CUDA thread, __shared__, __syncthreads, atomicAdd), comparing it with the CPU back end operation by operation: the 24 sums at every pyramid level, plain and Huber, agree to the float summation order (≤ 2·10⁻⁴ relative), the counts exactly, and the warps byte for byte; the whole loop through the Stabilizer differs by ≤ 7.6·10⁻⁶ px of correction and ≤ 1 grey level. Deliberately breaking the block reduction, or the index of a steepest-descent plane, fails it. Not verified: device arithmetic (FMA contraction), concurrency between blocks, ptxas register use, timing — run compute: cuda on the Orin and read stab_ms.

    CPU reference (x86, 4 threads, 1920 × 720): 63 ms per frame (registration 28, warp + template 30), so the CPU path is the reference and the fallback for tests, not a 30 Hz path: the node warns when stitching + stabilising is slower than the frame rate.

    9.9 What this does not do¶

    • Translation shake. A rotation model cannot represent the parallax of a camera that moves (b/Z); near objects keep a residual. Out of scope without a depth.
    • Rolling shutter. The 2 × IMX477 expose by rows: fast shake skews the frame within a frame time, which a global rotation does not remove.
    • The world orientation of the output is unobservable from images alone. The output follows the camera at low frequency; fusing the airframe gyro would add an absolute reference (not done).
    • Latency. The estimator is causal; its lag is the phase of §9.4. A fixed-lag smoother would remove it at the price of whole frames of delay inside loop 6a.
    • Extrinsics. See Stabilised output under Interfaces.
    • Not yet run on a GPU, on the master Jetson, or on footage of a real shaking rig: σς and σa are design values until stab_innovation_rms_deg and stab_nis are read there.

    Limitations¶

    • The CUDA kernels compile for sm_87 but have not run on a GPU here: run test_stitch --gtest_filter=*Cuda* on the Orin first. The same goes for the stabiliser's kernels (§9.7): run it with stabilizer.compute: cuda and read stab_ms.
    • The stabiliser has only been run on a synthetic shaking camera, never on footage of a real rig (§9.9).
    • panorama_node itself — parameters, messages, threads — has not been built under colcon nor run on ROS 2: it was compiled and linked, and its error path run, against stub ROS headers (a minimal ament_cmake for the CMake side). Everything it delegates to is tested without ROS (Architecture). Running it as a component in a container has not been tried.
    • Not yet run on the master Jetson: Argus with two IMX477 in one container, the 1920 × 1080 mode, the stitching time on the Orin's cores, and the gain filter's r (check gain_nis).
    • Parallax: objects nearer than ~5 m in the overlap are ghosted where the seam has to cross them; the seam avoids them when it can.
    • The sensors are not hardware-synchronised: fast motion misregisters by u̇ · skew in the overlap.
    • The homography model (no intrinsics) puts the panorama in camera 0's plane: the right camera is stretched and camera_info carries K = 0. Calibrate the intrinsics.
    • isaac_ros_snapshot_downlink crops the 8:3 panorama to the radio's 4:3 (centre).
