    Isaac ROS Integration¶

    Source

    This page is rendered from Source/ROS2_Lidar_AI_Solution/docs/isaac_ros_integration.md, the authoritative description kept next to the code in Source/ROS2_Lidar_AI_Solution/docs/.

    How the lidar perception stack in this package joins the Isaac ROS detectors (NanoOWL, YOLOv5, SSD-MobileNet) in Source/Isaac_ROS-Object_Detection, and how the result closes a control loop on the Jetbot.

    Every block below is derived rather than tuned by feel; each section states the model, the equation that is implemented, and the reference it comes from. The unit tests in tests/isaac_ros/ check those properties numerically.

    1. Why the layer exists¶

    knows where knows what
    CenterPoint / PointPillars / BEVFusion metric 3D boxes, velocities a fixed 5-class nuScenes head
    NanoOWL (Isaac ROS) 2D pixels only any prompt you write

    Neither is sufficient on its own. The integration layer projects the lidar geometry into the camera, associates it with the open-vocabulary detections, and maintains a calibrated posterior over the prompt vocabulary for each track.

    2. Projection: lidar box into the camera¶

    File: src/isaac_ros/camera_projection.hpp

    Camera model: pinhole with Brown-Conrady distortion, exactly what sensor_msgs/CameraInfo describes and OpenCV implements.

    p_C   = R p_L + t                              rigid transform, SE(3)
x_n   = X_C / Z_C ,  y_n = Y_C / Z_C           normalized coordinates
r²    = x_n² + y_n²
f_r   = 1 + k₁r² + k₂r⁴ + k₃r⁶                 radial
x_d   = x_n f_r + 2p₁x_n y_n + p₂(r² + 2x_n²)
y_d   = y_n f_r + p₁(r² + 2y_n²) + 2p₂x_n y_n  tangential
u     = f_x x_d + c_x ,  v = f_y y_d + c_y

    Three things the implementation gets right that a naive projection does not:

    1. Depth test. The perspective division is singular at Z_C = 0 and mirrors points behind the camera. Points with Z_C < min_depth are rejected, not projected.
    2. Partial visibility. An oriented box is projected corner by corner; min_visible_corners (default 4 of 8) rejects boxes straddling the image plane, whose 2D hull would be numerically valid but geometrically meaningless.
    3. Frame convention. A REP-103 lidar frame is x-forward / y-left / z-up; a ROS optical frame is x-right / y-down / z-forward. The rotation between them
    R_opt←body = [ 0 −1  0 ]
             [ 0  0 −1 ]
             [ 1  0  0 ]

    is applied automatically when static_extrinsic_is_optical is false. Getting this wrong is the single most common cause of "the projection lands nowhere near the object".

    With use_tf: true the extrinsics come from tf2 at the detection timestamp, so a moving sensor head is handled correctly; the static parameters are only the fallback.

    CameraInfo handling: the projection matrix P describes the rectified image an Isaac ROS pipeline actually publishes, K describes the raw image. P is used when populated (and distortion is then correctly skipped, because rectification already removed it); otherwise K plus d is used.

    References: Hartley & Zisserman, Multiple View Geometry, 2nd ed., ch. 6; Brown, Close-Range Camera Calibration, Photogrammetric Engineering 37(8), 1971.

    3. Association¶

    The projected hull of a 3D box is systematically larger than a tight 2D detection: the hull is the bounding box of eight corners, several of which are on the far face. Plain IoU therefore under-reports good matches. The default metric is intersection-over-minimum,

    IoM(A,B) = |A ∩ B| / min(|A|, |B|)

    which is 1 when one box contains the other. association_metric: iou selects the Jaccard index instead, appropriate for a tightly calibrated setup.

    Matching is greedy over the gated score matrix: candidates are visited in decreasing score and accepted when neither element is taken. This is a ½-approximation of the optimal weighted matching (Preis, STACS'99) at O(nm log nm) rather than the O(n³) of the Hungarian algorithm — tight enough here because the score gate leaves few candidates per track.

    Temporal alignment. The 2D and 3D pipelines run at different rates with different latencies, so the newest 2D frame is rarely the right one. Detections are buffered and the frame closest in time within sync_tolerance_ms is used; sync_error_ms in the output message reports the residual.

    4. Recursive Bayesian label estimation¶

    File: src/isaac_ros/bayesian_label_estimator.hpp

    State: the posterior p_k(c) = p(c | z_1:k) over the vocabulary C, |C| = N, held in the log domain.

    Observation model. A detector reports label z_k with confidence s_k. Treating s_k as the probability the report is correct and spreading the rest uniformly gives the standard discrete sensor model

    p(z_k | c) = s_k                  if c = z_k
           = (1 − s_k) / (N − 1)  otherwise

    which is a proper conditional pmf: Σ_{z_k} p(z_k | c) = 1 for every c.

    Update. Detections are conditionally independent given the class, so

    log p_k(c) = log p_{k−1}(c) + log p(z_k | c) − log η_k

    The normalizer uses log-sum-exp, log Σ exp(a_c) = a* + log Σ exp(a_c − a*), which is exact and does not underflow.

    Fading memory. Objects are not stationary — a misclassified track must be able to recover, and the prompt may change. The prediction step contracts the belief towards the uniform prior u = 1/N:

    log p(c) ← λ log p_{k−1}(c) + (1 − λ) log u ,  λ ∈ (0,1]

    In log-odds coordinates ℓ(c) = log p(c) − log u this is just ℓ ← λℓ, so an observation's influence decays as λ^k and the effective memory is 1/(1 − λ) steps: λ = 0.95 at 20 Hz is about one second.

    Clamping. log p(c) is floored at −max_log_odds before renormalizing, the bound used for occupancy grids in Thrun/Burgard/Fox §9.2. Without it a long run of agreeing detections drives one label so close to 1 that no finite amount of contradicting evidence can move it. The test suite checks exactly this: after 50 confident observations of label 0, 20 of label 1 must flip the MAP.

    Reported confidence. Alongside the MAP label the node publishes the full posterior and its Shannon entropy H(p) = −Σ p ln p in nats: 0 for a certain posterior, ln N for the prior. Entropy, not the MAP probability, is the honest measure of how much the camera has actually resolved.

    References: Thrun, Burgard & Fox, Probabilistic Robotics, MIT Press 2005, ch. 4 and §9.2; Bar-Shalom, Li & Kirubarajan, Estimation with Applications to Tracking and Navigation, Wiley 2001, ch. 11.

    5.1 Plant and error kinematics¶

    The Jetbot is a differential drive, i.e. a unicycle

    ẋ = v cos θ ,  ẏ = v sin θ ,  θ̇ = ω

    Writing the target in the body frame in polar form (d, ψ) and denoting the target's own velocity along and across the line of sight by (v_r, v_t):

    ḋ = v_r − v cos ψ                       (1)
ψ̇ = (v_t + v sin ψ) / d − ω             (2)

    5.2 Filtering and estimation¶

    (d, ψ) are measured, their rates are not — and (1), (2) need both. A two-state Kalman filter per channel under the continuous white-noise acceleration model supplies them:

    F = [1 dt; 0 1]
Q = q · [dt³/3  dt²/2 ;
         dt²/2  dt   ]                   Bar-Shalom §6.2.2
H = [1 0] ,  R = σ²

    q is the PSD of the acceleration noise in (m/s²)²/Hz, so it is set from how hard the target can actually accelerate rather than tuned blindly.

    Outlier gate. When the model holds, the normalized innovation squared NIS = ν²/S is χ²-distributed with one degree of freedom, so nis_gate: 9.0 rejects at roughly the 0.3 % level (Bar-Shalom §5.4). A rejected measurement leaves the state on its prediction instead of yanking it — this is what keeps a single bad association from producing a lurch in cmd_vel.

    The bearing filter wraps its innovation modulo 2π, so it stays well behaved across the ±π discontinuity.

    5.3 Ego-motion removal — what odometry is actually for¶

    The estimator observes relative motion, which mixes the target's motion with the robot's own. Inverting (1) and (2) with the measured v, ω from /odom:

    v_r = ḋ + v cos ψ
v_t = d (ψ̇ + ω) − v sin ψ

    v_r is what the safety filter needs (a target walking towards the robot must tighten the bound). Without wheel odometry these two quantities are simply not observable, which is why /odom is a required input and not decoration.

    5.4 Angular channel: feedforward plus PD¶

    ω = (v_t + v sin ψ)/d + K_p ψ + K_d ψ̇          (3)

    The feedforward term cancels the target-motion term in (2), leaving ψ̇ = −(K_p ψ + K_d ψ̇). With V = ½ψ²,

    V̇ = ψψ̇ = −K_p ψ² / (1 + K_d) ≤ 0

    so the bearing error is asymptotically stable for any K_p > 0, K_d > −1 (Khalil, Nonlinear Systems, Thm. 4.1). Substituting v_t back in collapses the feedforward to ψ̇ + ω, the line-of-sight rate in the inertial frame, which is how the node computes it — avoiding a division by the range that is ill-conditioned close to the target.

    5.5 Linear channel: PI gated by heading¶

    v = (K_p e_d + K_i ∫e_d) · max(cos ψ, 0) ,   e_d = d − d_des      (4)

    The gate is what makes the proof work. Substituting the proportional part of (4) into (1) for a stationary target gives ḋ = −K_p e_d cos²ψ, so with W = ½e_d²

    Ẇ = −K_p e_d² cos²ψ ≤ 0

    Clipping the gate at zero also stops the robot driving forward while the target is behind it, where cos ψ < 0 would flip the sign of the feedback.

    Anti-windup. The PI integrator uses back-calculation (Åström & Hägglund, Advanced PID Control, §3.5):

    İ = K_i e + K_t (sat(u) − u)

    which bounds the wind-up at u_max + K_i e / K_t instead of letting it grow without limit. The node additionally calls ApplyOutputCorrection with what the downstream stages actually applied, so the integrator also unwinds when the heading gate or the safety filter overrides the controller — not only when the actuator saturates.

    The derivative acts on a low-pass filtered error. This is mandatory: the raw difference of a noisy error amplifies noise by K_d/dt, a factor of 20 at 20 Hz.

    5.6 Safety: control barrier function¶

    Safe set C = {x : h(x) ≥ 0} with h = d − d_safe. Along (1), ḣ = v_r − v cos ψ, so the exponential CBF condition ḣ ≥ −αh is affine in v:

    v cos ψ ≤ α(d − d_safe) + v_r
⟺  v ≤ v_max_safe = (αh + v_r) / cos ψ        for cos ψ > ε        (5)

    The minimum-intervention QP min (v − v_des)² subject to (5) has the closed-form solution v* = min(v_des, v_max_safe), so no solver is needed. By Ames et al. (ECC 2019, Thm. 2) any locally Lipschitz controller satisfying (5) renders C forward invariant: if h(x₀) ≥ 0 then h(x_t) ≥ 0 for all t ≥ 0.

    The test suite verifies this numerically by running 400 cycles of a controller that always demands full speed and asserting the clearance never goes negative.

    Two cases sit outside (5) and are handled explicitly:

    • cos ψ ≤ ε — the target is abeam or behind, forward motion does not close the range, and the constraint is vacuous.
    • h < 0 — already inside the clearance. The bound turns negative and commands a reverse that drives h back to 0 exponentially. This is the intended recovery and requires allow_reverse: true; otherwise the robot is held at 0.

    α has a direct physical reading: the range may decay no faster than exp(−αt) towards d_safe.

    5.7 Actuator limits and fail-safe¶

    Slew limiters enforce |v̇| ≤ a_max and |ω̇| ≤ α_max. Commanding a step the motors cannot follow makes the measured velocity lag the command, which the feedback then reads as a disturbance; limiting the command keeps the plant inside the region where the linear design holds.

    The one open-loop path. When no target has been seen for target_timeout_s there is no feedback signal, so the loop cannot be closed. The node ramps the command to zero through the slew limiters and resets the estimators and integrators. This is the only open-loop path in the node and exists solely to bring the robot to a controlled stop. /safety/emergency_stop from safety_zone_node short-circuits everything and commands zero directly.

    5.8 Tuning order¶

    1. safe_distance and max_linear_velocity from the physical envelope.
    2. range_measurement_variance ≈ the tracker's position noise, in m²; range_process_psd ≈ the target's peak acceleration squared.
    3. angular_kp, then angular_kd — the heading loop settles first.
    4. linear_kp, then linear_ki just large enough to remove the steady-state offset.
    5. cbf_alpha last: raise it for a more assertive approach, lower it to stop further out.

    safe_distance must stay below desired_distance; the node clamps it to 0.8 · desired_distance and warns otherwise, because a barrier that opposes the set point produces a permanent standoff.

    6. vision_msgs bridge¶

    File: src/isaac_ros/isaac_ros_detection_bridge_node.cpp

    TrackedObjectArray  ─┐
SemanticObjectArray ─┼─▶ vision_msgs/Detection3DArray  (+ VisionInfo, latched)
DetectionResult     ─┘
vision_msgs/Detection3DArray ─▶ DetectionResult   (feeds detection_fusion_node)

    A SemanticObject carries a full posterior, which maps exactly onto the ObjectHypothesisWithPose[] array of vision_msgs: the top-k labels are published in decreasing probability, so a consumer can reason about the runner-up instead of only the MAP label.

    VisionInfo is published on a transient-local (latched) topic, so a consumer that starts later still receives the label database.

    Known limitation: vision_msgs/Detection3D has no velocity field. Consumers that need the tracked kinematics must subscribe to TrackedObjectArray or SemanticObjectArray directly.

    6b. GPU overlay¶

    File: src/isaac_ros/isaac_ros_semantic_overlay_node.cpp

    The fusion node already publishes each track's pixel box in SemanticObject.projected_bbox, so the overlay is a pure rendering stage: box plus label, drawn with cuOSD, NVIDIA's GPU on-screen display library.

    Rasterising text is the expensive half of an overlay — a glyph atlas blended per pixel — and that is what moves to the GPU. Box outlines are nearly free either way.

    What this does not buy you. sensor_msgs/Image lives in host memory, so each frame still pays one host-to-device and one device-to-host copy. The drawing is on the GPU; the transport is not. Those copies disappear only when the whole image pipeline is negotiated through NITROS. On a Jetson's unified memory the copies are cheap enough that text rasterisation still dominates, but the honest summary is: this replaces CPU glyph rendering, not the round-trip.

    Implementation notes worth knowing:

    • Labels are coloured by an FNV-1a hash of the label string, so a prompt keeps the same colour across frames and across runs — which matters when reviewing a recording. std::hash is not used because it may differ between standard library versions.
    • bgr8/bgra8 are supported by swapping the red and blue components of the drawing colours, which is exact and free. Unsupported encodings are republished unchanged rather than mangled.
    • Stride comes from Image::step, not width * channels, because ROS images may pad rows.
    • A font is accepted only if it exists and is non-empty: the .ttf files in the vendored sample trees are zero-byte placeholders, and stb_truetype on an empty buffer yields garbage metrics instead of failing cleanly.

    6c. GPU point extraction¶

    cuda_utils::ExtractXYZFromPointCloud2 de-interleaves a PointCloud2 on the device, replacing the per-point PointCloud2ConstIterator loop in centerpoint_node and pointcloud_preprocessor_node.

    Why the transfer does not get bigger. The staged copy is the raw message buffer — point_step bytes per point — instead of the packed feature array, feature_num floats per point. For a 16-byte point_step that is 16N bytes against 20N: strictly less. A wider point_step trades a larger copy for dropping the scalar CPU loop entirely, which on unified memory is the cheaper side of the trade.

    The guard. The kernel reinterprets raw bytes as floats, which PointCloud2 does not guarantee. src/common/pointcloud_layout.hpp checks, before every frame:

    1. x, y, z are FLOAT32 with count == 1;
    2. the cloud is little-endian;
    3. every field read lies fully inside point_step, and the points read are fully backed by data;
    4. intensity is FLOAT32 — otherwise it is dropped, not reinterpreted.

    Violating any of these is silent corruption, not a crash, because every byte pattern is a legal float. A cloud that fails is routed to the CPU loop and the reason is logged once. The header carries no ROS, CUDA or Eigen dependency precisely so this reasoning is unit tested on machines that cannot compile the kernel it guards (tests/pointcloud/).

    centerpoint_node reports which path each frame took as point_extraction: gpu|cpu in /diagnostics, so a silent fallback shows up as more than a lower frame rate.

    Not done: PointPillars. PointPillar::forward() takes a host pointer and copies internally, and its header lives in the CUDA-PointPillars submodule. Feeding it a device buffer would mean patching upstream vendored code, which breaks the ability to track upstream. It keeps the CPU loop.

    7. Bring-up¶

    # 1. Messages first (two-stage build)
colcon build --packages-select ros2_lidar_ai_msgs

# 2. The package
colcon build --packages-select ros2_lidar_ai_solution --symlink-install \
  --cmake-args -DBUILD_ISAAC_ROS=ON

source install/setup.bash

# 3. Lidar perception
ros2 launch ros2_lidar_ai_solution full_pipeline.launch.py

# 4. Isaac ROS NanoOWL (separate package)
ros2 launch isaac_ros_objectdetection nano_owl_tensor_rt.launch.py

# 5. Integration layer
ros2 launch ros2_lidar_ai_solution isaac_ros_perception.launch.py

# 6. Closed-loop following (commands the drive base)
ros2 launch ros2_lidar_ai_solution isaac_ros_perception.launch.py \
    enable_follower:=true target_label:="a person"

# 7. GPU overlay on the camera stream
ros2 launch ros2_lidar_ai_solution isaac_ros_perception.launch.py \
    enable_overlay:=true image_topic:=/image_raw

    The vocabulary parameter must list the NanoOWL prompts in the same order they were given to the encoder: the decoder publishes the prompt index as Detection2D.class_id. A mismatch shows up as a throttled warning naming the unrecognized class_id.

    Inspecting the loop¶

    ros2 topic echo /isaac_ros/semantic_objects --field objects[0].label
ros2 topic echo /isaac_ros/semantic_objects --field sync_error_ms
ros2 topic echo /diagnostics                       # follower internals, 20 Hz
ros2 run rqt_plot rqt_plot                         # plot /cmd_vel against /odom

    The follower's diagnostics expose range_m, bearing_rad, range_rate_mps, target_range_rate_mps, clearance_m, barrier_bound_mps, linear_integral and gate_rejections — enough to tell a tuning problem from a perception one without a debugger.

    8. Failure modes¶

    Symptom Cause Fix
    matched_count always 0 wrong extrinsics or frame convention check static_extrinsic_is_optical, verify ros2 run tf2_tools view_frames
    sync_error_ms near the tolerance camera and lidar pipelines far apart in latency raise sync_tolerance_ms, or detection_buffer_size
    labels flicker forgetting_factor too low raise towards 0.98
    labels stick after the object changes max_log_odds too high lower towards 4.0
    warning about an unrecognized class_id vocabulary does not match the NanoOWL prompt align order and spelling
    follower oscillates around the set point linear_ki too high, or derivative_tau too small halve linear_ki, raise derivative_tau
    follower stops short and never closes safe_distance too close to desired_distance, or cbf_alpha too low widen the gap, raise cbf_alpha
    cmd_vel stutters tracker dropouts; check gate_rejections in /diagnostics raise nis_gate, or measurement_tau above 0
    nodes missing after a build vision_msgs not installed sudo apt install ros-$ROS_DISTRO-vision-msgs
    overlay draws boxes but no text no usable TrueType font apt install fonts-dejavu-core, or set font_path
    overlay republishes the image unchanged encoding unsupported, or no semantic array within sync_tolerance_ms convert to rgb8, or raise the tolerance
    point_extraction: cpu in /diagnostics the cloud failed the GPU layout guard read the one-off warning; usually a non-FLOAT32 or big-endian publisher
