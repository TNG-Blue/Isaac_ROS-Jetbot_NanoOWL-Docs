    ROS2_JetOwl_Bridge — the one node for the vehicle's microcontrollers¶

    Source

    This page is rendered from Source/ROS2_JetOwl_Bridge/README.md, the authoritative description kept next to the code in Source/ROS2_JetOwl_Bridge/.

    ros2_jetowl_bridge 0.4.0 is the single ROS 2 node between the Jetson and every microcontroller on the vehicle. One C++ process (jetowl_bridge, also the rclcpp component ros2_jetowl_bridge::JetOwlBridgeNode) with one link per MCU, each switched by a parameter:

    Link MCU Transport Replaces Default
    fc JetOwl flight controller, STM32N657 (Microcontroller/JetOwl_FlightControl) micro-ROS over UDP/Ethernet (agent) Python jetowl_bridge 0.1.0 on
    vision_mcu JetOwl_Vision camera, STM32N655 + IMX335 (TNG-Blue/JetOwl_Vision) micro-ROS over UDP/Ethernet (same agent) — (new in 0.3.0) off
    vision OpenMV RT1062 camera (Microcontroller/OpenMV/OpenMV_RT1062.py) JSON lines over TCP or USB CDC ros2_microcontroller (Python openmv_communication) off
    sensor_link hexacopter flight MCU (Portenta H7) / Gazebo virtual MCU CRC-32 framed UDP (protocol.c) ros2_mcu_link (mcu_link_node) off

    All links report in one DiagnosticArray on /diagnostics (diagnostics_rate_hz, 1 Hz): jetowl_bridge/fc: link (+ the firmware's own status), jetowl_bridge/vision_mcu: link | image (+ the camera firmware's status), jetowl_bridge/vision: OpenMV RT1062 link, jetowl_bridge/sensor_link: link | clock | imu | gnss | encoders.

    Why one node: the three were separate packages (two Python, one C++) doing the same job — transport, framing, reconnect/watchdog, diagnostics — for different MCUs, each started by its own container. One process saves two Python interpreters and two executors, and gives one launch file, one parameter file and one diagnostics entry point. The 1 kHz sensor stream keeps its dedicated receive thread; the FC and vision links run on the executor.

    Usage¶

    colcon build --packages-select ros2_jetowl_bridge
ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py                  # JetOwl FC (+ micro-ROS agent)
ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py vision_mcu:=true # + JetOwl_Vision camera
ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py fc:=false vision_mcu:=true   # camera only
ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py vision:=true     # + OpenMV camera
ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py vision:=true connection_type:=usb
ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py fc:=false sensor_link:=true            # hexacopter MCU
ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py fc:=false sensor_link:=true sim:=true  # Gazebo
ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py agent:=docker    # agent in microros/micro-ros-agent:humble

# Bench, without ROS: listen 5 s, sync the clock with the MCU, print a summary
ros2 run ros2_jetowl_bridge mcu_link_dump --port 9870 --mcu 192.168.1.103:9871 --duration 5

    The micro-ROS agent (started when fc or vision_mcu is on; one agent serves both MCUs, each firmware being its own XRCE client session) is either built once from source — micro_ros_setup → create_agent_ws.sh → build_agent.sh (agent:=ros, default) — or run from the container (agent:=docker); with agent:=none it is started elsewhere (Docker compose service micro_ros_agent, Kubernetes sidecar).

    Parameters — config/jetowl_bridge.yaml (base), overlays config/sensor_link.yaml (vehicle with the hexacopter MCU) and config/sensor_link_sim.yaml (Gazebo):

    Group Parameters
    — diagnostics_rate_hz
    fc. enabled, link_timeout_s (1.5 s = 3 status periods), arm_relay_enabled, arm_retry_period_s, supervision_rate_hz, rpm_expected_rate_hz (50 = firmware 5 ms × 4)
    vision_mcu. enabled, link_timeout_s (3 s = 3 status periods), expected_rate_hz (5), image_timeout_s, max_latency_s, max_width, max_height, republish, output_topic, frame_id
    vision. enabled, transport (eth/usb), openmv_ip, openmv_port, usb_port, usb_baudrate, connect_timeout_s, reconnect_min_s, reconnect_max_s, poll_rate_hz, rx_timeout_s, image_width, image_height, frame_id, log_file, analyze_numeric_lines
    sensor_link. enabled, network.*, clock.*, imu.*, gnss.*, encoder.* (see sensor_link.yaml)

    Invalid values are rejected at start-up (the node exits with the reason). At run time vision.* can be changed (validated as a whole; an endpoint change reopens the link); every other parameter is read at start-up and a change is refused, not silently ignored.

    Link fc — JetOwl flight controller (micro-ROS)¶

    The firmware is a native ROS 2 node (jetowl_fc) behind the micro-ROS agent, so data topics need no relay; the link supervises it and relays arming.

     Jetson (ROS 2 Humble)                                             STM32N657 (FreeRTOS + lwIP)
 ┌─────────────────────────────┐                                    ┌──────────────────────────────┐

 │ (ros2_control_system, MPC)  │ /control/thrust            ───────▶│  ENU/FLU → NED/FRD           │
 │                             │                                    │  cmd_guard (timeout, failsafe)│
 │ uav_state_estimator (ESKF)  │◀─────── /imu/data (200 Hz) ────────│  attitude P law   250 Hz     │
 │ flight_controller (modes)   │                                    │  rate PID + ESO   1 kHz      │

 └──────────┬──────────────────┘                                    └──────────────┬───────────────┘

    Topic contract¶

    Must match Application/Interface/Inc/uros_app.h in the firmware.

    Dir Name Type QoS Rate
    FC → J /imu/data sensor_msgs/Imu (orientation ENU/FLU, frame imu_link) best effort 200 Hz
    FC → J /jetowl/status diagnostic_msgs/DiagnosticStatus; keys rc_authority (0 none, 1 pilot, 2 Jetson), rc_fresh, rc_link_lq_pct, rc_rssi_dbm, rc_snr_db, rc_rth_request report the LoRa RC link to Microcontroller/Remote_UAV (JetOwl_FlightControl docs/RFLINK.md).     FC → J /jetowl/motor_rpm std_msgs/Float32MultiArray (NaN = unknown, ≠ 0); supervised by the bridge (jetowl_bridge/fc: rotors: rate, per-rotor rpm and valid fraction, malformed count) best effort 50 Hz
    FC → J /baro/pressure sensor_msgs/FluidPressure [Pa], BMP280, variance 1.44 Pa² (Bosch BST-BMP280-DS001 table 8); read by the ESKF of ros2_control_system best effort 25 Hz
    J → FC /control/attitude_setpoint geometry_msgs/QuaternionStamped any MPC, 50 Hz
    J → FC /control/thrust std_msgs/Float64 [N] any MPC, 50 Hz
    J → FC /jetowl/arm std_srvs/SetBool (service) — on demand
    J → FC /jetowl/ota/start, /jetowl/ota/apply std_srvs/Trigger (service) — on demand — OTA from Server_OTA (192.168.1.101:8080), state in the fw_version/ota_* keys of /jetowl/status (JetOwl_FlightControl docs/OTA.md)
    bridge /jetowl/link_ok std_msgs/Bool default 5 Hz (fc.supervision_rate_hz)
    bridge /diagnostics diagnostic_msgs/DiagnosticArray default 1 Hz (diagnostics_rate_hz)

    /control/* are the exact topics uav_trajectory_controller publishes and /imu/data is the topic control_system.launch.py remaps the ESKF input to, so the stack runs unchanged on the vehicle. With the FC link on, keep sensor_link off: the firmware already publishes /imu/data (the node warns when both are enabled).

    Where the loops close (control-systems.md §1)¶

    This package contains no control law. The chain is:

    Stage Where Notes
    Sensor, filter, attitude estimate firmware (imu_acq task → imu_frontend → imu_fusion, BNO08x 200 Hz + BNO055 100 Hz) runs once I2C1/EXTI are enabled in CubeMX; before that the FC refuses to arm and does not publish /imu/data. Stamps = sensor sample time (SH-2 timing fields)
    Translational estimator + MPC Jetson, ros2_control_system ESKF on /imu/data + GNSS + baro
    Attitude controller firmware, 250 Hz Ω = K ⊙ 2 sgn(q̃_w) q̃_v, q̃ = q̂⁻¹ ⊗ q_sp (Wie, Weiss & Arapostathis 1989), V = 1 − |q̃_w|, K = ω_c,rate / 5
    Rate controller firmware, 1 kHz PID + ESO, crossover 15.8 rad/s (roll/pitch, sample gains)
    Allocation / actuator firmware mixer with saturation priority, DShot300, bidirectional RPM feedback
    Rotor speed loop firmware, 1 kHz per rotor 2-DOF: reference model + model-inverse feed-forward + PI (SIMC, Skogestad 2003) on 150 Hz-filtered RPM telemetry; PM ≥ 58°, GM ≥ 10 dB over ±20 % K/τ. /jetowl/status keys rotor_closed_mask (loop closed on RPM) and rotor_stall_mask (ESC stopped > stall time, level ERROR rotor stalled) — bit i = rotor i

    Frames: ROS uses ENU/FLU (REP-103), the firmware NED/FRD; the conversion q_ned_frd = q_NE ⊗ q_enu_flu ⊗ q_LB (both π-rotations) lives in the firmware (frame_conv.h, tested against the vector-image definition).

    Delay budget of the setpoint path: MPC period 20 ms + UDP/agent hop (< 1 ms on a direct 100 Mbit/s link) + firmware sampling at 250 Hz (≤ 4 ms). The MPC already books 40 ms for the attitude loop (ros2_control_system README), which covers this path.

    Link loss (firmware cmd_guard, open-loop only in the vertical axis, which has no sensor in the FC loop): setpoint older than 0.1 s → level attitude, heading held, descent profile a = −0.5 m/s² to v = −1 m/s using the weight estimate W = T_last cos θ_last (same profile as the ESKF-stale failsafe of ros2_control_system); disarm after 1.2 · t_fs with t_fs = v/a + (h_max − v²/2a)/v = 31 s for h_max = 30 m. A 5 % weight error gives a 0.49 m/s² vertical acceleration error — this bound is the reason the disarm timeout exists.

    Arming¶

    jetowl_bridge mirrors the armed: flag of flight/status (ros2_flight_controller) onto /jetowl/arm, forcing disarm in DISARMED, LANDED and EMERGENCY_STOP. An arm request is sent only while the link is up; at most one call per arm_retry_period_s. The firmware accepts arming only with a setpoint younger than 0.1 s, a valid attitude estimate, tilt < 20° and a thrust command below 20 % of its maximum thrust. The MPC idle thrust (thrust_min_n in uav_control.yaml) must be below that 20 % for the airframe in use, otherwise arming is refused with thrust command too high.

    Link vision_mcu — JetOwl_Vision camera (micro-ROS)¶

    The camera board (STM32N655, IMX335 over MIPI CSI-2, FreeRTOS) is a native ROS 2 node (jetowl_vision) behind the same micro-ROS agent as the FC. Its only control loop — auto-exposure / white balance — closes on the MCU (Kalman estimator on the ISP statistics, see JetOwl_Vision docs/camera/CAMERA_CSI_RTOS.md); this link reads the camera data, checks it and supervises the stream.

     STM32N655 (JetOwl_Vision)                                        Jetson
 IMX335 ─CSI-2─▶ DCMIPP/ISP ─▶ RGB565 640×480 (30 fps)            micro_ros_agent udp4 :8888
   │  AE/AWB closed loop on the MCU                                     │ DDS
   └▶ box filter D×D ─▶ decimate D=4 ─▶ rgb8 160×120 (5 Hz) ──UDP──▶ jetowl_bridge (vision_mcu)
                                                                     ├─ validate → jetowl_vision/image
                                                                     └─ rate/gaps/latency/loss → /diagnostics

    Topic contract¶

    Must match Appli/Uros/Inc/uros_app.h in JetOwl_Vision.

    Dir Name Type QoS Rate
    V → J /jetowl_vision/image_preview sensor_msgs/Image, rgb8 160×120 (or mono8), frame jetowl_vision_optical_frame reliable (required for XRCE fragmentation) 5 Hz
    V → J /jetowl_vision/status diagnostic_msgs/DiagnosticStatus (streaming, fps, exposure_us, gain_db, mean_r/g/b, preview_sent, pub_time_ms_max, …) reliable 1 Hz
    J → V /jetowl_vision/ota/start, /jetowl_vision/ota/apply std_srvs/Trigger (service) — on demand — OTA, state in the ota_* keys of the status (JetOwl_Vision docs/network/OTA.md)
    bridge vision_mcu.output_topic (jetowl_vision/image) sensor_msgs/Image, validated, frame_id optionally replaced sensor data as received
    bridge /diagnostics jetowl_bridge/vision_mcu: link, …: image, + the firmware status default diagnostics_rate_hz

    The bridge subscribes to the image with SensorDataQoS (best effort is compatible with the reliable writer of the agent and never stalls it on a slow reader).

    What the link checks (vision_mcu.hpp, test_vision_mcu)¶

    Check Rule
    Geometry encoding rgb8/mono8; 0 < w ≤ max_width, 0 < h ≤ max_height; step ≥ w·bpp; data.size() = step·h (64-bit, no wrap). Failing images are counted, never republished
    Gaps preview k is taken at the first camera frame at or after the grid point kT (firmware, phase-locked), so stamp = kT + j, 0 ≤ j < one frame (33 ms). With \|j₂ − j₁\| < T/2: missing previews m = round(Δt/T) − 1 exactly, gap iff Δt > 1.5 T (test: 200 random runs with the full admissible jitter)
    Latency t_receive − stamp per window (mean, max); stamps are end-of-frame on the MCU mapped to agent time by rmw_uros_sync_session (≤ 1 ms). WARN above max_latency_s
    End-to-end loss 1 − received/sent, sent = firmware preview_sent differenced between statuses; reboot (counter decreasing) restarts the reference; clamped to [0, 1] (boundary error ≤ 1 image per status)
    Liveness ERROR when no status for link_timeout_s or no image for image_timeout_s; WARN when the window rate is below 80 % of expected_rate_hz

    Preview filter (firmware, cam_preview.c): decimation by D needs a low-pass first (Oppenheim & Schafer, Discrete-Time Signal Processing, §4.6); the D×D mean has zeros at ω = 2πk/D — exactly the components that fold onto DC — and a residual side lobe of −11.3 dB (D = 4). Each 8-bit value is computed from exact integer sums with one rounding (≤ 0.5 LSB), checked on the host for all 65 536 RGB565 codes. The preview is a monitoring image, not a photometric measurement.

    Bandwidth: 57.6 kB per image → 40 XRCE fragments of 1472 B, 2.46 Mbit/s at 5 Hz (2.5 % of the 100 Mbit/s link); the firmware reports the blocking time of each publish (pub_time_ms, pub_time_ms_max) to verify the 5–10 ms estimate on the bench.

    Link vision — OpenMV RT1062 camera¶

    Newline-delimited JSON, both directions, identical over Ethernet and USB. The camera listens on openmv_port; the bridge is the TCP client (USB: /dev/ttyACM*, raw 8N1).

    {"type": "detection", "timestamp": <ms>, "objects": [
   {"id": 0, "label": "person", "confidence": 0.91,
    "rect": [x, y, w, h], "center": [cx, cy], "velocity": [vx, vy], "hits": 3}], "stats": {...}}
    Topic Type Content
    openmv_out_topic std_msgs/String every received line, unmodified
    target geometry_msgs/PointStamped primary target measurement (below), frame vision.frame_id
    target_velocity geometry_msgs/Vector3Stamped its image-plane velocity
    openmv_in_topic (in) std_msgs/String command lines forwarded to the camera

    Measurement model (highest-confidence object, W × H the camera frame): x = 2cx/W − 1, y = 2cy/H − 1 (both in [−1, 1], y down), z = √(wh/(WH)), vx = 2vcx/W, vy = 2vcy/H. z is a range proxy: a pinhole camera images an object of size S at range Z with size s = fS/Z, so Z ∝ 1/z. The camera already filters position and velocity (α-β, constant-velocity model) — consumers must not differentiate target again; use target_velocity as the feed-forward term. No control action here.

    Fault modes: link loss → reconnect with exponential back-off t ← min(2t, t_max), logged once per failure streak; silence > rx_timeout_s while connected → WARN; unframed run > 64 KiB or invalid UTF-8 → dropped and counted; malformed object → no measurement (never a wrong one); non-JSON lines → counted (statistics with analyze_numeric_lines).

    Link sensor_link — MCU sensor stream over Ethernet/UDP¶

    The IMU, GNSS receiver and motor encoders of the hexacopter are wired to its flight MCU (Portenta H7), which stamps every sample on its own clock and sends it to the Jetson. In simulation the same frames come from the Gazebo plugin (ros2_mcu_emulator, HexacopterSystem), so this link and every node downstream run identical code in SIL and on the vehicle.

    Part Language Runs on
    mcu_link/protocol.h, protocol.c — wire format v1, CRC-32 framing C99, no heap/OS MCU firmware, Jetson, Gazebo virtual MCU
    mcu_link::LinkDecoder — validation, sequence, clock sync, conversion, encoder estimator C++17, no ROS Jetson (and tests)
    jetowl_bridge (sensor_link) — ROS 2 side, dedicated receive thread C++17, rclcpp Jetson
    mcu_link_dump — bench tool, JSON summary C++17, no ROS Jetson / laptop on the bench

    Wire format (v1)¶

    All fields little-endian, written byte by byte (independent of compiler packing and host endianness). One datagram = one frame.

    Offset Size Field
    0 2 magic 0x4254 ("TB")
    2 1 version = 1
    3 1 type
    4 2 payload length (fixed per type, checked)
    6 1 device id
    7 1 flags (0)
    8 4 sequence number (per sender, all types)
    12 8 MCU time of the measurement [µs]
    20 n payload
    20+n 4 CRC-32/ISO-HDLC over bytes 0 … 19+n
    Type Dir Payload Content
    0x01 IMU MCU→J 32 gyro [rad/s], specific force [m/s²] in IMU axes (float32), temperature, status (saturation, overrun)
    0x02 GNSS MCU→J 52 UBX-NAV-PVT subset: lat/lon 1e-7 deg, ellipsoid/MSL height mm, NED velocity mm/s, h/v/s accuracy, pDOP, fix type, satellites, flags
    0x03 ENCODER MCU→J 8+4N+⌈N⌉₄ N ≤ 16 int32 multi-turn counters, counts/rev, per-channel AS5047P error flags
    0x04 ATTITUDE MCU→J 32 on-board estimate q (base_link→ENU), variance of roll/pitch/yaw
    0x05 HEARTBEAT MCU→J 16 uptime, firmware version, state, TX overruns, RX errors
    0x06 IMU_INFO MCU→J 44 f_s, N_g, N_a, B_g, B_a, full scales, mounting quaternion
    0x10 TIME_SYNC_REQUEST J→MCU 16 t1 [ns host], id
    0x11 TIME_SYNC_RESPONSE MCU→J 32 t1 echo, t2/t3 [µs MCU], id

    Integrity. CRC-32 (IEEE 802.3 polynomial) has Hamming distance 5 up to 2974 bits (Koopman, DSN 2002); every frame here is ≤ 1 kbit, so every error of ≤ 4 bits is detected. test_protocol flips every single and every pair of bits of a frame (100 576 cases) and checks all are rejected. The STM32H7 CRC peripheral computes the same polynomial.

    Why UDP. A late sensor sample is worthless; TCP retransmission would delay every later sample (head-of-line blocking). Loss is instead detected by the sequence number and shown in /diagnostics.

    Link budget (100 Mbit/s): IMU 1 kHz 98 kB/s + 12 encoders 1 kHz 134 kB/s + attitude 100 Hz 10 kB/s + GNSS 10 Hz 1 kB/s ≈ 1.95 Mbit/s = 2 % of the link.

    Signal chain and estimation design¶

    Scope of the rule control-systems.md: this link is the sensor interface and first estimation stage; low-pass filtering and state fusion happen in the consumers (ros2_control_system/uav_state_estimator: IMU guard + LPF + ESKF).

    Clock synchronisation (mcu_link/clock_sync.hpp)¶

    • State x = [θ, γ]: offset host−MCU and relative frequency, indexed by MCU time.
    • Model (Zucca & Tavella 2005): F = [1 Δ; 0 1], Q = [q₁Δ + q₂Δ³/3, q₂Δ²/2; q₂Δ²/2, q₂Δ], σ_y²(τ) = q₁/τ + q₂τ/3, so q₁, q₂ come from the crystal's Allan deviation (allan_dev_1s = 1e-8, random_walk_fm = 1e-14 s⁻¹ ≈ 1 ppm thermal wander over 10 min — [A], to be measured on the Portenta).
    • Measurement (RFC 5905 §8): z = ((t1 − t2) + (t4 − t3))/2, round trip δ = (t4 − t1) − (t3 − t2). The error (d↓ − d↑)/2 lies in [−δ/2, δ/2] ⇒ R = δ²/12: slow exchanges weigh less automatically; δ > 20 ms is discarded.
    • Gate NIS > χ²₁(0.999) = 10.83 rejected; 5 consecutive rejections ⇒ re-initialise (MCU reboot, host clock step). Observability rank [1 0; 1 Δ] = 2.
    • Evidence (test_clock_sync, test_virtual_mcu): 40 ppm skew, 1234 s offset, asymmetric exponential delays → stamp error < 60 µs (bound: half the 60 µs asymmetry + queueing); 30 ppm / 7.25 s through the virtual MCU's UDP service → < 20 µs.

    Encoder speed estimator (mcu_link/encoder_estimator.hpp)¶

    • Model discrete white-noise acceleration (Bar-Shalom, Li, Kirubarajan §6.3.3), x = [θ, ω], Q = σ_a²[T⁴/4 T³/2; T³/2 T²], T from the MCU stamps (drops and jitter are exact). Counters are unwrapped modulo 2³².
    • σ_a = 0.5·a_max (Bar-Shalom's rule), a_max = K_t I_max / J_rotor = 0.0105·25 / 8.6e-5 = 3050 rad/s² ⇒ σ_a = 1500 rad/s² (X12 rotor; set per vehicle).
    • Steady state at T = 1 ms: tracking index λ = σ_a T²/σ_v = 13.55 ⇒ Kalata's α-β gains α = 0.9867, β = 1.5647 (test: Riccati limit = closed form to 1e-6); closed-loop poles of (I − KH)F: z = −0.025, −0.526 (|z| < 1, Jury: 2α + β = 3.54 < 4); speed σ = 0.542 rad/s (0.12 % of the 449 rad/s hover speed) — the Gazebo run reports exactly this value.
    • Consistency on a model-matched trajectory: NEES and NIS mean = 1 ± 0.15 (χ²₁). In hover the mean NIS is ≈ 0.2: real rotor accelerations are below σ_a, i.e. the filter is conservative (speed noise larger than necessary, never over-confident).
    • Gate NIS > 15.14 (χ²₁ 99.99 %) → sample not used; 10 in a row → re-initialise.

    Attitude (imu/data orientation)¶

    Not estimated here. The flight MCU already runs the attitude filter at 1 kHz next to the IMU; its estimate and the variance it derives are forwarded. For the X12 flight controller (Mahony, ω_c = 0.05 rad/s, ζ = 1) the tilt σ is 0.020 rad, dominated by the 20 mg accelerometer bias (b/g); yaw is unobservable without a magnetometer and is flagged with a variance of π². Derivation: mcu_attitude_variance() in hexacopter_system.cpp.

    MCU firmware integration¶

    protocol.c is the only file the firmware needs. With lwIP's raw API the sender is (illustrative, not compiled in this repository):

    #include "ros2_jetowl_bridge/mcu_link/protocol.h"   /* protocol.c is the only source needed */

static uint32_t seq, tx_overruns;
void send_imu(struct udp_pcb *pcb, const ip_addr_t *jetson, uint64_t t_us,
              const float g[3], const float a[3]) {
  uint8_t buf[MCU_LINK_MAX_FRAME];
  mcu_link_header_t h = {.device_id = 0, .seq = seq++, .stamp_us = t_us};
  mcu_link_imu_t s = {{g[0], g[1], g[2]}, {a[0], a[1], a[2]}, 35.0f, 0};
  int n = mcu_link_encode_imu(buf, sizeof buf, &h, &s);
  struct pbuf *p = pbuf_alloc(PBUF_TRANSPORT, (u16_t)n, PBUF_RAM);
  memcpy(p->payload, buf, (size_t)n);
  if (udp_sendto(pcb, p, jetson, MCU_LINK_DEFAULT_DATA_PORT) != ERR_OK) tx_overruns++;
  pbuf_free(p);
}

    Stamp with a 1 MHz timer extended to 64 bit, at the IMU data-ready interrupt (not at transmission); stamp GNSS with the time-pulse input capture of the epoch. Answer TIME_SYNC_REQUEST on port 9871 with t2 = receive-interrupt time, t3 = time just before udp_sendto.

    Known limitations¶

    • Not yet run against hardware: bench / HIL evidence (control-systems.md §4) is still to be produced for all links. 0.4.0 built and tested (62 gtests in 9 suites) on ROS 2 Humble (ros:humble-ros-base).
    • FC: the firmware IMU path needs I2C1 + EXTI in CubeMX (BOARD_CUBEMX_PERIPHERALS_READY = 1); Imu covariances from the FC are zero ("unknown") until its Allan-variance log is recorded; header stamps are in agent time (rmw_uros_sync_session every 10 s).
    • vision_mcu: the JetOwl_Vision firmware has not run on hardware; its RMII pins/PHY are board items to check against the schematic. No CameraInfo is published: the IMX335 module has not been calibrated (intrinsics unknown), so none is invented.
    • Sensor link: clock-sync noise parameters of the Portenta crystal (allan_dev_1s, random_walk_fm) are assumptions; measure the Allan deviation of the offset and update config/sensor_link.yaml.
    • Sensor link: quantisation noise of a slow or stopped encoder is not white; the reported speed σ is then optimistic.
    • Sensor link: imu/data orientation covariance uses roll/pitch/yaw variances on the diagonal (small-angle approximation of the rotation-vector covariance).
    • Sensor link: no authentication/encryption on the link: it is meant for a dedicated vehicle Ethernet segment.
