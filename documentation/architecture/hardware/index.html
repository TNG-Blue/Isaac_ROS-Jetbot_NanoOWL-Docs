    Architecture

    Hardware Design Philosophy¶

    Hardware architecture and design decisions for Isaac ROS Jetbot NanoOWL.

    🎯 Design Goals¶

    Primary Objectives¶

    1. Performance: 35+ FPS real-time AI perception
    2. Efficiency: 10-15W power consumption
    3. Modularity: Easy sensor integration
    4. Scalability: Multi-robot capable
    5. Production Ready: Robust and reliable

    Trade-offs¶

    Performance vs Power:
  - Selected Jetson Orin Nano Super (optimal balance)
  - CUDA acceleration for efficiency
  - TensorRT quantization for speed

Size vs Capability:
  - Compact form factor
  - Modular sensor additions
  - Extensible architecture

Cost vs Quality:
  - Enterprise-grade components
  - Long-term support
  - Proven reliability

    🔌 Hardware Stack¶

    Computing Platform¶

    Component Specification Rationale
    CPU ARM Cortex-A78 (8 cores) Real-time processing
    GPU NVIDIA Ampere (1024 CUDA cores) AI inference
    Memory 8GB LPDDR5 Multi-model support
    Storage 128GB UFS 3.1 Fast model loading
    TDP 25W max Energy efficient

    Sensor Suite¶

    Vision Sensors¶

    Primary Camera:
  Type: USB 3.0 Camera
  Resolution: 1280x720 @ 30 FPS
  Field of View: 90° horizontal
  Use Case: Object detection

Thermal Camera (Optional):
  Type: Lepton FLIR thermal
  Resolution: 160x120
  Frame Rate: 60 FPS
  Use Case: Night vision, thermal analysis

    Inertial Sensors¶

    IMU:
  Type: 6-axis (Accel + Gyro)
  Sampling Rate: 200 Hz
  Use Case: Motion tracking, stabilization

Barometer:
  Type: Digital pressure sensor
  Accuracy: ±1 hPa
  Use Case: Altitude estimation

    Navigation Sensors¶

    GPS/GNSS:
  Type: Multi-constellation receiver
  Accuracy: ±5-10 meters
  Update Rate: 1 Hz
  Use Case: Global positioning

Compass (Magnetometer):
  Type: 3-axis magnetometer
  Accuracy: ±1° heading
  Use Case: Absolute orientation references

    Distance Sensing¶

    LIDAR (Optional):
  Type: 2D laser scanner
  Range: 30 meters
  Field of View: 270°
  Update Rate: 10 Hz
  Use Case: SLAM, obstacle detection

Time-of-Flight (ToF):
  Type: Depth camera
  Range: 0.1-4 meters
  Resolution: 320x240
  Use Case: Close-range obstacle detection

    Power Budget¶

    Component Max (W) Typical (W)
    Jetson CPU 5 2-3
    Jetson GPU 15 5-8
    Camera 0.5 0.3
    LIDAR 1.5 1.2
    IMU/GPS 0.3 0.2
    Motors 10 3-5
    Network 0.5 0.3
    Total 33W 12-17W

    Actual Usage: 10-15W for typical operation

    Battery Selection¶

    Recommended Battery:
  Type: LiPo 3S (11.1V)
  Capacity: 5000mAh
  Continuous Discharge: 25A
  Runtime: 45-60 minutes

Charging:
  Charger: XT60 connector
  Max Charge Rate: 1C
  Charge Time: 60-90 minutes

    Specification Range
    Operating Temperature 0°C to 50°C

    Vibration Tolerance Up to 2G

    🔌 Connectivity¶

    Onboard Interfaces¶

    USB Ports:
  - 4x USB 3.0 (high-speed devices)
  - 2x USB 2.0 (low-power devices)
  Use: Cameras, LIDAR, external drives

Ethernet:
  - 1x Gigabit RJ45
  - Use: High-bandwidth communication

WiFi:
  - 802.11ac (2.4GHz & 5GHz)
  - Use: Wireless telemetry, updates

GPIO/SPI/I2C:
  - Multiple pins for custom sensors
  - Use: IMU, compass, additional sensors

    🔐 Thermal Management¶

    Cooling Strategy¶

    Active Cooling:
├─ Aluminum heatsink (Jetson)
├─ Thermal paste application
└─ Passive airflow

Passive Cooling:
├─ Ventilation slots
├─ Thermal interface pads
└─ Heat spreading chassis

    Temperature Monitoring¶

    Thermal Monitoring:
  Update Rate: 1 Hz
  Warning Threshold: 80°C
  Throttle Threshold: 90°C
  Shutdown Threshold: 95°C

Actions:
  At Warning: Log alert, notify user
  At Throttle: Reduce GPU frequency
  At Shutdown: Emergency stop

    🛡️ Reliability & Durability¶

    Component Selection Criteria¶

    ✅ MTBF (Mean Time Between Failure) > 50,000 hours
✅ Military-grade components where applicable
✅ AEC-Q200 certified for automotive reliability
✅ Long-term availability (5+ years)
✅ Repair/replacement paths available

    Redundancy Strategy¶

    Single Points of Failure:
  Jetson:       No redundancy (cost-prohibitive)
  Power:        Battery + external supply option
  Sensors:      Multi-sensor fusion mitigates failures
  Communication: Multiple protocols (WiFi + LoRa)

Graceful Degradation:
  Loss of LIDAR → Use vision-only SLAM
  Loss of Thermal → Use regular camera
  Loss of GPS → Use visual odometry
  Loss of 5GHz WiFi → Fall back to 2.4GHz

    📈 Scalability Considerations¶

    Multi-Robot Deployment¶

    Shared Infrastructure:
  - Centralized parameter server
  - Shared SLAM map
  - Cooperative planning

Per-Robot Hardware:
  - Independent compute
  - Local sensors
  - Individual power systems

Communication Network:
  - LoRa mesh for long-range
  - WiFi for high-bandwidth
  - Fault-tolerant routing

    Modular Expansion¶

    Base Robot
├── Add LIDAR → Full SLAM
├── Add Thermal Camera → Night vision
├── Add Arm → Manipulation
├── Add Additional Motors → Increased speed
└── Add Docking Station → Autonomous charging

    🔧 Maintenance & Support¶

    Preventive Maintenance¶

    Item Interval Action
    Battery Monthly Check health, balance cells
    Connectors Quarterly Clean, verify contacts
    Cooling Quarterly Check dust, clean vents
    Software Monthly Update drivers, check logs
    Sensors Annually Recalibrate if needed

    Diagnostic Features¶

    Built-in Diagnostics:
  - Temperature monitoring
  - Power consumption tracking
  - Sensor health checks
  - Network diagnostics
  - Storage health monitoring
