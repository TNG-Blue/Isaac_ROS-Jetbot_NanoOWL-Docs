    Architecture¶

    Source

    This page is rendered from DeepLearning/docs/ARCHITECTURE.md, the authoritative description kept next to the code in DeepLearning/docs/.

    The pipeline¶

    The module is a perception pipeline. Each stage has a defined role in the chain from sensor to state estimate, and the chain stops there: this module produces perception output and does not command actuators.

    ┌───────────────┐   NV12/YUYV (device ptr, zero copy on Argus)
│  CSI / USB    │
│  camera       │──────────────┐
└───────────────┘              ▼
                    ┌─────────────────────┐
   SENSOR           │ colour conversion   │  CUDA, §2
   CONDITIONING     │ temporal filter     │  CUDA, §4
                    │ letterbox+normalise │  CUDA, §3
                    └──────────┬──────────┘
                               │ NCHW tensor
                    ┌──────────▼──────────┐
   MEASUREMENT      │ CNN inference       │  TensorRT / cuDNN / CUDA, §6
                    │ decode + NMS        │  CUDA, §5
                    └──────────┬──────────┘
                               │
                               │   ── or, with no model at all ──
                               │   ┌─────────────────────────┐
                               │   │ exemplar matching, §10  │  CUDA
                               │   │ mark once -> find again │
                               │   └────────────┬────────────┘
                               │                │
                               ▼◄───────────────┘
                               │ detections (noisy, intermittent)
                    ┌──────────▼──────────┐
   STATE            │ Kalman filter       │  §8
   ESTIMATION       │ Hungarian assoc.    │  §8
                    └──────────┬──────────┘
                               │
                               ▼
                    tracks: stable id, smoothed box,
                    velocity, explicit covariance

    Section numbers refer to MATH.md.

    Why each stage exists¶

    Sensor conditioning. The camera delivers YCbCr, not RGB, and its output carries read and shot noise. Colour conversion is a fixed affine map from the sensor's standard; the temporal filter is a steady-state scalar Kalman filter whose gain is derived from the noise variances rather than tuned, with a robust gate so it does not smear moving objects.

    Measurement. The detector converts the conditioned image into box measurements. It is a sensor, not an estimator: its output jitters frame to frame, misses objects, and carries no identity.

    State estimation. Any consumer that acts on raw detections inherits that measurement noise. The Kalman filter provides a minimum-variance estimate with an explicit covariance, keeps predicting through missed frames, and — with optimal assignment — maintains identity through crossings. This is the module's output: a track carries a stable id, a smoothed box, a velocity and the uncertainty of each.

    What this module does not do¶

    There is no controller and no actuator interface here. The estimate is handed to whatever consumes it — a ROS 2 node, a logger, an application — and any control law built on top lives outside this module. Consequences worth stating:

    • Nothing in the pipeline depends on a robot being present, so every stage is testable offline against the synthetic camera's ground truth.
    • The tracker's dt comes from the caller, not from a control loop's period, so the module imposes no rate.
    • depth_from_bbox_height (§9.2) reports a monocular range estimate as data. It is not used to close any loop.

    Design decisions¶

    One implementation of every formula¶

    math_core.h is annotated __host__ __device__ and includes no CUDA headers. CUDA kernels call it on the device; the unit tests call the same functions on the host. There is no second copy to drift out of sync, and a test that passes has validated the code that actually runs on the GPU.

    No OpenCV anywhere in the image path¶

    Step Implementation
    Capture libargus + EGLStream (CSI) or V4L2 ioctl (USB)
    YUV → RGB CUDA kernel, image_kernels.cu
    Denoise CUDA kernel
    Resize CUDA kernel, bilinear
    Normalise + NCHW fused into the resize kernel
    Image output (examples) PPM writer, 15-byte header + raw bytes

    The CSI path never copies: the ISP publishes into an EGLStream and CUDA consumes device pointers to NVMM memory. The V4L2 path has one unavoidable copy — a UVC device DMAs into kernel buffers CUDA cannot import — staged through pinned memory so it overlaps with compute.

    Two ways to produce detections¶

      trained detector                     exemplar matching
  ----------------                     -----------------
  needs an ONNX/TensorRT model         needs nothing
  recognises trained categories        recognises the marked instance
  setup: train or download             setup: draw one box
  cost: one forward pass               cost: one descriptor per candidate

            \                                 /
             \        they compose:          /
              +--> class-agnostic proposals from the detector,
                   filtered down to what was marked

    ExemplarMatcher::filter is the composed path and the cheap one: the detector supplies a handful of proposals and each is described and matched. ExemplarMatcher::search is the standalone path: multi-scale sliding windows over the whole frame, which needs no model but costs proportionally to frame area times scale count.

    Both run the same descriptor kernels, with one CUDA block per candidate region — the block resamples the region, accumulates its histogram in shared memory and normalises it before writing one row. That mapping is what makes a thousand-window search a single launch.

    Three inference backends¶

                        ┌──────────────────────────────────────────┐
                    │              Detector                    │
                    └───────────────┬──────────────────────────┘
                 ┌──────────────────┴──────────────────┐
                 ▼                                     ▼
        ┌─────────────────┐                  ┌──────────────────┐
        │   TrtEngine     │                  │     Network      │
        │   (TensorRT)    │                  │   (DAG runner)   │
        └─────────────────┘                  └────────┬─────────┘
         whole-network,                    per layer  │
         ahead-of-time:              ┌────────────────┴───────────────┐
         cross-layer fusion,         ▼                                ▼
         measured tactics,   ┌───────────────┐              ┌──────────────────┐
         FP16 / INT8         │    cuDNN      │─ can't serve→│  native  kernels │
                             │ (per-layer)   │   fall back  │  (im2col + GEMM) │
                             └───────────────┘              └──────────────────┘

    TensorRT compiles the whole network ahead of time. It fuses across layer boundaries, selects tactics by benchmarking them on the actual GPU, and reaches the Ampere tensor cores through FP16 and INT8. Fastest, but the graph is frozen at build time and the engine is tied to one GPU architecture and TensorRT version.

    cuDNN accelerates individual layers of a graph this module still executes itself. It carries hand-tuned kernels for every NVIDIA architecture, so it beats a portable hand-written GEMM substantially, while the graph stays malleable at runtime. Algorithm choice is a heuristic query by default (cudnnGetConvolutionForwardAlgorithm_v7, no startup cost) with real benchmarking available through CudnnConvOptions::benchmark.

    Native CUDA kernels are the fallback and, together with the CPU references in reference_ops.cpp, the specification the other two are checked against.

    Selection is per layer and resolved at the first forward pass, because whether cuDNN can serve a layer depends on the input shape and the workspace budget. A graph can legitimately run partly on each backend; Network::backend_summary() reports what actually ran, with the cuDNN algorithm name and workspace size per layer.

    The fallback chain is deliberate: ComputeBackend::AUTO takes cuDNN when the build and the device provide it; a layer cuDNN cannot serve — an unsupported geometry, or no algorithm within the budget — silently uses the native kernels rather than failing. Asking for ComputeBackend::CUDNN explicitly where it is unavailable throws and names the CMake flag, because that is a configuration mistake rather than a runtime condition.

    Fusion, and where it stops¶

    Layer pattern TensorRT cuDNN Native
    conv + bias fused fused fused (GEMM epilogue)
    conv + bias + ReLU/sigmoid fused fused (cudnnConvolutionBiasActivationForward) fused
    conv + bias + SiLU/hard-swish/leaky fused conv+bias fused, activation separate fused
    conv + BN folded at load (§6.5) folded at load folded at load
    across layer boundaries yes no no

    cuDNN has no SiLU, hard-swish or leaky-ReLU activation mode, so for those this module applies its own element-wise kernel over the output cuDNN just wrote — one extra bandwidth-bound pass, still far cheaper than the unfused alternative. That gap is the main reason TensorRT wins on real SiLU-heavy backbones.

    Numerical consequences¶

    cuDNN uses TF32 on Ampere by default for FP32 convolutions: FP32's exponent with a 10-bit mantissa. Agreement with the CPU reference is therefore ~1e-3 relative, not ~1e-6. That is well below the 8-bit quantisation of the sensor feeding the pipeline, so it is the right default — but it is a real difference, so CudnnConvOptions::allow_tf32 turns it off and 05_backend_benchmark --strict compares in true FP32. TensorRT's FP16 makes a comparable trade for a larger speed-up, and is likewise opt-out through TrtPrecision::FP32.

    Tracking runs on the CPU, deliberately¶

    The Kalman filter operates on 8×8 matrices and the assignment problem is sequential. At the tens-of-tracks scale this module targets, a kernel launch (~5 µs) costs more than the entire update (~2 µs for 100 tracks). Moving it to the GPU would be slower and harder to verify. The GPU is used where the work is genuinely parallel: per-pixel conversion, convolution, per-anchor decoding, and the \(N^2\) overlap matrix.

    Aspect-preserving resize only¶

    An anisotropic stretch is not a similarity transform: a box in network coordinates would no longer map back to the source by a single scale, and every shape prior the detector learned is distorted by a ratio that varies with the camera's resolution. The module therefore letterboxes and does not offer a stretch mode.

    Exemplar matching earns its thresholds¶

    Everything about the exemplar path could have been a tuned constant, and none of it is:

    Decision Basis
    The prototype Normalised mean maximises total similarity (Cauchy-Schwarz)
    Refining a prototype Exact incremental mean, no stored history
    Similarity measure Cosine on the unit sphere; for histograms, the Bhattacharyya coefficient via the Hellinger map
    Acceptance threshold μ_bg + z·σ_bg, calibrated per class against background regions
    False-accept rate Bounded by 1/(1+z²) — Cantelli, distribution-free
    Ambiguity Rejected when the margin to the runner-up is too small

    The calibration is per class and per learning frame, so an object marked in a cluttered scene gets a stricter gate than one marked against a blank wall — automatically, because that is what the background statistics say.

    Failure is explicit¶

    Backends that are not compiled in throw NotAvailableError with the CMake flag that would enable them. A Cholesky factorisation that fails returns false rather than propagating NaNs. A Kalman update that cannot be applied leaves the previous valid state untouched. The candidate counter deliberately overruns its buffer so an overflow is visible rather than silent.

    Integration with the rest of the repository¶

    Module Relationship
    CUDA/ Sibling GPU library; its PID/MPC controllers are a possible downstream consumer, not a dependency
    Source/Isaac_ROS-Object_Detection/ ROS 2 packaging of detection; this module is the CUDA-native alternative
    Source/ROS2_Control_System/ A possible downstream consumer of the tracks
    Train_Pytorch/ Produces the checkpoints tools/export_weights.py converts

    To publish results into ROS 2, wrap Detector and MultiObjectTracker in a node and publish vision_msgs/Detection2DArray, carrying the track id in Detection2D::id and the filter's covariance alongside each box.

    Performance notes¶

    Measure before tuning. The examples report per-stage latency; Network::summary prints per-layer MAC counts for a roofline estimate. On an Orin Nano Super (sm_87, 1024 CUDA cores, ~102 GB/s):

    • Colour conversion and letterbox are bandwidth bound — they touch every pixel once and do a handful of FLOPs each. Their floor is set by DRAM.
    • Convolution is compute bound once lowered to GEMM, which is why the tiled kernel matters: the 16×16 tile cuts global traffic by 16×.
    • Decoding is branch-divergent but sparse — the score gate means well under 1% of anchors do the expensive DFL work.
    • TensorRT will beat both other paths substantially on real backbones, and cuDNN will beat the native kernels. Use the native path for debugging and portability, cuDNN when the graph must change at runtime, TensorRT for deployment. 05_backend_benchmark measures the first two side by side on the actual device and checks both against the CPU reference — a faster backend is only useful if it computes the same thing.
    • A cuDNN handle costs tens of milliseconds to create and is shared process-wide through CudnnContext::instance(). It is not thread-safe across stream changes: use one context per inference thread, or serialise access.
    • Exemplar search cost is frames x scales x positions descriptor evaluations. The window count is computed exactly on the host before launching, so the budget is knowable in advance; ExemplarMatcher::last_window_count reports what was actually examined and last_search_overflowed says when the cap was hit rather than silently truncating.
    • TensorRT's first build takes minutes because tactic selection is measured. Set TrtBuildConfig::timing_cache_path and the next build takes seconds; save_engine removes the build from the deployment path entirely.
