    UAV console: 6-DoF state, 3-D map and flight display¶

    Source

    Snapshot of docs/UAV_3D.md from TNG-Blue/JetbotNanoOWL at commit f2ccd4b (submodule Mobile/Android/JetbotNanoOWL). Regenerate with Scripts/mkdocs_hooks/snapshot_submodules.py after updating the submodule.

    The vehicle is a multirotor, not a ground robot, so its state is 3-D (position, velocity, attitude) and its map is a volume rather than a floor plan. This document covers the console side of that change: what arrives over MAVLink, how it is filtered, how a planar scanner builds a 3-D map, and how both are drawn. The 2-D ground-robot path (DiffDriveEKF, occupancy grid) is unchanged and is still used when the source is the JetBot link.

    1. Signal chain¶

    The console observes the vehicle and does not command it (docs/MAVLINK_LINK.md §4). There is no actuator on this side, so the chain ends at the operator display:

     Jetson (Isaac_ROS-Jetbot_NanoOWL)                         Phone (this app)
 ┌─────────────────────┐   ODOMETRY #331, 10 Hz      ┌──────────────────────────┐
 │ flight estimator    │──────────────────────────▶│ delay estimate τ (§2.4)  │
 │ (pose, twist, Σ)    │   LOCAL_NED / BODY_FRD      │ frame change ENU / FLU   │
 └─────────────────────┘                             │ Kalman filter [p; v]     │──▶ PFD, tiles
 ┌─────────────────────┐   OBSTACLE_DISTANCE #330    │ attitude carried forward │
 │ LD19 /scan          │──▶ mount + de-skew ────────▶│ pose at fan time (§3.3)  │
 │ (planar, 10 Hz)     │   5 × 72 sectors / scan     │ log-odds voxels (§3.1)   │──▶ 3-D view
 └─────────────────────┘                             └──────────────────────────┘

    The vehicle's own estimator has already done the sensor filtering (IMU, GNSS, encoders). The console has the vehicle's estimate plus its covariance, received late and at a lower rate. Its job is narrower: carry the estimate across the link delay, show it between packets, and check it against its stated covariance. The NIS test in §2.6 does that check.

    2. State filter¶

    2.1 State and model¶

    State x = [p; v] ∈ ℝ⁶ in world ENU. With white acceleration noise on each axis (the continuous white-noise acceleration model, CWNA),

    ẋ = A x + G w,   A = [[0, I], [0, 0]],   G = [0; I],   E[w(t) w(s)ᵀ] = diag(q̃_xy, q̃_xy, q̃_z) δ(t − s)

    the exact discretisation over any interval T is

    Φ(T) = e^{AT} = [[I, T I], [0, I]]
Q(T) = ∫₀ᵀ Φ(s) G q̃ Gᵀ Φ(s)ᵀ ds = q̃ ⊗ [[T³/3, T²/2], [T²/2, T]]

    (Bar-Shalom, Li, Kirubarajan 2001, §6.2.2). The model is linear, so a Kalman filter is the exact MMSE estimator under the Gaussian assumptions, and no EKF is needed. Because the discretisation is exact, Φ(t₂) Q(t₁) Φ(t₂)ᵀ + Q(t₂) = Q(t₁ + t₂). The filter can therefore run at the UI rate between measurements and still give the same covariance as one step over the whole gap. A test checks this to 1e-16.

    2.2 Process noise from the vehicle's limits¶

    Bar-Shalom's guideline for CWNA is that over a measurement interval T_m the velocity changes by about √(q̃ T_m). A vehicle that manoeuvres up to a_max changes velocity by a_max T_m in that interval. Equating the two:

    q̃ = a_max² · T_m

    a_max is taken from the controller limits of the vehicle itself, Isaac_ROS-Jetbot_NanoOWL/Source/ROS2_Control_System/config/uav_control.yaml: accel_xy_max = accel_z_max = 4 m/s². With T_m = 0.1 s (10 Hz ODOMETRY):

    q̃_xy = q̃_z = 16 · 0.1 = 1.6 m²/s³

    No term is tuned. If the controller limits or the ODOMETRY rate change, q̃ follows from the same formula.

    2.3 Measurement¶

    ODOMETRY carries the pose (position and attitude, LOCAL_NED) and the body twist (BODY_FRD), each with a 6×6 covariance. The frame change is exact: T = [[0,1,0],[1,0,0],[0,0,−1]] (NED ↔ ENU) and B = diag(1, −1, −1) (FRD ↔ FLU), so

    p_enu = T p_ned,   R_enu←flu = T R_ned←frd B,   v_flu = B v_frd,   ω_flu = B ω_frd

    The attitude covariance arrives over ZYX Euler angles. It is mapped to a world-frame rotation error δφ through the Euler-rate Jacobian E = [R_z R_y e_x, R_z e_y, e_z] (Σ_δφ = T E Σ_eul Eᵀ Tᵀ). The bridge applies the inverse map, so a round trip through both repositories recovers the covariance to 1e-7 (§6).

    The filter measures z = [p; v_w] with v_w = R v_b. To first order in the errors, with R̃ = Exp(δφ) R ≈ (I + [δφ]×) R:

    ṽ_w = (I + [δφ]×) R (v_b + δv_b) ≈ v_w + [δφ]× v_w + R δv_b = v_w − [v_w]× δφ + R δv_b

    so over (p, δφ, v_b)

    J = [[I, 0, 0], [0, −[v_w]×, R]],    R_z = J · blockdiag(Σ_pose, Σ_v_b) · Jᵀ

    Including the attitude uncertainty matters at speed. At 5 m/s with σ_φ = 2° it adds 5 · 0.035 = 0.17 m/s of velocity error, which is larger than a typical twist covariance. A test checks the Jacobian against finite differences (5e-11).

    2.4 Latency compensation¶

    The arrival delay τ of each frame is measured as in docs/MAVLINK_LINK.md §8: τ = s − min_W s, with s = t_arrival − t_stamp and W = 30 s. The clock offset cancels. Because the model is linear, carrying the measurement to the present is exact:

    z_now = Φ(τ) z,     R_now = Φ(τ) R_z Φ(τ)ᵀ + Q(τ)

    The attitude is carried forward on the reported body rate, q_now = q ⊗ Exp(ω_b τ), which is exact for a constant rate. Its variance grows to first order by τ² tr Σ_ω.

    2.5 Update and initialisation¶

    • Update: Joseph form, P ← (I − KH) P (I − KH)ᵀ + K R Kᵀ, which keeps P symmetric positive semi-definite under rounding.
    • First usable measurement: sets x = z, P = R_z.
    • Pose but no valid twist: a 3-D position update is fused, and the velocity starts from the envelope prior. A velocity that has never been measured is only known to satisfy |v_i| ≤ v_max (limits.speed_max = 5 m/s). The maximum-entropy distribution on that interval is uniform, with variance (2 v_max)² / 12 = v_max² / 3.
    • Attitude: not re-filtered. The flight controller's estimate already fuses the IMU at a far higher rate than the link carries, so a second filter on its output would only add lag.

    2.6 Consistency¶

    Every update records the normalised innovation squared, NIS = νᵀ S⁻¹ ν, S = H P Hᵀ + R, and its degrees of freedom. The diagnostics panel shows NIS against its χ² bounds. If the vehicle's covariances are honest, the mean NIS is dim z.

    3. A 3-D map from a planar scanner¶

    3.1 Occupancy¶

    A sparse voxel map with 5 cm voxels. It mirrors the design of ros2_qt/core/voxel_map.hpp in Isaac_ROS-Jetbot_NanoOWL, so the phone and the desktop dashboard build the same map from the same data.

    • Bayes filter in log-odds: l(v) ← clamp(l(v) + l_meas, −4, 4), p = 1 − 1/(1 + eˡ) (Thrun, Burgard, Fox §9.2; clamping as OctoMap, Hornung et al. 2013).
    • Inverse sensor model: from the detection and false-alarm probabilities of the ros2_lidar_slam grid, P_D = 0.6 and P_FA = 0.05:
    l_hit  = logit(P_D / (P_D + P_FA))                        = ln 12   =  2.485
l_pass = logit((1 − P_D) / ((1 − P_D) + (1 − P_FA)))      = ln(0.4/0.95) = −0.865
    • Ray traversal: Amanatides–Woo. Every voxel the segment crosses is visited exactly once, in order.
    • Storage: hit-anchored. A voxel is created only by a hit; free space updates voxels that already exist and never creates new ones. Memory therefore grows with the observed surface, not with the swept volume. The map is capped at 400 000 voxels (about 10 MB).

    3.2 On the vehicle: the scan as OBSTACLE_DISTANCE¶

    ros2_network_bridge sends each LD19 scan as the standard MAVLink OBSTACLE_DISTANCE (#330), so no dialect is needed. Each scan is 360 one-degree sectors in BODY_FRD, sent as five messages of 72 (angle_offset −180, −108, −36, 36, 108°).

    • Mount: each ray is moved from the sensor frame to body FLU by the mount yaw and offset.
    • De-skew: ray i is taken at t_i = stamp + i·Δt. With the body twist held constant over the revolution, the body at t_i sits at R_z(ω dt) and v dt relative to the stamp pose, so p_ref = R_z(ω dt) p_b + v dt. The neglected chord term |v||ω| dt²/2 is 5 mm at 1 m/s, 1 rad/s and 0.1 s.
    • Sector value: a sector reports the nearest echo within ±0.5° (every ray in the sector is free up to that range). If a ray saw nothing within range it reports max + 1; if there was no data it reports UINT16_MAX.
    • Quantisation: 1 cm steps give σ = 1/√12 cm = 0.29 cm, against σ_r = 2.8 cm for the LD19.
    • Link budget: a v2 frame is 12 + len bytes, so one scan is 5 × 179 B. At 10 Hz that is 8950 B/s. The bridge sends one scan in
    n = ⌈ B_scan / (u_max C − B_streams) ⌉

    so the scan never pushes the link past u_max of its capacity C. Examples from the tests: Wi-Fi n = 1; a 57.6 kbaud radio with the default streams n = 16; no headroom n = 0 (off).

    3.3 On the console: placing a fan in 3-D¶

    A planar fan becomes 3-D by placing it with the vehicle's full pose at the fan's own time. Slices taken at different altitudes and attitudes then stack into a volume, the same construction as ros2_qt/core/slam3d_mapper.hpp.

    • Pose at t: fans and ODOMETRY share the vehicle clock, so no clock sync is needed. The pose is interpolated between the samples that bracket t: p(t) = p₀ + s(p₁ − p₀), q(t) = slerp(q₀, q₁, s), with s = (t − t₀)/(t₁ − t₀). For linear interpolation over an interval h, the error is bounded by h²/8 · max|p̈|. At 10 Hz with a_max = 4 m/s² that is 4 · 0.01 / 8 = 5 mm, a tenth of a voxel.
    • Waiting: a fan newer than the last pose waits for the next one, for up to 0.3 s. That time is measured on the vehicle clock by the stamps of later fans, not by the phone's clock. After that the fan is placed at the newest pose if it is within 0.15 s, and otherwise dropped. The diagnostics panel shows the count of dropped fans.
    • Ray: the body direction is d = (cos b, sin b, 0) (FLU, counter-clockwise), and the end point is e = p + r R d. An echo in [r_min, r_max] is a hit. +∞ means free space up to r_max. NaN is not used.

    On a tilted vehicle the beam is not horizontal. A test places a wall 4 m ahead with the vehicle rolled, and the hit lands at the height the beam actually reached, 3 + 4 tan(roll). Placing the fan with yaw only would put it at 3 m.

    4. Renderer¶

    A software rasteriser draws straight into the ARGB_8888 bitmap of MapView3D. It needs no GPU context, and the same code runs in the host tests.

    • Orbit camera: c = t + d (cos e cos a, cos e sin a, sin e). The elevation is clamped below ±89° so the up vector stays defined. The camera either follows the vehicle or is panned freely.
    • Pinhole projection: f = (H/2) / tan(fov_y/2), x' = W/2 + f x_c/z_c, y' = H/2 − f y_c/z_c. Points behind the near plane are culled, and line segments are clipped against it.
    • Visibility: a per-pixel depth buffer. Each voxel is drawn as a square splat of its projected edge f · res / z_c, so the map keeps its apparent density at every zoom.
    • Colour: height mapped through an ordered ramp over the map's z range, dimmed with depth. The ground grid, the flight path (a point every 10 cm of travel) and a hexarotor glyph (arms, rotor discs, nose, altitude stem) are drawn into the same depth buffer.
    • Cost: the view renders at most 1100 px on the long side and scales up. The voxel snapshot is refreshed at most every 0.5 s, and rendering happens outside the core's lock, so the 3-D view never stalls the estimator.

    Gestures:

    Gesture Action
    One finger Orbit
    Pinch Zoom
    Two fingers Pan (stops following the vehicle)
    Double tap Back to the preset

    The presets are oblique, top-down, and chase (behind the vehicle, turning with it). A compass in the corner shows where north is for the current azimuth.

    5. Flight display¶

    The primary flight display follows the standard glass-cockpit layout:

    • Attitude: roll and pitch, ±25° of pitch over the height, a 2.5/5/10° ladder, a roll arc with a sky pointer, and the aircraft symbol. Rungs are drawn only within 17.5° of the current pitch, so no label is ever cut by the edge of the instrument.
    • Speed tape: ground speed, |v_xy|.
    • Altitude tape: altitude z, with a vertical-speed bar for v_z.
    • Heading tape: heading with a lubber line.

    Every number is a filter output from §2: p, v and q carried to the present. The tiles under the map show altitude, vertical speed, ground speed, heading, the filter's position σ and the voxel count. The flight-mode chip takes its colour from MAV_STATE.

    The horizon is drawn from the first frame, without waiting for a connection:

    • before the vehicle reports, it is level;
    • after a dropout, it holds the last estimate;
    • whenever the attitude is not live, a red NO ATTITUDE flag sits below the aircraft symbol and the readouts show ---. That way a held or level horizon is never read as live "wings level".

    The bridge side has gtests in Source/ROS2_Network_Bridge/tests. They cover sector geometry, mount yaw and no-return handling, de-skew (raw 415 cm vs de-skewed 400 cm for a 3 m/s pass) and the budget decimation.

    7. Known limitations¶

    • No mount height: the scanner's mount height is not carried by OBSTACLE_DISTANCE, which expresses the fan in the body frame. The fan is placed at the body origin, so the map is offset vertically by the mount height. With the LD19 a few centimetres above the body origin, this is under one voxel.
    • Pose-only updates are not delay-compensated: they are fused as received, because there is no velocity to carry them with.
    • Fan delay is not compensated: fans are placed by their own stamp, so they need no delay compensation. However, the 3-D view lags the vehicle by up to one ODOMETRY interval while a fan waits for its bracketing pose.
    • Not tested on hardware: no flight test or HIL run has been done yet. All the numbers above come from host tests and simulation.
