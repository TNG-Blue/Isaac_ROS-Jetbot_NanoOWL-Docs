    Remote controller link — the phone's side¶

    Source

    Snapshot of docs/REMOTE_LINK.md from TNG-Blue/JetbotNanoOWL at commit d3d7467 (submodule Mobile/Android/JetbotNanoOWL/Qt). Regenerate with Scripts/mkdocs_hooks/snapshot_submodules.py after updating the submodule.

    core/src/remote/phone_link.{h,c} (framing and messages, shared verbatim with Remote_UAV's src/phone/ in Isaac_ROS-Jetbot_NanoOWL), core/src/remote/remote_session.cpp (protocol state machine), core/src/remote/command_arbiter.cpp (who may command), core/src/gnss_track.cpp (position filter), app/src/rc/ (transports and the QML singleton Remote), app/android/…/UsbSerial.java (USB host driver).     1. Who commands the aircraft¶

                          ┌──────────── phone_link (USB-C or BLE) ────────────┐
   pilot ── sticks ──▶ Remote_UAV ──── LoRa uplink (sole transmitter) ───▶ FC ──▶ Jetson planner
     ▲   accept/start      ▲   STATUS · POSITION · MISSION                │
     └─── screen ──────────┘◀──────────────────────────────── telemetry ──┘
                           ▲
                 phone: map, planner ── (DIRECT only: no remote, armed by the operator) ──▶ MAVLink ─▶ Jetson

    The requirement: when the remote and the phone are both on, only the remote commands the aircraft and the phone sends nothing to it. CommandArbiter decides, once per 50 ms:

    state condition mission traffic
    REMOTE the remote's STATUS is younger than 1.5 s plans and commands go to the remote; the pilot accepts and starts them on its screen; the direct MAVLink path is closed in the core (MavlinkLink::setCommandsAllowed(false), every frame refused, a transfer in flight cancelled)
    DIRECT no remote and the vehicle's MAVLink heartbeat < 3 s and the operator armed direct control plans as a MAVLink mission upload to ros2_network_bridge, START as MAV_CMD_MISSION_START, abort as MAV_CMD_NAV_RETURN_TO_LAUNCH
    NONE otherwise the plan can be drawn and saved, not sent
    • No timer hands control back to the phone. The direct latch is cleared whenever a remote is heard; after that, only a new tap by the operator re-arms it. Two devices therefore never command at once, and control never moves without a human decision.
    • Defence in depth. The Jetson refuses a MAVLink mission while the flight controller reports the remote's uplink fresh (MISSION_ACK DENIED, bridge mission_upload.h), and geo_mission_node checks it again before flying.
    • The phone's observer HEARTBEAT (MAV_TYPE_LOG) is not a command and stays on in every state: the bridge never counts it as a ground station (MAVLINK_LINK.md §4).
    • Sticks, ARM, KILL and MODE never come from the phone, on either path. A mission flies only in AUTO, which the pilot selects on the remote.

    2. Transports¶

    USB-C Bluetooth LE
    Android USB host API, UsbSerial.java: the CDC data interface's bulk IN/OUT; SET_LINE_CODING 115200 8N1 and SET_CONTROL_LINE_STATE DTR|RTS on the communication interface (USB CDC PSTN 1.2) — mbed's USBCDC only lets the remote write once DTR is set QtBluetooth GATT client of the Nordic UART Service 6E400001-B5A3-F393-E0A9-E50E24DCCA9E
    Linux desktop the kernel's cdc_acm: /dev/serial/by-id/*Arduino*, else /dev/ttyACM*, cfmakeraw BlueZ through QtBluetooth
    Permission the system's USB dialog (plugging in the remote offers to open the app: usb_device_filter.xml, vendor 0x2341) QBluetoothPermission; before Android 12 also the location permission, without which a BLE scan returns nothing
    Flow control USB bulk one write request outstanding (WriteWithResponse): ATT allows a client a single pending request (Core v5.3 Vol 3 Part F §3.3.2), so the remote's server paces the phone and its 512-byte receive pipe cannot overflow on a 32-item burst (≈ 640 B)
    Chunk any 20 B (the remote's characteristic: ATT_MTU 23 − 3)
    In flight preferred — no radio an existing link is kept; the remote does not advertise while armed

    Both are byte pipes; the COBS framing does not care where a frame is split.

    3. Session (RemoteSession)¶

    No threads and no clock of its own: the caller passes monotonic time, so every transition is host-tested.

    • Presence. CONNECTED while the newest STATUS is younger than 1.5 s — the remote's own rule for the phone (3 periods of the 2 Hz heartbeat).
    • Heartbeat. 2 Hz, protocol version + app build. Without it the remote sends nothing on the transport.

    • Upload. BEGIN → ACK(OK) → ITEM × n → END → ACK. ITEMs carry no ACK; END's result confirms the whole set by CRC-32 (pl_mission_crc = rflink_mission_crc, check value 0xCBF43926 — asserted).

      answer to END meaning session
      PENDING_PILOT complete and valid; the pilot decides phase Pilot
      CRC, INCOMPLETE the remote dropped the set restart from BEGIN (≤ 3 times)
      BAD_MSG after a re-sent END, while MISSION shows our id staged the first END was taken, its ACK lost phase from MISSION
      BUSY (to BEGIN) the pilot has another mission open Failed with that reason

      MISSION then reports the pilot's answer (Accepted / Rejected), the aircraft's acknowledgements (acked / count, the progress bar) and Loaded once the RF sender reaches LOADED. * Timeout. 1 s, at most 3 retries. The bound it must exceed: the remote's phone task (20 ms) + its BLE poll (10 ms) + two connection intervals (≤ 2 × 50 ms at Android's balanced priority) ≈ 130 ms. 1 s is ≥ 7× that, so a timeout means a lost frame, not a slow one; four lost frames in a row (p⁴ = 10⁻⁴ at p = 0.1) end the transfer with "the remote did not answer". * Commands. START (only a question for the pilot: PENDING_PILOT), ABORT (passes directly: it can only end a mission), CLEAR — same ACK rule, with the RF mission id the remote reported.

    4. The aircraft's position on the map¶

    The remote relays the flight controller's GNSS fix (LoRa GNSS pages, 3 per second; on the FC gated by gnss_frontend, σ_h = HDOP · σ_UERE). The phone runs it through a constant-velocity Kalman filter before drawing it.

    Measurement time. Each POSITION carries the fix's age at the FC (fix_age, 10 ms) and at the remote (rx_age, ms), so the measurement is placed at t = t_received − rx_age − fix_age on the phone's clock: latency becomes a time shift, not a position error. A fix with either age unknown, without σ_h, or with a verdict other than ok is not fused. Fixes older than the filter state are dropped.

    Model (Bar-Shalom, Li, Kirubarajan, Estimation with Applications to Tracking and Navigation, §6.2.2, continuous white-noise acceleration), per horizontal axis of the ENU tangent plane at the first fix (WGS-84 → ECEF → ENU, Groves eq. 2.150, exact):

    x = [p, v]ᵀ,   F(T) = [[1, T], [0, 1]],   Q(T) = q̃ [[T³/3, T²/2], [T²/2, T]]
H = [1 0],     R = σ_h²

    Its intensity follows the book's rule that the velocity change over a sampling period T_m is of order √(q̃ T_m) ≈ a_M T_m, hence q̃ = a_M² T_m, with

    • a_M = g tan θ_max = 9.80665 · tan 35° = 6.87 m/s² — the largest horizontal acceleration the airframe can command (θ_max = ATT_CMD_TILT_MAX on the FC);
    • T_m = ⅓ s — three GNSS pages per second (rflink page schedule).

    Both axes have the same F, Q, H, R and initial P, so their covariances stay identical (the Riccati recursion does not see the data): one 2 × 2 P serves both, and the 2-D innovation covariance is S·I with S = p₀₀ + σ_h².

    Gate. NIS ε = (ν_e² + ν_n²)/S ~ χ²(2); ε > 11.83 (P = 0.9973) rejects the fix; three rejections in a row restart the track at the newest fix.

    Consistency, demonstrated (testGnssTrack): with truth drawn from the model itself (exact discretisation, w ~ N(0, Q)), the time-average NIS over 866 fixes lies in its 99 % interval 1.963 ± 0.175 — the gate removes the tail, so the expected mean is 2 − (c + 2)e^(−c/2) = 1.963, not 2. Position within 3σ, speed within 3σ.

    Drawn: the predicted position at display time, the 1σ circle of radius σ / r(φ, z) px, and a course arrow only when the speed is resolved (v > 2σ_v; otherwise a disc — no guessed heading). Without a remote, the Jetson's GLOBAL_POSITION_INT is drawn as it comes: it reports no accuracy, so it is neither filtered nor given a circle. Home is the position at the moment the aircraft's measured arm state rises — the instant the FC and the Jetson latch theirs.

    The filter only draws the aircraft. No command is derived from any measurement on the phone: there is no control loop here; missions are flown by the Jetson's planner on the FC's closed loops.

    5. Direct path (no remote)¶

    The ground side of the MAVLink mission microservice (core/src/mavlink_mission.cpp): MISSION_COUNT(n) → the bridge requests each item (MISSION_REQUEST_INT) → MISSION_ITEM_INT → MISSION_ACK. After every frame the client waits 1.5 s (the protocol's default) and re-sends, at most 5 times. Items are what the bridge accepts: DO_CHANGE_SPEED where the speed changes (0 = planner default), NAV_WAYPOINT in GLOBAL_RELATIVE_ALT_INT with the hold in param1, and NAV_RETURN_TO_LAUNCH / NAV_LAND last (none = hover) — built from the same quantised waypoints as the remote path, so both paths fly the same mission. Commands use COMMAND_LONG with the bridge's closed-loop acknowledgement: IN_PROGRESS at once, ACCEPTED when the FC's measured mode confirms (≤ 3 s); the client re-sends after 1.5 s of silence (confirmation + 1) and waits 5 s after IN_PROGRESS. Golden frames from pymavlink 2.4.50 check every byte.

    Starting from the phone asks for confirmation: nobody confirms on a remote's screen in this mode.

    6. Checking it on a desktop¶

    cc -O2 -Icore/include/jetbot/remote tools/fake_remote.c core/src/remote/phone_link.c -lm -o fake_remote
sudo ./fake_remote /dev/ttyACM7 &          # a pty that answers like the remote
./build/app/jetbotnanoowl --remote-usb --upload-after 4000 --page map

    The stand-in uses the real phone_link.c, flies a 60 m circle at 5 m/s with σ_h = 1.5 m noise, arms after 3 s, accepts an upload after 2 s and acknowledges one item per 200 ms. Expected: the track and the 1σ circle on the map, H where it armed, "Loaded on the aircraft · 5/5 acknowledged" in the plan card.
