    Driving the Isaac ROS graph from the console¶

    Source

    Snapshot of docs/ISAAC_ROS_INTEGRATION.md from TNG-Blue/JetbotNanoOWL at commit f2ccd4b (submodule Mobile/Android/JetbotNanoOWL). Regenerate with Scripts/mkdocs_hooks/snapshot_submodules.py after updating the submodule.

    How the Android console gets its data from Isaac_ROS-Jetbot_NanoOWL and sends commands back, without a single change to that repository.

    Two transports. This page covers JBL1 through tools/isaac_ros_bridge.py. The Isaac repository also has its own MAVLink node, ros2_network_bridge, and the console can read it instead. That path gives pose and twist with full covariances, battery and status texts, but no scan or detections. See MAVLINK_LINK.md. Only one transport is open at a time; the choice is in Settings → ROS2 Connection.

    Why a bridge and not rclcpp on the phone¶

    ROS2 is a peer-to-peer DDS network. Putting a participant on a phone means cross-compiling rclcpp and the type support for the Android ABI, and then relying on multicast discovery across a Wi-Fi link that usually blocks it. The app can be built that way — app/src/main/cpp/CMakeLists.txt uses rclcpp when it finds it — but the supported path is a small node on the Jetson that subscribes with DDS, where DDS works well, and forwards over one UDP socket, where a phone works well.

    The bridge is tools/isaac_ros_bridge.py. It is an ordinary ROS2 node: it subscribes to topics the Isaac ROS graph already publishes and publishes to topics it already subscribes to. Every topic name is a command-line argument, so a remapped graph needs a different launch line, not a different bridge.

    Topic map¶

    Direction Link packet ROS2 topic (default) Type
    console → robot 0x02 CmdTwist /jetbot/cmd_vel geometry_msgs/Twist
    console → robot 0x04 OwlQuery /input_query std_msgs/String
    console → robot 0x05 SafetyCmd /safety/emergency_stop std_msgs/Bool
    robot → console 0x10 StateOdom /joint_states, /imu sensor_msgs/JointState, sensor_msgs/Imu
    robot → console 0x11 Scan /scan sensor_msgs/LaserScan
    robot → console 0x12 PoseFix /odometry nav_msgs/Odometry
    robot → console 0x13 Detections /output_detections vision_msgs/Detection2DArray
    robot → console 0x14 NodeStatus /diagnostics diagnostic_msgs/DiagnosticArray
    robot → console (image size only) /input_image/camera_info sensor_msgs/CameraInfo

    The defaults come from the Isaac ROS repository itself:

    • /jetbot/cmd_vel and /odometry are the remapped names in Source/ROS2_Control_System/launch/control_system.launch.py;
    • /input_query, /output_detections and /output_image are the NanoOWL node's own topics in Source/Isaac_ROS-Object_Detection/isaac_ros_objectdetection/OWL/;
    • /safety/emergency_stop and /diagnostics are published by Source/ROS2_Lidar_AI_Solution/src/safety/safety_zone_node.cpp.

    Where the data goes once it arrives¶

      /joint_states ─┐
        /imu ────┼─▶ median ─▶ low-pass ─▶ noise ID ─▶ ┌──────┐
                 │                                     │ EKF  │─▶ state estimate
   /odometry ────┼──────────── pose fix (with R) ─────▶│      │       │
       /scan ────┴──▶ ICP scan match ─▶ pose fix ─────▶└──────┘       │
                                    └─▶ occupancy grid                │
                                                                      ▼
  operator ──▶ guidance (Manual │ Kanayama │ polar │ LQR) ──▶ inner loop (PID │ MPC)
                                                                      │
                                    rate & jerk limit ─▶ inverse kinematics
                                                                      │
                                                          /jetbot/cmd_vel ─▶ robot
                                                                      │
                          measured wheel rates close both loops ◀─────┘

    The chain is unchanged from ESTIMATION_DESIGN.md; what the Isaac ROS graph adds is the pose fix, and it matters more than the topic count suggests.

    A differential drive that integrates wheel rates has heading variance growing linearly in time and position error growing with its integral — the estimate drifts without bound, and no amount of filtering fixes that, because the information simply is not there. /odometry is an exteroceptive measurement in a fixed frame, so it bounds the error. It is applied as an ordinary Kalman update (ControlPipeline::applyPoseFix), weighted by the covariance the publisher supplied.

    That last part is why the bridge floors the variance. A node that leaves pose.covariance at zero — a common placeholder — is claiming a perfect measurement; taken literally the Kalman gain goes to 1, the filter throws away its own prediction, and the estimate jumps to the fix on every message. --min-var-xy and --min-var-yaw (default 1e-4) are the floor, and the receiver rejects a non-positive variance outright.

    Running it¶

    On the Jetson, with the Isaac ROS graph already up:

    # workspace sourced as usual, e.g.
source /opt/ros/humble/setup.bash
source ~/workspaces/isaac_ros-dev/install/setup.bash

python3 tools/isaac_ros_bridge.py --phone 192.168.1.50

    tools/jetbot_link.py must sit next to it — it holds the wire format shared with the C++ side.

    In the console: ☰ → Settings → ROS2 Connection, choose JBL1, set the Jetson's address and Save. Ports default to 9600 on the robot and 9601 on the phone.

    A graph with different names:

    python3 tools/isaac_ros_bridge.py --phone 192.168.1.50 \
    --cmd-vel-topic /jetbot/cmd_vel \
    --odom-topic /odometry/filtered \
    --scan-topic /ld19/scan \
    --detections-topic /output_detections

    A chassis that is not the stock Jetbot:

    python3 tools/isaac_ros_bridge.py --phone 192.168.1.50 \
    --wheel-radius 0.0325 --wheel-base 0.112 \
    --left-joint wheel_left_joint --right-joint wheel_right_joint

    --help lists every topic and chassis parameter.

    Trying it without a robot¶

    python3 tools/isaac_ros_bridge.py --phone 192.168.1.50 --dry-run

    No ROS2 needed. The bridge simulates a differential drive, a lidar in a square room and a detector watching two landmarks, and emits the full packet set — enough to bring up the link, the estimator, the map, the detection overlay and the graph-health panel before any of it meets the Jetson.

    The console has its own simulation as well, and the two answer different questions. Simulation mode in the console (Settings → simulation) runs the plant model inside the app, so nothing leaves the phone: it exercises the control chain and the perception overlay with no network at all. --dry-run exercises the transport as well, over real sockets.

    The detector prompt¶

    NanoOWL is open vocabulary: there is no fixed class list, and the prompt on the query topic is the class list. The console's 🔍 button on the perception card sets it, sends it as 0x04, and the bridge republishes it on /input_query.

    Two details about the Isaac ROS node shape how the bridge handles the result:

    • it publishes boxes in pixels, so the bridge normalises them against the camera resolution — from /input_image/camera_info when that is available, otherwise from --image-width / --image-height;
    • it sets hypothesis.class_id to the index of the matched phrase in the query, and leaves hypothesis.score unset. The bridge resolves the index back to the phrase by splitting the query exactly the way the node does (prompt.strip("][()").split(",")), and forwards the missing score as 0, which the console renders as a label with no percentage rather than as 0 %.

    If the graph is restarted the prompt has to be restated, so the app resends it on every connect.

    Checking the two codecs still agree¶

    The wire format has two implementations — udp_link.cpp and jetbot_link.py — and they are checked against each other over real sockets:

    cmake -S app/src/main/cpp -B build-host && cmake --build build-host -j
g++ -std=c++17 -O2 -Iapp/src/main/cpp/include -Iapp/src/main/cpp \
    tools/link_interop_test.cpp -Lbuild-host -ljetbot_core -lpthread -o link_interop_test

python3 tools/isaac_ros_bridge.py --phone 127.0.0.1 --dry-run &
./link_interop_test 9600 9601 --isaac

    --isaac requires the pose fix, the detections and the graph status as well as the original packet types. The message conversion itself is covered separately, without ROS2:

    python3 tools/test_isaac_ros_bridge.py

    Troubleshooting¶

    Console shows Likely cause
    no link host or port wrong, or the bridge is not running
    link up · no feedback the bridge is sending nothing the estimator can use — check /joint_states is publishing and that --left-joint / --right-joint match the names in it
    ROS2 live · odometry packets arriving, but no pose fix in the last 2 s — check /odometry
    detector offline no 0x13 yet — check /output_detections is publishing
    stale · Ns since last frame the detector stopped; the last frame is kept but faded
    boxes in the wrong place the image size is wrong — publish camera_info or pass --image-width / --image-height
    pose jumping to the fix the publisher's covariance is zero or tiny; raise --min-var-xy
    degraded / error in the graph panel a node reported it on /diagnostics; the message names which
