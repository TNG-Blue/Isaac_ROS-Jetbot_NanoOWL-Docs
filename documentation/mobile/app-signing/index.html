    App signing, updates, and the Play Protect warning¶

    Source

    Snapshot of docs/APP_SIGNING_AND_PLAY_PROTECT.md from TNG-Blue/JetbotNanoOWL at commit d3d7467 (submodule Mobile/Android/JetbotNanoOWL/Qt). Regenerate with Scripts/mkdocs_hooks/snapshot_submodules.py after updating the submodule.

    This document explains the "Đã chặn ứng dụng để bảo vệ thiết bị của bạn / Play Protect chưa từng thấy ứng dụng nào của nhà phát triển này" dialog, what in this repository was causing it, and what was changed.

    1. What the dialog actually is¶

    Play Protect is a server-side reputation service, not a local setting. When an APK is installed from outside Google Play, the installer sends Play Protect a summary of the package — most importantly the signing certificate, the package name, and the APK hash — and Play Protect answers with a verdict.

    The exact string shown in the screenshot is the unknown developer verdict. It means: Play Protect has no install history for this signing certificate, so it cannot vouch for it.

    Two consequences follow directly, and they are the whole basis for the fix:

    1. There is no manifest attribute, Gradle flag, or permission that turns this dialog off. If such a switch existed, malware would set it. Anyone claiming otherwise is describing a device-side setting the user toggles (Play Protect → scan apps), not something an app can declare.
    2. The verdict is attached to the signing certificate, and reputation is accumulated over installs of that certificate. So the achievable goal is: present the same, stable, real certificate every time, and stop looking like a brand-new unknown package on every build.

    2. Why this project triggered it every single time¶

    Three things in the build, each of which resets Play Protect's view of the app:

    Cause Effect
    Releases were debug builds signed with keystore/debug.keystore (alias androiddebugkey, password android) The Android debug key is a publicly known, shared key with a CN=Android Debug subject. It carries no developer identity, and a debuggable APK is a strong negative signal on its own.
    versionCode was hard-coded to 1 in app/build.gradle.kts Android accepts an install as an update only when versionCode strictly increases. With every build stamped 1, installing a newer APK over an older one is rejected as a downgrade (INSTALL_FAILED_VERSION_DOWNGRADE), forcing an uninstall + fresh install — and a fresh install is precisely what Play Protect screens. An update over an existing install with a matching signature normally does not show this dialog.
    android:usesCleartextTraffic="true" plus unused READ_MEDIA_IMAGES/VIDEO/AUDIO permissions Traits weighed by the heuristics when there is no reputation to fall back on. The app never used any of them: SSH and VNC are raw TCP sockets, which the cleartext flag does not govern, and file upload goes through the Storage Access Framework, which needs no permission.

    3. What was changed¶

    app/build.gradle.kts¶

    • A release signing config reading the key from keystore/keystore.properties (git-ignored) or from RELEASE_STORE_FILE / RELEASE_STORE_PASSWORD / RELEASE_KEY_ALIAS / RELEASE_KEY_PASSWORD environment variables.
    • v1 + v2 + v3 + v4 signature schemes enabled explicitly. v2/v3 verify the archive as a whole rather than entry-by-entry; a v1-only APK looks legacy.
    • versionCode is now injected: -PappVersionCode=N or APP_VERSION_CODE=N, falling back to a baseline of 2 locally. versionName follows as 1.0.N.
    • release is explicitly isDebuggable = false.
    • A verifyReleaseSigning task that fails the build when no real key is configured, so a debug-signed "release" cannot be published by accident.

    app/src/main/AndroidManifest.xml¶

    • android:usesCleartextTraffic="true" replaced by android:networkSecurityConfig="@xml/network_security_config", which denies cleartext HTTP. SSH (port 22) and RFB/VNC (port 5900) are unaffected — that setting only constrains the HTTP stacks, which this app does not use.
    • READ_MEDIA_IMAGES, READ_MEDIA_VIDEO, READ_MEDIA_AUDIO removed (unused).
    • READ_EXTERNAL_STORAGE capped at maxSdkVersion="28", matching WRITE_EXTERNAL_STORAGE; only the legacy download path on API ≤ 28 needs it.

    .github/workflows/build-apk.yml¶

    • Decodes a release keystore from the RELEASE_KEYSTORE_BASE64 secret and builds assembleRelease when it is present; falls back to debug with a warning when it is not.
    • Passes -PappVersionCode=${{ github.run_number }}, which is monotonic, so every build is installable as an update over the previous one.
    • Runs apksigner verify --print-certs and publishes the certificate's SHA-256 in the build summary and in the release notes. If that fingerprint ever changes between releases, updates will break and the reputation built up so far is lost.

    4. One-time setup you have to do¶

    The key itself cannot live in the repository. Create it once and keep it forever — losing it means every user must uninstall and reinstall.

    keytool -genkeypair -v \
  -keystore release.keystore \
  -alias jetbotnanoowl \
  -keyalg RSA -keysize 4096 \
  -validity 10000 \
  -storetype pkcs12 \
  -dname "CN=<your name>, O=TNG-Blue, C=VN"

    Local builds — create keystore/keystore.properties (git-ignored):

    storeFile=release.keystore
storePassword=<store password>
keyAlias=jetbotnanoowl
keyPassword=<key password>

    Place release.keystore next to it in keystore/, then:

    ./gradlew verifyReleaseSigning assembleRelease -PappVersionCode=3

    CI — add four repository secrets under Settings → Secrets and variables → Actions:

    base64 -w0 release.keystore   # paste the output as RELEASE_KEYSTORE_BASE64
    Secret Value
    RELEASE_KEYSTORE_BASE64 base64 of release.keystore
    RELEASE_STORE_PASSWORD store password
    RELEASE_KEY_ALIAS jetbotnanoowl
    RELEASE_KEY_PASSWORD key password

    Back the keystore file and both passwords up somewhere outside the repository.

    5. What to expect afterwards¶

    • Updating an existing install: the dialog goes away. Once a user has the app installed and a later APK arrives with the same certificate and a higher versionCode, the installer treats it as an update, not as a new unknown package. This is the case in the screenshot — it says "Đang cài đặt…" for a fresh install — and it is what the versionCode fix addresses.
    • The very first install on a new device may still warn. A certificate with no install history is unknown by definition. It fades as installs of that same certificate accumulate; it cannot be switched off from the APK.
    • To remove it entirely, the certificate has to become known to Google. Publishing the app through the Play Console — even to an internal testing or closed testing track, which is not a public listing — registers the certificate and clears the unknown-developer verdict for installs from Play. A one-time USD 25 developer registration is required.
    • Never change the signing key. A new key is a new identity: reputation restarts at zero and existing installs can no longer be updated (INSTALL_FAILED_UPDATE_INCOMPATIBLE).

    6. Verifying a build before handing it out¶

    # Confirm the certificate and that v2/v3 are present
apksigner verify --print-certs -v app/build/outputs/apk/release/*.apk

# Confirm versionCode increased and the app is not debuggable
aapt dump badging app/build/outputs/apk/release/*.apk | head -3

    Expect Verified using v2 scheme: true, Verified using v3 scheme: true, a certificate SHA-256 identical to the previous release, and no application-debuggable line.
