    Estimation and perception design — Jetbot NanoOWL¶

    Source

    Snapshot of docs/ESTIMATION_DESIGN.md from TNG-Blue/JetbotNanoOWL at commit f2ccd4b (submodule Mobile/Android/JetbotNanoOWL). Regenerate with Scripts/mkdocs_hooks/snapshot_submodules.py after updating the submodule.

    Every block in the app's sensor-to-state path is a discretisation of a named continuous-time design, with the derivation written out here and a property test in app/src/main/cpp/tests/test_main.cpp that checks the implementation still matches the mathematics. Nothing in the chain is tuned by feel alone: where a gain has a stability condition, the condition is enforced in code.

    The app no longer controls the robot. The guidance laws (Kanayama tracker, polar pose stabiliser, cross-track LQR), the inner velocity loops (PID, MPC), the reference shaper, the inverse kinematics, the plant simulator and the operator surfaces that drove them were removed; this end observes. The sections they occupied are gone from this document and their derivations are in the git history. What is left is what still runs: conditioning, noise identification, estimation, odometry and mapping.

    The PID of §5 survives because the Linux environment's display pacing loop uses it — see docs/LINUX_ENVIRONMENT.md §6.2, which together with §6.1 is derived in the same style and covered by the same host suite.

    Section numbers are referenced from the source comments (§2, §5, …).

    1. Architecture¶

      encoders ─┐
  gyro ─────┼─► median ─► low-pass ─► noise ID ─► EKF ─────────┐
  lidar ────┴────────────────────► ICP scan match ─► pose fix ─┤
                                                              │
                                        x̂ = [x y θ v ω] ◄──────┘
                                                              │
                          occupancy grid ◄── scan, at the estimated pose
                                                              │
                                 console: map, charts, diagnostics
                                                              ▲
                      UDP link  ◄── telemetry ◄── robot ───────┘

    Implementation: jetbot::pipeline::EstimationPipeline (src/core/estimation_pipeline.cpp).

    One loop, and it is an observer. The estimator runs at a fixed rate (50 Hz by default) and consumes whatever the link delivers. There is no actuator path: nothing this app computes is written back to the robot, and the link's wheel command and safety-stop messages, though still part of the wire protocol, are never sent from here.

    Staleness is reported, not hidden. When telemetry stops arriving (time_since_sample > watchdog_timeout) the EKF keeps propagating its motion model, because that is still the best available prediction — but the output is flagged (feedback_valid = false, the source dot turns amber), because a pose that is pure dead reckoning is a different claim from one a measurement just corrected.

    Why the heavy work is native. The loop must keep a fixed period regardless of what the Android UI thread is doing, so it runs on a native thread (nativeStartLoop). Per second, at the default settings, the core performs ~50 EKF predict/update cycles (5×5 matrices), ~10 ICP alignments, ~10 scan integrations touching ~10⁵ grid cells, and one full-viewport map rasterisation per UI frame. Measured on the host test machine, integrating a 360-beam scan into a 200×200 grid takes 0.21 ms, i.e. ~2 % of one 10 Hz period.

    2. Sensor conditioning¶

    jetbot::filter — include/jetbot/filter/filters.h, src/core/filters.cpp.

    2.1 Median pre-filter¶

    A window of length w = 2k+1 rejects any burst of at most k corrupted samples exactly. The median minimises Σ|x_i − m|, so a single arbitrarily large outlier cannot move it past its neighbours — no linear filter has this property, because a linear filter's output is an affine function of every input. Encoder counters produce exactly this kind of impulsive fault (a missed or doubled tick), which is why the non-linear stage comes first.

    2.2 First-order low-pass, pre-warped bilinear¶

    Target: H(s) = ω_c / (s + ω_c). Substituting the pre-warped bilinear map s = K(z−1)/(z+1) with K = ω_c / tan(ω_c T/2), and writing α = tan(ω_c T/2):

    H(z) = α(1 + z⁻¹) / ((1+α) − (1−α)z⁻¹)

y[n] = a(x[n] + x[n−1]) + b y[n−1],   a = α/(1+α),  b = (1−α)/(1+α)

    Properties, all verified in the tests:

    • DC gain exactly 1: 2a/(1−b) = 1 algebraically, so the filter cannot bias a velocity measurement.
    • −3 dB exactly at f_c: pre-warping maps the digital frequency ω_c to the analogue frequency ω_c, so |H(e^{jω_c T})| = 1/√2 with no frequency warping error. Without pre-warping the cutoff lands at (2/T)tan(ω_c T/2), which at f_c = 8 Hz, T = 20 ms is a 4 % error — small, but free to avoid.
    • Unconditionally stable: b ∈ (0,1) for every ω_c > 0.

    OnePoleLowPass::magnitudeAt() evaluates the realised difference equation on the unit circle, so the UI and the tests read the true response of the code rather than of the ideal prototype.

    2.3 Second-order Butterworth / notch¶

    Standard RBJ bilinear realisation with Q = 1/√2 (maximally flat). Available for chassis-resonance rejection; magnitudeAt() confirms unity DC gain, 1/√2 at the cutoff and monotone roll-off.

    3. Noise identification¶

    jetbot::estimation — include/jetbot/estimation/noise_estimator.h.

    3.1 Welford moments¶

    mean_k = mean_{k−1} + (x_k − mean_{k−1})/k
M2_k   = M2_{k−1} + (x_k − mean_{k−1})(x_k − mean_k)
var    = M2_k/(k−1)

    One pass, no catastrophic cancellation (Welford 1962; Knuth TAOCP vol. 2 §4.2.2). Used for the loop-period jitter monitor, where the mean dominates the variance by four orders of magnitude and the naive sum-of-squares form would lose all significance.

    3.2 Innovation-based measurement-noise identification¶

    For a Kalman filter the innovation ν_k = z_k − H x̂_k⁻ is zero-mean white with

    C_ν = H P⁻ Hᵗ + R                                     (Mehra 1970)

    so averaging the empirical innovation power over a sliding window and subtracting the model term identifies R without ever observing the true state:

    R̂ = (1/N) Σ ν_k²  −  (1/N) Σ H P_k⁻ Hᵗ,    projected onto [floor, ceiling]

    The projection is the Myers & Tapley (1976) positivity safeguard: without it a window where the innovations happen to be small would make R̂ negative and destroy the positive definiteness of the filter.

    The same identity gives a consistency monitor, NIS = E[ν²/(HP⁻Hᵗ + R)] ≈ 1 for a correctly tuned filter; the console shows it, and the estimator indicator turns amber outside [0.2, 4].

    A rejected alternative, for the record. The first implementation estimated the wheel-rate variance from the raw-minus-filtered residual. That residual contains the signal's high-frequency content as well as the noise, so under a manoeuvre it over-estimated the variance by ~70×, the filter stopped trusting odometry, and the velocity estimate became both laggy and noisy — which then destabilised the inner loop. The innovation-based estimator has no such coupling because the model term H P⁻ Hᵗ is subtracted explicitly.

    4. State estimation — EKF¶

    jetbot::estimation::DiffDriveEKF — src/core/diff_drive_ekf.cpp. State x = [x, y, θ, v, ω]ᵗ.

    4.1 Motion model¶

    Exact integration of a constant twist over one sample (a circular arc), with the straight-line branch for |ω| ≤ 10⁻⁴ rad/s:

    |ω| > ε:   x⁺ = x + (v/ω)(sin(θ + ωT) − sin θ)
           y⁺ = y − (v/ω)(cos(θ + ωT) − cos θ)
|ω| ≤ ε:   x⁺ = x + vT cos θ,   y⁺ = y + vT sin θ
           θ⁺ = wrap(θ + ωT),   v⁺ = v,   ω⁺ = ω

    v and ω are random walks driven by white acceleration noise. Using the exact arc rather than an Euler step removes a systematic cross-track error of ½ v ω T² per step — at v = 0.3 m/s, ω = 1 rad/s, T = 20 ms that is 60 µm/step, i.e. 3 mm/s of accumulating bias, which dead reckoning would integrate without bound.

    4.2 Jacobian¶

    For the arc branch, with θ₁ = θ + ωT:

    ∂x⁺/∂θ = (v/ω)(cos θ₁ − cos θ)
∂x⁺/∂v = (sin θ₁ − sin θ)/ω
∂x⁺/∂ω = −(v/ω²)(sin θ₁ − sin θ) + (v/ω)T cos θ₁
∂y⁺/∂θ = (v/ω)(sin θ₁ − sin θ)
∂y⁺/∂v = −(cos θ₁ − cos θ)/ω
∂y⁺/∂ω =  (v/ω²)(cos θ₁ − cos θ) + (v/ω)T sin θ₁
∂θ⁺/∂ω = T

    The straight-line branch uses the leading terms of the same expansion (∂x⁺/∂ω = −½vT² sin θ), which is why the threshold can be small without the Jacobian becoming singular.

    4.3 Process noise¶

    With σ_a, σ_α the 1-σ unmodelled linear and angular accelerations,

    G = [½T²cos θ   0   ;  ½T²sin θ   0  ;  0   ½T²  ;  T   0  ;  0   T]
Q = G · diag(σ_a², σ_α²) · Gᵗ

    the standard discretised continuous-white-noise-acceleration model (Bar-Shalom §6.2). Two parameters with physical units replace five covariance entries, which is what makes the filter tunable from the UI.

    4.4 Measurement models¶

    source H R
    wheel odometry (v, ω) rows selecting v, ω identified per §3.2
    rate gyro row selecting ω identified per §3.2
    absolute yaw row selecting θ, wrapped residual fixed
    ICP pose fix rows selecting x, y, θ from the match RMSE (§11)
    MAVLink ODOMETRY I₅, θ residual wrapped blockdiag(R_pose 3×3, R_twist 2×2) from the source, mapped exactly (MAVLINK_LINK.md §5), carried forward over the measured delay: F R Fᵀ + Q(τ) (§8 there)

    A part of ODOMETRY whose covariance is unknown or not positive definite is not fused, and it is never replaced by a constant. Positive definiteness is tested by Cholesky with pivots above float32 round-off. With one valid part, that part alone is fused through the 3×3 or 2×2 rows, without compensation.

    4.5 Joseph-form update¶

    S = H P⁻ Hᵗ + R,   K = P⁻ Hᵗ S⁻¹
P⁺ = (I − KH) P⁻ (I − KH)ᵗ + K R Kᵗ

    Algebraically equal to (I−KH)P⁻, but positive semi-definite even under round-off (Bar-Shalom §5.2.3). Every angular residual passes through wrapAngle, and the covariance diagonal has a 10⁻⁹ floor so the filter cannot become so confident that it ignores new measurements.

    Verified: over a 60 s noisy arc, estimated velocity error is <25 % of raw odometry error and yaw-rate error <10 %; the time-averaged estimate is unbiased to 0.01; mean NIS stays in the consistency band; P stays symmetric and positive on the diagonal; a pose fix moves the estimate toward the measurement.

    5. PID¶

    jetbot::control::PIDController — src/core/pid.cpp.

    This is the one controller still in the tree. It no longer drives the robot; its only consumer is the IMC-tuned loop that paces the Linux desktop's frame requests (docs/LINUX_ENVIRONMENT.md §6.2). The derivation is kept here because that loop depends on every property below.

    Continuous law (Åström & Hägglund, Advanced PID Control, ch. 3):

    u = Kp(b·r − y) + (Ki/s)(r − y) − (Kd·s/(1 + Tf·s))·y
    • derivative on −y only: a setpoint step cannot produce a derivative kick;
    • the derivative is low-passed with Tf, bounding its high-frequency gain at Kd/Tf instead of letting measurement noise through with gain Kd·ω;
    • b < 1 softens the response to setpoint steps without changing the disturbance-rejection loop shape.

    Discretisation (backward Euler, exact at DC):

    D[k] = (Tf/(Tf+T))·D[k−1] − (Kd/(Tf+T))·(y[k] − y[k−1])
I[k] = I[k−1] + Ki·T·e[k] + (T/Tt)·(u_applied[k−1] − u_unsat[k−1])

    5.1 Anti-wind-up, with a closed-form check¶

    The last term is back-calculation. While the actuator is saturated the integrator is driven toward the value that makes the controller output achievable, with time constant Tt. At steady state the update is zero, so

    0 = Ki·e + (1/Tt)(u_sat − u_unsat)   ⟹   I* = u_sat − Kp·b·r + Kp·y + Ki·Tt·e

    For the test case (Kp=1, Ki=5, Tt=0.1, e=r=10, y=0, u_sat=1) this predicts I* = 1 − 10 + 5 = −4, and the implementation lands on −4 to 10⁻⁶. The same run without anti-wind-up (Tt → ∞) charges the integrator to Ki·e·t = 500, i.e. 125× further, and takes 100× longer to leave saturation.

    u_applied is an optional input: the pipeline passes the command that actually reached the actuator, so the integrator back-calculates against reality (external anti-wind-up / tracking mode) rather than against the controller's own clamp. This is what keeps the integrator honest when the reference shaper or the wheel-speed saturation of §6 has reduced the command.

    6. Differential-drive odometry¶

    jetbot::control — src/core/diff_drive_kinematics.cpp.

    inverse:  v_r = v + ωL/2,  v_l = v − ωL/2,   ω_i = v_i/r
forward:  v   = r(ω_r + ω_l)/2,  ω = r(ω_r − ω_l)/L

    6.1 Variance propagation¶

    With independent wheel-rate noise of variance σ_ω²:

    var(v) = r²σ_ω²/2,      var(ω) = 2r²σ_ω²/L²

    so the ratio between the two channels is var(ω)/var(v) = 4/L². For the stock Jetbot (L = 112 mm) that is 319 rad²/m²: the same wheel-rate noise is amplified into the yaw channel far more strongly than into the linear one, because a narrow wheel base means a small rate difference implies a large yaw rate. That is the quantitative reason the gyro carries most of the weight on ω in §4.4, and it falls out of the kinematics rather than out of a tuning session.

    7. Occupancy mapping¶

    jetbot::mapping::OccupancyGrid — src/core/occupancy_grid.cpp.

    Under the standard assumptions of cell independence and a static world, recursive Bayes over measurements z_{1:t} gives, in odds form,

    odds(m_i | z_{1:t}) = odds(m_i | z_t) · odds(m_i | z_{1:t−1}) / odds(m_i)

    and taking logarithms turns the product into a sum:

    l_{i,t} = l_{i,t−1} + log( p(m_i|z_t)/(1 − p(m_i|z_t)) ) − l_{i,0}

    With a uniform prior (l_{i,0} = 0) the increments are the two constants log(p_hit/(1−p_hit)) for the beam endpoint and log(p_miss/(1−p_miss)) for every cell the beam passed through, so integrating a scan costs one addition per traversed cell (Thrun, Burgard & Fox, Probabilistic Robotics, §9.2). That is the whole reason for the log-odds parameterisation, and it is what makes a 360-beam scan affordable at 10 Hz on a phone.

    Cells along a beam are selected with Bresenham's integer line algorithm: exact, symmetric, and free of floating-point drift. Log-odds are clamped to [l_min, l_max] so the map stays responsive to change instead of saturating permanently. Recovering the probability is p = 1 − 1/(1 + e^l).

    Verified: the prior reads 0.5 everywhere; the endpoint becomes occupied and the traversed cells free; k repeated hits give exactly k·log(p_hit/(1−p_hit)) until the clamp; the clamp holds; save/load round-trips geometry and log-odds bit-for-bit; the rasteriser writes an opaque ARGB word for every pixel of the viewport, and its device-byte-order path is exactly the red/blue swap of the logical one.

    8. Scan matching (ICP)¶

    jetbot::mapping::alignScans — src/core/scan_matcher.cpp.

    Alternates the two standard steps (Besl & McKay 1992):

    1. correspondence — nearest target point per source point, with a gating radius that rejects outliers;
    2. minimisation — the rigid transform minimising Σ‖R(θ)q_i + t − p_i‖². Removing both centroids decouples translation from rotation, and the rotation has the closed form (the 2-D case of Kabsch/Umeyama)
    θ* = atan2( Σ(q_ix p_iy − q_iy p_ix),  Σ(q_ix p_ix + q_iy p_iy) )
t* = mean(p) − R(θ*)·mean(q)

    Each iteration is therefore exactly optimal for its correspondence set, and the cost is monotonically non-increasing.

    ICP is a local method, so the pipeline always seeds it with the odometry prior — the relative motion the EKF believes has happened since the previous scan, expressed in the previous scan's frame. The result is composed back onto the previous scan pose and fed to DiffDriveEKF::updatePose with a variance taken from the match RMSE, so a loose fit cannot drag the estimate around. This is the measurement that bounds odometry drift: without an exteroceptive fix the position error of any dead-reckoning chain grows without bound.

    Known limitation, stated rather than hidden: point-to-point correspondences slide along long featureless walls, so a wall-only scan is well constrained in the normal direction and weakly constrained along it. That is a property of the cost function; the prior plus the RMSE-derived variance is what keeps it from hurting the estimate. The tests check both cases — exact recovery of a known transform on a well-conditioned cloud, and a bounded residual on a wall-like scan seeded with the prior.

    9. Verification¶

    The native core is platform independent, so the same code that runs on the phone is exercised by a host test suite:

    cmake -S app/src/main/cpp -B build-host
cmake --build build-host -j
./build-host/jetbot_core_tests

    381 checks, 0 failures at the time of writing. Coverage by area:

    area what is asserted
    filters analytic DC gain and −3 dB point, roll-off, notch rejection, median outlier rejection
    noise ID Welford mean/variance recovery, Mehra R̂ recovery from a known innovation sequence, NIS ≈ 1
    EKF error reduction vs raw odometry, unbiasedness, NIS consistency band, covariance symmetry and positivity, pose-fix correction
    PID integral action, proportional path, clamping, analytic anti-wind-up fixed point, 50× improvement over the naive form, external anti-wind-up fixed point, bounded derivative gain (kept for the display pacer of §6.2 in LINUX_ENVIRONMENT.md)
    odometry forward map against its closed form, in-place rotation, variance propagation
    mapping log-odds linearity and clamping, ray-cast free/occupied classification, timing, save/load round trip, rasteriser output
    ICP exact transform recovery, residual RMSE, inlier count, wall-like scan with prior
    transport CRC-16/CCITT check value, packet round trip, single-bit corruption detection, loopback delivery
    MAVLink CRC-16/MCRF4XX check value, ODOMETRY and observer HEARTBEAT byte-exact against pymavlink, resync and noise immunity, exact heading map over 500 attitudes, Σ_enu = J Σ_ned Jᵀ, refusal of unknown/zero/singular covariances, posterior (P⁻¹+R⁻¹)⁻¹, watchdog fed by ODOMETRY, loopback with vehicle lock and gap counting, excess-delay estimate with the clock offset cancelled, latency compensation landing on the present state with E[NIS] = 5, stream mode for the relay (MAVLINK_LINK.md §10)
    UAV (6-DoF) OBSTACLE_DISTANCE byte-exact against pymavlink, ODOMETRY → 6-DoF measurement (frames, Euler-rate Jacobian, twist signs), SO(3) Exp/Shepperd/ZYX/slerp, exact CWNA Q composition, velocity Jacobian by finite differences, Monte-Carlo NEES/NIS = 6, latency compensation, attitude carried forward, voxel traversal properties, log-odds model, fan placement on a tilted vehicle, renderer projection and depth test (UAV_3D.md §6)
    RFB raw/copyrect/RRE decoding, bounds rejection, RGB565 scaling, device byte order
    pipeline unbiased velocity and yaw-rate estimates over a settled window against an exactly integrated unicycle, online noise identification, watchdog staleness, covariance shrinking on a pose fix, bounded dead-reckoning drift, map built from the estimated pose
    progress tracker Kalata's gain pairing, complex pole pair of modulus exactly √(1−α), Jury region, exact convergence on a ramp, noise rejection against the raw difference quotient, stall handling (docs/LINUX_ENVIRONMENT.md §6.1)

    Known issue, surfaced by the estimator test. The adaptive measurement-noise estimator of §3.2 collapses onto its positivity floor for the odometry channels. Mehra's identity assumes a white innovation sequence, but the wheel rates are low-passed before forward kinematics, so consecutive innovations are strongly correlated: mean(ν²) then measures the step-to-step change rather than the measurement noise, comes out below H P⁻ Hᵀ, and the difference is projected onto the floor. The odometry channel is thereafter treated as near-exact, its Kalman gain goes to one, the state follows odometry, the innovations stay small, and the collapse sustains itself — so the gyro contributes nothing to the fused yaw rate. The test prints the numbers (ratio 1.0000) and deliberately asserts nothing, since the only honest assertion would pin the defect in place. This pre-dates the removal of the controllers.

    The Android build itself (./gradlew assembleDebug) requires the Android SDK and NDK and is not run by this suite.
