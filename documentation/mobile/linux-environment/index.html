    Linux environment — Jetbot NanoOWL (Qt)¶

    Source

    Snapshot of docs/LINUX_ENVIRONMENT.md from TNG-Blue/JetbotNanoOWL at commit b6f46a4 (submodule Mobile/Android/JetbotNanoOWL/Qt). Regenerate with Scripts/mkdocs_hooks/snapshot_submodules.py after updating the submodule.

    An Ubuntu 22.04 guest that runs inside the app, without root: a login shell on a real terminal, apt, vendor repositories (ROS 2 Humble, VS Code, Chrome), the apps you install, and their windows on the phone's screen the way WSLg shows Linux windows on Windows.

    This document says how each piece works, why it is built that way, and derives the one estimator the feature uses. Everything described here is in apps/jetbotnanoowl/src/linux/ and is exercised by tests/tst_linux.cpp.

    2. The runtime, and why the app targets SDK 28¶

    An unrooted Android device gives an app no chroot(2) and no user namespaces. PRoot does the job in user space: it ptraces the guest and rewrites the path argument of every syscall, so /usr/bin/apt is served from <files>/linux/rootfs/usr/bin/apt. -0 reports uid 0, which is what lets a package manager believe it may write to /usr.

    W^X. Since Android 10 a file the app itself wrote can never be executed, unless the app targets SDK 28 or lower. PRoot, its loader and every program in the guest are files the app wrote, so the Qt app sets QT_ANDROID_TARGET_SDK_VERSION 28 — the same trade Termux makes.

    What it buys: the guest's programs, the runtime downloaded from Termux and the Syncthing binary are all files the app wrote, and all of them run.

    What it costs: Google Play will not accept the app (sideloading and GitHub releases only), and the whole app opts out of the Android 10+ behaviour changes.

    Two PRoots. The APK that CI builds carries its own, in lib/<abi>/ (the one directory Android executes from at any target): Termux's source with DroidDeck's patches, built from vendor/proot/ (§3.4; that directory is GPL and is the binary's corresponding source). It is used when it is there and starts — libproot.so --version is tried once per process — and the guest needs no download to run. The other is Termux's package as published, fetched onto the phone as before; it is used when the APK has none (a build made without the NDK step), when the app's own does not start, or when Linux → Home → PRoot build is set to Termux — the way back if the patched build misbehaves on some device.

    Installing it. PRootRuntime::install downloads the repository's dists/stable/main/binary-<arch>/Packages index, then proot, libtalloc and libandroid-shmem. Each .deb is checked against the SHA-256 that index publishes before anything is unpacked. A .deb is an ar archive whose data.tar.xz holds the files under the Termux prefix; those are relocated into files/runtime/ and everything else (docs, licences) is skipped. Installation is not complete until proot --version has run: a device that refuses to exec the files fails here, by name (execve: Permission denied is reported through a close-on-exec error pipe rather than as an anonymous exit status 127).

    The invocation:

    proot [--kill-on-exit] [--kernel-release=\Linux\Blue\<release>\…]   (patched PRoot only, §3.4)
      -r <rootfs> -0 [--link2symlink]
      -b /dev -b /proc -b /sys
      -b <files>/linux/tmp:/tmp  -b <files>/linux/shm:/dev/shm
      -b <shared folder>:/mnt/android            (when it exists: the phone's
                                                  Download, or <external>/shared)
      -b /proc/self/fd:/dev/fd
      -w /home/jetbot_owl
      /usr/bin/env -i <guest environment> /bin/sh -lc "<command>"
    • --kill-on-exit and --link2symlink are used when this PRoot advertises them in --help (Termux's build and upstream 5.4 do; Ubuntu's packaged 5.1 does not). --link2symlink is added only where link(2) fails in the guest's directory — Android's app storage — because dpkg relies on hard links.
    • env -i makes the guest's environment exactly the one listed below, instead of Android's ANDROID_ROOT and LD_LIBRARY_PATH.
    • /dev/std* are not bound. PRoot resolves such a binding to the terminal when it starts, after which ttyname(3) in the guest reports /proc/<pid>/fd/0 instead of /dev/pts/N and tmux, screen, ssh and gpg lose their terminal (found by the on-device self-test, see §8). /dev/fd/0..2 are the same descriptors.
    • Each session runs in its own process group (setsid), so stopping it reaches every tracee even without --kill-on-exit.

    3. The guest, and the bootstrap¶

    Ubuntu 22.04.5 LTS, only. It is the userspace of a Jetson on JetPack 6 and the release ROS 2 Humble is built for, so a package name resolves on the phone the way it does on the robot.

    ABI image SHA-256 (Canonical's SHA256SUMS)
    arm64-v8a ubuntu-base-22.04.5-base-arm64.tar.gz 075d4abd2817a5023ab0a82f5cb314c5ec0aa64a9c0b40fd3154ca3bfdae979f
    armeabi-v7a …-armhf.tar.gz fd77cb0659326b75c08ce06b6b8649d2e13ef9a704a8e9212fec32cb97d42add
    x86_64 …-amd64.tar.gz 242cd8898b33ea806ef5f13b1076ed7c76f9f989d18384452f7166692438ff1a

    The sequence: download (streamed to disk, hashed on the way) → verify → extract → configure. A mismatching digest stops before a single entry is written: a base image is code that will run with the app's authority, so checking after extraction would be no check at all.

    Extraction cannot escape the rootfs. An entry is refused when its normalised path climbs out (../x), or when an ancestor already on disk is a symlink resolving outside — the case a lexical check misses (evil -> /, then evil/etc/passwd). Hard-link targets are checked the same way. Symlink targets are written verbatim and never followed on the host: in the guest an absolute /lib/... is right, here it would point at Android. Directory modes are applied last, deepest first, so a read-only directory does not stop its own children being written; device nodes and FIFOs are skipped (PRoot serves Android's /dev). All of this is in tests/tst_linux.cpp (tarSlipIsRefused, tarGzipAndXzRoundTrip).

    Configuration writes what a base image lacks: resolv.conf (PRoot has no resolver of its own), hosts, hostname, the marker file — and then the identity pass below. The apt sources are left alone: the image already enables main, restricted, universe and multiverse on the right archive host.

    3.1 Who the guest says you are¶

    The prompt is jetbot_owl@Blue: an account jetbot_owl (first free uid ≥ 1000, kept stable across runs) whose home is the working directory of every guest process, and the hostname Blue. The pass runs before every guest process, behind a version marker (/.jetbot-identity, now 4), so a guest installed by an older build picks up what a newer one writes.

    • sudo and su are shims in /usr/local/bin. A real sudo is setuid, which PRoot cannot honour (there is no kernel transition to make), and every guest process already holds the authority it would grant. The shim parses sudo's options and runs the command; sudo -i gives a login shell.
    • /usr/sbin/policy-rc.d answers 101 ("action forbidden", invoke-rc.d(8)), as Ubuntu's container images do: there is no init system in the guest, so a package's maintainer script must not try to start its service. Without it, x11-common's postinst fails and leaves every X package unconfigured.
    • Android's supplementary groups get names in /etc/group (inet, everybody, u0_a368_cache, …, from android_filesystem_config.h and the per-user id scheme), or Ubuntu's bash.bashrc prints "cannot find name for group ID" in every shell.
    • ~/.bashrc and ~/.profile start from /etc/skel and are never overwritten.
    • The prompt shows the git branch in bash, in yellow after the path: jetbot_owl@Blue:~/Isaac_ROS-Jetbot_NanoOWL (master)#. It comes from /etc/profile.d/00-jetbot.sh, which ~/.bashrc sources last. The branch is read from .git/HEAD, walking up from $PWD; for a submodule or worktree, .git is a file naming the gitdir, relative to it. Bash reads these files itself, without running git, because the base image has no git and every exec under PRoot is a ptrace round trip on each prompt. A detached HEAD shows nothing, as git symbolic-ref would fail there. Do not use \u@\h in your own PS1: under -0 it gives root@localhost.

    3.2 Builds that do not get the app killed¶

    Every guest process is a child of this app, so to Android the guest's memory is the app's. A build that asks for more than the phone has gets the whole app killed. Each shell therefore starts with

    \[\text{jobs} = \operatorname{clamp}\!\left(\left\lfloor \frac{M - R}{J} \right\rfloor,\ 1,\ \text{cpus}\right),\qquad R = J = 1536\ \text{MB},\]

    where \(M\) is MemAvailable when the shell starts. For jobs > 1 this guarantees \(\text{jobs}\cdot J + R \le M\) (asserted over a sweep in buildLimits). The result goes to MAKEFLAGS and CMAKE_BUILD_PARALLEL_LEVEL, and ~/.colcon/defaults.yaml (written only if missing) sets colcon to one package at a time, so the two do not multiply. While anything runs, a foreground service tells Android the app is doing work the user is waiting for.

    3.3 What PRoot costs, and what was taken from DroidDeck¶

    DroidDeck runs Steam under the same PRoot and measured where its time goes (docs/development/proot-performance.md, tools/proot/PATCHES.md in that repository; figures quoted from it below are its own, taken on a Snapdragon 8 Elite Gen 5, and were not reproduced here). Its findings, in the terms this guest needs:

    • PRoot installs a seccomp filter, so only the system calls it has to act on stop the process: those that take a path, execve, brk, process and thread creation — and every call Android's app policy forbids, which arrives as a SIGSYS that PRoot answers. read, write, mmap, futex, ioctl run at native speed.
    • One stop is two wake-ups across cores, 15–60 µs against ~0.5 µs for the call itself, and one PRoot serves all its processes through a single thread.

    So the time PRoot adds to a job is

    \[T_\text{PRoot} = \sum_k n_k\, c_k ,\]

    \(n_k\) the stops of kind \(k\) the job makes and \(c_k\) what one costs. \(c_k\) belongs to the tracer: lowering it takes a different PRoot (below). \(n_k\) belongs to the guest, and that is what can be changed from here.

    Fewer stops: GLIBC_TUNABLES=glibc.pthread.rseq=0. glibc ≥ 2.35 registers a restartable sequence, rseq(2), once per process and once per thread. Android's policy does not allow rseq (it is absent from bionic's SYSCALLS.TXT; DroidDeck checked android16-release), so each registration is one SIGSYS stop that ends in ENOSYS. The tunable (glibc manual, POSIX Thread Tunables) makes glibc not ask. Counted with strace -f -c:

    Workload rseq calls with the tunable
    jammy's own glibc 2.35 running /bin/true, 10 times 10 0
    one process starting 16 threads 17 0
    sh running /bin/true 10 times 12 0

    \(n_\text{rseq}\) = processes + threads started, to 0. Nothing is lost on the phone: the registration never succeeded there.

    Not taken: glibc.malloc.top_pad. DroidDeck also sets glibc.malloc.top_pad=16777216, so the heap grows 16 MiB at a time and brk (two stops each under PRoot) is called less often. The saving is real and small — one g++ -O2 of a file using <regex>: 116 brk calls, 15 at 4 MiB, 12 at 16 MiB; apt-cache policy: 81 → 15 — about a hundred stops, a few milliseconds, per compiler run. The cost is not small. Setting the tunable switches off malloc's adaptive mmap threshold (malloc.c, do_set_top_pad: mp_.no_dyn_threshold = 1), the mechanism by which a large buffer that is freed and asked for again is reused from the heap instead of being mapped, zero-filled page by page and unmapped each time. A loop of malloc(n), memset, free:

    Buffer default top_pad 4 MiB top_pad 16 MiB
    1 MiB 19.9 µs 20.0 µs 23.2 µs
    8 MiB 293 µs 2869 µs 310 µs
    20 MiB 798 µs 7384 µs (400 turns: 408 mmap, 401 munmap; default: 9 and 2)
    24 MiB 1004 µs 9292 µs

    Any buffer larger than the pad (and under malloc's 32 MiB ceiling for the threshold) costs 9–10 times more per turn. A 1920 × 1080 float RGB image is 23.7 MiB, and images and point clouds allocated per frame are what this guest is for; a compiler saving a few milliseconds is not worth that. DroidDeck's workload (Steam, Wine) differs, and so does the answer.

    What Android hides. Three bindings, each added only where the phone needs it (LinuxEnvironment::hostBindings), so a desktop host gets none:

    Binding Why
    a stand-in for each /proc file the app cannot read Android's SELinux policy keeps /proc/stat (since Android 8), /proc/loadavg, /proc/version, /proc/vmstat and others from apps; which ones depends on the release, so each is tried, not assumed. procps gives up when a read fails: with those reads failing, jammy's uptime, ps and vmstat print /proc/uptime: <error> and top prints failed /proc/stat read (reproduced under PRoot); with the stand-ins all four run
    an empty directory over /sys/fs/selinux libselinux takes SELinux as enabled when statfs there answers SELINUX_MAGIC (init.c, verify_selinuxmnt). Android's does, and dpkg, tar and coreutils would label every file they create by a policy that is the phone's, not the guest's. The binding is checked on Android 14 (the directory lists empty in the guest); its effect on install time is not measured. It is what DroidDeck and Termux's proot-distro do
    /system/fonts at /usr/local/share/fonts/android a directory fontconfig scans by default: Android's Latin, Vietnamese, CJK and emoji fonts for guest applications, with nothing to download

    A stand-in is the kernel's own figure wherever a permitted system call gives it, and is written when a guest process starts (a snapshot, not a live file):

    File Content Source
    /proc/uptime seconds up; idle 0.00 sysinfo(2).uptime
    /proc/loadavg the three averages, 1/<processes> 0 sysinfo(2).loads / 2¹⁶, .procs
    /proc/version Linux version <release> (android@localhost) <version> uname(2)
    /proc/stat one line per CPU, btime, processes; counters 0 sysconf(_SC_NPROCESSORS_CONF), now − uptime

    /proc/sys/kernel/overflow{u,g}id 65534 include/linux/highuid.h

    A file the app can read is never replaced (substituteBinds, asserted).

    On Android 14 (the CI emulator, kernel 6.1.23-android14, Termux PRoot 5.1.107) the app could read none of the eight: the self-test logged all of them bound, and in the guest uptime then printed up 2 min, load average: 23.52, 11.61, 4.48, /proc/version the kernel's release, /sys/fs/selinux listed 0 entries and /usr/local/share/fonts/android 207 fonts. Before, uptime, ps, top and vmstat could not run in the guest on that release.

    apt. /etc/apt/apt.conf.d/99jetbot-proot sets APT::Sandbox::User "root": apt's unprivileged fetch user needs setgroups(2) and setresuid(2), which PRoot can only pretend to perform (as DroidDeck's 50droiddeck does).

    Already so, for the reasons DroidDeck gives.

    DroidDeck's finding Here

    Never pin the tracer away from its processes (a stop across clusters costs 42–61 µs, on one core 6 µs) no CPU affinity is set anywhere; the display session's nice +10 (§5.5) is inherited by its tracer and its processes alike
    Avoid exec in loops (0.4–0.8 ms each) the prompt reads the git branch in bash itself (§3.1)

    Taken later: the patched PRoot itself — §3.4. What is still not taken:

    DroidDeck Why not here

    3.4 The patched PRoot¶

    The stops of §3.3 that the guest cannot avoid are decided by the tracer: which calls its seccomp filter stops (\(n_k\)), and what one stop costs (\(c_k\)). vendor/proot/ builds Termux's PRoot (the source of its 5.1.107 package) with DroidDeck's 28 patches, unchanged; vendor/proot/README.md says what each group does and where each file comes from. For this guest — -0, --link2symlink — the ones that count:

    Patch Before After

    0005 a stop on exit for every stopped call none where nothing is rewritten on exit

The stock PRoot is never given the option.

    4. The terminal¶

    A pipe is not a terminal: behind one, isatty() is 0, so apt prints no progress, sh offers no prompt, nano and htop refuse to start, and Ctrl+C cannot be delivered. The shell gets a real pseudo-terminal:

    posix_openpt → grantpt → unlockpt → ptsname_r → TIOCSWINSZ
fork
  child:  setsid · open(slave) · TIOCSCTTY · dup2 → 0,1,2 · close the rest · execve(proot …)
  parent: master fd → QSocketNotifier on the GUI thread

    The command is if command -v bash …; then exec bash -l; fi; exec sh -l, so the PTY's child is the login shell itself. Resizing sends TIOCSWINSZ (the kernel raises SIGWINCH and curses programs reflow); closing sends SIGHUP to the whole process group, so a package manager caught mid-install does not survive as an orphan holding dpkg's lock.

    Flow control is free here. The master is read only when the GUI event loop gets to it, and each read is bounded (64 KiB). A compiler that writes faster than the emulator parses fills the kernel's PTY buffer and blocks in write(2): the build slows to the speed of the screen, nothing is dropped and nothing queues in this process. (The Kotlin terminal needed an explicit bounded queue because its emulator ran in a separate WebView process.)

    The terminal also exports the shared desktop's DISPLAY and session bus, and starts that desktop in the background, so a graphical program typed at the prompt has a screen; the monitor button opens it.

    5. Windows on the phone — no display protocol¶

    WSLg needs RDP because its guest is a virtual machine sharing no memory with the host. This guest is a process tree whose /tmp is a directory the app owns, so:

    • Xvfb -fbdir /tmp/xfb-N keeps its screen in a memory-mapped XWD file, which LinuxSurfaceView maps directly (XSurfaceSession in the core);
    • its socket /tmp/.X11-unix/XN is a local path here too, and the server is started -nolisten tcp, so there is no port for anything to reach;
    • DAMAGE reports each rectangle the server draws, after it has drawn it; the frame thread copies only that into its image, and only that is sent to the GPU (§5.7);
    • the pointer is drawn by the app, where the finger sent it, from the picture the server gives through XFIXES (§5.7);
    • XTEST carries taps and keys. Input uses a second X connection, owned by an input thread (XInputQueue), so each connection has exactly one owner and the GUI thread only queues what the person did — it never waits on the guest (§5.5).

    Frames arrive when the guest draws and never otherwise: there is no rate to choose, so no pacing loop is needed on this path (the M/G/1 pacer in the core, frame_pacer.h, serves request-driven protocols such as RFB).

    One desktop for every app. Each app opens on the shared desktop (with a desktop environment installed, that one: §5.4), and an openbox rule — added to the stock rc.xml, so its keys and menus stay — maximises every type="normal" window, while dialogs keep the size they ask for (Alt+Tab, on the key row, switches between apps). One X server is one server's memory, and there is no limit on how many apps run: the earlier "display per app" mode needed a server each and capped them at eight, which is why it was removed. A LinuxSurfaceView maps frames only while it is visible (ItemVisibleHasChanged), and the app keeps at most one display page in its stack. The session script waits on the X socket by elapsed time, loads the X resources below, starts a session bus at a chosen address and the window manager, then waits on the server; its log (/tmp/xsession-N.log) is one tap away in the viewer.

    Gestures (shared with the VNC viewer, TouchPointer): a tap is a left click, a long press a right click, two fingers scroll, a two-finger tap toggles the keyboard. On the Linux display one finger swiping up or down scrolls, with a fling, and sideways drags with the left button (§5.3.1); the bar's swipe button turns that off, one finger then being the left button as in the VNC viewer. The on-screen touchpad (§5.3) points without covering the target. A key row supplies Esc, Tab, arrows, F-keys and sticky Ctrl, Alt, Shift and Super.

    Geometry: a physical panel. The guest screen is described the way a phone's is — aspect \(a{:}b = 20{:}9\), diagonal \(D\) (default 6.8 in) and density \(\rho\) (default 400 dpi) — not by a resolution. Its sides follow by Pythagoras:

    \[W = \rho\,D\,\frac{a}{\sqrt{a^2+b^2}},\qquad H = \rho\,D\,\frac{b}{\sqrt{a^2+b^2}}\qquad(\text{rounded to even})\]

    so 6.8 in at 400 dpi is 2480 × 1116 (and \(\sqrt{W^2+H^2}/\rho = 6.80\) in back). Xvfb runs at that size with -dpi 400.

    Scaling every app. X toolkits assume 96 dpi and lay out in their own pixels; on a phone each is scaled by

    \[s = \frac{\rho}{160}.\]

    160 dpi is where Android's density-independent pixel is one pixel, and it is the CSS reference pixel — the visual angle of one pixel at 96 dpi from 28 in, 0.0213° (CSS Values and Units §5.2) — for a phone read at 16.8 in: \(96 \cdot 28 / 16.8 = 160\). Apps then lay out on

    \[\frac{W}{s} \times \frac{H}{s} = 160\,D\,\frac{a}{\sqrt{a^2+b^2}} \times 160\,D\,\frac{b}{\sqrt{a^2+b^2}} = 992 \times 446 \text{ (6.8 in)},\]

    which does not depend on \(\rho\): density buys sharpness, the diagonal buys room. \(s\) reaches each toolkit the way it reads it:

    toolkit setting (s = 2.5)
    Xft, Chromium/Electron (VS Code), Pango (openbox), Tk X resource Xft.dpi: 240 (= 96 s), via xrdb -nocpp -merge
    GTK ¾ GDK_SCALE=2 (integer) and GDK_DPI_SCALE=1.25, product = s
    Qt ⅚ QT_SCALE_FACTOR=2.5, QT_FONT_DPI=96 so Xft.dpi does not scale text twice, automatic scaling off

    The Linux page's Display tab picks \(D\) and \(\rho\); a change applies when the desktop next starts (Restart desktop to apply).

    The unix-socket limit. PRoot hands the X server the host path of its socket, which must fit sockaddr_un.sun_path (108 bytes). On a phone it is about 72; a session refuses to start, with a message saying why, when the app's data directory makes it longer.

    5.1 Closing the app closes the guest¶

    Every process the app starts is a process-group leader (setsid), recorded until reaped. Closing the app ends all of them in one pass — SIGTERM to every group, one shared grace period of 0.8 s, then SIGKILL — and PRoot's --kill-on-exit takes the guest processes it traces with it, X servers and apps included, even those that left their group. Three paths lead there:

    How the app goes What runs
    Back out of the last page, or the app quits QCoreApplication::aboutToQuit → linuxenv::shutdownAllGuests()
    Swiped away from Recents LinuxGuestService.onTaskRemoved → the same, through JNI; then the process ends, since the foreground service would otherwise keep it, and the guest, alive (stopWithTask="false" so that callback is delivered)
    Killed by Android outright (no callback) on the next start, killStrays() stops any PRoot of this app's user that is not a child of the new process

    The terminal's shells go the same way: they are groups like any other.

    5.2 The keyboard held sideways¶

    In landscape an IME shows a full-screen "extract" editor (an empty text box and Done) unless the editor sets IME_FLAG_NO_EXTRACT_UI / IME_FLAG_NO_FULLSCREEN, which Qt 6.8 never does. Qt writes its options into its QtEditText on every show, then restarts the input 15 ms later. LinuxPlatform.installImeFix adds the two flags back when focus moves to that editor and after the layout pass every show requests; if the layout pass came after the restart (a 60 Hz frame is 16.7 ms), it restarts the input once more so the IME reads the flags. The keyboard then takes only its own height, for every text field in the app.

    5.3 The on-screen touchpad¶

    A finger on the picture is the pointer, so it hides what it points at. The bar's touchpad button shows a see-through touchpad over the picture instead (VirtualTouchpad + LinuxDisplayPage.qml): it moves the pointer relatively, like a laptop's, while the picture stays visible through it. Drag its top strip to move it, its corner to size it; the strip's dot steps the fill through three opacities, ✕ hides it. Shown or not, where, how large and how see-through are kept in SettingsStore for the next app. Its position is stored as a fraction \(f\in[0,1]\) of the room beside it, \(x = m + f\,(W_{view} - w - 2m)\), so it is on screen at any size and after a rotation by construction.

    on the pad sends
    one finger moving pointer motion
    tap left click; two taps a double click
    tap, then touch again within 0.3 s left button held while the finger moves (drag)
    two fingers moving wheel steps, the content following the fingers
    two- / three-finger tap right / middle click
    L, M, R that button, held while held — one finger can hold L while another drags

    The chain (libs/jetbot_core/include/jetbot/display/touchpad.h) is the one this code base uses for a sensor, with the X server's pointer as the actuator:

    touch samples (p_k, t_k) → speed s_k = |Δp_k|/Δt_k → ZOH low-pass → gain G(v̂)
   → integrator projected onto the screen → XTEST motion (absolute)
   ↑                                                     │
   └──────── XQueryPointer at each stroke (feedback) ────┘

    Speed estimate. The panel's samples arrive at an irregular \(\Delta t_k\), and \(s_k\) carries the position and time quantisation of each sample. It is low-passed by \(\tau\dot{\hat v} = s - \hat v\), discretised exactly for a piecewise-constant input (zero-order hold):

    \[\hat v_k = \hat v_{k-1} + a_k\,(s_k - \hat v_{k-1}),\qquad a_k = 1 - e^{-\Delta t_k/\tau},\quad \tau = 30\ \text{ms}.\]

    Because \((1-a(\Delta t/2))^2 = e^{-\Delta t/\tau} = 1 - a(\Delta t)\), two steps of \(\Delta t/2\) equal one of \(\Delta t\): the estimate does not depend on the panel's touch rate (60, 120 or 240 Hz). And \(0 < a_k < 1\) for every \(\Delta t_k > 0\), so \(\hat v_k\) is a convex combination of \(\hat v_{k-1}\) and \(s_k\) — no overshoot, unity DC gain, stable at any sample time.

    Gain schedule (the control–display gain of the pointing literature [11]):

    \[G(\hat v) = g_{lo} + (g_{hi} - g_{lo})\,\mathrm{clamp}\!\left(\frac{\hat v - v_{lo}}{v_{hi} - v_{lo}},\,0,\,1\right)\]

    with \(g_{lo} = 1\), \(g_{hi} = 3.5\), \(v_{lo} = 60\) dp/s, \(v_{hi} = 900\) dp/s. \(G\) is continuous and non-decreasing, so a faster stroke never moves the cursor less; \(G \ge g_{lo} > 0\) is a scalar, so the cursor moves in exactly the finger's direction. \(g_{lo} = 1\) is the one value fixed by geometry: slow motion moves the cursor across the picture as far as the finger moved on the pad. The other three are tuning, inside the range [11] measured.

    Integrator and actuator. With \(c\) the guest pixels per view pixel,

    \[q_k = P_{[0,W-1]\times[0,H-1]}\big(q_{k-1} + c\,G(\hat v_k)\,\Delta p_k\big),\qquad \text{sent: } \mathrm{round}(q_k).\]

    The projection onto a box is non-expansive [12], so the screen edge stops the cursor as a real edge does and motion back leaves it at once, with no hidden overshoot stored behind it. Rounding only the output keeps the pointer within 0.5 px of the exact integral at every step: sub-pixel motion is never lost and never drifts.

    Feedback. An XTEST motion puts the pointer exactly where it is sent, so the only error the integrator can accumulate is a move it did not make — a warp by the guest, or a finger on the picture. At the first finger of each stroke it reads the pointer back (XQueryPointer, one round trip) and integrates from there.

    Gestures. Motion is always the difference of two samples taken with the same fingers down: when one lands or lifts the reference is taken again, so a change of contact count cannot make the pointer jump, and a stroke that had two fingers moves the pointer no more until all are up. A tap is shorter than 200 ms and travelled less than 12 dp; two-finger travel of 40 dp is one wheel step.

    The cursor ring. While the touchpad is shown, a ring marks where it put the pointer, brighter for a moment after each move. The pointer itself is drawn by the app at the same place (§5.7); the ring is what stays visible on a picture the pointer's own colours disappear into.

    Checked in jetbot_core_tests (section on-screen touchpad): the ZOH semigroup identity, rate independence at 60 vs 240 Hz, no overshoot on a step, monotonicity and continuity of \(G\), the finger's direction kept, the 0.5 px rounding bound over 5000 sub-pixel steps, the edge, and each gesture.

    5.3.1 Swipe scrolling¶

    On a phone a finger moving up or down scrolls, and a quick release flings the page on. The guest knows only a mouse, whose wheel moves in whole clicks (X buttons 4 and 5), so the swipe is turned into clicks (jetbot::display::TouchScroller, used by TouchPointer):

    touch samples (t_k, y_k)
  -> intent: scroll or drag, decided once past the slop
  -> travel dy_k = y_k - y_{k-1}
  -> release velocity: least-squares slope over the last 100 ms
  -> fling: tau v' = -v, integrated exactly between ticks
  -> sigma-delta quantiser: travel -> whole wheel steps
  -> XTEST buttons 4 / 5

    Intent. Nothing is pressed while the finger stays within the slop \(s\) (10 dp) of where it landed. Past it, the displacement \(d\) decides once: scroll if \(|d_y| > |d_x|\) (a cone of ±45° about the vertical), otherwise a drag. A drag presses the left button where the finger landed and follows it in every direction from then on. A finger lifted inside the slop is a click there, and one held still is a right click. Travel is measured from the point of decision, so the slop is never a jump.

    Quantiser. With step \(h\) (40 dp of travel per click) and travel \(u_k\):

    \[e_k = e_{k-1} + u_k,\qquad n_k = \operatorname{trunc}(e_k/h),\qquad e_k \leftarrow e_k - n_k h .\]

    After every sample \(|e_k| < h\), so the clicks sent never lag the finger by a whole step and never lead it. When the gesture ends, \(\operatorname{round}(e/h)\) more are sent. Writing \(T = \sum u_k\) and \(N = \sum n_k\), \(T = Nh + e\) with \(N\) an integer, so \(N + \operatorname{round}(e/h) = \operatorname{round}(T/h)\): the gesture as a whole sends the nearest whole number of clicks, within \(h/2\), and nothing drifts however long it lasts. Content follows the finger: travel down the screen is wheel up.

    Release velocity. Over the samples of the last \(W\) = 100 ms,

    \[\hat v = \frac{\sum (t_i - \bar t)(y_i - \bar y)}{\sum (t_i - \bar t)^2},\]

    the least-squares slope. For \(y_i = y_0 + v t_i + \varepsilon_i\) with zero-mean, uncorrelated \(\varepsilon_i\) of equal variance, it is the Gauss–Markov estimate: unbiased, and of least variance among linear unbiased estimates. It is exact for a finger moving at constant speed whatever the sample times are. It reads the speed at release, not the stroke's average. A finger that stopped \(W\) before lifting leaves fewer than two samples, so \(\hat v = 0\). \(|\hat v|\) is clamped to 6000 dp/s. Below 150 dp/s, or when the whole fling would travel less than \(h/2\), the page simply stops.

    Fling. Friction proportional to speed, \(\tau \dot v = -v\):

    \[v(t) = v_0 e^{-t/\tau},\qquad y(t) = v_0\tau\,(1 - e^{-t/\tau}).\]

    Each tick (16 ms, timed by the clock, not assumed) moves along this solution exactly: \(\Delta y = v\tau(1 - e^{-\Delta t/\tau})\) and \(v \leftarrow v e^{-\Delta t/\tau}\). Two ticks of \(\Delta t/2\) equal one of \(\Delta t\), so a late or missed tick costs no distance. The travel still to come is exactly \(v\tau\). The fling stops once that is under \(h/2\), which could not round to another click. \(\tau = 0.5\) s is UIScrollView's normal deceleration: 0.998 of the speed kept per millisecond gives \(\tau = -1\,\text{ms}/\ln 0.998 = 0.4995\) s.

    So with \(D\) the finger's travel, the clicks sent add up to within one step of \(D + v_0\tau\), the place an unquantised, never-ending fling would reach: at most \(h/2\) from the rounding and \(h/2\) from the stop. A finger landing during a fling stops it at once (what is left is rounded off), and that touch is not a click.

    Two fingers scroll through the same chain, so they fling too.

    Checked in jetbot_core_tests (section swipe scrolling): the intent cone; the quantiser's \(|e| < h\) invariant and \(\operatorname{round}(T/h)\) total over 2000 random samples in both directions; the exact LSQ slope at irregular sample times; release speed rather than stroke average; no bias under noise; the fling's exact solution at 60 vs 7 ticks and \(y + v\tau = v_0\tau\); the one-step end bound; a caught fling. tst_frontend (touchSwipeScroll) drives TouchPointer with touch events: a tap's click, a swipe's clicks at the landing point with no button, a sideways drag, a fling and its catch, and the VNC behaviour with swipe scrolling off.

    5.4 A desktop environment: the panel and the running apps¶

    With the window manager alone (openbox, from the Desktop base bundle) every app is maximised and the desktop has no panel, so only the app in front is visible. A desktop environment installed in the guest — GNOME (ubuntu-desktop-minimal, or gnome-session / ubuntu-session), Xfce, MATE, ... — brings its own window manager, panel and list of running apps, and the desktop runs it instead.

    When. Only the desktop starts it. An app opened from the app list gets the window manager alone and fills the screen by itself, with no shell around it and none of the desktop's daemons, so it starts sooner and costs less. All apps share the one X server, so opening the desktop later (the app list's desktop button) starts the desktop environment on that display, around the apps already open. The window manager steps aside first (openbox --exit, then its process by name if it is still there after a second). The desktop's window manager takes over the open windows, and its panel and dock list them. An app opened from the list while the desktop runs opens on it (DisplaySession::ensureRunning(…, withDesktop), buildDesktopScript).

    Scale, around open apps. Those apps were started with GDK_SCALE and GDK_DPI_SCALE in their environment, and that cannot change. GTK with its window scale fixed by GDK_SCALE takes the font DPI from XSETTINGS' Xft/DPI (gdk/x11/xsettings-client.c, GTK 3.24, which reads Gdk/UnscaledDPI only when the scale is not fixed). gsd-xsettings multiplies Xft/DPI by the window scale, so their text would grow by that factor; a phone showed exactly that. So a desktop started around open apps does three things:

    • it runs without the XSettings daemon (left out of the required components and hidden from autostart);
    • it keeps GDK_* for every app, including those the shell starts;
    • it gives the shell a text factor of 1, since the shell has GDK_DPI_SCALE in its environment already.

    Text is then the same size before and after, and as large as on a desktop started first (\(1 \times\) GDK_DPI_SCALE against text-scaling-factor = GDK_DPI_SCALE). What is lost is XSETTINGS itself: a theme or font changed in GNOME's settings reaches running GTK apps only after Restart desktop.

    Which. The app reads /usr/share/xsessions/*.desktop from the rootfs, the list a display manager (GDM, LightDM) shows on its login screen, so any desktop installed with apt appears without the app knowing it by name (scanXSessions). An entry is kept when its TryExec= is installed, it is not only a window manager, and no earlier entry has the same Exec= and DesktopNames= ("Ubuntu on Xorg" is "Ubuntu" on an X server, which is all there is here). The Linux page's Display tab picks one: Automatic (Ubuntu's GNOME first, whose dock lists running apps, then other GNOME sessions, then by name), Window manager only, or a session by name. A change applies when the desktop next starts.

    How. As a display manager does: XDG_CURRENT_DESKTOP from DesktopNames=, XDG_SESSION_DESKTOP and DESKTOP_SESSION from the file name, then Exec= run by sh. PRoot has no systemd, which GNOME assumes, so the script also:

    5.5 A busy guest never freezes the app or the phone¶

    What happened. With a desktop running, the app — sometimes the phone — stopped responding until it was restarted. Three causes, each in the code:

    1. The GUI thread waited on the X server. Taps, keys and the touchpad's pointer read-back went over a blocking socket from the GUI thread, with no deadline. The guest's X server answers only when PRoot schedules it, and a desktop starting or compositing in software can keep it from answering for seconds; a guest stopped under memory pressure never answers. Android shows App isn't responding after 5 s of a blocked input dispatch.
    2. The GUI thread joined a thread that waited on the X server. Leaving the display page (or the page going under another) stops the frame thread with join(). That thread could be inside the X handshake or a reply wait, again with no deadline, so the join never returned.
    3. The GUI thread stopped dead sessions. The session list is polled from the GUI thread every 4 s; finding a session whose X server had died, it stopped its process groups right there, up to 1.5 s of grace for each group.

    And around them, the desktop itself competed with Android's UI on equal terms for CPU and memory.

    What is done now.

    Bound Where Value and why
    Deadline on every X call XControlLink (core) socket non-blocking; each connect, send and reply waits in poll() for at most the link's timeout, then fails and closes the link (a reply cut short leaves the stream at an unknown position). Frame thread 5 s, input thread 1 s, library default 3 s
    Abort from another thread XControlLink::abort a byte on a self-pipe that every wait polls beside the socket: the owner's current or next wait fails at once. Not shutdown(2) on the socket, whose descriptor number may be closed and reused by then
    Input off the GUI thread XInputQueue (core) the GUI thread queues each action and returns; one worker owns the connection. At most 512 actions wait (4 s of a 120 Hz finger), dropping the oldest so a release is never lost behind its press; a failed connection is retried with backoff 50 ms → 1 s, and actions that waited through it are dropped rather than replayed as a late burst
    Stop without waiting on X LinuxSurfaceView::stop aborts whatever the frame thread holds, every 2 ms until it has returned, then joins: bounded by one system call
    Reconnect, not die frame thread a connection that times out (a guest too busy to answer) is opened again within the same 20 s window as the first time; the picture stays as it was meanwhile
    Repaints coalesced LinuxSurfaceView::requestUpdate at most one update() queued to the GUI thread; a guest drawing faster than the screen refreshes no longer fills the event queue
    Dead sessions stopped elsewhere DisplayManager::reapDeadLocked / stopDetached the poll only takes them off the list; a detached thread stops their groups
    CPU spawn of every display process nice +10, set between fork and exec so PRoot and the whole guest inherit it. CFS weights (kernel/sched/core.c, sched_prio_to_weight): nice 0 → 1024, nice 10 → 110, nice −10 → 9548. On a contended core the guest gets 110/(110+1024) = 9.7 % against a nice-0 thread and 110/(110+9548) = 1.1 % against Android's display-priority threads; an idle core it still gets whole
    Memory same, except the X server oom_score_adj 800 (Android's SERVICE_B_ADJ): the kernel OOM killer takes the guest desktop before this app (0 in front, 200 as a foreground service), the launcher (600) and the previous app (700). A killed desktop is restarted from the app (the display stopped), a phone thrashing until the OOM killer reaches the app is not. Android's lmkd kills whole apps by the app's own score; this governs the kernel's last resort.     5.6 Sound¶

    What a guest program plays is heard on the phone. DroidDeck does this with a PulseAudio daemon on the Android side, built for Android, whose sink writes to AAudio; the guest connects to its socket. The same shape here, with the daemon one step over: it is Ubuntu's own pulseaudio, in the guest (the Sound bundle: pulseaudio, pulseaudio-utils, libasound2-plugins), and its sink is a pipe the app reads and plays through AAudio. linux/guestaudio.h has the design; in short:

    guest program ─ PulseAudio protocol ─▶ pulseaudio      (a guest process of its own PRoot)
                                          │ module-pipe-sink, s16le · 2 ch · 48 kHz
                                          ▼
                             <files>/linux/tmp/jetbot-audio/out.fifo
                                          │ read when the ring has room
                                          ▼
                           ring ──▶ AAudio's callback ──▶ speaker

    One clock. The pipe sink has no timer: it renders when the pipe has room. The reader takes frames only as AAudio's callback consumes them, so the speaker's clock paces the whole chain and there is nothing to resample or drift against. Measured with PulseAudio 16.1 and a 3 s tone:

    The pipe's reader The player finishes after
    never reads still waiting at 8 s
    reads at 48 kHz 3.03 s
    reads as fast as it can 0.21 s

    Latency, from the sink to the speaker's driver, in frames at \(f_s\) = 48 kHz:

    \[L = T + \frac{C}{4} + D\]
    Term What Value
    \(T\) the ring's target fill 960 frames (20 ms) to start
    \(C/4\) the pipe's capacity, at 4 bytes a frame 1024 frames (21.3 ms)
    \(D\) AAudio's buffer: two bursts, low-latency mode typically 384 frames (8 ms)

    about 49 ms. Two of the three are choices:

    • The pipe. Linux gives a pipe 64 KiB — 341 ms of sound that no latency figure reports. The reader shrinks it to one page with F_SETPIPE_SZ. Measured: the 3 s tone came out as 3.36 s of frames through the 64 KiB pipe and as 3.04 s through a 4 KiB one. (Where pages are 16 KiB the term is 85 ms; the app shows the figure it computes from what the kernel granted.)
    • The target. PulseAudio writes the pipe one 1024-frame block at a time and only into an empty pipe, so each time the pipe runs out the ring alone feeds the speaker until the daemon has woken and rendered the next block: \(T \ge B + \delta f_s\), with \(B\) the device's burst and \(\delta\) that wake-up time. \(\delta\) is not known beforehand, so \(T\) starts at 20 ms (rides out \(\delta \le 15\) ms) and is raised by 5 ms each time the ring runs dry in the middle of a sound, up to 200 ms: at most 36 such gaps, ever, and none once \(T\) covers the device's \(\delta\). A gap counts only if it is at most 100 ms and the stream flows on for 100 ms after it — the end of a sound is also a gap followed by a tail, and the first version counted it (one "underrun" at 1065 ms of every 1 s tone, which would have raised \(T\) after every sound).

    Kept out of the desktop's way. The daemon is started by the app as a guest process of its own PRoot — its own tracer, not the desktop's (§3.3) — and at the app's priority, not the nice +10 of a display's processes (§5.5). Its audio thread makes poll, read, write and futex calls, which PRoot does not stop (§3.4).

    It runs while a display is open, the guest has PulseAudio and Display → Sound is on; that switch also silences it at once without stopping the stream. Clients need no setting: /etc/pulse/client.conf.d/00-jetbot.conf names the socket, and where libasound2-plugins is installed /etc/asound.conf (written only if absent) sends ALSA programs through PulseAudio.

    Checked. tst_linux: the ring from two threads; the device as the only clock (a writer offering a second of frames at once is held to a second, every frame comes out once and in order, and what is in flight never exceeds \(T + C/4\)); a hole in a stream raises \(T\) by one step and a sound's end does not; and with a real PulseAudio, a 440 Hz tone played by paplay arrives at the device with its length (±200 frames), its power at 440 Hz within 2 % of \(A^2/4\), less than 10⁻⁴ of that at 1 kHz, and its peak sample for sample. In CI the same tone is played by a guest program, after apt installed PulseAudio in the guest under the patched PRoot (run 249: target 960 frames, pipe 4096 bytes, latency 49.3 ms, underruns 0). The Android self-test opens the AAudio output and requires it to ask for frames at its rate; on the Android 14 emulator it reported AAudio 48000 Hz, burst 960, buffer 1920, not low latency; asked for 29120 frames in 600 ms (28800 expected).

    The figure depends on the device. \(D\) and the floor of \(T\) are the device's: an emulator has no low-latency mixer and gave a burst of 960 frames, so there \(D\) = 1920 frames (40 ms), \(T\) starts at two bursts (40 ms) and \(L\) ≈ 101 ms. A phone's low-latency path gives bursts of 96–240 frames, which is where the 49 ms above comes from. The app shows the figure for the device it runs on (Display → Sound); it has not been read on a real phone yet.

    5.7 From the finger to the picture¶

    What a finger does is seen after

    \[L = L_{touch} + L_{guest} + L_{copy} + L_{gpu} + L_{panel}\]

    — the event reaching the view, the guest drawing its answer, the app copying what changed, sending it to the GPU, and the panel showing the frame. The guest's share is the guest's (§3.3, §3.4). DroidDeck's sessions were read for the rest (InputSurfaceView.kt: unbuffered touch; PerfMode.kt: the display mode; its pointer layer); what was taken, what was found on the way, and what each is worth:

    1. The pointer does not wait for the guest. Xvfb draws its pointer straight into the framebuffer and reports no DAMAGE for it, so a reader of the framebuffer shows the pointer where, and as, it was when something else last drew there. The app now takes it over: XFIXES HideCursor removes the server's from the picture, GetCursorImage gives its picture and hot spot, CursorNotify says when it changes (an I-beam over text, an arrow elsewhere), and GuestPointerItem draws that picture at the position the view itself sent with XTEST. Moving it changes one item's position: no pixel of the guest's screen is read or uploaded, and \(L_{guest} = L_{copy} = 0\) for the pointer — it is at the finger's position in the frame that handles the finger's event.

    2. No change is lost. The reader asked DAMAGE for bounding boxes: the server then sends an event only when the box of what it has accumulated grows, and DamageSubtract empties the accumulation. With \(B\) the box last reported:

    reader                         server
reads the event for B
sends DamageSubtract ─────┐
copies B                  │    draws d inside B   (B does not grow: no event)
                          └──▶ runs DamageSubtract (d is forgotten)

    The copy was taken before \(d\) and no event will ever name \(d\): the last character typed stays missing until something else is drawn there. It now asks for raw rectangles, where the argument is short. The server is one thread, and the extension reports after the operation (DamageSetReportAfterOp): the event for a drawing \(d\) is written after \(d\) is in the framebuffer. The reader copies a box containing \(d\)'s rectangle after reading that event, hence after \(d\). So every drawing is covered by a copy made after it, and when the server stops drawing, the reader's picture is the server's. The price is one 32-byte event per drawing request.

    tests/tst_guestdisplay.cpp is where this was found: an X client rewrites a counter in place as fast as it can, stops, and the window is compared with the server's framebuffer, pixel for pixel, twelve times.

    rounds of 12 that left the window wrong
    bounding boxes, the server's pointer in the picture 7 to 10
    raw rectangles, the server's pointer in the picture 1 to 2 (the pointer's shape under a new window)
    raw rectangles, the pointer drawn by the app 0, in each of 9 runs

    3. Only what changed goes to the GPU. Each frame used to make a new texture from the whole image: \(4WH\) bytes, 11.07 MB at 2480 × 1116, whatever had changed. GuestTexture is one texture for the screen's life, and each changed box is uploaded into its place (QRhiTextureSubresourceUploadDescription with a destination): \(4wh\) bytes. Between two frames the boxes are kept apart by DirtyRegion rather than merged — a text cursor and a clock in the far corner are 3 900 pixels, and their bounding box is most of the screen — under three properties its test checks over 300 random sequences: every pixel added is inside a kept box (cover), there are at most 8 boxes (few), and their area never exceeds the screen's (bound: past it, one box of the whole screen replaces them). On this machine, where Mesa draws on the CPU and an upload is a copy:

    a frame at 2480 × 1116 bytes time
    as it was: a new texture from the whole image 11.07 MB 6.3 – 7.4 ms
    the whole screen, as a patch 11.07 MB 1.2 – 1.8 ms
    a text cursor's 6 × 50 box 1.2 kB 0.2 – 0.35 ms

    The bytes hold on any device; the times are this machine's. (With Qt Quick's software renderer there is no texture to patch, and whole images are sent as before.)

    4. Touch is not held for the next frame, twice. Android hands a window its movement samples once per frame, and Qt Quick stores movements and delivers them merged when the next frame is prepared (QQuickDeliveryAgentPrivate::compressTouchEvent). Each is a wait for the next multiple of the frame period \(T\): for a sample arriving a time \(u\) after the last, \(T - u\); with \(u\) uniform on \([0, T)\) the mean is \(T/2\) and the worst \(T\) — 8.3 and 16.7 ms at 60 Hz, each. That is right when Qt Quick draws what moves; here the guest does, and it cannot start before the view has the event. While a guest display is open the window asks for requestUnbufferedDispatch(SOURCE_CLASS_POINTER) (Android 11+), and the app sets QML_NO_TOUCH_COMPRESSION at start. tests/tst_touchdelivery.cpp: five movements between two frames reach an item as none and then one, as Qt ships; as five, each in the call that made it, as the app runs.

    5. The panel's fastest mode. Every step from a finished picture to the panel is taken once per frame, so each costs \(T\), or \(T/2\) on average where the picture arrives at any moment of the frame: all of it halves from 60 to 120 Hz. While a guest display is open the window asks for the mode of the size in use with the highest refresh rate (preferredDisplayModeId); the system may refuse (battery saver, heat). The session report (the display's ⓘ) shows the rate in use and what the phone answered.

    6. Fewer pixels. The guest draws on the CPU, and a full repaint is \(4WH\) bytes for it to write and for the app to copy; with the panel's size fixed, \(WH \propto \text{dpi}^2\). 240 dpi is \((400/240)^2 = 2.8\) times fewer pixels than 400. Display → Pixels shows the count for the chosen size and density.

    Not measured: any of this on a phone. The emulator self-test shows only that the two requests of (4) and (5) are made on a real window and answered — on the Android 14 emulator (CI run 250): display pacing: touch as it arrives; display 60 Hz, the fastest of 1 mode. The same run passed the display tests above through Mesa's OpenGL on the CI machine, with no test skipped.

    7. The one estimator: transfer progress¶

    A byte counter sampled four times a second gives a difference quotient that swings by tens of percent; an ETA computed from it is unusable. Model the transfer as constant rate disturbed by white acceleration:

    \[x = \begin{bmatrix} b \\ \dot b\end{bmatrix},\quad F = \begin{bmatrix} 1 & T_s \\ 0 & 1\end{bmatrix},\quad H = \begin{bmatrix}1 & 0\end{bmatrix}.\]

    The Kalman gain of this pair converges to a constant; running the filter at that limit is the alpha-beta tracker (libs/jetbot_core/src/alpha_beta.cpp):

    \[b^- = b + \dot b\,T_s,\quad r = b_\text{meas} - b^-,\quad b \leftarrow b^- + \alpha r,\quad \dot b \leftarrow \dot b + \tfrac{\beta}{T_s} r.\]

    With a constant true rate the error \(e = [e_b,\ T_s e_{\dot b}]^\top\) obeys \(e_k = A e_{k-1}\) with

    \[A = \begin{bmatrix} 1-\alpha & 1-\alpha \\ -\beta & 1-\beta \end{bmatrix},\qquad z^2 - (2-\alpha-\beta)z + (1-\alpha) = 0. \tag{P}\]

    The Jury test gives stability iff \(0 < \alpha < 2\) and \(0 < \beta < 4 - 2\alpha\). With the pairing the constant-velocity Kalman filter converges to (Kalata 1984),

    \[\beta = \frac{\alpha^2}{2-\alpha}, \tag{K}\]

    the discriminant of (P) is \(-4\alpha^2(1-\alpha)/(2-\alpha)^2 \le 0\), so the poles are a complex pair of modulus exactly

    \[|z| = \sqrt{1-\alpha}. \tag{M}\]

    The error decays like \((1-\alpha)^{k/2}\) for every admissible \(\alpha\), independent of \(T_s\). With \(\alpha = 0.3\) that is \(0.837\) per step — a factor of ten in about 13 samples, ~3 s at 4 Hz — and zero steady-state error on a ramp. ProgressMeter drives the tracker at a fixed 250 ms with the measured interval, for the rootfs download (bytes) and its extraction (compressed bytes consumed — the only total known up front). The host suites check (K), (M), the Jury region (jetbot_core_tests) and convergence to within 10 % of the true rate under ±20 % jitter (progressMeterConverges).

    9. Security properties¶

    • The display listens on no network socket (-nolisten tcp); its only endpoint is a unix socket inside the app's private storage.
    • The rootfs and every runtime package are verified against digests published separately from the files, over HTTPS, before anything is unpacked; archive entries cannot escape their root.
    • One runtime permission, and only when the user opens the shared folder: storage (and All files access where Android 11+ needs it) for the Download folder (§6). Without it the guest sees only the app's own folder. The guest runs as the app's uid with the app's access; -0 makes it believe it is root, and with Download shared it can read and write that folder. It is a convenience boundary, not a security one: anything in it can read and write everything the app can.
    • Package names and repository fields are validated and shell-quoted; a repository key must be an OpenPGP public key fetched over HTTPS.
    • targetSdk 28 is a deliberate reduction in platform hardening (§2).

    10. Known limitations¶

    • PRoot's cost. Every system call that takes a path, every exec, and — because of -0 — every fstat and sendmsg stops for the tracer (§3.3, §3.4); builds and anything that walks many files run slower than natively. The patched PRoot removes the stops that -0 does not require; removing those would take a guest that is not fake root (§3.3).
    • /proc stand-ins are snapshots (§3.3): uptime and the load in top are those of the moment the shell or the session started, and CPU percentages read 0.
    • No /dev/stdin|stdout|stderr on Android inside the guest (§2) — use /dev/fd/0..2.
    • Phantom-process limits (Android 12+) can kill large process trees: more than 32 child processes across the app, or one using much CPU while the app is in the background. A full desktop (GNOME: shell, session, settings daemons) can reach the limit by itself; the display then ends with SIGKILL, and the view says so with the process count (§5.5). Linux → Home → Android's process limit shows whether the limit is on and switches it (§5.5.1); Xfce or the window manager alone stays well under it.
    • No GPU acceleration in the guest: Xvfb renders in software.
    • Display latency (§5.7) is argued and tested on a desktop, not timed on a phone. A guest that moves the pointer itself (a warp) is not followed until the next touch: the app draws the pointer where it last sent it.
    • Sound (§5.6) plays only while a display is open, and only out: there is no microphone for the guest. On the desktop build the stream is consumed at the right rate and not played. The speaker itself — AAudio on a real phone — is exercised by the emulator self-test, not yet heard on one.
