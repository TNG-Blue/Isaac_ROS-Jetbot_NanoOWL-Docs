    Jetbot NanoOWL¶

    Android console for NVIDIA Jetbot and Isaac ROS NanoOWL robots — Qt 6 / C++, with Ubuntu running inside the app

    Features • Install • Build • Usage • Architecture • Testing

    Source

    Snapshot of README.md from TNG-Blue/JetbotNanoOWL at commit d3d7467 (submodule Mobile/Android/JetbotNanoOWL/Qt). Regenerate with Scripts/mkdocs_hooks/snapshot_submodules.py after updating the submodule.

    This is the qt branch — the Qt 6 / C++ (QML) app, developed here. The repository has three branches:

    branch holds how it changes
    qt (this one) the Qt 6 / C++ app pull requests
    kotlin the original Kotlin app, with the on-device Linux environment pull requests
    master both: Qt/ and Kotlin/ Qt/ and Kotlin/ are git subtrees of qt and kotlin, updated automatically once a branch's whole CI has passed (sync)

    Make Qt changes here, never in master's Qt/: a conflicting edit there stops the sync.

    📋 Overview¶

    Jetbot NanoOWL watches a robot from a phone. The sensor-to-state chain — conditioning, noise identification, state estimation, mapping and the transports — is C++ on its own thread; Qt Quick only draws. It is laid out for a 20:9 phone held sideways and tuned on a Samsung Galaxy S21 Ultra (3200 × 1440, arm64-v8a).

    It observes; it does not drive. Nothing computed here is written back to the robot's actuators, and there is no control loop on the phone. Missions drawn on the satellite map reach the aircraft through the Remote_UAV controller, whose pilot accepts and starts them — or, with no remote on, straight to the Jetson's planner only after the operator arms direct control. Every block between a sensor sample and the displayed state is a discretisation of a named continuous-time design, derived in docs/ESTIMATION_DESIGN.md and checked by a host suite that asserts the derived property, not a recorded output.

    And because the robot runs Ubuntu 22.04, so can the phone: a full Linux environment in the app — terminal, apt, ROS 2 Humble, and graphical Linux apps on the phone's screen.

    Highlights¶

    • 🧮 Provable estimation chain — median → pre-warped low-pass → innovation-based noise ID → EKF (Joseph form, NIS monitor) → covariance-weighted pose fix, each stage derived and tested
    • 🗺️ SLAM front end — log-odds occupancy grid, ICP scan matching feeding the EKF, a 3-D voxel map from the LD19 lidar for the multirotor
    • 🛩️ MAVLink observer — 6-DoF Kalman filter, primary flight display, delay-compensated fixes, TLS relay with key pinning for robots behind NAT
    • 🐧 Ubuntu 22.04 on the phone — PRoot guest, a real PTY terminal, apt and vendor repositories, each app full screen on its own X server, shown through a memory-mapped framebuffer with no display protocol in between
    • 🛰️ Satellite map & mission planner — Web Mercator tiles (Esri / OSM / custom) with offline cache, the aircraft's Kalman-filtered GNSS track and 1σ circle, waypoints checked exactly as the remote checks them (SATELLITE_MAP.md)
    • 🎮 Remote_UAV link — USB-C (CDC, no radio) or Bluetooth LE; with the remote on, only the remote commands the aircraft (REMOTE_LINK.md)
    • 📡 RViz2 — in the phone's Ubuntu on the Jetson's ROS 2 graph, or the robot's own over VNC
    • 🖥️ Remote access — VNC (RFB 3.8, DES auth), SSH terminal and SFTP (libssh2, host keys trusted on first use)
    • ✅ Tested where it runs — 493 core checks, front-end and Linux-engine suites on the host, and an Android 14 emulator run that boots the Linux guest on every pull request and every push to qt

    ✨ Features¶

    Estimation chain (native C++)¶

    stage implementation reference
    spike rejection sliding median, rejects bursts of ≤ (w−1)/2 samples exactly Tukey 1977
    filtering first-order low-pass, pre-warped bilinear (−3 dB exactly at f_c), biquads ESTIMATION_DESIGN §2
    noise identification Welford moments + innovation-based R̂ with positivity projection Mehra 1970
    odometry differential-drive kinematics with variance propagation §6
    state estimation EKF on [x y θ v ω], exact constant-twist arc, Joseph-form update, NIS Bar-Shalom §5.2.3
    absolute fix ICP scan match, or the Isaac ROS pose, weighted by its covariance §8
    multirotor KF on [p; v] (continuous white-noise acceleration, q̃ = a_max² T_m) UAV_3D.md

    Console¶

    • 2-D occupancy map with the path and the robot, or the 3-D voxel map with a hexarotor glyph (orbit, zoom, pan, oblique / top / chase), pinch and long-press to measure
    • Primary flight display, telemetry tiles, NanoOWL detections and the open-vocabulary prompt
    • Diagnostics drawer: pose and 1σ, NIS, identified noise, raw odometry against the fused estimate, link counters, loop jitter, Isaac ROS graph health
    • Settings: transport (JBL1 UDP, MAVLink UDP, TLS relay), estimator overrides with range and Nyquist checks, map parameters

    Transports¶

    • JBL1 — binary UDP, CRC-16/CCITT-FALSE, sequence-gap accounting (protocol), bridged by tools/jetbot_bridge.py or tools/isaac_ros_bridge.py
    • MAVLink v2 to ros2_network_bridge of Isaac_ROS-Jetbot_NanoOWL; the console's heartbeat is MAV_TYPE_LOG, so it can never be taken for the GCS (MAVLINK_LINK.md)
    • Relay — both ends dial out over TLS to Server_Relay; with a pinned key, chain and name errors are ignored only when the presented key matches the pin

    Linux environment¶
    Guest Ubuntu 22.04.5 LTS base image, verified against Canonical's SHA-256 before extraction
    Runtime PRoot from the Termux repository, each .deb verified against the repository index, self-tested
    You are jetbot_owl@Blue, with sudo/su shims (PRoot cannot honour setuid)
    Terminal bash on a real pseudo-terminal: apt progress, nano, htop, tmux, Ctrl+C
    Packages apt with sane non-interactive defaults; bundles for the desktop, seamless windows, build tools
    Repositories ROS 2 Humble, VS Code, Chrome, or any deb line with an HTTPS key — rolled back if apt rejects it
    Apps read from the guest's .desktop files; each opens full screen on its own X server
    Display Xvfb -fbdir mapped straight into the view, DAMAGE for changes, XTEST for input, -nolisten tcp
    Files one shared folder: /mnt/android in the guest, the system picker on the phone
    Builds compiler jobs from free memory, jobs·J + R ≤ M, so colcon build does not get the app killed

    Design, derivations and verification: docs/LINUX_ENVIRONMENT.md.

    📦 Install¶

    1. Open the newest qt-build-N release under Releases (every push to qt that passes CI publishes one; N is the build number and the APK's versionCode).
    2. Download JetbotNanoOWL-Qt-v2.0.N-arm64-v8a.apk (Galaxy S21 Ultra and any 64-bit ARM phone, Android 9+). A pull request's build is also attached to its CI run as the qt-apk-arm64-v8a artifact, kept for 3 days.
    3. Open the APK on the phone and allow Install unknown apps for the file manager once.

    The package id is com.tng_blue.jetbotnanoowl.qt, so it installs next to the Kotlin app. Successive builds update each other when they carry the same signing certificate — see docs/APP_SIGNING_AND_PLAY_PROTECT.md.

    targetSdk is 28, on purpose. Android 10+ refuses to execute files an app wrote itself unless it targets 28 or lower, and the Linux environment's runtime and every guest program are such files — the trade Termux makes. Consequence: the app is for sideloading and GitHub releases, not Google Play. See LINUX_ENVIRONMENT.md §2.

    🛠️ Build¶

    Requirements: CMake ≥ 3.28, Ninja, a C++17 compiler, Qt 6.8.3 (installed with aqtinstall). For Android: JDK 17, SDK platform 34, build-tools 34.0.0, NDK r26b (26.1.10909125), and KDAB android_openssl. libssh2 and liblzma are fetched and pinned by hash at configure time.

    Desktop (development and tests)¶

    pip install aqtinstall==3.3.0
python -m aqt install-qt linux desktop 6.8.3 linux_gcc_64 -O ~/Qt
~/Qt/6.8.3/gcc_64/bin/qt-cmake -S . -B build -G Ninja
cmake --build build
ctest --test-dir build --output-on-failure
./build/app/jetbotnanoowl                 # --page linux opens the Linux page

    On the desktop the Linux guest runs under the system's PRoot (5.4 or newer; JETBOT_PROOT= to choose one).

    Android¶

    Keep the build tree outside the checkout (on master, Gradle would otherwise adopt the Kotlin app's settings file):

    python -m aqt install-qt all_os android 6.8.3 android_arm64_v8a -O ~/Qt
git clone https://github.com/KDAB/android_openssl.git third_party/android_openssl
~/Qt/6.8.3/android_arm64_v8a/bin/qt-cmake -S . -B ../build-android -G Ninja \
    -DCMAKE_BUILD_TYPE=Release -DQT_HOST_PATH=$HOME/Qt/6.8.3/gcc_64 \
    -DANDROID_SDK_ROOT=$ANDROID_SDK_ROOT -DANDROID_NDK_ROOT=$ANDROID_SDK_ROOT/ndk/26.1.10909125
cmake --build ../build-android --target apk
# ../build-android/app/android-build/build/outputs/apk/release/*-unsigned.apk

    Then zipalign and apksigner as in the workflow's Sign APK step. Details: docs/QT_APP.md.

    🚀 Usage¶

    With the Isaac ROS graph (MAVLink)¶

    ros2 launch ros2_network_bridge jetbot_console.launch.py phone_host:=<phone-ip>

    In the app: Settings → Connection → ROS2 connection → MAVLink. The status chip turns green when telemetry arrives; the UAV layout (3-D map, flight display) is the default.

    With the JBL1 bridge¶

    python3 tools/isaac_ros_bridge.py --phone <phone-ip>     # --dry-run: synthetic traffic, no ROS 2

    Pick JBL1 in Settings. Detections fill the perception card; tap 🔍 to change what NanoOWL looks for. Full topic map: docs/ISAAC_ROS_INTEGRATION.md.

    Map, missions and the remote controller¶

    1. Menu → Remote controller: connect the Remote_UAV over USB-C (OTG, no radio — the transport for flight) or Bluetooth LE (the remote advertises as JetOwl-RC while disarmed). The page shows what the remote sends and what the aircraft reports through it: batteries, switches, GNSS, attitude, the mission state.
    2. Menu → Map & missions: the aircraft on a satellite map with its filtered GNSS track. In edit mode, tap to add a waypoint, long-press to insert one into the nearest leg, drag to move; each waypoint has altitude, speed and hold. The plan is checked exactly as the remote checks it.
    3. Send to remote: the pilot accepts the plan on the remote and starts it there. With no remote connected, Upload to Jetson is offered only after the operator arms direct control — with a remote on, only the remote commands the aircraft.

    Details: docs/REMOTE_LINK.md, docs/SATELLITE_MAP.md.

    Linux on the phone¶

    1. Tap the penguin in the top bar (or menu → Linux).
    2. Install runtime (~450 KB), then Install Ubuntu 22.04.5 LTS (~27 MB download).
    3. Terminal — you are jetbot_owl@Blue; sudo apt install … works.
    4. For windows: install the Desktop base bundle (and Seamless windows), then open an app from Apps. For ROS 2: Repositories → ROS 2 Humble → Add, then install ros-humble-ros-base (ros-humble-rviz2 also runs, software-rendered).

    Gestures on a Linux window: one finger = left button, long press = right click, two fingers = scroll, two-finger tap = keyboard; the key row has Esc, Tab, arrows, F-keys and sticky Ctrl/Alt/Shift/Super.

    Remote machines¶

    The menu lists the saved VNC connections (open, delete, or Quick connect with host, port and password) and SSH connections (terminal, or SFTP files with a text editor); Menu → Remote desktop & SSH adds and edits them. SSH host keys are trusted on first use and verified afterwards. Menu → RViz2 runs RViz2 in the phone's Ubuntu on the Jetson's ROS 2 graph, or opens the robot's own over VNC.

        │
        ▼

  mapping, render             log-odds grid, ICP, voxels, scene renderer

    🧪 Testing¶

    cmake -S core -B build-core && cmake --build build-core && ./build-core/jetbot_core_tests
ctest --test-dir build --output-on-failure            # core + tst_frontend + tst_linux
JETBOT_LINUX_E2E=1 JETBOT_LINUX_E2E_X=1 JETBOT_LINUX_E2E_DIR=/tmp/jle2e ./build/tests/tst_linux
python3 tools/test_isaac_ros_bridge.py
    Suite Checks
    jetbot_core_tests 493 property checks: Web Mercator and ENU round trips, flight-plan checks on quantised waypoints, CWNA GNSS track NIS in its χ² interval, the remote session's upload/timeout paths, the command arbiter, MAVLink mission frames against pymavlink, −3 dB points, Mehra's R̂, EKF unbiasedness against an exactly integrated unicycle, ICP recovery, CRCs, alpha-beta pole modulus √(1−α), M/G/1 optimum, the MAVLink codec, RFB, XWD, X11 requests
    tst_frontend flight-plan model and files, DES vs FIPS 46-3, VT100, relay TLS handshake and pinning, keysyms, SSH fingerprints, VNC
    tst_linux RViz2 launcher and DDS profile, tar/xz/gzip, tar-slip refusal, .deb, Packages index, identity, build limits, DPI rule, PTY, desktop entries, repositories, start script, DAMAGE/XTEST on a real Xvfb; opt-in: Ubuntu under PRoot, apt, a guest X display
    CI emulator (Android 14) the APK starts, QML loads, OpenSSL is found; --selftest=linux installs PRoot, boots Ubuntu, runs a command and a PTY shell

    CI (build-apk.yml → build-qt.yml), on every pull request and every push to qt:

    Prepare ──▶ host tests ──▶ APK arm64-v8a ─┬──────────────────────────▶ release qt-build-N ──▶ sync master:Qt/
(storage    + headless     APK x86_64 ────┴─▶ emulator smoke test ──┘   (push to qt only)      (push to qt only)
 cleanup)   start-up check                     (waits for Android to finish booting)

    Every job has a timeout. On master the same pipeline builds Qt/, but skips everything when a push left Qt/ unchanged, and skips the x86_64 APK and the emulator, which only re-test what qt already tested (Actions minutes).

    🐛 Known limitations¶

    • No ROS 2 inside the APK — the robot side runs a bridge; ROS 2 in the Linux guest works.
    • Adaptive noise estimator collapses on the low-passed odometry channels (correlated innovations violate Mehra's whiteness assumption) — see ESTIMATION_DESIGN §9.
    • No loop closure — scan matching bounds drift but does not remove it.
    • RFB encodings — Raw, CopyRect and RRE only.
    • Linux guest — PRoot costs a ptrace detour per syscall; no GPU acceleration; one shared desktop (apps maximised on it); no /dev/std* (use /dev/fd/0..2); Android 12+ phantom-process limits can kill large background trees (Developer options → Disable child process restrictions).
    • targetSdk 28 — no Google Play distribution (see Install).

    📝 Roadmap¶

    • Qt 6 / C++ rewrite with the same native core as the Kotlin app
    • Linux environment ported to C++ (no display protocol, PTY terminal, apt repositories)
    • Partial texture uploads for guest displays (upload only the damaged box)
    • Camera stream in the perception card
    • Loop closure and pose-graph optimisation
    • Recorded-telemetry replay

    🤝 Contributing¶

    1. Branch from qt, keep commits focused, and describe why in the message.
    2. Open a pull request into qt (a draft is enough) to get CI: pushes to other branches do not build on their own.
    3. Run ctest (and the Linux end-to-end test when touching app/src/linux).
    4. C++: C++17, RAII, no raw owning pointers, comments that explain the reason rather than the line. QML: presentation only — logic belongs in C++.
    5. Anything on the estimation path needs its derivation in the docs and a test that asserts it.
