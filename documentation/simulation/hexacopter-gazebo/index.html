    Coaxial X12 hexacopter — Gazebo C++ simulation¶

    Source

    This page is rendered from Gazebo/ROS2_Hexacopter_Gazebo/README.md, the authoritative description kept next to the code in Gazebo/ROS2_Hexacopter_Gazebo/.

    A hexacopter with 6 arms × 2 counter-rotating BLDC motors (12 rotors), each with an encoder, simulated in Gazebo Harmonic (gz-sim 8) by a native C++ system plugin. The motor physics, the ESC firmware and the flight controller all run inside the physics step (lock-step, deterministic). Three colcon packages make up the stack:

    Package Content
    ros2_hexacopter_description hexacopter_physical.yaml (single source of truth), URDF/xacro, RViz display
    ros2_hexacopter_control ROS/Gazebo-independent C++17 core: BLDC + FOC ESC + encoder observer, allocation, estimators, cascaded control, gain synthesis + margin proofs, 6-DOF simulator, gtest suite, hexa_design_report
    ros2_hexacopter_gazebo (this) HexacopterSystem gz-sim plugin, world, ros_gz bridge, launch, headless Gazebo SIL tests
    ros2_mcu_emulator virtual MCU: GNSS/IMU/encoder error models + the MCU side of the Ethernet link
    ros2_jetowl_bridge Jetson side of the MCU Ethernet link (jetowl_bridge, sensor_link) — same node on the vehicle

    Why a C++ system plugin¶

    • Lock-step, zero-latency loop. Sensors, estimator, controller, 12 ESCs and the wrench on the body are computed inside PreUpdate of the same physics step, so there is no transport hop, no thread scheduling jitter and runs are bit-reproducible for a given seed.
    • Electrical time scale. The FOC current loop and the motor's L/R = 1.4 ms need sub-millisecond integration: each rotor runs 20 × 50 µs RK4 sub-steps per 1 ms physics step (240 motor integrations per step). Measured: 20 s of flight simulated in 5.0 s wall-clock (4× real time, 4 cores, incl. start-up), headless.
    • One code base for SIL and the vehicle. The plugin is a thin adapter around ros2_hexacopter_control; the same classes run in the stand-alone simulator used by the unit tests and can run on the Jetson or be ported to the ESC/flight firmware.
    • Gazebo's MulticopterMotorModel models the rotor speed as a first-order lag. It has no dq electrical model, no FOC and no encoder, so it cannot represent "12 BLDC with encoders".

    Gazebo version. The plugin targets Harmonic (LTS until 2028). Gazebo Fortress reached end-of-life in September 2026. With ROS 2 Humble, install the OSRF ros-humble-ros-gzharmonic packages.

    MCU link: sensor topics for the nodes in Source/¶

    On the vehicle the IMU, GNSS and the 12 encoders are read by the flight MCU, which sends them to the Jetson over Ethernet. The plugin is the flight MCU, so with <mcu_link> it also sends those frames over UDP — same protocol, same C encoder — to the Jetson node jetowl_bridge (its sensor_link), which publishes the topics the Source/ nodes subscribe to:

    HexacopterSystem (flight MCU)                          jetowl_bridge (Jetson)          Source/
 BMI088 sample used by the FC ─┐                        CRC/seq ─▶ stamp ─▶ covariance ─▶ /imu/data, /imu/data_raw ─▶ ROS2_Control_System,
 12 rotor angles (AS5047P)  ───┼─▶ sensor link ─UDP─▶ encoder Kalman (α-β)           ─▶ /encoders/joint_states      ROS2_Flight_Controller,
 u-blox GNSS model          ───┤   frames (9870)        GNSS gate                     ─▶ /gps/fix, /gps/vel(_cov)    ROS2_Mission_Planner …
 Mahony attitude + variance ───┘                                                      ─▶ /diagnostics
    Stream Rate Content (details: ros2_jetowl_bridge)
    IMU 1 kHz the very sample the flight controller used (one noise realisation for both)
    IMU description 1 Hz BMI088 noise densities and full scales from hexacopter_physical.yaml
    encoders 1 kHz 12 × 14-bit counters of the true rotor angle, θ += ½(ω_{k−1} + ω_k)·dt
    attitude 100 Hz Mahony estimate; tilt σ = 0.020 rad (accelerometer bias / g), yaw unobservable (π²)
    GNSS 10 Hz NEO-M9N model at the CoM, geodetic origin from gnss_latitude/longitude/height
    heartbeat 1 Hz 1 ready, 2 armed, 3 degraded (a rotor failed)

    hexacopter_sim.launch.py starts jetowl_bridge with sensor_link_sim.yaml (mcu_link:=true, default; fc and vision links off) with clock.mode: passthrough — the virtual MCU stamps with simulation time — and with sensor_fusion:=true also the stack's ESKF (ros2_control_system/uav_state_estimator) on those topics, with the MCU attitude as heading source → /odometry/filtered.

    HexacopterSystem::PreUpdate — one physics step¶

    flowchart TD
    A(["PreUpdate(info, ecm)"]) --> B{"configured and not paused?"}
    B -- no --> Z(["return"])
    B -- yes --> C["read pose, v, ω, a from the ECM"]
    C --> D["apply queued faults and commands<br/>(arm refused until at-rest calibration done)"]
    D --> E["BMI088 IMU + MS5611 baro models<br/>(σ = N·√f_s, biases)"]
    E --> F{"autopilot?"}
    F -- yes --> G["FlightController.step: gyro LPF · Mahony · KF[z, v, b]<br/>altitude → climb PI → thrust; attitude P → rate PI → torque<br/>allocation (min-norm, priorities, failed rotors) → ω_ref × 12"]
    F -- no --> H["ω_ref from /hexa/motor_speed_cmd"]
    G --> I["12 × ESC/BLDC at 20 kHz over the step:<br/>FOC current IMC, Luenberger observer, speed PI + FF,<br/>fault detection"]
    H --> I
    I --> J["AddWorldWrench: thrust, reaction,<br/>gyroscopic torque, drag"]
    J --> K{"mcu_link?"}
    K -- yes --> L["virtual MCU: IMU 1 kHz, encoders 1 kHz,<br/>attitude 100 Hz, GNSS 10 Hz → UDP frames"]
    K -- no --> M
    L --> M["publish /hexa/motor_speeds, state_estimate, status<br/>(at the publish rate) + optional CSV log"]
    I -. "rotor failed flags" .-> G
    J -. "body motion → next ECM state (closed loop)" .-> C

    Quick start¶

    # ROS 2 Humble + Gazebo Harmonic
sudo apt install ros-humble-ros-gzharmonic libeigen3-dev libyaml-cpp-dev
colcon build --packages-up-to ros2_hexacopter_gazebo
source install/setup.bash                       # sets GZ_SIM_SYSTEM_PLUGIN_PATH

ros2 launch ros2_hexacopter_gazebo hexacopter_sim.launch.py      # gui:=false for headless
# wait ~2 s (at-rest gyro/accel calibration), then:
ros2 topic pub --once /hexa/arm std_msgs/msg/Bool "{data: true}"
ros2 topic pub -r 20 /hexa/cmd geometry_msgs/msg/Twist "{linear: {z: 1.0}}"          # climb
ros2 topic pub -r 20 /hexa/cmd geometry_msgs/msg/Twist "{angular: {x: 0.15}}"        # roll
ros2 topic pub --once /hexa/fault/open_circuit std_msgs/msg/Int32 "{data: 4}"       # kill motor 4
ros2 topic echo /hexa/status          # [armed, calibrated, healthy rotors, rp scale, yaw scale, NIS]
ros2 topic hz /imu/data               # MCU link → jetowl_bridge: 1 kHz
ros2 topic echo /gps/fix --once       # WGS-84 fix with covariance
ros2 topic echo /diagnostics          # link loss, clock, per-stream watchdogs

ros2 run ros2_hexacopter_control hexa_design_report                 # gains, margins, SIL: PASS/FAIL
colcon test --packages-select ros2_hexacopter_control ros2_hexacopter_description ros2_hexacopter_gazebo

    Without ROS (plain CMake, e.g. on a CI runner with libgz-sim8-dev):

    cmake -S Gazebo/ROS2_Hexacopter_Gazebo -B build && cmake --build build -j
HEXA_PLUGIN_DIR=$PWD/build python3 -m pytest Gazebo/ROS2_Hexacopter_Gazebo/test -q   # both SIL tests

    Interface¶

    gz topic (ROS topic via bridge) Type Dir Meaning
    /hexa/cmd Twist in angular.x roll [rad], angular.y pitch [rad], angular.z yaw rate [rad/s], linear.z climb rate [m/s]
    /hexa/arm Boolean / std_msgs/Bool in refused until the 2 s at-rest calibration completes
    /hexa/fault/open_circuit, /hexa/fault/propeller Int32 in fault injection, rotor index 0–11
    /hexa/motor_speed_cmd Actuators in 12 speeds [rad/s] when autopilot:=false (external autopilot)
    /hexa/motor_speeds Actuators out ESC speed estimates (gz side)
    /hexa/state_estimate Pose out estimated attitude, altitude in position.z
    /hexa/status Float_V / ros_gz_interfaces/Float32Array out armed, calibrated, healthy rotors, allocation scales, baro NIS
    /hexa/ground_truth/odometry nav_msgs/Odometry out evaluation only
    UDP 9870 → jetowl_bridge sensor-link frames out IMU, IMU info, GNSS, 12 encoders, attitude, heartbeat (mcu_link:=true)
    UDP 9871 TIME_SYNC_REQUEST in time-sync service of the virtual MCU

    Rotor numbering: arm i at azimuth 30° + 60°·i (nose between arms 0 and 5); rotor 2i is the upper rotor, 2i+1 the lower one; upper rotors spin CCW on even arms.

    Control design (summary — full derivations in the headers of ros2_hexacopter_control)¶

    Stage Choice Numbers (from hexa_design_report)
    Propulsion momentum-theory k_T = C_T ρ D⁴/4π², k_Q = C_P ρ D⁵/8π³; lower rotor ×0.8 T/W = 3.46 (6S); 2.28 with the 4S of the MATLAB config
    Motor surface PMSM dq model, ω_e L cross-coupling, voltage circle V_bus/√2 ω_max 855 / 909 rad/s
    ESC current IMC PI K_p = ω_ci L, K_i = ω_ci R, decoupling, 1-PWM delay ω_ci = 6283 rad/s, PM 63°
    ESC speed Luenberger observer on the 14-bit encoder (triple pole 600 rad/s) + PI pole placement + exact FF PM ≥ 69.5°, GM ≥ 24 dB (±20 %)
    ESC failsafe speed-error, observer-load and observer-residual tests healthy residual ≤ 0.33 counts, prop-loss ≥ 70 → threshold 5
    Allocation min-norm pseudo-inverse, priority roll/pitch > yaw > thrust rank 4 with any single rotor removed
    Rate PI, crossover placed exactly (30 / 30 / 12 rad/s), gyroscopic FF, yaw-torque LPF worst GM 17.3 dB, PM 65.3° (±20 % I, m, k_T, J_r)
    Attitude quaternion P (Lyapunov V = 1 − |q_w|), separation 5 PM ≥ 53°
    Vertical KF [z, v, b_a] + climb PI pole placement + slew/FF, altitude P PM ≥ 71.8° / 88.7°
    Attitude estimate Mahony, K_P = 2ζω_c, K_I = ω_c², ω_c = 0.05 rad/s, gyro bias calibrated at rest see limits

    Two findings of the analysis that changed the design:

    1. Yaw is actuated by the motor reaction torque −s(J ω̇ + k_Q ω²), not by the aerodynamic torque the allocator assumes. That adds a zero at 2.4 rad/s. Above it the yaw actuator behaves like a differentiator, and without a yaw-torque low-pass the yaw loop drops below GM = 6 dB at −20 % inertia (test_design.cpp: YawFilterIsNecessary).
    2. On a multirotor the accelerometer measures thrust, not gravity, during horizontal acceleration, so tilt is not observable from it (Martin & Salaün 2010). With the sensor-noise-optimal crossover of 1.4 rad/s the attitude estimate was pulled level during a 0.2 rad roll and the vehicle kept rolling. With ω_c = 0.05 rad/s and the gyro bias calibrated at rest, the pull is ≤ 10 % after 2 s.

    Assumptions and limits¶

    • Airframe mass/inertia, lower-rotor efficiency, rotor drag, pole pairs and the 6S bus are assumptions ([A] in the YAML). Identify them on a thrust stand and with a bifilar pendulum, then re-run hexa_design_report. The gains follow automatically.
    • The MATLAB configs (MATLAB/scripts/control/Config*_Hexacopter.m) describe a 6-motor/1.5 kg vehicle with hand-set gains. They are not used here and are not consistent with this model.
    • Tilt/accelerometer-bias and yaw are not observable without velocity or heading aiding. In Gazebo the true tilt differs from the estimate by ≈ 0.027 rad (20 mg bias) and yaw drifts slowly. Horizontal position/velocity hold therefore needs GNSS or optical flow and a magnetometer (not in scope). The interface is attitude + climb rate, for a pilot or for the outer loops of Source/ROS2_Flight_Controller.
    • Rotor wake interaction is a constant efficiency; ground effect, blade flapping, battery sag and ESC thermal limits are not modelled.
    • Verified with gz-sim 8.15 (OSRF packages) on Ubuntu 24.04; the ROS 2 launch file was run with ROS 2 Jazzy (same launch/rclcpp API as Humble), not with Humble.
    • The MCU link has been verified in simulation only; the Portenta firmware side is not written yet (see ros2_jetowl_bridge "MCU firmware integration").
