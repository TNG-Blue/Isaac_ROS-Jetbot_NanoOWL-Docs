    OTA Web Interface¶

    The firmware dashboard shipped with Server_OTA v3.0.0 is published next to this documentation as a static preview, so the UI can be inspected without deploying a server.

    🖥️ Open the Preview¶

    🚀

    Full-Screen Preview

    The complete dashboard — upload zone, firmware grid, statistics and theming — rendered from the real templates.

    Open UI →
    📦

    Server Source

    Go backend, templates and deployment scripts under Server_OTA/.

    Browse →

    Preview, not a deployment

    The preview is static and read-only. It is served by GitHub Pages, which has no Go backend, so upload, download and delete are disabled and the API responses are demo payloads. Everything else — layout, theming, filtering, sorting, view switching — is the production UI, byte-for-byte from Server_OTA/web/templates/index.html.

    Embedded frame is empty locally

    The preview only exists in the deployed dual build. When you run mkdocs serve from a checkout, build it first with the command in Reproduce the dual build locally.

    🔌 What the Preview Simulates¶

    Server_OTA/web/static/js/script.js polls three read-only endpoints every 5 seconds. On a static host those paths do not exist, so the preview build injects static/js/preview-demo.js, which answers them with payloads that follow the exact contract of the Go handlers.

    Endpoint Go handler data payload Preview source
    /api/stats handlers.HandleStats total_files, total_size, downloads, server_version derived from the demo dataset
    /api/health handlers.HandleHealth status, memory_mb, goroutines, timestamp (models.HealthStatus) fixed operational status
    /api/firmware/list handlers.HandleFirmwareList array of size, mod_time, name, version, device_type, description (models.FirmwareInfo) 5 demo firmware entries

    The firmware entries carry exactly the version, device_type and description that services.ListFirmwareFiles() would derive from those file names — see Firmware metadata. The two health counters are illustrative: today the live server reports goroutines: 0 and timestamp: 0 (see Current gaps).

    Every response is wrapped in the standard envelope produced by utils.RespondSuccess (models.APIResponse):

    JSON
    {
  "data": { "total_files": 5, "total_size": 272105472, "downloads": 128, "server_version": "3.0.0" },
  "message": "Server statistics",
  "success": true
}

    The totals are computed from the demo dataset at runtime rather than hard-coded, so the navbar counters, the dashboard cards and the firmware grid always agree with each other.

    Write operations (/upload, /download, delete) have no static equivalent. The shim replaces them with an explanatory notification instead of letting the request fail.

    🏗️ Dual Build Pipeline¶

    .github/workflows/docs_deploy.yaml builds two independent artifacts and publishes them as one site to the public documentation repository Isaac_ROS-Jetbot_NanoOWL-Docs.

    graph LR
    subgraph "Build (parallel)"
        A["build
    MkDocs → site/"]
        B["build-ota-preview
    Server_OTA/web → ota-preview/"]
    end

    A --> C["test
    6 quality gates"]
    C --> D["deploy-to-public-repo"]
    B --> D
    D --> E["merge:
    site/ + site/ota-preview/"]
    E --> F["gh-pages @ Isaac_ROS-Jetbot_NanoOWL-Docs"]
    Stage Job Output
    Documentation build documentation-site-<run_id> artifact
    Web interface build-ota-preview ota-preview-site-<run_id> artifact
    Quality gates test HTML, assets, secrets, performance, link checks
    Publication deploy-to-public-repo merged tree pushed to gh-pages

    The preview job is a peer of the docs job, not a step inside it: a failure in the OTA UI build blocks publication, but the two builds do not share state. The deployment step places the preview at ota-preview/ inside the published site and fails if either half is missing.

    Workflow triggers — a push to master touching any of:

    • Docs/**, mkdocs.yml — documentation content
    • Server_OTA/web/** — templates, stylesheets, scripts of the dashboard
    • Server_OTA/scripts/build_preview.sh — the preview builder itself
    • .github/workflows/docs_deploy.yaml — the pipeline

    💻 Reproduce the Dual Build Locally¶

    Bash
    # 1. Preview of the OTA UI only (serves it on http://localhost:8081)
./Server_OTA/scripts/build_preview.sh --serve 8081

# 2. Both halves, exactly as CI assembles them
mkdocs build --clean                                      # → site/
./Server_OTA/scripts/build_preview.sh --output site/ota-preview
python3 -m http.server 8000 --directory site              # → http://localhost:8000

    build_preview.sh performs the transformations that make the server-rendered template work on a static host:

    1. copies web/templates/index.html, 404.html and web/static/ into the output directory
    2. rewrites the absolute /static/… references the Go server relies on into relative ones
    3. injects window.OTA_PREVIEW_MODE = true and the demo shim before script.js, so the fetch override is installed before the first API call
    4. writes preview-info.json (commit, build time, simulated endpoints)
    5. verifies the result and exits non-zero if an asset, the flag or the shim is missing
    Option Default Purpose
    --source DIR Server_OTA/web Location of templates and static assets
    --output DIR Server_OTA/preview Output directory (wiped before each build)
    --serve [PORT] 8081 Serve the result over HTTP after building

    🚀 Run the Real Dashboard¶

    The preview replaces a server only for looking at the UI. To exercise uploads, downloads and live statistics, run the actual binary:

    Bash
    cd Server_OTA
./scripts/build.sh        # builds bin/ota-server-3.0.0-linux (+ -rpi)
./scripts/run.sh          # serves http://localhost:8080
    Bash
    docker run -d --name ota-server \
  -p 8080:8080 \
  -v $(pwd)/data:/app/data \
  tngblue/server_ota:latest
    Bash
    curl -s http://localhost:8080/api/health  | jq
curl -s http://localhost:8080/api/stats   | jq
curl -s http://localhost:8080/api/firmware/list | jq

    Upload limits and accepted extensions come from Server_OTA/config/config.json (50 MB per file; .bin, .hex, .elf, .img, .fw).
