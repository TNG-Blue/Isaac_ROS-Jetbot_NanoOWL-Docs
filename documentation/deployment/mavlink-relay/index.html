    Server_Relay — MAVLink relay for robots and consoles on different networks¶

    Source

    This page is rendered from Server_Relay/README.md, the authoritative description kept next to the code in Server_Relay/.

    ros2_network_bridge and the JetbotNanoOWL console normally share a LAN: the console's UDP heartbeat reaches the bridge and the bridge answers to its address. Put the robot on one network and the phone on another (a 4G phone, a robot behind a home router) and neither can reach the other: both sit behind NAT, the phone usually behind the carrier's (CGNAT), and neither has a port anyone can open.

    The relay removes the problem instead of working around NAT: both ends dial out to one server with a public address, over TLS, and the server joins them. Outbound TCP crosses every NAT, CGNAT included; nothing is opened on the robot or the phone.

     Jetson (any network)                    relay (public IP)                 phone (any network)
 network_bridge_node                     relay -listen :5790               JetbotNanoOWL
   transport: relay ──── TLS ──────────▶ ┌──────────────────────┐ ◀────── TLS ──── MAVLink relay
   MAVRELAY/1 vehicle jetbot-01 <tok>    │ robot "jetbot-01"    │      MAVRELAY/1 observer
                                         │  vehicle ──▶ all     │      jetbot-01 <tok>
                                         │  observers ──▶ only  │
                                         │  verified HEARTBEAT  │
                                         └──────────────────────┘

    Go 1.21, standard library only. Package relay is the server; main.go is the command.

    Protocol¶

    1. TLS (1.2 minimum, 1.3 when both ends offer it) to the relay, port 5790 by default.
    2. The client sends one line, at most 512 bytes, within 5 s:
    MAVRELAY/1 <vehicle|observer> <robot-id> <token>\n

    robot-id is [A-Za-z0-9_.-]{1,64}. 3. The relay answers OK\n, or ERR auth\n / ERR malformed\n / ERR full\n and closes. 4. From then on, the connection carries raw MAVLink v1/v2 frames both ways.

    The relay cuts each stream into whole frames (from the header length, signed frames included) and forwards frames, never byte ranges, so frames from two observers can never interleave into one corrupt frame on the vehicle's stream.

    Roles and the safety rule¶

    from forwarded to what passes
    vehicle every observer of that robot every frame
    observer the vehicle only a HEARTBEAT whose CRC (with CRC_EXTRA 50) verifies, unsigned
    observer other observers nothing

    An observer credential therefore cannot command the robot: no COMMAND_LONG, no set-point, no parameter, no mission item ever reaches the vehicle from it, whatever the client sends — the rule is enforced here, not trusted to the client. It is the network form of the console's own rule (it is an observer and announces itself as MAV_TYPE_LOG, which the bridge never takes for its GCS; see Source/ROS2_Network_Bridge/README.md). A commanding GCS over the relay would need a third role and is deliberately not offered.

    • One vehicle per robot. A new authenticated vehicle replaces the old connection, which can linger after the robot changes network until its idle timeout.
    • Observers per robot: at most -max-observers (default 8).
    • Idle timeout (-idle, default 10 s): both ends send HEARTBEAT at 1 Hz and TCP loses no bytes, so 10 s of silence is a dead path; it also outlasts three TCP retransmission back-offs (1 + 2 + 4 s) of a stalled one.
    • Back-pressure: each peer has a 256-frame send queue. A full queue drops the new frame — a slow observer must not stall the vehicle or the other observers, and to both ends a dropped frame is an ordinary loss that their sequence-gap counters already report.

    Security model¶

    threat what stops it
    eavesdropping, tampering on the path TLS; the client verifies the server (system CA + host name, or a pinned SHA-256 of the server key)
    connecting without a credential 256-bit random token per robot and role; the server stores only SHA-256 hashes, compared in constant time
    guessing tokens 2²⁵⁶ space; every failure waits 1 s and gets the same ERR auth, so nothing tells a wrong robot from a wrong token
    a leaked observer token the holder can watch, never command (safety rule above); rotate the hash
    a leaked vehicle token the holder can impersonate the robot to the consoles; it still cannot reach the real robot. Rotate
    a leaked credentials file it holds hashes, not tokens
    a relay operator sees telemetry in clear inside the relay; host it yourself. MAVLink signing end to end is not implemented by the bridge (its README, Known limitations)

    Deploying¶

    Any host with a public address — a small VPS is enough: the console's stream is about 2.5 kB/s per robot (bridge rates.*, 10 Hz ODOMETRY).

    # 1. tokens: one per robot and role, kept by the robot / the phone only
VTOKEN=$(openssl rand -hex 32); OTOKEN=$(openssl rand -hex 32)
cd Server_Relay/src && go build -o relay .
cat > ../config/credentials.json <<EOF
[
  {"robot": "jetbot-01", "role": "vehicle",  "sha256": "$(printf %s "$VTOKEN" | ./relay -hash)"},
  {"robot": "jetbot-01", "role": "observer", "sha256": "$(printf %s "$OTOKEN" | ./relay -hash)"}
]
EOF

# 2. a certificate for the relay's name (Let's Encrypt, or self-signed + pin on the clients)
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -days 825 \
    -subj /CN=relay.example.org -addext subjectAltName=DNS:relay.example.org \
    -keyout privkey.pem -out fullchain.pem
# pin for the clients (SHA-256 of the public key, hex):
openssl x509 -in fullchain.pem -pubkey -noout | openssl pkey -pubin -outform der \
    | openssl dgst -sha256 | cut -d' ' -f2

# 3. run (or: docker build -t mavlink-relay Server_Relay)
./relay -listen :5790 -cert fullchain.pem -key privkey.pem -credentials ../config/credentials.json

    Robot side: ros2 launch ros2_network_bridge jetbot_console.launch.py transport:=relay relay_host:=relay.example.org relay_robot:=jetbot-01 relay_token_file:=/etc/jetbot/relay.token (see Source/ROS2_Network_Bridge/README.md). Phone side: Settings → ROS2 Connection → MAVLink relay, with the same host, port, robot id, the observer token and, for a self-signed certificate, the pin.

    config/credentials.json and *.pem are git-ignored; config/credentials.example.json shows the format.

    Tests¶

    cd Server_Relay/src && gofmt -l . && go vet ./... && go test -race ./...

    TLS with a generated certificate, pymavlink golden frames: authentication (wrong token, wrong role), fan-out to two observers, an ARM COMMAND_LONG from an observer dropped while its heartbeat passes, corrupted and signed heartbeats refused, observer limit, vehicle replacement, a stalled observer not holding up the stream of another, the full-queue drop rule, idle timeout. CI: .github/workflows/relay-server-ci.yml.

    Latency¶

    The relay adds the detour through its host, and TCP replaces loss with delay (a retransmitted segment holds back the ones behind it). The console does not assume either away: it estimates each fix's excess delay from its timestamp and predicts the fix forward with its own motion model and process noise before fusing it (JetbotNanoOWL docs/MAVLINK_LINK.md, §8).
