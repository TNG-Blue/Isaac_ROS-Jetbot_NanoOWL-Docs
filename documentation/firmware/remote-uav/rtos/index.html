    Real-time task design (Remote_UAV)¶

    Source

    This page is rendered from Microcontroller/Remote_UAV/docs/RTOS.md, the authoritative description kept next to the code in Microcontroller/Remote_UAV/docs/.

    Code: src/os/os_port.h (RTOS API), src/os/os_port_cmsis.cpp (GIGA backend), src/os/os_port_freertos.c (FreeRTOS backend), src/os/rt_sched.{h,c} (analysis, pure C), src/app/app.cpp (task table), src/system/supervisor.cpp (run-time analysis). Tests: tests/host/test_rt_sched.c, tests/rtos/test_os_freertos.c (real FreeRTOS kernel).

    1. Which kernel runs on the GIGA¶

    The Arduino GIGA R1 core is Mbed OS, and its kernel is Keil RTX5 behind the CMSIS-RTOS2 API. The drivers this remote needs are built on that kernel and ship precompiled in the core: Wi-Fi (Murata 1DX through Cypress WHD), Bluetooth LE (Cordio), the display (Arduino_H7_Video and its LVGL tick thread) and KVStore. RTX5 therefore cannot be swapped for the FreeRTOS kernel on this board without rewriting those drivers.

    What the firmware does instead:

    • The application uses only os_port.h, never rtos::Thread, osThreadNew or xTaskCreate directly.
    • os_port.h is the subset of primitives whose semantics RTX5 and FreeRTOS implement identically (table below). Both backends exist.
    • The FreeRTOS backend is tested on the real FreeRTOS kernel (V11.1.0, POSIX port, tests/rtos). Moving the remote to a FreeRTOS board therefore means compiling with -DOS_PORT_FREERTOS and supplying FreeRTOSConfig.h plus the board hooks listed in os_port_freertos.c; no application file changes.
    os_port RTX5 / CMSIS-RTOS2 (GIGA) FreeRTOS
    os_task_create (static TCB + stack) osThreadNew with cb_mem, stack_mem xTaskCreateStatic
    os_notify / os_notify_from_isr osThreadFlagsSet (ISR-safe) xTaskNotify / xTaskNotifyFromISR + portYIELD_FROM_ISR
    os_wait(mask) (other bits stay pending) osThreadFlagsWait(osFlagsWaitAny) ulTaskNotifyValueClear + xTaskNotifyWait
    os_mutex_* (priority inheritance) osMutexNew(osMutexPrioInherit) xSemaphoreCreateMutexStatic
    os_queue_* (FIFO, copy) osMessageQueueNew (static) xQueueCreateStatic
    os_hwtimer_start (periodic, ISR context) mbed::Ticker (us_ticker, 1 µs) board timer hook, else software timer
    os_task_stack_free fill pattern 0xCCCCCCCC, scanned uxTaskGetStackHighWaterMark
    os_time_us ticker_read_us(us_ticker) OS_PORT_TIME_US() hook

    2. Design rules and why¶

    Rule Reason
    Static allocation of every TCB, stack, mutex and queue no kernel heap, no fragmentation, RAM known at link time (§7)
    Direct-to-task notifications for ISR → task signalling cheapest IPC of both kernels; no shared event object that two tasks contend on
    Priority-inheritance mutexes only, with measured hold times blocking is bounded (Sha, Rajkumar & Lehoczky 1990) and enters the analysis as a number
    Periodic tasks released by a hardware timer the Butterworth stick filter assumes a uniform sample period (§4)
    Flash writes in a background task a KVStore write can erase a QSPI sector (tens–hundreds of ms)
    Priorities by deadline-monotonic assignment at boot optimal for fixed priorities with D ≤ T (§3), and the order follows from the deadlines instead of being chosen by hand
    Every application rank on its own native level RTX round-robins equal priorities (OS_ROBIN_TIMEOUT = 5 ticks); no task shares a level with an Mbed thread (main, lwIP and LVGL tick at Normal, timer thread at High)

    3. Task set and priority assignment¶

    Task Release T D Where D comes from
    input hardware timer 2 ms 2 ms the sample must be processed before the next one
    uplink hardware timer 20 ms 3 ms TX start must stay inside the jitter budget RFLINK_UL_JITTER_US of the FC hop guard (LINK_DESIGN §4)
    downlink RX interrupt T_hdr = 10.37 ms T_hdr sporadic: two RX interrupts are at least one preamble + sync + header apart
    downlink (poll) 20 ms timeout 20 ms 20 ms missed-edge poll, hop deadline, link-quality update
    supervisor 250 ms 250 ms 250 ms watchdog kick
    ui LVGL due time — soft, 33 ms one display frame; overruns are dropped frames, counted
    net, store, phone, Arduino loop queue / notify / 20 ms — — background (phone: docs/PHONE_LINK.md)

    T_hdr = (n_pre + 4.25 + 8) · 2^SF / BW (Semtech AN1200.13; link_dl_min_interarrival_us()). For the default band plan (SF7, 250 kHz, 8 preamble symbols) this is 20.25 × 512 µs = 10.37 ms.

    Deadline-monotonic (Leung & Whitehead 1982): the shorter D, the higher the priority. For D ≤ T it is optimal among fixed-priority assignments — if any fixed assignment meets every deadline, DM does. rt_dm_assign() runs at boot on the table above:

    input (D 2 ms) > uplink (D 3 ms) > downlink (D 10.4 ms) > supervisor (D 250 ms)   → OS ranks 6, 5, 4, 3
ui → rank 1;  net, store, loop() → rank 0

    The previous firmware ran the uplink above the input. That order is also feasible here, but DM is the provably optimal one, and the analysis below shows the extra input interference on the uplink: ⌈R/2 ms⌉ · C_input, a few hundred µs at most against the 3 ms guard.

    4. Release jitter: why a hardware timer¶

    The kernel tick is 1 ms (OS_TICK_FREQ), tickless on the LPTIM. A task released by sleep_until() therefore wakes on tick boundaries, and its sampling instant can wander by up to one tick, which is 50 % of the 2 ms input period. The Butterworth anti-alias filter of stick_dsp.h is designed for a uniform T_s: a sampling-time error δ on a signal with slope ẋ adds an error ẋ·δ, a noise source the filter design does not include.

    With os_hwtimer_start() the release comes from the us_ticker interrupt (1 µs resolution). The residual jitter is the interrupt latency plus, at most, one blocking critical section (§5). Both appear in the measured response time R − C.

    5. Response-time analysis¶

    rt_rta() (Joseph & Pandya 1986; Audsley, Burns, Richardson, Tindell & Wellings 1993; jitter from Tindell, Burns & Wellings 1994):

    w⁰      = C_i + B_i
wᵏ⁺¹    = C_i + B_i + Σ_{j ∈ hp(i)} ⌈(wᵏ + J_j) / T_j⌉ · C_j
R_i     = w* + J_i        schedulable  ⇔  R_i ≤ D_i

    The iteration is monotone non-decreasing. It stops at a fixed point, or as soon as it exceeds D_i − J_i, which proves a miss. For independent tasks (B = 0) the test is exact; with blocking it is sufficient.

    Blocking. Under priority inheritance a job is blocked at most once per mutex, for one critical section of a lower-priority task (Sha et al. 1990, Theorem 6). B = Σ max hold(m) over the mutexes a real-time task takes: input, link, fit, session. The hold times are measured by os_mutex_unlock().

    Downlink. The downlink has two release sources in one task: RX interrupts (T = T_hdr) and the poll (T = 20 ms). It enters the analysis as two entries. The poll entry is ranked just below the interrupt entry, so the interrupt entry is additionally blocked by one poll job of the same task. Their interference on lower tasks is the exact sum ⌈w/T_hdr⌉C + ⌈w/T_poll⌉C.

    Uplink. The deadline applies to the TX start (first CPU segment). The second segment, which reads out TX_DONE, is added to the uplink's C when it interferes with lower tasks.

    Measured C. Every job records release r, start s and finish f. C = f − s includes preemption by higher tasks and interrupts, so max(f − s) is an upper bound of the WCET observed so far, and RTA fed with it is conservative. R = f − r is the observed response; a job with R > D is counted as a miss. If timer ticks coalesce during an overrun, the job is charged from the oldest unserved release, so the miss shows up in R.

    At run time the supervisor recomputes the analysis every second with the measured C_max and B. It publishes an RtReport that the System page shows: verdict, U = ΣC/T against the Liu & Layland bound n(2^{1/n} − 1), and per task the rank, T, D, C_max, worst observed R, RTA bound, misses and stack used. Serial prints it every 10 s and whenever the verdict changes.

    tests/host/test_rt_sched.c checks:

    • RTA on a hand-computed three-task set (iterates 5, 11, 14, 17, 20 → R = 20 = D, with U = 0.93 above the LL bound, so LL alone is inconclusive).
    • A two-task set that rate-monotonic misses and deadline-monotonic schedules.
    • The blocking and jitter terms.
    • The sequence-locked statistics under a concurrent writer thread: about 10⁶ reads, no torn snapshot.

    6. Shared data¶

    Data Writer(s) Readers Mechanism
    InputState input; store (notices) uplink, ui, net, supervisor, loop PI mutex, struct copy
    LinkState uplink, downlink input, ui, net, supervisor, loop PI mutex, struct copy
    job statistics each task its own supervisor, ui sequence lock (Lamport 1977): the writer never waits
    RtReport supervisor ui, loop PI mutex
    UI → input requests ui input FIFO queue (InputCmd), drained every 2 ms
    UI → net requests ui net FIFO queue (NetCmd)
    settings to persist input store latest-wins record + notification

    The sequence lock is safe here because every reader runs below the writer it reads. A reader is preempted by the writer and retries; it can never preempt a writer that is halfway through. Retries are capped at RT_STATS_READ_TRIES.

    7. Memory¶

    All stacks are static (OS_STACK_DEFINE), so they appear in the link map:

    Task Stack
    input, uplink, downlink, store 4 KiB
    supervisor 3 KiB
    net 8 KiB
    ui 16 KiB

    Build result: 884 KB flash, 351 KB static RAM. The 45 KB jump in "global variables" relative to 2.1.0 is the stacks moving from rtos::Thread's heap allocation into .bss; total RAM use is unchanged. The other 48 KB is the third LVGL pool chunk (docs/UI.md §7).

    The stack high-water marks are on the System page. A stack whose used part exceeds 75 % of its size should be enlarged.

    8. FreeRTOS verification (tests/rtos)¶

    cmake -S tests/rtos -B build-rtos        # fetches FreeRTOS-Kernel V11.1.0 (or -DFREERTOS_DIR=...)
cmake --build build-rtos && ctest --test-dir build-rtos --output-on-failure

    The test runs the FreeRTOS backend on the real kernel (POSIX port) and checks:

    • masked notifications;
    • the FIFO queue, including the full and empty-with-timeout cases;
    • priority inheritance: while a rank-6 task waits on a mutex, the rank-0 holder runs at rank 6, and drops back to rank 0 after the unlock;
    • periodic timer release with job statistics (100 jobs per second at 100 Hz);
    • RTA on the measured C;
    • the stack high-water mark.

    9. Not yet verified on hardware¶

    The firmware compiles for the GIGA, and the analysis and the FreeRTOS backend are tested on the host. Still to be measured on the board, all of which the System page reports directly:

    • the real C_max of every task (in particular four analogRead() calls per input job);
    • the interrupt latency of the us_ticker release;
    • the mutex hold times;
    • the stack high-water marks.

    If the verdict ever reads RTA FAILED, the row marked ! names the task whose bound exceeds its deadline.
