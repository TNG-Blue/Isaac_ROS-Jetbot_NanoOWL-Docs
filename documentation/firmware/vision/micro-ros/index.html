    micro-ROS over UDP/Ethernet: JetOwl_Vision → Jetson (Isaac_ROS-Jetbot_NanoOWL)¶

    Source

    Snapshot of docs/network/MICROROS_ETHERNET.md from TNG-Blue/JetOwl_Vision at commit 09cd68c (submodule Microcontroller/JetOwl_Vision). Regenerate with Scripts/mkdocs_hooks/snapshot_submodules.py after updating the submodule.

    This document describes what has been built, linked and host-tested in the repository, and separates out what is not yet verified on hardware (section 8). Read section 8 before flashing a board.

    1. Architecture¶

     STM32N655 — Appli (secure, FreeRTOS)                              Jetson Orin (ROS 2 Humble)
 ┌──────────────────────────────────────────────┐                ┌──────────────────────────────┐
 │ IMX335 ─CSI-2─▶ DCMIPP pipe 1 ─▶ RGB565 640×480│                │ micro_ros_agent udp4 :8888   │
 │   ▲ closed AE/AWB (cam_isp_ctrl, "cam" thread,│                │   (shared with JetOwl FC)    │
 │   │  priority 40, ISP statistics → sensor I2C) │                │             │ DDS            │
 │   └──────── feedback: next frame's statistics ─│                │             ▼                │
 │                                               │                │ jetowl_bridge (vision_mcu):  │
 │ defaultTask: CAM_AcquireFrame                 │                │  checks image, rate, latency,│
 │   └▶ UrosApp_OfferFrame (5 Hz):               │                │  lost samples → /diagnostics  │
 │       D×D box filter → decimation D → rgb8    │                │  valid image → camera/image   │
 │ "uros" task (10 ms): reliable rcl_publish ────┼── UDP 1472 B ─▶│                              │
 │ lwIP 2.2.1 ← ethernetif ← ETH1 + LAN8742 RMII  │  192.168.10.0/24│                              │
 └──────────────────────────────────────────────┘                └──────────────────────────────┘

    Principle: the only control loop on this MCU is AE/AWB, and it is always closed on the ISP statistics (docs/camera/CAMERA_CSI_RTOS.md). The micro-ROS path is a best-effort output — every network thread has a lower priority than the camera thread (lwipopts.h): camera 40 > eth_rx 34 > tcpip 33 > uros 24. Losing the network never opens a loop; it only means the Jetson receives no images.

    2. Topic contract¶

    Must match Source/ROS2_JetOwl_Bridge/include/ros2_jetowl_bridge/vision_mcu.hpp on the Jetson.

    Direction Name Type QoS Rate
    V→J /jetowl_vision/image_preview sensor_msgs/Image, rgb8 160×120 (or mono8), frame jetowl_vision_optical_frame reliable 5 Hz
    V→J /jetowl_vision/status diagnostic_msgs/DiagnosticStatus reliable 1 Hz

    Keys of /jetowl_vision/status: streaming, frames, fps, dropped, errors, ctrl_steps, exposure_us, gain_db, mean_r/g/b, preview_made, preview_sent, preview_pub_errors, preview_busy_skips, preview_errors, preview_last_seq, pub_time_ms, pub_time_ms_max, status_pub_errors, eth_rx_drops, uptime_s. Levels: ERROR = camera failure, WARN = camera starting / no new frame within 1 s, OK otherwise.

    Why reliable: XRCE-DDS fragments a sample larger than the MTU only on a reliable stream (rmw_microxrcedds humble, src/rmw_publish.c: uxr_prepare_output_stream_fragmented + flush_session). A reliable publisher is QoS-compatible with both reliable and best-effort subscribers.

    Timestamps: stamp = t0 + tick_ms, tick_ms = the HAL tick in the DCMIPP end-of-frame interrupt, t0 from rmw_uros_sync_session (agent clock = Jetson clock), re-synchronised every 10 s. Resolution 1 ms; the stamp is the end of the frame, later than the exposure centre by ≈ the sensor read-out time + t_exp/2.

    4. Preview image — anti-aliasing filter and decimation¶

    Chain: RGB565 frame (sensor → ISP with calibrated black level/WB/gamma) → D×D box filter → decimation by D → 8-bit quantisation (Appli/Camera/Src/cam_preview.c, pure C, tested on the host).

    • Down-sampling requires low-pass filtering first (Oppenheim & Schafer, Discrete-Time Signal Processing, 3rd ed., §4.6): X_d(e^{jω}) = (1/D) Σ_k X(e^{j(ω−2πk)/D}) — every component at ω = 2πk/D folds onto DC.
    • The box filter y[m,n] = D⁻² Σ_{i,j<D} x[Dm+i, Dn+j] has the separable response |H(ω)| = |sin(Dω/2) / (D sin(ω/2))|: zeros exactly at ω = 2πk/D, DC gain = 1. The largest gain beyond the first zero (2π/D < ω ≤ π): −11.3 dB for D = 4, −12.8 dB for D = 8, → −13.3 dB (single-stage CIC, Hogenauer, IEEE TASSP 29(2), 1981). It is not an ideal filter; residual aliasing is bounded by that side-lobe level — sufficient for a monitoring image, not for photometric measurement.
    • Quantisation: the ideal 8-bit value of a c-bit code k is 255k/(2^c−1); averaging and the linear map commute, so each output is computed from an exact integer sum with one rounding: c8 = ⌊(2·255·S + D²(2^c−1)) / (2D²(2^c−1))⌋ ⇒ error ≤ 0.5 LSB.
    • mono8 = BT.601 luma on gamma-encoded R'G'B' (ITU-R BT.601-7 §2.5.1: Y' = 0.299R' + 0.587G' + 0.114B'), also with a single rounding (64-bit integers).

    Verification (make -C tests/host, test_cam_preview.c, 177 checks; gcc, clang, ASan+UBSan): all 65 536 RGB565 codes map exactly to round(255k/(2^c−1)); luma error ≤ 0.5 LSB; a constant image is preserved for every D = 1…8 (DC gain = 1); every pattern periodic in D (including the Nyquist checkerboard with D = 2) yields exactly its constant mean (zeros at 2πk/D); random frames: every channel and the luma are within 0.5 LSB of the exact mean; unaligned sources / padded pitch give the same result.

    Phase-locked preview schedule (uros_app.c): image k is taken from the first camera frame with tick ≥ kT (t_{k+1} = t_k + T, T = 200 ms), not "previous image tick + T" — the latter makes the period drift up to a multiple of the frame period (7 frames = 233 ms ⇒ 4.3 Hz at 30 fps). The lag behind the grid is 0 ≤ j < one frame period (33 ms), so the long-term rate is exactly 5 Hz and the Jetson side counts lost images exactly, m = round(Δt/T) − 1, when |j₂ − j₁| < T/2 (vision_mcu.hpp). More than one period late (just reconnected to the agent) ⇒ the grid is re-anchored; no burst of catch-up images.

    Buffer hand-over (uros_app.c): one 57 600 B buffer whose FREE/WRITING/READY/SENDING state changes inside a critical section of a few instructions. defaultTask (the only consumer of CAM_AcquireFrame) filters a frame when the 200 ms period is due and the buffer is not SENDING; the uros task sends a READY image. No long-held locks, no allocation; an image being sent is never overwritten (counted in preview_busy_skips).

    5. Bandwidth budget and send time¶

    Library configuration (microros_static_library/library_generation/colcon.meta, changed from the upstream defaults): UCLIENT_CUSTOM_TRANSPORT_MTU = 1472 (= 1500 − 20 IP − 8 UDP: no IP fragmentation), RMW_UXRCE_STREAM_HISTORY_OUTPUT = 16 (= the agent's default UAGENT_CONFIG_RELIABLE_STREAM_DEPTH), …_INPUT = 4. The agent accepts datagrams up to UAGENT_SERVER_BUFFER_SIZE = 65535 B and uses the MTU the client sends in CREATE_CLIENT (ProxyClient.cpp).

    Quantity Value
    rgb8 160×120 image payload 57 600 B (+ ≈ 70 B of CDR Image fields)
    XRCE fragments (≈ 12 B header per fragment) N = ⌈57 670 / 1460⌉ = 40
    Windows (16 fragments per window) 3 (16 + 16 + 8)
    Wire time per fragment 1538 B·8 / 100 Mbit/s = 123 µs (incl. Ethernet header, FCS, preamble, IFG)
    Wire time per image 40 × 123 µs = 4.9 ms
    Link load at 5 Hz 40·1538·8·5 = 2.46 Mbit/s = 2.5 % of 100 Mbit/s

    Blocking-time model of rcl_publish: the agent sends an ACKNACK after every reliable message it receives (Processor.cpp), so each window costs 16·t_wire + RTT: T_pub ≈ N·(t_wire + t_sw) + ⌈N/16⌉·RTT. With RTT < 1 ms on a direct link, T_pub is about 5–10 ms ≪ the 200 ms period (the uros task is busy < 5 % of the time). t_sw (the lwIP/HAL cost per packet) is not yet measured — which is why the firmware reports pub_time_ms and pub_time_ms_max in its status, for verification on the bench. One lost packet triggers the heartbeat path: UXR_CONFIG_MIN_HEARTBEAT_TIME_INTERVAL = 100 ms, so an image with a lost packet costs ≥ 100 ms more (still < the 1 s RMW_UXRCE_PUBLISH_RELIABLE_TIMEOUT).

    Memory (measured with arm-none-eabi-size, Debug -Og): Appli ROM 181.4 KB / 511 KB, RAM 324.9 KB / 1536 KB (two 64 KB heaps: FreeRTOS + micro-ROS; 57.6 KB preview buffer; XRCE output buffer 1472 × 16 B). Without micro-ROS: ROM 54.8 KB, RAM 20.5 KB.

    6. Build¶

    make microros              # first time: builds libmicroros.a in docker (micro_ros_static_library_builder:humble)
make                       # FSBL + Appli (micro-ROS enabled)
make appli MICROROS=0      # network-less build
make agent                 # micro-ROS agent (docker) on the Jetson/host — one agent for both FC and Vision
    • The repository root contains a directory Makefile/, so the entry point is GNUmakefile. The builder runs make print_cflags at the repository root, which prints exactly the firmware's ABI flags (-mcpu=cortex-m55 -mthumb -mfpu=fpv5-d16 -mfloat-abi=hard …).
    • Makefile/common.mk comes from JetOwl_FlightControl: .o files are named after their source path (lwIP, FreeRTOS and the HAL have files with the same name).
    • CMake still works: cd Appli && cmake --preset Debug -DJETOWL_WITH_MICROROS=ON (OFF by default; CI builds CMake without micro-ROS, and a separate job builds the Makefile with micro-ROS).

    7. Jetson side¶

    ros2_jetowl_bridge (vision_mcu link) — see Source/ROS2_JetOwl_Bridge/README.md:

    ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py vision_mcu:=true            # + FC (default)
ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py fc:=false vision_mcu:=true  # camera only

    8. Not yet verified / open items¶

    • Not yet run on hardware. In order: ping 192.168.10.3 → the agent sees a second session → ros2 topic hz /jetowl_vision/image_preview → read pub_time_ms_max to verify section 5.
    • [BOARD] PHY and RMII pins currently follow the NUCLEO-N657X0-Q (LAN8742). The STM32N6570-DK board (the camera module's default in camera_conf.h) uses a different PHY over RGMII — that would require a different PHY driver and MediaInterface configuration, not just different pins. Check the JetOwl_Vision schematic before flashing.
    • ETH1 is not enabled in the .ioc (CubeMX) yet. HAL_ETH_MODULE_ENABLED is defined by a compile flag so that stm32n6xx_hal_conf.h need not be edited; when ETH1 is enabled in CubeMX, define JETOWL_ETH_MSP_FROM_CUBEMX / JETOWL_ETH_HANDLE_FROM_CUBEMX to use the MSP/handle generated by CubeMX.
    • MPU region 0 is used by ethernetif.c for the DMA block; if CubeMX configures the MPU later, the two must be merged.
    • While a frame is held for filtering (~a few ms every 200 ms) the DCMIPP may have to drop a frame if the other buffer is ready (two buffers) — counted in dropped; the AE/AWB loop does not depend on the frame buffers.
