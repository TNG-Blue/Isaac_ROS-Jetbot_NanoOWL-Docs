    Firmware Hardware STM32

    Peripheral configuration in STM32CubeMX¶

    Source

    Snapshot of docs/CUBEMX_SETUP.md from TNG-Blue/JetOwl_FlightControl at commit 23b5ac3 (submodule Microcontroller/JetOwl_FlightControl). Regenerate with Scripts/mkdocs_hooks/snapshot_submodules.py after updating the submodule.

    This list is derived from the actual driver code in Drivers/JetOwl/, not from guesswork. Every line can be traced to a specific function signature or #define.

    0a. Board: NUCLEO-N657X0-Q — pinout looked up¶

    The .ioc is set to board=custom, but the real hardware is a NUCLEO-N657X0-Q (STM32N657X0H3Q, VFBGA264) with ARDUINO Uno V3 / ST Zio and ST morpho headers.

    So the pinout does not have to be guessed. The complete pin assignment is in Application/Interface/Inc/board_config.h, taken from the Zephyr Project board support (boards/st/nucleo_n657x0_q) — a verifiable source.

    Summary of the assignment:

    Function Peripheral Pins Arduino
    Sensors (2 IMUs, baro, INA260) I2C1 SCL=PH9, SDA=PC1 D15 / D14
    GNSS USART3 + DMA + IDLE interrupt TX=PD8, RX=PD9 D1 / D0
    Debug (VCP through ST-LINK) USART1 TX=PE5, RX=PE6 —
    FRAM + 2 × LoRa LR1121 SPI5 (prescaler 16 = 12.5 MHz) SCK=PE15, MISO=PG1, MOSI=PG2; CS FRAM=PA3, LoRa UL=PD7, DL=PA10 D13/D12/D11/D10, D9, A2
    DShot to 4 ESCs TIM1 CH1–CH4 PE9, PE11, PE13, PE14 D3, D7, —, —
    1 kHz control tick TIM6 no pins —

    Do not change board=custom to the Nucleo board in CubeMX — that pulls in the board's default configuration and overwrites the existing 4-context configuration. Only the pins above need to be assigned.

    Three points to confirm before wiring¶

    1. TIM1 CH1–CH4 on PE9/PE11/PE13/PE14 — lower confidence than the other rows. This mapping is the common STM32 convention and matches the STM32N6570-DK board documentation, but it could not be taken directly from the STM32N657 datasheet's alternate-function table. Verified in the repository: TIM1 is an advanced timer on APB2 (stm32n657xx.h:3106, :42139) and GPIO_AF1_TIM1 exists (stm32n6xx_hal_gpio_ex.h:65). In CubeMX select TIM1 → 4 PWM channels: if the pins shown match the table, the table is correct.
    2. The two LoRa LR1121 modules share SPI5 with the FRAM — see §2.1 below and docs/RFLINK.md.
    3. TIM1's 400 MHz clock — check it in the Clock Configuration tab after enabling TIM1/TIM6, since TIM1 is on APB2 and the timer multiplier depends on the APB divider.

    0. Current state: the .ioc is almost empty¶

    JetOwl_FlightControl.ioc currently enables only:

    Mcu.IP0=CORTEX_M55_FSBL   Mcu.IP1=CORTEX_M55_NS   Mcu.IP2=CORTEX_M55_S
Mcu.IP3=NVIC1             Mcu.IP4=NVIC2           Mcu.IP5=NVIC
Mcu.IP6=RCC               Mcu.IP7=RIF             Mcu.IP8=SYS
Mcu.PinsNb=2              (VP_RIF_VS_RIF1, VP_SYS_VS_Systick)

    No I2C, UART, SPI, TIM or ETH at all. Consequence: the 9 driver files just added to the build in AppliNonSecure/CMakeLists.txt compile but do not link, because they call HAL_I2C_*, HAL_UART* and HAL_SPI_* while those HAL modules are not in STM32_Drivers_Src (see AppliNonSecure/mx-generated.cmake — currently only hal, cortex, pwr, pwr_ex, rcc, rcc_ex, gpio, dma, dma_ex, exti, tim, tim_ex).

    CubeMX adds the corresponding HAL modules to mx-generated.cmake when the peripherals are enabled. Do not edit that file by hand.

    1. Peripherals to enable¶

    Peripheral Used by Evidence in the code
    I2C (≥ 1 bus) Adafruit_IMU, Adafruit_INA260, Adafruit_PCA9548, DFRobot_IMU, DFRobot_GNSS, WaveShare_GNSS (optional) Adafruit_IMU_Init(..., I2C_HandleTypeDef *hi2c, ...)
    UART/USART (1–3) Adafruit_GPS, WaveShare_GNSS GPS_Init(gps, UART_HandleTypeDef *huart); WSGNSS_Init_UART(h, huart_nmea, huart_rtcm)
    DMA (for the UART) WaveShare_GNSS HAL_UARTEx_ReceiveToIdle_DMA() in WaveShare_GNSS.c
    SPI (1–2) Adafruit_FRAM, WaveShare_LoRa FRAM_Init(dev, SPI_HandleTypeDef *hspi, cs_port, cs_pin)
    GPIO IMU RESET/INT, GNSS RST/PWR, FRAM CS, LoRa NSS/RST/DIO Adafruit_IMU_Init(..., reset_port, reset_pin, int_port, int_pin)
    TIM Control-loop tick + PWM to the ESCs docs/CONTROL_DESIGN.md
    ETH + LwIP micro-ROS, OTA integrated outside CubeMX: Application/Network, docs/MICROROS_ETHERNET.md

    I2C address of each device (7-bit, from the headers)¶

    Device Address Source
    Adafruit IMU (BNO08x / SH-2) 0x4A (DI=0) or 0x4B (DI=1) Adafruit_IMU.h:32-33
    INA260 (current/voltage) 0x40 default Adafruit_INA260.h:37
    PCA9548 (I2C mux) 0x70 with A2=A1=A0=0 Adafruit_PCA9548.h:30
    BNO055 (DFRobot IMU) 0x28 (COM3=GND) or 0x29 DFRobot_IMU.h:44-45
    BMP280 (pressure) 0x76 (SDO=GND) or 0x77 DFRobot_IMU.h:189-190
    DFRobot GNSS 0x20 DFRobot_GNSS.h:47

    There is no address conflict among these devices → one hardware I2C bus is sufficient. The PCA9548 is only needed when several devices share an address (for example two BNO08x IMUs both at 0x4A).

    Note: the headers already shift the addresses to 8-bit (0x4A << 1) for the HAL, except INA260_I2C_ADDRESS_DEFAULT and PCA9548_BASE_ADDR_7BIT, which are raw 7-bit values. Check how each driver uses its address before passing it to HAL_I2C_Master_Transmit() (the HAL always expects the address shifted left by one bit).

    2. Specific constraints¶

    2.1 Two Core1121-XF (LR1121) LoRa modules on SPI5¶

    The full-duplex control link to Remote_UAV (docs/RFLINK.md) uses the driver Application/RfLink/Src/lr1121.c — the driver takes a port layer (function pointers), so it works on any bus. Drivers/JetOwl/WaveShare_LoRa is a driver for the LR2021 chip (Core2021-XF module) and is not used for this link.

    Signal UL module (receives 2.4 GHz commands) DL module (transmits telemetry)
    NSS (GPIO out, idle high) PD7 (D9) PA10 (A2)
    BUSY (GPIO in) PA8 (A0) PA12 (A3)
    DIO9 / IRQ (rising-edge EXTI) PE10 (D5) PF3 (A4)
    NRESET (GPIO out, idle high) PA9 (A1) PG15 (A5)
    • SPI5: mode 0, MSB first, 8 bit, prescaler 16 (12.5 MHz ≤ 16 MHz for the LR1121, ≤ 33 MHz for the FRAM).
    • The two EXTIs have different line numbers (EXTI10, EXTI3), so they do not share a vector.
    • Every other SPI5 user must take RfLinkApp_SpiLock() (rflink_app.h).
    • RfLinkApp_Start() is already called in app_freertos.c; it returns false until BOARD_CUBEMX_PERIPHERALS_READY = 1.

    2.2 SPI parameters for the FRAM¶

    Adafruit_FRAM.h (comment of FRAM_Init) requires:

    • SPI mode 0 (CPOL=0, CPHA=0)
    • MSB first
    • 8-bit data size
    • a baud-rate prescaler giving ≤ 33 MHz

    2.3 The GNSS UART must enable DMA + the IDLE interrupt¶

    WaveShare_GNSS.c uses HAL_UARTEx_ReceiveToIdle_DMA(). In CubeMX:

    1. Enable USARTx in Asynchronous mode.
    2. DMA Settings tab → Add → select USARTx_RX, mode Circular.
    3. NVIC Settings tab → enable USARTx global interrupt and the corresponding DMA channel interrupt.

    If any step is missing the driver runs but never receives data.

    The driver also requires forwarding from the HAL callbacks:

    void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size) {
    WSGNSS_UART_RxEventCallback(&h_gnss, huart, Size);
}
void HAL_UART_ErrorCallback(UART_HandleTypeDef *huart) {
    WSGNSS_UART_ErrorCallback(&h_gnss, huart);
}

    The module's default baud rate is 460800 (supported range 4800–921600) — WaveShare_GNSS.h:305. The Adafruit GPS uses PMTK, 9600 by default, with a command to switch to 115200 (Adafruit_GPS.h:69-70).

    2.4 WaveShare_GNSS over I2C is currently unusable¶

    The header states it explicitly: Waveshare has not published the LG290P's I2C protocol, so WSGNSS_Init_I2C() only prepares the handle and every transfer returns WSGNSS_NOT_SUPPORTED. In addition, RTCM is only available on UART2. Use WSGNSS_Init_UART() when RTK is needed.

    2.5 CubeMX's "CoupleFile" option¶

    The .ioc sets ProjectManager.CoupleFile=false, i.e. CubeMX does not generate i2c.c/i2c.h, spi.c/spi.h… pairs but puts everything into main.c.

    DFRobot_IMU.h used to #include "i2c.h" → it would not compile. It now includes "stm32n6xx_hal.h" (the driver receives its handle as a parameter, so no global variable is needed).

    If you enable CoupleFile=true in CubeMX (Project Manager → Code Generator → Generate peripheral initialization as a pair of .c/.h files per peripheral), keep that choice consistently and update AppliNonSecure/CMakeLists.txt if needed — but do not go back to including i2c.h in the drivers, because that would make the drivers depend on an IDE configuration option.

    2.6 Parameters precomputed from the clock tree¶

    The following values are derived directly from JetOwl_FlightControl.ioc (RCC.TIMGFreq_Value = 400 MHz, RCC.SPI1Freq_Value = RCC.I2C1Freq_Value = RCC.USART1Freq_Value = 200 MHz) and all divide exactly, so the frequencies obtained are exact, with no rounding error. This matters because all the discretisation in Application/Control/ assumes a fixed Ts exactly equal to its design value.

    They are in Application/Interface/Inc/board_config.h — enter exactly these numbers in CubeMX:

    Item Value Derivation
    Control tick TIM (TIM6/TIM7) PSC = 399, ARR = 999 400 MHz / 400 = 1 MHz; 1 MHz / 1000 = exactly 1000 Hz
    TIM1 for DShot300 PSC = 0, ARR = 1332, T0H=500, T1H=1000 see the table in §2.7
    SPI for the FRAM Prescaler = 8 → 25 MHz 200 MHz / 8 = 25 MHz ≤ the required 33 MHz. Prescaler 4 gives 50 MHz — over the limit
    GNSS UART 460800 baud USARTDIV = 200e6/460800 = 434.03 → error 0.0064 %, well within tolerance
    I2C Fast Mode 400 kHz Do not set TIMINGR by hand — let CubeMX compute it, because the value depends on the bus's actual edge times

    2.7 DShot — the selected ESC protocol¶

    DShot encodes each bit as a pulse width within a fixed period: bit 0 → high for 37.5 % of the period, bit 1 → 75 %. Hence PSC = 0 (counting at the full 400 MHz) and ARR set from the bit rate:

    Variant ARR Actual frequency Error T0H T1H 16-bit frame % of a 1 kHz period
    DShot150 2666 149 981 Hz −0.0125 % 1000 2000 107 µs 10.7 %
    DShot300 1332 300 075 Hz +0.0250 % 500 1000 53 µs 5.3 %
    DShot600 666 599 700 Hz −0.0500 % 250 500 27 µs 2.7 %

    DShot300 is the default because: T0H/T1H fall on round numbers (500/1000), so the 37.5 %/75 % ratios are practically exact; the 53 µs frame takes only 5.3 % of the 1 kHz period, leaving ample room for the turnaround and the ~30 µs telemetry reply; and the lower bit rate tolerates long wires and noise better — decisive when ESCs are connected to the Nucleo with jumper wires. Switching to DShot600 only means changing three constants in board_config.h.

    CubeMX configuration of TIM1¶

    1. Move the AppliNonSecure HAL timebase away from TIM1 (SYS → Timebase Source, e.g. TIM16/TIM17). CubeMX currently uses TIM1 as the 1 kHz timebase. If this is forgotten, FlightControl_Start() refuses to start (esc_prepare() sees TIM1's PSC/ARR do not match DShot) rather than sending malformed frames.
    2. TIM1 → Channel1..4 = PWM Generation CHx (not CHxN), context NonSecure.
    3. Counter Period (ARR) = 1332, Prescaler = 0, auto-reload preload = Enable, Output compare preload = Enable (the firmware also re-enables it). Pulse = 0.
    4. GPDMA1: add a channel (context NonSecure), request TIM1_UP, Memory→Peripheral, Source: increment, Word; Destination: fixed, Word; Normal (not circular, not linked-list). Link the DMA to TIM1 (hdma[TIM_DMA_ID_UPDATE]) — CubeMX generates __HAL_LINKDMA when the TIM1_UP request is selected.
    5. NVIC: enable the GPDMA channel interrupt with priority ≥ 5 (the callback runs in the DMA ISR).
    6. Set BOARD_CUBEMX_PERIPHERALS_READY = 1.

    What the firmware does every 1 ms (flight_control.c, esc_write_dshot):

    mixer → throttle 48..2047 → 16-bit frame (inverted CRC if bidirectional)
  → dshot_build_dma_burst_u32(): 4 channels × (16 bits + 2 idle slots), WORD, interleaved  (host-tested)
  → SCB_CleanDCache_by_Addr (D-cache enabled; 32 B-aligned buffer, 288 B)
  → [bidir] pins PE9/11/13/14 back to AF
  → HAL_TIM_DMABurst_MultiWriteStart(TIM1, DBA = CCR1, DBL = 4, req = UPDATE, 288 BYTE)
TC (GPDMA ISR → HAL_TIM_PeriodElapsedCallback(TIM1) → esc_dma_done):
  → [bidir] pins back to input + pull-up (release the line for the ESC's reply)
  → HAL_TIM_DMABurst_WriteStop

    Why 2 idle slots: the CCRs are preloaded, so slot k written by the DMA at update u_k is output only during [u_(k+1), u_(k+2)). With N slots, TC occurs right after u_(N−1); the last bit (slot 15) has completed when N − 2 ≥ 16 ⇒ ≥ 2 idle slots are needed to release the line at TC without truncating the last bit (dshot.h).

    Time budget: frame (16 + 2) × 3.33 µs = 60 µs; a bidirectional ESC replies after ~30 µs, 21 bits × 2.67 µs = 56 µs ⇒ ~146 µs ≪ 1 ms. If the previous transaction has not finished at the next tick, the frame is dropped and counted (dshot_skipped on /jetowl/status, which must always be 0); DMA errors are counted in dshot_errors.

    DMA burst mode (registers DMAR/DCR) lets one DMA transaction update all four CCRs, so the four ESCs receive their frames in phase — no skew of tens of µs as with four separate timers.

    Bidirectional — mandatory condition¶

    The ESC must run firmware with bidirectional DShot enabled (BLHeli_32 / Bluejay). Otherwise the ESC never answers and the inverted CRC of bidirectional mode makes it drop every frame → the motor does not turn at all. This symptom is easily mistaken for a wiring fault.

    The bidirectional signal is inverted (idle high, each bit a low pulse T0H/T1H): the firmware sets low polarity on CC1..CC4 and pull-ups on the 4 pins; after each frame the pins are released to inputs so that the ESC can drive the line — there is no push-pull contention between MCU and ESC.

    Receiving bidirectional telemetry — GPIO sampling through DMA¶

    Pin-level sampling was chosen over 4-channel input capture: it needs only 1 timer + 1 DMA channel, all 4 ESCs are received simultaneously in one stream, and all decoding is pure software with host tests (dshot_rx_decode_samples, Application/Control/Src/dshot.c).

    Item Configuration Reason
    TIM3 Internal clock, PSC = 0, ARR = 355, no channels, context NonSecure update 400 MHz / 356 = 1.1236 MHz ≈ 3 samples per telemetry bit (r = 2.9955)
    GPDMA1 (second channel) Request TIM3_UP, Peripheral→Memory, Source fixed Word, Destination increment Word, Normal; NonSecure captures GPIOE->IDR at every update; esc_prepare() checks direction/width and refuses to start if they are wrong
    NVIC for that channel priority ≥ 5 decoding runs in the TC ISR (~a few µs)

    Sequence every 1 ms: transmit the frame (60 µs) → TC: release the 4 pins to input + pull-up, start TIM3 + DMA for 192 samples (171 µs) → receive TC: decode each pin → telemetry_apply (GCR + CRC checks) → RPM. Total 231 µs < 1 ms. A channel that does not answer is counted in esc_telem_missing; a corrupted frame in telem_errors; both make that rotor's RPM "unknown", not 0.

    Run-length decoding: from the first falling edge, each run of m samples at the same level = round(m/r) bits. Runs inside a frame must be 1..3 bits long (the GCR table never has more than 2 consecutive zeros — a test enumerating the whole table proves it); otherwise the whole frame is dropped. Correct while the ESC/FC clock mismatch is < 5.5 % (dshot.h); the test checks ±4 % at 7 phases.

    3. Secure / non-secure assignment through RIF — DECISION: KEEP TrustZone¶

    Decided: keep the 4-context architecture. Mcu.ContextProject=SecureNSecure stays; the project structure is not regenerated.

    3.1 How the .ioc represents context assignment¶

    Each context has a key listing the peripherals that belong to it:

    FSBL.IPs           = CORTEX_M55_FSBL,GPDMA1,HDP,HPDMA1,LINKEDLIST,RCC,GPIO,NVIC:I,DEBUG,THREADX
AppliSecure.IPs    = CORTEX_M55_S,GPDMA1,HPDMA1,LINKEDLIST,RCC,RIF,SAU,GPIO,NVIC1:I,DEBUG,THREADX
AppliNonSecure.IPs = CORTEX_M55_NS,GPDMA1:I,HDP,HPDMA1:I,LINKEDLIST,RCC,SYS:I,GPIO:I,NVIC2:I,DEBUG,THREADX
ExtMemLoader.IPs   = EXTMEM_LOADER,EXTMEM_MANAGER,RCC:I,GPIO,DEBUG

    The :I suffix marks the context that generates the initialisation code for that peripheral. For example GPDMA1 appears in both AppliSecure and AppliNonSecure, but only NonSecure has :I — so MX_GPDMA1_Init() is generated in AppliNonSecure.

    In addition, RIF.RIFAWARE.* (554 lines) covers only GPDMA1, GPIO, HPDMA1, LTDC, PWR, RCC, RTC — the peripherals with per-feature access control. I2C/SPI/USART/TIM are not in that group; they are partitioned as whole blocks through RISUP, i.e. through the context assignment above.

    3.2 Boundary principle¶

    The whole 1 kHz control loop runs entirely in the non-secure state, with no NSC calls inside the loop. The secure side keeps only three jobs, all at very low rates, so the NSC veneer cost is not measurable:

    Secure job Call rate Why it is secure
    Motor arm/disarm latch a few times per flight A bug in the NMEA/LoRa/OTA parsers must never spin the motors
    OTA image signature verification once per update The authentication key must not share memory with code that processes network data
    Safety watchdog 1–10 Hz If the non-secure application hangs, the secure side cuts the motor output

    Reason for this boundary: the three parsers in Drivers/JetOwl/ — NMEA from the GNSS, LoRa packets from the ground, firmware from the OTA network — all process data controlled by outside parties. That is precisely the kind of risk TrustZone exists to contain.

    Default rule:

    Peripheral Assigned to Reason
    I2C (IMU, baro, INA260, mux) Non-secure In the 1 kHz control loop; must not go through an NSC veneer
    UART (GNSS, GPS) Non-secure As above
    SPI (FRAM, LoRa) Non-secure As above
    TIM (control tick + ESC PWM) Non-secure As above
    Ordinary GPIO Non-secure
    Motor safety-latch GPIO (if implemented) Secure Out of reach of bugs in the flight application
    OTA key/authentication (RNG, PKA, HASH if used) Secure Security assets

    Symptoms of a wrong assignment¶

    If a peripheral is left Secure and non-secure code accesses it, RIF/IAC raises an Illegal Access Interrupt. It shows up as the callback registered through

    SECURE_RegisterCallback(IAC_ERROR_CB_ID, my_handler);   /* AppliSecure/Core/Src/secure_nsc.c */

    being called, or as the program hanging in Error_Handler for no apparent reason. This is the most common error when starting with TrustZone on the N6 — if a peripheral "does not respond" despite a correct configuration, check RIF first.

    Recommendation: register both callbacks right in AppliNonSecure's main() so that a fault yields diagnostic information instead of a silent hang.

    3.3 Which peripheral is enabled in which context¶

    Peripheral Context :I (generates init code)
    I2C (IMU, baro, INA260, mux) AppliNonSecure yes
    USART/UART (GNSS, GPS) + DMA AppliNonSecure yes
    SPI5 (FRAM + 2 × LoRa LR1121) AppliNonSecure yes
    Control tick TIM (TIM6/TIM7) AppliNonSecure yes
    ESC PWM TIM AppliNonSecure yes
    GPIO (sensor reset/int/CS) AppliNonSecure yes (already GPIO:I)
    Motor safety-latch GPIO (if implemented) AppliSecure yes
    RNG / PKA / HASH (if signed OTA is implemented) AppliSecure yes

    The FSBL stays as it is — it only needs RCC/GPIO to bring up the clocks and XSPI.

    Order of work: enable TIM6 (control tick) first. It is the only peripheral that needs no pinout — a basic timer has no output pins. That lets you verify the whole build + boot + 1 kHz tick chain before touching any sensor.

    3.4 IMU read path (Application/Interface/Src/imu_acq.c)¶

    Item Configuration Reason
    I2C1 Fast Mode 400 kHz, PH9 SCL / PC1 SDA (board_config.h §2.1), context NonSecure bus budget ~41 % (airframe_config.h §6.3)
    PE0 GPIO_EXTI0, falling edge, pull-up the BNO08x's active-low INT; HAL_GPIO_EXTI_Falling_Callback is in imu_acq.c
    NVIC EXTI0 priority ≥ 5 (e.g. 6) the ISR calls osThreadFlagsSet — must be ≥ configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY
    PD0, PD5 GPIO_Output BNO08x / BNO055 RESET

    After generating: set BOARD_CUBEMX_PERIPHERALS_READY = 1 and build with make DRIVERS=1 (Make) — the CMake build already includes Drivers/JetOwl. Check ros2 topic echo /jetowl/status: imu_fusion = 3, imu_rejected not increasing, then perform the static check of CONTROL_DESIGN.md §1.4.

    4. After configuring CubeMX¶
