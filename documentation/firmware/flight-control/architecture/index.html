    JetOwl_FlightControl architecture (STM32N657X0HxQ)¶

    Source

    Snapshot of docs/ARCHITECTURE.md from TNG-Blue/JetOwl_FlightControl at commit 23b5ac3 (submodule Microcontroller/JetOwl_FlightControl). Regenerate with Scripts/mkdocs_hooks/snapshot_submodules.py after updating the submodule.

    This document describes the actual structure, verified against the code in this repository, not a theoretical one. Every address and size is taken from the linker scripts and configuration files in the repository.

    1. Why there are four directories, each with its own main.c¶

    The four directories FSBL/, AppliSecure/, AppliNonSecure/ and ExtMemLoader/ are not four modules of one program. They are four independent firmware images, each compiled into its own .elf file and loaded at a different location on the chip. Every executable C image needs exactly one main() entry point — so a separate main.c per directory is a necessity, not duplication.

    Evidence in the repository:

    • JetOwl_FlightControl.ioc: 

      Mcu.ContextNb=4
Mcu.Context0=FSBL
Mcu.Context1=AppliSecure
Mcu.Context2=AppliNonSecure
Mcu.Context3=ExtMemLoader
Mcu.ContextProject=SecureNSecure

    • mx-generated.cmake (at the root): calls ExternalProject_Add() four times, each pointing to a subdirectory with its own CMakeLists.txt, toolchain and linker script.

    Root cause: the STM32N657 has no internal user flash¶

    The STM32N6 family has only a Boot ROM (programmed by ST, read-only) and RAM (large AXISRAM/SRAM). Unlike the STM32F4/H7 there is no internal flash for user programs. Code must therefore:

    • reside in external XSPI flash, or
    • be loaded into RAM and run there (LRUN mode — Load & RUN).

    Both approaches need an earlier software stage that sets up the clocks and the external memory. That is why a multi-stage boot chain is mandatory.

    2. Boot chain¶

      [Boot ROM in the chip]          provided by ST, cannot be changed
          |  finds and loads the FSBL
          v
  [FSBL]  AXISRAM2                configures clocks, RIF, XSPI
          |  jumps to the application
          v
  [AppliSecure]  secure state     configures SAU/TrustZone, exports NSC functions
          |  NonSecure_Init() -> 0x24100400
          v
  [AppliNonSecure]  non-secure    <<< THE FLIGHT APPLICATION RUNS HERE >>>

    ExtMemLoader is not part of this chain — see section 4.

    3. Memory map¶

    Image Linker script ROM (ORIGIN / LENGTH) RAM (ORIGIN / LENGTH)
    FSBL/ STM32N657XX_AXISRAM2_fsbl.ld 0x34180400 / 255K 0x341C0000 / 256K
    AppliSecure/ STM32N657XX_LRUN_s.ld 0x34000400 / 399K 0x34064000 / 624K
    AppliNonSecure/ STM32N657XX_LRUN_ns.ld 0x24100400 / 511K 0x24180000 / 512K

    The most common confusion: the 0x34… and 0x24… aliases¶

    0x34000000 and 0x24000000 are the same physical RAM, seen through two different address windows:

    • 0x34… = secure alias — accessible only to code running in the secure state.
    • 0x24… = non-secure alias — accessible to non-secure code.

    This is the standard Arm TrustZone-M mechanism. In Drivers/CMSIS/Device/ST/STM32N6xx/Include/stm32n657xx.h:3016:

    #define SRAM2_AXI_BASE_NS   0x24100000UL

    And in AppliSecure/Core/Src/main.c:

    #define VECT_TAB_NS_OFFSET       0x00400
#define VTOR_TABLE_NS_START_ADDR (SRAM2_AXI_BASE_NS|VECT_TAB_NS_OFFSET)  /* = 0x24100400 */

    0x24100400 is exactly ORIGIN(ROM) in AppliNonSecure/STM32N657XX_LRUN_ns.ld. That is how AppliSecure knows where to jump.

    The 0x400 (1 KB) offset at the start of each ROM region is reserved for the boot header that ST's signing/packaging tool inserts in front of the firmware image.

    LRUN and the other linker scripts¶

    • LRUN = **L**oad & RUN: the image is loaded into RAM and executed from RAM. This is the configuration in use.
    • AppliSecure/ also contains unused alternatives: STM32N657XX_ROMxspi1.ld, STM32N657XX_ROMxspi2_RAMxspi1.ld, STM32N657XX_ROMxspi3_RAMxspi1xspi2.ld, … — these are execute-in-place (XIP) configurations running directly from XSPI1/XSPI2/XSPI3 flash. Switching to XIP means changing the STM32_LINKER_SCRIPT variable in AppliSecure/CMakeLists.txt.

    4. Role of each image¶

    FSBL/ — First Stage Boot Loader¶

    The first of your code to run. Its job: configure the system clock, configure RIF (Resource Isolation Framework), initialise XSPI for external-flash access, then hand over to the application.

    SystemClock_Config() is at FSBL/Core/Src/main.c:107:

    • Supply: PWR_EXTERNAL_SOURCE_SUPPLY, voltage scale 1
    • HSI on, HSIDiv = 1
    • PLL1: HSI source, M=1, N=25, P1=1, P2=1
    • Distribution through IC2 / IC6 / IC11, each with ClockDivider = 4
    • AHBCLKDivider = DIV2, APB½/⅘ = DIV1

    Note: the function temporarily switches back to HSI before moving to the PLL (see the HAL_RCC_GetClockConfig → CPUCLKSOURCE_HSI sequence). This ordering is required on the N6 to avoid losing the clock during the source switch.

    When to change it: CPU/bus frequency or clock source changes. The A/B boot-image selection for OTA lives in FSBL/Boot/ (called from USER CODE 2 of main.c) — see docs/OTA.md.

    AppliSecure/ — secure application (TrustZone secure state)¶

    Compiled with -mcmse (AppliSecure/CMakeLists.txt:28). Its job:

    1. Configure the SAU / security partitioning through AppliSecure/Core/Inc/partition_stm32n657xx.h.
    2. Export NSC (Non-Secure Callable) functions in AppliSecure/Core/Src/secure_nsc.c. There is currently one: 
      CMSE_NS_ENTRY void SECURE_RegisterCallback(SECURE_CallbackIDTypeDef CallbackId, void *func);
      which lets the non-secure side register callbacks for a SecureFault or an illegal-access (IAC) error.
    3. HAL_SuspendTick(), then NonSecure_Init() — sets SCB_NS->VTOR, loads MSP_NS, fetches the non-secure reset handler and jumps to it. It never returns.

    When to change it: to place safety/security assets out of reach of bugs in the flight application — for example the OTA authentication key, the motor arm/disarm latch, a safety watchdog. Each such service adds a CMSE_NS_ENTRY function to secure_nsc.c and its declaration to Secure_nsclib/secure_nsc.h.

    AppliNonSecure/ — flight application¶

    Almost all code is written here. The complete chain: read sensors → filter → disturbance estimation → controller → mixer → ESC/servo → feedback.

    AppliNonSecure/Core/Src/main.c is currently an empty template: HAL_Init() then while(1){}. There is no SystemClock_Config() — the clocks have already been configured by the FSBL.

    ExtMemLoader/ — flash-programming tool, does NOT run on the drone¶

    This is the most frequently misunderstood part. ExtMemLoader builds an external loader (.stldr) for STM32CubeProgrammer / STM32CubeIDE — it teaches the programming tool how to erase/write/read the XSPI flash on your board. It runs temporarily in the chip's RAM while you press the program button, then disappears.

    It therefore has no main.c but ExtMemLoader/Core/Src/extmemloader_init.c — an entry point following the external-loader convention, not the application convention.

    ExtMemLoader/postbuild.sh copies the .elf file as a .stldr into STM32CubeProgrammer's ExternalLoader/ directory (located through the STM32_PRG_PATH environment variable).

    When to change it: when the board's XSPI flash part changes.

    5. Build-order constraint¶

    AppliSecure/CMakeLists.txt:31 generates the CMSE import library:

    set(STM32_LINKER_OPTION -Wl,--cmse-implib\ -Wl,--out-implib="${CMAKE_CURRENT_SOURCE_DIR}/../Secure_nsclib/secure_nsclib.o")

    AppliNonSecure/mx-generated.cmake links that very file:

    set (MX_LINK_LIBS
    STM32_Drivers
    ${TOOLCHAIN_LINK_LIBRARIES}
    ${CMAKE_CURRENT_SOURCE_DIR}/../Secure_nsclib/secure_nsclib.o
)

    So the root mx-generated.cmake declares:

    ExternalProject_Add(JetOwl_FlightControl_AppliNonSecure
    ...
    DEPENDS  JetOwl_FlightControl_AppliSecure
)

    Practical consequence: after adding or changing a CMSE_NS_ENTRY function in AppliSecure, you must rebuild AppliSecure first; otherwise AppliNonSecure links against a stale secure_nsclib.o and fails in a way that is very hard to diagnose (calls jump to wrong veneer addresses).

    6. Where to write code¶

    Task Location
    Flight logic: filtering, estimation, control, mixer Application/Control/ (pure maths, no HAL)
    Glue between HAL and flight logic, scheduler, airframe configuration Application/Interface/
    New sensor/device driver Drivers/JetOwl/{Inc,Src}/
    Driver calls, initialisation, main loop AppliNonSecure/Core/Src/main.c (inside a USER CODE block)
    Clock / boot / external flash changes FSBL/Core/Src/main.c
    Security services (OTA key, arming latch) AppliSecure/Core/Src/secure_nsc.c + Secure_nsclib/secure_nsc.h
    Change of the board's XSPI flash ExtMemLoader/

    Mandatory rule for CubeMX-generated files¶

    STM32CubeMX overwrites the files under Core/ every time "Generate Code" is pressed. Only the parts between the marker pairs are preserved:

    /* USER CODE BEGIN 2 */
   ... your code is safe here ...
/* USER CODE END 2 */

    Code outside the markers is lost. That is why the flight logic lives in Application/ and Drivers/JetOwl/ — directories CubeMX never touches — and main.c contains only calls.

    Conversely, the CMakeLists.txt files in the four subdirectories are safe to edit — their own header says so:

    # This file is generated only once,
# and is not re-generated if converter is called multiple times.
# User is free to modify the file as much as necessary

    mx-generated.cmake, however, must not be edited ("File automatically-generated by STM32CubeMX - Do not modify").

    6b. The Application/ directory and host tests¶

    Application/Control/{Inc,Src}/     pure control maths — NO HAL includes
Application/Interface/Inc/         airframe_config.h (airframe parameters)
tests/host/                        unit tests built with the native gcc

    The rule "Application/Control/ must not include HAL" is not a formality — it is what makes it possible to run the unit tests on an ordinary computer, without a board:

    cmake -S tests/host -B build-host
cmake --build build-host
ctest --test-dir build-host --output-on-failure

    Modules currently in Application/Control/:

    File Content Mathematical source
    ctrl_math.c vectors, quaternions, attitude integration —
    attitude_filter.c Mahony filter on SO(3) + gyro-bias estimation Mahony et al., IEEE TAC 53(5), 2008
    eso.c Extended State Observer, exact ZOH discretisation Han 2009; Gao 2003; Guo & Zhao 2011
    pid.c discrete PID, derivative filtering, back-calculation anti-windup Åström & Hägglund, Advanced PID Control, 2006
    mixer.c quad-X control allocation, torque-priority saturation Leishman 2006; Johansen & Fossen 2013
    rate_loop.c 1 kHz rate loop: ESO + PID + mixer on three axes, feedback of the achieved torque composition of the above
    scheduler.c fixed-tick scheduling by rate group, overrun detection —
    esc_map.c rotor speed → PWM pulse width (fallback, not used on the main path) —
    dshot.c DShot protocol: framing + CRC + GCR telemetry decoding, DMA bit patterns CONTROL_DESIGN.md §6
    rotor_speed.c 1 kHz rotor-speed loop on RPM telemetry: two degrees of freedom (reference model + inverse-model feed-forward) + LPF + SIMC PI, FF_ONLY/STARTUP/STALLED modes Skogestad 2003; Åström & Murray 2021; Bangura & Mahony 2012 — CONTROL_DESIGN.md §6.6
    imu_fusion.c dual-IMU fusion by weighted quaternion averaging Markley et al., JGCD 30(4), 2007
    foc.c FOC for an encoder-equipped BLDC: Clarke/Park, SVPWM, two current PI loops. Runs in the ESC, not on the MCU — kept as a reference Park 1929; Clarke 1943; van der Broeck 1988
    qp_solver.c box-constrained QP, fast gradient with a bounded iteration count Nesterov 1983/2004; Richter et al. 2012; Gershgorin 1931
    mpc.c primary MPC at 50 Hz, condensed form, acceleration constraints Rawlings et al. 2017; Maciejowski 2002
    supervisor.c MPC/PID arbiter with reflex semantics CONTROL_DESIGN.md §4.1b

    Application/Interface/Src/flight_control.c is the only file of the control chain that #includes HAL — it connects the tick TIM ISR to scheduler → rate_loop → rotor_speed → DShot. The TIM-dependent parts sit behind #if defined(BOARD_TIM_*), so the file already compiles (with a #warning reminding that the tick is not running yet).

    Derivations: docs/CONTROL_DESIGN.md.

    7. Build¶

    # Build all four contexts
cmake --preset Debug
cmake --build --preset Debug

# Build a single context
cmake --preset Debug -DBUILD_CONTEXT=FSBL
cmake --build --preset Debug

    The BUILD_CONTEXT variable is tested in the root mx-generated.cmake (if((${BUILD_CONTEXT} MATCHES .*FSBL.*) OR (NOT DEFINED BUILD_CONTEXT))).

    Requirements: arm-none-eabi-gcc (toolchain declared in gcc-arm-none-eabi.cmake), CMake ≥ 3.22, Ninja.

    Make build (with micro-ROS over Ethernet)¶

    make microros     # first time: builds libmicroros.a in docker
make              # GNUmakefile -> Makefile/Makefile: AppliSecure, then AppliNonSecure

    The CMake configuration above is the network-less build; lwIP + micro-ROS exist only in Makefile/AppliNonSecure. Details: docs/MICROROS_ETHERNET.md.

    OTA¶

    The sample STM32N6_OTA driver (never part of the build, no server checksum, no A/B, no bootloader) has been replaced by a complete OTA layer: Application/Ota/ (pure C, host-tested), Application/Ota/Port/ (XSPI2 NOR, lwIP, FreeRTOS task) and an A/B bootloader in FSBL/Boot/. The real XSPI flash map, package format, boot state machine and proofs: docs/OTA.md.
