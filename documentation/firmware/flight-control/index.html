    JetOwl_FlightControl¶

    Source

    Snapshot of README.md from TNG-Blue/JetOwl_FlightControl at commit 23b5ac3 (submodule Microcontroller/JetOwl_FlightControl). Regenerate with Scripts/mkdocs_hooks/snapshot_submodules.py after updating the submodule.

    Flight-control firmware for a multirotor built on the STM32N657X0HxQ (Arm Cortex-M55, TrustZone-M), generated from STM32CubeMX as a four-context project.

    The control code in this repository follows one rule: every formula must be traceable to a verifiable source — a peer-reviewed paper, a textbook, or a datasheet — and the source is cited in the header of the file that implements it. No hand-tuned or invented coefficients. The derivations live in docs/CONTROL_DESIGN.md; the code is only their implementation.

    Not flight-ready. The airframe constants in Application/Interface/Inc/airframe_config.h (k_f, k_m, arm length, inertia) are placeholder values used by the unit tests. They must be measured on the real airframe (procedure in docs/CONTROL_DESIGN.md §5.4) before propellers are fitted. The CubeMX peripherals (I2C/SPI/UART/TIM) are not enabled yet, so the control tick does not run on hardware — see docs/CUBEMX_SETUP.md and the status table below.

    Control architecture¶

    sensors → calibration → filter → disturbance observer → controller → mixer → actuators
   ↑                                                                            │
   └───────────────────────── feedback (closed loop) ───────────────────────────┘

    Three cascaded tiers, separated by at least a 3–5× time-scale ratio:

    Tier Rate Role Implementation
    MPC 50 Hz primary — look-ahead, explicit constraints mpc.c + qp_solver.c
    Attitude 250 Hz intermediate — q_sp, q_hat → omega_sp attitude_filter.c
    PID + ESO 1 kHz secondary — reflex, always running rate_loop.c, pid.c, eso.c
    FOC ~20 kHz inside the ESC (reference implementation only) foc.c

    A supervisor (supervisor.c) arbitrates between MPC and PID. When the tracking error spikes, the ESO-estimated disturbance jumps, or a measurement fails, it discards the MPC plan rather than blending it — a plan computed for a world that no longer exists actively pulls the aircraft toward an infeasible trajectory. Entry and exit use different thresholds plus a dwell time, so the arbiter cannot chatter.

    The loop is closed at the IMU/GNSS. The one segment that would otherwise be open — ESC command → actual rotor speed — is closed with bidirectional DShot300 telemetry (dshot.c, docs/CONTROL_DESIGN.md §6).

    Modules in Application/Control/¶

    File What it does Mathematical source
    ctrl_math.c vectors, quaternions, attitude integration —
    attitude_filter.c Mahony filter on SO(3) + gyro-bias estimation Mahony et al., IEEE TAC 53(5), 2008
    imu_fusion.c dual-IMU fusion by weighted quaternion averaging Markley et al., JGCD 30(4), 2007
    eso.c Extended State Observer, exact ZOH discretization Han 2009; Gao 2003; Guo & Zhao 2011
    pid.c discrete PID, derivative filtering, back-calculation anti-windup Åström & Hägglund, Advanced PID Control, 2006
    mpc.c condensed-form MPC with acceleration constraints Rawlings et al. 2017; Maciejowski 2002
    qp_solver.c box-constrained fast-gradient QP with a proven iteration bound Nesterov 1983/2004; Richter et al. 2012
    supervisor.c MPC/PID arbiter with reflex semantics CONTROL_DESIGN.md §4.1b
    mixer.c quad-X control allocation, torque-priority saturation Leishman 2006; Johansen & Fossen 2013
    rate_loop.c 1 kHz rate loop: ESO + PID + mixer on three axes composition of the above
    scheduler.c fixed-tick scheduling by rate group, overrun detection —
    dshot.c DShot framing, CRC, GCR telemetry decoding, DMA bit patterns CONTROL_DESIGN.md §6
    esc_map.c rotor speed → PWM pulse width (fallback path) —
    foc.c Clarke/Park, SVPWM, dual current PI loops — runs in the ESC, kept as reference Park 1929; Clarke 1943; van der Broeck 1988

    Full reference table: docs/CONTROL_DESIGN.md §8. Known limitations are listed honestly in §9.

    Repository layout¶

    The four top-level firmware directories are four independent firmware images, not four modules of one program — which is why each has its own main.c. The STM32N6 has no user flash, only boot ROM and RAM, so code must be loaded into RAM (LRUN) or executed from external XSPI flash; that forces a multi-stage boot chain.

    Boot ROM (ST, fixed)
   └─> FSBL/            clock, RIF, XSPI      AXISRAM2  0x34180400
        └─> AppliSecure/    SAU/TrustZone, NSC exports  0x34000400
             └─> AppliNonSecure/  <<< the flight application >>>  0x24100400
    Directory What it is When you touch it
    FSBL/ First Stage Boot Loader, runs first clock / boot / XSPI flash configuration
    AppliSecure/ TrustZone secure application (-mcmse) security services (OTA keys, arming latch)
    AppliNonSecure/ flight application init + main loop (calls only, no logic)
    ExtMemLoader/ .stldr tool for STM32CubeProgrammer — does not run on the drone changing the XSPI flash part
    Application/Control/ pure control math — no HAL includes filters, observers, controllers, mixer
    Application/Interface/ glue between HAL and Control/: scheduler, airframe/board config tick ISR, device I/O
    Application/RfLink/ LR1121 driver + full-duplex LoRa link protocol (pure C, identical copy in Remote_UAV/src/rflink/) radio link changes — edit both repos
    Drivers/JetOwl/ sensor and device drivers (IMU, GNSS, LoRa, FRAM, INA260, PCA9548, OTA) new hardware
    tests/host/ native unit tests for the control math every control change

    0x34… and 0x24… address the same physical RAM through the secure and non-secure aliases — this is standard Arm TrustZone-M behaviour, not a typo. The 0x400 offset at the start of each ROM region is the boot header inserted by ST's signing/packaging tool. Details: docs/ARCHITECTURE.md.

    Rules that are not optional¶

    1. Files under Core/ are generated by CubeMX and will be overwritten. Only write between /* USER CODE BEGIN x */ and /* USER CODE END x */.
    2. Never edit mx-generated.cmake (at any level) — it is generated. The per-context CMakeLists.txt files are generated once and are safe to edit.
    3. Build AppliSecure before AppliNonSecure. Secure emits Secure_nsclib/secure_nsclib.o (the CMSE import library) that NonSecure links against; a stale copy produces wrong veneer addresses.
    4. Do not commit build/.
    5. No HAL_Delay() inside the control loop — use a fixed-rate TIM interrupt.
    6. No HAL includes in Application/Control/. That constraint is what makes the host tests possible.

    Building¶

    Requires arm-none-eabi-gcc (with libnewlib-arm-none-eabi), CMake ≥ 3.22, and Ninja.

    # all four contexts
cmake --preset Debug
cmake --build --preset Debug

# a single context
cmake --preset Debug -DBUILD_CONTEXT=FSBL
cmake --build --preset Debug

    Make build with micro-ROS over Ethernet (talks ROS 2 to the Jetson)¶

    make microros   # once: build libmicroros.a in docker (microros/micro_ros_static_library_builder:humble)
make            # AppliSecure, then AppliNonSecure with lwIP + micro-ROS (UDP to 192.168.10.1:8888)
make -C Makefile nonsecure MICROROS=0   # without networking

    The repository root holds the CubeMX Makefile/ directory, so the root entry point is GNUmakefile. Topic contract, frame conversion, failsafe derivation and build notes: docs/MICROROS_ETHERNET.md. The Jetson side is Source/ROS2_JetOwl_Bridge in Isaac_ROS-Jetbot_NanoOWL.

    ExtMemLoader has a CubeMX-generated post-build step that invokes the Windows cmd shell, so it builds only in an STM32CubeIDE environment. It is a programmer tool, not drone firmware.

    Host tests (no hardware needed)¶

    cmake -S tests/host -B build-host
cmake --build build-host
ctest --test-dir build-host --output-on-failure

    13 test binaries, currently 13/13 passing. The control library is compiled with -Wall -Wextra -Werror -Wconversion -Wdouble-promotion -Wshadow, so a warning is a build failure. The tests compare against analytic solutions and independently computed reference values — compiling is not proof that an algorithm is correct.

    Continuous integration¶

    .github/workflows/build.yml runs three separate stages so a red build points straight at the cause:

    1. host-tests — actually runs the control math on the host.
    2. arm-compile — compiles every project source with the real ARM compiler (catches width, alignment, float and Cortex-M55/Helium issues the host compiler cannot see).
    3. firmware-link — links FSBL and AppliSecure and reports sizes. AppliNonSecure is not linked yet: its drivers call HAL_I2C_*/HAL_SPI_*/ HAL_UART_* and need the TIM handles CubeMX generates, and those peripherals are not enabled in the .ioc yet.
