    Firmware OTA

    OTA: over-the-network firmware updates for JetOwl_FlightControl and JetOwl_Vision¶

    Source

    Snapshot of docs/OTA.md from TNG-Blue/JetOwl_FlightControl at commit 23b5ac3 (submodule Microcontroller/JetOwl_FlightControl). Regenerate with Scripts/mkdocs_hooks/snapshot_submodules.py after updating the submodule.

    This document describes what has been written, compiled, linked and tested on the host in the repository, and separates out what is not yet verified on hardware (section 9). Read section 9 before flashing a board. The OTA layer (Application/Ota/, FSBL/Boot/, tools/ota_pack.py, tests/host/test_ota.c) is identical in JetOwl_Vision (Appli/Ota/); only ota_board.h differs.

    1. Architecture¶

     Server_OTA (Go, Isaac_ROS-Jetbot_NanoOWL)        STM32N6 (FC or Vision)
 192.168.1.101:8080                               ┌────────────────────────────────────────────┐
 ┌──────────────────────────────┐   HTTP/TCP      │ "ota" task (ota_service.c, low priority)   │
 │ GET /api/ota/manifest?device │◀──────────────── │   ota_client: manifest → download → SHA-256│
 │ GET /download?file= (Range)  │◀──────────────── │   → flash read-back → header check → READY │
 │ POST /api/ota/report         │◀──────────────── │   ota/apply: set pending, persist, reset   │
 │ POST /upload  (.fw validated) │                 │   trial image healthy 30 s → confirm; IWDG │
 └──────────────────────────────┘                  │ micro-ROS: /jetowl/ota/start, /ota/apply   │
          ▲ make ota-upload                        ├────────────────────────────────────────────┤
          │                                        │ FSBL (fsbl_boot.c): read boot record →     │
   tools/ota_pack.py → <device>_v<M.m.p>.fw        │ choose slot → SHA-256 → copy to RAM → IWDG │
                                                   │ (if trial) → jump                          │
                                                   ├────────────────────────────────────────────┤
                                                   │ NOR XSPI2 (64 MB): FSBL | bootctl×2 | A | B │
                                                   └────────────────────────────────────────────┘

    Principles: OTA never overwrites the running image (A/B); a new image becomes the primary image only after it has proven itself healthy; every failure (power loss, network loss, corrupted image, hanging image) leads back to a bootable state.

    2. Flash map (Ota/Inc/ota_layout.h)¶

    Offset Size Content
    0x0000_0000 1 MB FSBL (signed with STM32_SigningTool, loaded by the Boot ROM)
    0x0010_0000 4 KB boot control record, copy 0
    0x0010_1000 4 KB boot control record, copy 1
    0x0020_0000 4 MB slot A (.fw package)
    0x0060_0000 4 MB slot B

    Bus (memory-mapped) address = 0x7000_0000 + offset. [BOARD] MX25UM51245G NOR on XSPI2 (NUCLEO-N657X0-Q, STM32N6570-DK): 4 KB sector, 64 KB block, 256 B page.

    3. The .fw package (JOWL v1, Ota/Inc/ota_image.h)¶

    A 256 B little-endian header followed by contiguous segments: magic JOWL, device (jetowl_fc / jetowl_vision), version M.m.p, total_size, entry (vector table), ≤ 4 segments {load_addr, offset, size}, SHA-256 of the payload, CRC-32 of the header.

    Device Segments Permitted RAM windows (ota_board.h)
    jetowl_fc AppliSecure.bin @ 0x34000400, AppliNonSecure.bin @ 0x34100400 (secure alias of 0x24100400) [0x34000400, 0x34064000), [0x34100400, 0x34180000)
    jetowl_vision JetOwl_Vision_Appli.bin @ 0x34000400 [0x34000400, 0x34080000)

    The FSBL runs at 0x34180400… (AXISRAM2), outside every window: a corrupted or malicious package cannot overwrite the running FSBL. Invariants checked (C: ota_image_parse, Go: ParsePackageHeader, Python: ota_pack.py parse): contiguous segments, total = 256 + Σ size, each segment inside one window, no overlap, entry = load_addr[0] aligned to 128 B (ARMv8-M VTOR), reserved fields = 0.

    Integrity: CRC-32/ISO-HDLC has a Hamming distance ≥ 2 at every length, so every single-bit error in the header is detected (the test flips every one of the 2048 bits: none slips through, in both C and Go). The content is protected by SHA-256 (FIPS 180-4) — checked four times: (1) downloaded file == the manifest's sha256, (2) full read-back of the slot from flash == manifest (catches silent flash write errors), (3) payload == header (ota_slot_verify), (4) the FSBL hashes the copy in RAM — exactly what will run — before jumping. SHA-256 protects against corruption, not against forgery (section 9).

    4. Server (Isaac_ROS-Jetbot_NanoOWL/Server_OTA)¶

    Endpoint Meaning
    GET /api/ota/manifest?device=<id> latest valid release for the device, key=value text (device, version, file, size, sha256); 404 if none
    GET /download?file=<file> download; supports Range: bytes=n- → 206 + Content-Range (used to resume)
    POST /upload (multipart firmware) stores a package; a .fw must pass the header + SHA-256 check and be named <device>_v<M.m.p>.fw; never overwrites (409)
    POST /api/ota/report?device=&version=&state=&detail= the MCU reports its state (running, trial, downloaded, staged, confirmed, error…)
    GET /api/ota/devices last state of each MCU (JSON)

    Versions are compared numerically (1.10.0 > 1.9.99). A package with the newest name but a corrupted content is skipped (an MCU is never invited to download it).

    5. A/B boot state machine (Ota/Inc/ota_bootctl.h)¶

     application: download + verify slot S ≠ running ── ota/apply ──▶ pending = S, trials = 0, PERSIST, reset
 FSBL, pending ≠ NONE:
     trials < 3 and S valid ─▶ trials++, PERSIST, boot S in trial mode (IWDG 8 s)
     otherwise              ─▶ pending = NONE (rollback), PERSIST, boot active
 FSBL, active corrupted ─▶ the other slot if valid (fallback)
 application in trial + continuously healthy for 30 s ─▶ confirm: active = S, pending = NONE, PERSIST

    Atomic update, proven: two copies in two sectors; the new copy (seq = seq_max + 1) is always written to the sector not holding the newest copy; reading selects the CRC-valid copy with the largest seq under serial-number arithmetic (RFC 1982, correct even when seq wraps at 2³²). A power loss during any operation of one persist leaves the old sector intact ⇒ the state read back is either old or new, never a mixture. test_ota.c cuts power at every operation (half-erased, half-written) from four different histories and checks exactly this property.

    No infinite loop: trials is incremented and persisted before jumping into the trial image, so an image that hangs or keeps resetting runs at most OTA_MAX_TRIALS = 3 times (the test simulates 10 boots: a hanging image ⇒ exactly 3 trials, then back to A; a healthy image ⇒ one trial, then confirm). If the FSBL cannot persist the record it does not boot the trial image.

    The application knows which slot it runs without anything passed from the FSBL: pending ≠ NONE while the application runs ⇔ the application is the trial image.

    IWDG: 32 kHz LSI, prescaler 256, reload 1000 ⇒ T = 1001·256/32000 = 8.008 s. The FSBL enables it only when booting a trial image; the IWDG cannot be stopped until the next reset, so ota_service refreshes it for the whole session. Invariant: the interval between two refreshes is < 8 s. The task refreshes at the start of every cycle (≤ 1 s) and before every blocking operation on the network and flash; each blocking operation is bounded: connect 2 s (non-blocking + select, because lwIP's blocking connect can wait tens of seconds when the server is down), send/recv 5 s, erasing one flash block ≤ 2 s (datasheet); the computation between two operations takes microseconds ⇒ the largest interval is ≈ 5 s < 8 s. A stopped OTA server therefore does not reset or roll back a healthy image. If the ota task is starved for

    8 s ⇒ reset ⇒ the FSBL counts one more trial.

    Confirmation ("healthy")¶

    OTA_SVC_CONFIRM_S = 30 s of continuous health — a policy, not a control constant: much longer than the status period (1–2 Hz), the agent ping (1 Hz) and the time synchronisation (10 s), so an image that only half starts is not confirmed.

    Device Healthy when Applied (reset) when
    FC micro-ROS session alive and the control TIM tick running (when BOARD_CUBEMX_PERIPHERALS_READY = 1) disarmed; arming is refused for the whole trial-boot session (even after confirmation, because the IWDG keeps running) — power-cycle once, then fly
    Vision micro-ROS session alive and the camera streaming (UROS_OTA_CONFIRM_REQUIRES_CAMERA) always (no actuator)

    6. Usage¶

    # 1) Release (on the build machine): package and upload to the server
make ota-upload VERSION=1.2.3              # FC  -> jetowl_fc_v1.2.3.fw
make ota-upload VERSION=1.0.1              # Vision (JetOwl_Vision repository) -> jetowl_vision_v1.0.1.fw
#    (OTA_SERVER=192.168.1.101:8080 by default; package only: make ota VERSION=...)

# 2) On the Jetson (ROS 2): check + download, monitor, apply
ros2 service call /jetowl/ota/start std_srvs/srv/Trigger
ros2 topic echo /jetowl/status        # fw_version, ota_state, ota_progress_pct, ota_available, ota_error
ros2 service call /jetowl/ota/apply std_srvs/srv/Trigger    # the FC must be disarmed
#    Vision: /jetowl_vision/ota/start, /jetowl_vision/ota/apply, /jetowl_vision/status
#    ros2_jetowl_bridge forwards the firmware status to /diagnostics, so ota_* is there too.

# 3) Server: which device runs which version
curl http://192.168.1.101:8080/api/ota/devices

    ota_state: idle → checking → up_to_date | downloading → ready → (ota/apply) applying → reset. ota_trial = 1 during the first 30 s of a new image; ota_last_event: staged, confirmed, rollback_trials, rollback_invalid, fallback.

    First flash (once, with STM32CubeProgrammer and the board's external loader)¶

    1. Signed FSBL (STM32_SigningTool_CLI -bin FSBL.bin -nk -of 0x80000000 -t fsbl -hv 2.3) → offset 0.
    2. .fw package (make ota VERSION=…) → offset 0x00200000 (slot A), i.e. 0x70200000.
    3. No boot record needs to be written: on blank flash the FSBL boots slot A and creates the record itself.

    Development with a debugger (loading the application straight into RAM) still works: without a boot record, ota/apply treats the other slot as active and writes into slot A.

    7. Network¶

    The MCUs are on 192.168.10.0/24 and the server on 192.168.1.101: packets go through the gateway 192.168.10.1 (the Jetson, net_config.h).

    • Server_OTA runs on the Jetson itself and the Jetson owns 192.168.1.101 on another interface (Wi-Fi/LAN): no extra configuration — Linux accepts packets for every local address on every interface.
    • Server on another machine in 192.168.1.0/24: the Jetson must forward: 
      sudo sysctl -w net.ipv4.ip_forward=1
sudo iptables -t nat -A POSTROUTING -s 192.168.10.0/24 -o <LAN interface> -j MASQUERADE
      (or replace NAT with a static route 192.168.10.0/24 via <Jetson LAN IP> on the router/server).

    Check: curl http://192.168.1.101:8080/api/ota/manifest?device=jetowl_fc from the Jetson.

    8. Verification¶

    Level Content Result
    Host C (tests/host/test_ota.c, gcc + clang + ASan/UBSan, -Wconversion -Wsign-conversion) 504 checks: NIST SHA-256 vectors (empty, abc, 448 bit, 10⁶×a) + random buffer splits; CRC-32 check value 0xCBF43926; every header bit flipped (package + boot record); every package invariant; power cut at every flash operation; boot decisions (fresh, trial, trials exhausted, corrupted pending, fallback); 10-boot life cycle; malformed HTTP/manifest; client against a fake server: odd-sized recv, connection dropped 3 times (resumed with Range), server ignoring Range, trials exhausted, wrong SHA, flash write error, 404, too large, wrong device, wrong version pass
    Cross-check in 3 languages the same package built by ota_pack.py decodes identically in C (test_ota.c) and Go (ota_test.go), and the Go builder produces it byte for byte pass
    Go server (go test -race) newest release by number, corrupted/misnamed packages skipped; manifest; upload (409/413/422/400); Range 206 with the correct Content-Range; ../ blocked; report pass
    ARM (arm-none-eabi-gcc 13.2) FC FSBL (ROM 60.5 KB) and Vision FSBL (36.4 KB) link; FC AppliNonSecure with OTA (ROM 221 KB / 511 KB, RAM 232 KB / 512 KB); Vision Appli with OTA (ROM 215 KB / 511 KB); arm-compile-check.sh (41 files) pass
    End to end on the host the real Server_OTA (Go) + make ota-upload of a real FC package (236 KB, 2 segments) + the C client (same source as the firmware) over real TCP, with one disconnection mid-way: resumed with Range, slot == file byte for byte, ota_slot_verify passes, the report appears in /api/ota/devices pass
    Hardware XSPI2, FSBL jump, IWDG, download over a real network not yet

    9. Not yet verified / limitations¶

    • Not yet run on hardware. In order: FSBL boots slot A → ota_state other than no_flash (the driver reads the Macronix JEDEC ID) → ota/start against the real server → ota/apply → confirmation → a deliberately corrupted image to observe the rollback.
    • [BOARD] flash and pins: MX25UM51245G on XSPI2/port N, VDDIO3 = 1.8 V (as on the NUCLEO-N657X0-Q). The JetOwl_Vision board must be checked against its schematic. XSPI runs single-line SPI ≤ 50 MHz and does not depend on the HSLV fuse configuration.
    • Boot ROM → FSBL: the FSBL must be signed and placed at offset 0 (ST documentation, RM0486 "Boot"); the driver resets the NOR chip in OPI-DTR, OPI-STR and SPI modes before use, so it does not depend on the mode the Boot ROM leaves behind.
    • No digital signature: SHA-256 only protects against corruption. Anyone who can write to the server (or impersonate it on the network) can install firmware. This network must be a dedicated vehicle segment. ECDSA/Ed25519 signatures verified in the FSBL (public key in OTP) are the next step.
    • FC: AppliSecure assigns XSPI2/XSPIM/IWDG to AppliNonSecure (as for ETH1), so the non-secure side can write the whole flash, FSBL included. Moving flash writes into a secure (CMSE) service that only allows writes to the slots is the next improvement (docs/TRUSTZONE_TRADEOFF.md).
    • The IWDG enabled during a trial-boot session runs until the next reset, even after confirmation. The FC refuses to arm for that whole session (power-cycle after OTA before flight): the IWDG never runs in flight.
    • Server WriteTimeout 30 s: if slow flash erasure (BE64K up to 2 s per block) makes one download exceed 30 s, the client resumes with Range — verified by the dropped-connection test.
