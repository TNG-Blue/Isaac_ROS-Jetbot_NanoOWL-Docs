    Deployment Kubernetes Tutorial

    Deploy the Stack on a Two-Jetson Cluster¶

    Build one container image per ROS 2 node, bootstrap a k3s cluster on two Jetson Orin Nano Super boards, deploy every node with Helm, and prove that DDS traffic crosses the boards and that the cluster survives the loss of the worker.

    Before you start

    • Time: about 3 hours, most of it image builds
    • You need: two Jetson Orin Nano Super boards with JetPack 6.2, an Ethernet switch on the robot, the JetOwl MCUs (optional), the repository cloned with submodules on the master
    • You learn: the image template and runtime contract, k3s settings and where their numbers come from, DDS in Kubernetes, scheduling and failover

    One Jetson only?

    The same images run with Docker Compose on a single board: see Quick Start, option C.

    Topology¶

    Board Role Address (192.168.10.0/24) Runs
    Jetson #1 master: k3s server + agent .1 API server, image registry :5000, nodes pinned to hardware, floating nodes
    Jetson #2 worker: k3s agent .4 floating nodes, nodes pinned to worker
    JetOwl FC / JetOwl Vision MCUs .2 / .3 micro-ROS clients of the agent at .1:8888
    MetalLB pool .200–.220 .200 = OTA server

    k3s is used because it is a single binary with containerd and a SQLite datastore; a full kubeadm control plane would take a large share of a 6-core, 8 GB board that also runs the robot. There is one server on purpose: an etcd control plane needs a quorum of ⌊n/2⌋ + 1, so two servers tolerate no failure, exactly like one, at twice the load.

    1. Network¶

    Both Jetsons and both MCUs go on one switch with static addresses (the MCU firmware has no DHCP):

    # master
sudo cp Source/ROS2_JetOwl_Bridge/config/netplan-jetowl.yaml /etc/netplan/60-jetowl.yaml
# worker
sudo cp Kubernetes/cluster/netplan/60-jetowl-worker.yaml /etc/netplan/60-jetowl.yaml
# both: set the interface name first (ip link; enP8p1s0 on the Orin Nano developer kit)
sudo netplan apply

    Between the boards, keep open: TCP 6443 (API), 10250 (kubelet), UDP 8472 (flannel VXLAN), TCP 5000 (registry), UDP 7400–7700 (DDS, domain 0) and multicast 239.255.0.1. Wi-Fi stays for the internet and the operator laptop.

    2. Bootstrap the cluster¶

    # master: k3s server, registry, nvidia RuntimeClass, kubeconfig; prints the join command
sudo Kubernetes/cluster/install-master.sh
# worker
sudo Kubernetes/cluster/install-worker.sh --token <token printed by the master>
# master: both nodes Ready with their role label
kubectl get nodes -L jetowl.tng-blue.io/role -o wide

    The k3s configuration sets values that change failover time and stability:

    Setting Value Reason
    node-status-update-frequency 4 s kubelet status period
    node-monitor-grace-period 20 s 5 kubelet retries × 4 s; the 40 s default would double failover time
    system-reserved 500m, 1 GiB JetPack services, Docker, the registry
    eviction-hard memory.available<300Mi the kubelet evicts before the kernel OOM killer picks a ROS 2 node at random

    The resulting allocatable (5.0 CPU / 5.1 GiB on the master, 5.25 CPU / 5.6 GiB on the worker) is the budget the chart's resource requests are checked against.

    3. Build the images¶

    The build context is the checkout, so populate the submodules first (the LiDAR AI package needs its NVIDIA sources):

    git submodule update --init --recursive

    On the master (arm64, native build), push to the cluster registry:

    Docker/scripts/build_all.sh --push --tag v0.3.0

    From an x86 PC, cross-build with buildx and QEMU instead: Docker/scripts/build_all.sh --platform linux/arm64 --push --tag v0.3.0.

    Each image is built from Docker/templates/ros_package.Dockerfile:

    • the build stage builds only the package and the in-repo packages it depends on (colcon build --packages-up-to), with CMAKE_CUDA_ARCHITECTURES=87;
    • the runtime stage keeps install/ and the exec dependencies; the build fails if any installed binary has an unresolved shared library, so a missing <exec_depend> is found at build time, not on the robot.

    The entrypoint stays PID 1 and forwards SIGTERM as SIGINT, because ros2 launch in Humble only handles SIGINT. Measured: a clean exit 0 in 0.3 s instead of exit 137 after the grace period.

    4. Deploy with Helm¶

    Helm/scripts/deploy.sh --set global.imageTag=v0.3.0     # MetalLB + chart, waits until Ready
make -C Helm status                                     # which Jetson runs what
make -C Helm test                                       # talker on the worker → listener on the master

    helm test passes only if a ROS 2 message crosses the Ethernet link between the boards.

    Nodes pinned to a device (jetowl-bridge, lidar-slam, stereo, night-vision, the micro-ROS agent and the OTA server) run on the master; the others float and are placed by the scheduler on resource requests, an even pod count and GPU spread. Change a node per robot:

    Helm/scripts/deploy.sh --set global.imageTag=v0.3.0 \
    --set nodes.flight-controller.enabled=true \
    --set nodes.mission-planner.enabled=true \
    --set nodes.lidar-ai.placement=worker

    The values schema rejects unknown keys and invalid enums before anything is deployed.

    Why host networking¶

    DDS discovery is UDP multicast to 239.255.0.1:7400 + 250·domainId. Flannel's VXLAN does not forward multicast between nodes; the physical switch does. ROS 2 pods therefore use hostNetwork: true, and the Fast DDS profile whitelists the cluster addresses so a participant never announces docker0 (172.17.0.1 on both boards). hostIPC: true and the host /dev/shm are mounted so the shared-memory transport works between pods on the same board; without them, nodes discover each other but never receive data.

    5. Operate¶

    Task Command
    Roll out a new tag Docker/scripts/build_all.sh --push --tag v0.3.1 && Helm/scripts/deploy.sh --set global.imageTag=v0.3.1
    Roll back helm -n jetowl rollback jetowl
    Logs kubectl -n jetowl logs deploy/jetowl-ros2-jetson-control-system -f
    ROS 2 CLI in the cluster kubectl -n jetowl exec -it deploy/jetowl-ros2-jetson-monitoring -- ros2 topic list
    Resource balance make -C Kubernetes balance
    Maintenance on the worker make -C Kubernetes drain-worker, later make -C Kubernetes uncordon-worker

    6. Test failover¶

    Power off the worker and watch the pods:

    watch kubectl -n jetowl get pods -o wide

    Expected: the worker becomes unreachable after 20 s + up to 5 s, floating pods tolerate that for 10 s, then are recreated on the master, about 35 s plus container start. The master cannot hold every pod (5.35 CPU / 6.5 GiB requested against 5.0 CPU / 5.1 GiB), so the scheduler preempts by priority: the critical tier and most of the high tier run; normal pods and one GPU perception pod stay Pending until the worker returns.

    Losing the master

    The worker keeps its pods but nothing is rescheduled, and the MCUs lose their micro-ROS agent (their firmware targets 192.168.10.1). A partition of only the inter-board link can leave both boards running the floating nodes. Design the vehicle's failsafes in the firmware and the flight controller, not in the cluster.
