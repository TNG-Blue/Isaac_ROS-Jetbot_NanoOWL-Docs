    Microcontroller Sensors Tutorial

    Connect the Flight Controller and Sensors¶

    Bring up the Ethernet link between the Jetson and the vehicle's microcontrollers, start the micro-ROS agent and jetowl_bridge, and check that every sensor stream arrives at its expected rate with valid timestamps before any controller is allowed to use it.

    Before you start

    • Time: about 30 minutes
    • You need: the Jetson; the JetOwl flight controller (STM32N657) on the Jetson's Ethernet port, or no hardware for the simulated sensor link in part B
    • You learn: the vehicle network, the micro-ROS agent, the bridge's links and diagnostics, how to tell a healthy sensor stream from a broken one

    The links¶

    ros2_jetowl_bridge is the single ROS 2 node between the Jetson and every microcontroller. Each link is switched by a launch argument:

    Link Device Transport Default
    fc JetOwl flight controller, STM32N657 micro-ROS over UDP (agent on port 8888) on
    vision_mcu JetOwl_Vision camera, STM32N655 + IMX335 micro-ROS over UDP (same agent) off
    vision OpenMV RT1062 camera JSON lines over TCP or USB CDC off
    sensor_link hexacopter flight MCU / Gazebo virtual MCU CRC-32 framed UDP off

    All links report in one DiagnosticArray on /diagnostics, under jetowl_bridge/<link>.

    Part A: the JetOwl flight controller¶

    1. Configure the Jetson's Ethernet port¶

    The firmware uses static addressing (lwIP with DHCP off):

    Host Address
    Jetson 192.168.10.1/24
    JetOwl FC 192.168.10.2/24
    JetOwl_Vision (if fitted, through a switch) 192.168.10.3/24
    micro-ROS agent UDP 8888 on the Jetson 
    ip link                                   # find the interface name
sudo cp Source/ROS2_JetOwl_Bridge/config/netplan-jetowl.yaml /etc/netplan/60-jetowl.yaml
sudo nano /etc/netplan/60-jetowl.yaml     # replace eth0 with your interface if needed
sudo netplan apply
ping -c 3 192.168.10.2                    # the FC answers once its firmware is running

    2. Build and launch¶

    ROS/build.sh -p ros2_jetowl_bridge
source install/setup.bash
ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py

    The launch file also starts the micro-ROS agent. Choose where it comes from with agent:=:

    agent:= Agent
    ros (default) built once from source with micro_ros_setup (create_agent_ws.sh, build_agent.sh)
    docker the microros/micro-ros-agent:humble container
    none started elsewhere (Docker Compose service, Kubernetes sidecar)

    3. Verify the streams¶

    ros2 topic hz /imu/data              # 200 Hz, frame imu_link, orientation ENU/FLU
ros2 topic hz /jetowl/motor_rpm      # 50 Hz, NaN = unknown (not zero)
ros2 topic hz /baro/pressure         # 25 Hz, variance 1.44 Pa²
ros2 topic echo /jetowl/status       # 2 Hz firmware status, RC link keys
ros2 topic echo /jetowl/link_ok      # true while the FC is alive
ros2 topic echo /diagnostics         # jetowl_bridge/fc: link, rotors, firmware status

    The link is declared lost after fc.link_timeout_s = 1.5 s, three status periods.

    No /imu/data from the FC?

    The firmware IMU path needs I2C1 and EXTI enabled in CubeMX (BOARD_CUBEMX_PERIPHERALS_READY = 1). Until then the FC does not publish /imu/data and refuses to arm. See the CubeMX Setup page.

    4. Understand what you must not skip¶

    The bridge contains no control law. The attitude estimate, attitude controller (250 Hz), rate controller with extended state observer (1 kHz), mixer and rotor speed loops run in the firmware; the translational ESKF and MPC run on the Jetson in ros2_control_system. The bridge relays arming from ros2_flight_controller and the firmware only accepts it with:

    • a set-point younger than 0.1 s;
    • a valid attitude estimate;
    • tilt below 20°;
    • a thrust command below 20 % of the maximum thrust.

    The MPC idle thrust (thrust_min_n in uav_control.yaml) must therefore be below that 20 % for your airframe, or arming is refused with thrust command too high.

    Before the first powered test

    Remove the propellers. The FC and vision links have not been run against hardware yet; bench and hardware-in-the-loop evidence is still to be produced (see the JetOwl Bridge limitations).

    5. Add the cameras (optional)¶

    ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py vision_mcu:=true           # + JetOwl_Vision
ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py vision:=true               # + OpenMV over TCP
ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py vision:=true connection_type:=usb

    Part B: the MCU sensor link without hardware¶

    The hexacopter's IMU, GNSS and motor encoders reach the Jetson through a CRC-32 framed UDP protocol. In simulation the same frames come from the Gazebo virtual MCU, so the link and every node downstream run identical code in SIL and on the vehicle.

    1. Start the simulator and the link¶

    ROS/build.sh --rosdep -u ros2_hexacopter_gazebo -u ros2_jetowl_bridge
source install/setup.bash
ros2 launch ros2_hexacopter_gazebo hexacopter_sim.launch.py gui:=false

    hexacopter_sim.launch.py also starts jetowl_bridge with only its sensor link enabled and the sensor_link_sim.yaml overlay. To start the bridge alone against an external virtual MCU:

    ros2 launch ros2_jetowl_bridge jetowl_bridge.launch.py fc:=false sensor_link:=true sim:=true

    2. Verify¶

    ros2 topic hz /imu/data                 # ≈ 1 kHz
ros2 topic hz /encoders/joint_states    # ≈ 1 kHz, 12 channels
ros2 topic echo /gps/fix --once         # STATUS_FIX with an ENU covariance
ros2 topic echo /diagnostics            # sensor_link: link, clock, imu, gnss, encoders

    Observed on the reference run: /imu/data 996 Hz, /encoders/joint_states 998 Hz, /gps/fix with σ_h = 1.27 m, 0.00 % link loss.

    3. What makes a stream healthy¶

    Check Where Healthy
    Rate …: imu / gnss / encoders at the configured rate, watchdog not tripped
    Loss and errors …: link 0 % loss, no CRC errors, no unexpected MCU reboots
    Clock …: clock offset and skew converged; σ small against the IMU period
    Timestamps message headers the measurement instant mapped to ROS time, never the arrival time

    On the vehicle, sensor_link.clock.require_sync: true keeps every topic silent until the clock filter has converged. Do not disable it: the ESKF fuses IMU and GNSS by timestamp, and an arrival-time stamp adds the network jitter directly to the estimation error.

    4. Bench check without ROS¶

    On the bench, mcu_link_dump listens, synchronises the clock with the MCU and prints a JSON summary:

    ros2 run ros2_jetowl_bridge mcu_link_dump --port 9870 --mcu 192.168.1.103:9871 --duration 5
